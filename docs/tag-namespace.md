# Git Tag 命名空间（v2-tag-namespace）

治理 Git Tag 命名空间，消除 `v1/v2/v3` 这类裸版本 tag 与计划版本（0.7.x）的歧义。

> ⚠️ **本文档描述的 `plan-<semver>/v<n>` 规则已被 ADR-110 取代。**
>
> **ADR-110**（`docs/adr/adr-110-version-tag-plan-scoped-namespace.md`）
> 把命名空间改为**按计划寻址**：`plan-<planId>/v<n>`，
> 并把 `<semver>` 从 tag 里移出去。
>
> 取代理由（四个实测缺陷）：
> ① `<semver>` 与 `package.json` 绑定 → **升版当天历史 tag 全部变非法**，
>    而 `build.mjs --release` 无参跑 `tag-namespace.mjs` → **发布闸门自锁**；
> ② 多个计划各有自己的 v1 → 同一个 `<semver>/v<n>` **装不下**，名字被抢占；
> ③ `ship` 默认派生的是裸 tag → **工具自己造自己的非法**；
> ④ 版本计划在 `.zelto/`（被 gitignore）→ **CI 读不到 plan↔tag 关系**。
>
> **本文档保留**作为「旧规则与迁移历史」的记录；
> 实施 ADR-110 后本文件将重写。

## 命名规则

- **计划-版本二级命名**：`plan-<semver>/v<n>`，如 `plan-0.7.1/v1`。
  - `<semver>`：计划版本的 semver，形如 `0.7.1`。
  - `<n>`：该计划版本下的版本序号，形如 `1`。
- **裸版本 tag（`v1` / `v2` / `v3`）非法**，须迁移到新命名空间。
- **纯 semver tag（`^v\d+\.\d+\.\d+$`，如 `v0.3.0`、`v0.6.0`）合法**，不受影响、不迁移。

## 存量迁移

存量裸 tag `v1` / `v2` / `v3` 重命名迁移到新命名空间，旧名到新名的映射保留在
`scripts/tag-map.json`（固定为 `{ "<old>": "<new>" }` 扁平映射）：

| 旧名 | 新名 |
|------|------|
| `v1` | `plan-0.7.1/v1` |
| `v2` | `plan-0.7.1/v2` |
| `v3` | `plan-0.7.1/v3` |

迁移只改文档与映射、不自动改 tag；删除远端旧 tag 是人的手动动作。
若 `v1/v2/v3` 已被外部引用，重命名后旧引用会失效 —— 新名在文档与映射中声明，
旧 tag 由人确认后再删。

### 已完成的迁移（2026-11-25）

迁移前的实测事实：裸 tag `v1` / `v2` / `v3` **从未推到远程**
（远程只有 `v0.3.0`–`v0.6.0` 与 `archive-prefilter/v0.3.0`、`v0.4.0`），
所以删本地裸 tag 不破坏任何外部引用。

**最终状态：**

| tag | 指向 | 装的是什么 | 在 main 上 |
|-----|------|-----------|-----------|
| `plan-0.7.1/v1` | `532f942` | 计划 `plan-1794562105642`（sign-review）的 v1 | ❌ |
| `plan-0.7.1/v2` | `b61c118` | 计划 `plan-1795507341754`（本计划）的 v2 | ✅ |
| `plan-0.7.1/v3` | `482e0a4` | 计划 `plan-1795507341754`（本计划）的 v3 | ✅ |

裸 tag `v1` / `v2` / `v3` **全部已删**，
仓库的 tag 命名空间现已全部合法
（`node scripts/tag-namespace.mjs` 无参运行退出码 0）。

> **`plan-0.7.1/v1` 为什么装着别的计划的内容** ——
> 它原本是裸 tag `v1` 的直接改名（指向同一提交 `532f942`）。
> 迁移过程中查清：`532f942`（sign-review 计划的 v1）
> **只被这一个 tag 引用** —— 其它任何 ref（main、`version/*`、其余 tag）
> 都不含它。
>
> 而 sign-review 的**代码内容全都在 main 上**（以 `fa8e34e` 等重新提交进入，
> ADR-104 又做了改进）—— 所以改指向不会丢代码，
> 丢的只是「原始提交历史」这个追溯锚点。
>
> 按人批决定：**保留 `plan-0.7.1/v1` 不动** ——
> 宁可让这一个 tag 装的是历史计划的内容，也不毁掉一个计划的锚点。
> 本计划 v1 的锚点因此暂缺（其正确锚点应为 `84be3ce`，
> 即 `v1-acceptance-triage` 的合并点，在 main 上）；
> 等本计划 v1 走 `zelto version ship` 时由工具按版本分支 tip 自行打 tag。
>
> **这是「命名空间语义」与「锚点唯一性」的冲突**：
> `plan-<semver>/v<n>` 表达「0.7.x 这一批里的第 n 个版本」，
> 但历史上多个计划各自都有自己的 v1/v2/v3，
> 同一个 `<semver>/v<n>` 装不下它们 —— 一旦一个 plan- tag 被占用，
> 另一个计划的同版本号就**没有合法名字可放**。
> 彻底解法是给 tag 命名空间加上计划维度（如 `plan-0.7.0/v3` vs `plan-0.7.1/v3`），
> 但那会改掉 v2 规格定的规则 —— **属规则变更，需另立 ADR**。

### 映射表的已知局限

`scripts/tag-map.json` 只被 `scripts/tag-namespace.mjs` 用来校验
**新名的命名合法性**（`^plan-\d+\.\d+\.\d+/v\d+$`）——
**它不校验映射的内容对不对**（旧 tag 与新 tag 是否真的指向同一个版本）。

后果：映射表可以把 `v3` 映射到 `plan-0.7.1/v3` 而两者内容不同，
校验照样通过。**这是 v2 规格留下的口子**（验收标准 2 只断言键存在 + 值合法）。

本次迁移中它暴露了两次：

1. 裸 `v3`（`0f50c73`）与 `plan-0.7.1/v3`（`482e0a4`）指向不同版本，
   而映射表对此**一言不发**。
   （后续查清：裸 `v3` 实为 `plan-0.7.1/v3` 的**祖先**，内容已被其完全覆盖 ——
   所以删掉它不丢内容。）

2. `plan-0.7.1/v1` 装的是 sign-review 计划的 v1，而映射表声称
   `v1 → plan-0.7.1/v1` 是一次「重命名」——
   但那个计划的 v1 与本计划的 v1 **是两个不同的版本**。
   映射表把「按批次编号」误当成「按计划编号」，
   于是它把三个不同计划的 v1/v2/v3 塞进了同一组 `<semver>/v<n>`。

**这张表现在是「历史迁移的记录」，不是「当前 tag 归属的声明」。**
读它的人要记住：映射给出的是**旧名 → 迁移目标名**，
不保证两者的内容相同 —— 内容相同与否要用
`git merge-base --is-ancestor` 自己对。


## 校验脚本

`scripts/tag-namespace.mjs` 只做校验（列出非法 tag + 非零退出），不自动改 tag：

```bash
node scripts/tag-namespace.mjs [tag...]
```

- 带参：校验给定的 tag 列表。
- 无参：从 stdin 逐行读 tag；stdin 无输入时读 `git tag`（校验仓库当前状态）。
- 退出码：`0` = 全部合法；`1` = 有非法命名 / 版本号不一致 / `tag-map.json` 不合法。

脚本区分两种错误并分别列出：

- **非法命名**：tag 不符合任何合法形态 —— 裸 `v1` / `v2` / `v3` 落在这里。
- **版本号不一致**：`plan-<semver>/v<n>` 的 `<semver>` 与 `package.json` 当前版本漂移。

## 版本一致性

新 tag `plan-<semver>/v<n>` 的 `<semver>` 应与 `package.json` 的 `version` 一致，
防止 tag 与当前版本漂移。映射表指向计划版本（可能超前于当前发布版本），
因此映射只校验命名合法性；对实际 tag 列表的校验才包含版本一致性检查。
