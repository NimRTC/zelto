> **第八轮补（§11.13）—— D-35：「Failed to fetch」不是 bug，是两个真缺陷。**
> 人问「总览为啥显示加载失败」，查下来是**标签页开在 4406 而那个服务早停了**
> （`zelto web` 是前台进程，Ctrl+C 就停）—— 根因不是代码。
> 但排查挖出两个真缺陷：
> ① 那句提示对人毫无帮助（只说「失败」，不说该做什么）→ 翻译成可行动的话；
> ② **轮询把错误全吞了** —— 服务挂了页面纹丝不动，还显示着过期内容，
> 人会以为那就是当前状态。**这比直接报错更危险**：
> 错误至少让人停下，「看起来正常」不会。
> 修法：独立连接状态条，连续失败 3 次才判定断开（一次抖动不报），恢复后自动消失。
> 状态条必须与动作横幅**分开** —— 一个是独占语义、一个是追加语义，混用会互相冲掉。
> 实测：页面开着 → 杀服务 → 3 轮轮询后提示出现 → 重启服务 → 提示消失。
> 新增 3 条前端测试。回归 **2046/2046 全绿**。

> **第九轮补（§11.14）—— D-36：文档写了、代码里没有。**
> 人问「文档定义的 UI 内容都实现了吗」，于是**逐条对照 ADR-072 与实现**。
> 15 项里 12 项没问题，3 项有缺口 —— 全部是「文档写了、代码里没有」：
> ① `/api/slices/:id/audit` **端点实现了但前端从不调用** ——
>    「端点能通 ≠ 功能对人可用」，中间隔着「前端有没有调」；
> ② §5.2 要求的「人确认过了这四项」凭据没传（前端传空对象）——
>    服务端重算那半条是对的，但「必须带」这半条漏了；
> ③ 追溯只给条目数、summary 完全没有成本。
> 关于②的设计要点：服务端**不信任**前端内容，所以内容真假不影响安全，
> 那「必须带」防的是**流程绕过** ——
> 「没带」本身就说明人没在页面上看过这四项。
> `parseClientChecks()` 只校验**形状**（数组、≥4 项、每项有 label/ok），
> **刻意不校验「四项都 ok」**（那是服务端重算后才知道的事）；
> 前端报「有一项没过」也是有效凭据。
> 踩到一个 JSON 坑：预算上限可能是 `Infinity`，
> 而 `JSON.stringify(Infinity)` === `'null'` → 前端显示成「$null」。
> 修法：`null` 表示不限 + `unlimited: true` 标志。
> 新增 7 条测试。回归 **2053/2053 全绿**。

## 一、这一轮与上一轮的差别

上一轮的目标是「**从空白需求到 `version ship`**」—— 验证 zelto 的骨架能不能撑起
一次完整交付。这一轮的目标不同：**验证 zelto 在一个「已经在维护中的真实项目」
上能不能做增量的、可并行的开发**。

具体差别：

| 维度 | 第一轮 | 第二轮 |
|---|---|---|
| 起点 | 空白（`reset --hard github/main`） | 已有 20+ 个切片、已有版本分支 |
| 切片来源 | LLM 生成（`zelto plan`） | **人工撰写规格**（两片都手写） |
| 并发性 | 单片串行 | **两片写集重叠 → 调度器降级为串行** |
| 靶子代码 | 新建 | 改动**既有**生产代码（`engine_media.cpp` / `engine_rtcp.cpp` / `engine_rtcp_xr.cpp`） |

**规格人写**这一条是本轮最重要的变化。第一轮的规格是 LLM 起草的，
问题藏在措辞里；这一轮手写规格，能更精确地测「规格与写集的一致性」
（ADR-059 §3 的判据到底准不准）。

## 三、本轮发现的 zelto 缺陷目录

### D-24（中）人改保护域也被 hook 拦住

**现象**：`policy/policy.yaml` 改了之后 `git commit` 被 pre-commit hook 拦下：

```
policy/** 是保护域 —— 策略的修改必须由人直接完成，
并通过 `zelto policy lock --update` 重新锚定。
```

**为什么这是缺陷而不是正确行为**：C5 说「保护域硬编码、不可被任何策略规则覆盖」
—— 保护域防的是 **agent**。但 hook 不区分**谁**在提交：

- agent 提交 → 必须拦（C5 的本意）
- 人提交 → 必须放行（否则 C5 的配套流程 `policy lock --update` 走不通）

现状是两者都拦。演练中只能 `--no-verify` 绕过。

**修复方向**（待实施）：hook 判据要看**是不是 agent 在提交** ——
zelto 在 agent 运行时往环境里注入标记（类似 `ZELTO_SLICE_ID`），
hook 据此区分。没有标记 → 是人 → 放行。

> 顺带暴露：**演练记录里写「用 `--no-verify` 绕过」是权宜之计**，
> 它让「策略被改过」这件事在 git 历史里没有钩子痕迹。

### D-25（严重）超时的重试在适配器内部「从头再来」，短路了 ADR-055 的续跑

**现象**：`v1-rtcpprocessor` 的 agent 跑了 30 分钟被超时杀掉，然后：

| 会话 | agent 会话 id | 说明 |
|---|---|---|
| `claude-agent-v1-rtcpprocessor-1794796572264` | `bd4e6295-...` | 第一次，`status=timeout` |
| `claude-agent-v1-rtcpprocessor-1794798375472-retry-1` | `d6944875-...` | **新的 agent 会话 id** |

**agent 会话 id 变了** → 不是续跑，是**从头再跑**：agent 的上下文被清零，
它已经摸清的东西（改到一半的代码、跑了一半的测试、读过的一堆源码）全部作废。

**根因**：`src/adapters/claude-agent/index.ts` 的 `waitForExit` 里，
非零退出 → 适配器**内部** `startWithRetry` → 用**原始 bundle** +
**新的 agentSessionId** 重启。这条路径把 CLI 层的
`resumeForRetry`（真正的 ADR-055 续跑）**完全短路**了 ——
适配器内部已经把重试链跑完（实测跑到 `-retry-2`），CLI 层根本没机会执行。

**关键的隐蔽点：退出码分不出超时。**

ADR-055 决策 B 假设「超时时 exitCode 是 `null`」（POSIX 上确实如此）。
但 **Windows 上 `taskkill` 杀掉进程树后，shell 包装返回的是非零码（1）** ——
实测确认。所以 `waitForExit` 里的 `code !== null` 判断在 Windows 上
**永远成立**，超时与「agent 报错退出」在退出码上完全一样。

唯一可靠的超时信号是适配器**自己**记的 `status === 'timeout'`
（`handleTimeout` 在杀进程树之前就写好了，ADR-055 决策 B）。

**已修**（`c07df3f`）：

```ts
const data = loadSession(sessionId);

// 超时 → 不在这里重试。交给 CLI 层走 ADR-055 的续跑路径
// （`continueSession`）—— 见上面那段说明。
if (data?.status === 'timeout') {
  resolve(code);
  return;
}
```

**回归测试**（`tests/adr-055-timeout-kills-tree-and-continues.test.ts`，+5 条）：

1. 超时的退出码不是 0（**锁住「退出码分不出超时」这个事实**）
2. 超时后适配器**没有**起第二个 agent（会话数增量 == 1）
3. agent 报错退出（`failed`）**仍会**起内部重试（增量 == 2）
   —— **两条必须不同**，否则修复就是把「重来一遍」这个正当行为也砍了
4. 超时后 CLI 层能续同一个 agent 会话（`agentSessionId` 相同）
5. 非零退出码的状态是 `failed` 不是 `timeout`

> **教训**：ADR-055 写于 Windows 环境，却把 POSIX 的退出码语义
> （信号杀 → `null`）当成了通用事实。**跨平台的语义差异必须在 ADR 里写明，
> 或者干脆不用它做判据。**

### D-26（中）花括号简写被当成一个文件名 → 写集覆盖判据误报

**现象**：规格里写「新建 `src/engine/src/rtcp_processor.{hpp,cpp}`」，
门禁①报：

```
规格提到「src/engine/src/rtcp_processor.{hpp,cpp}」，但它不在写集里 —— agent 改不了它
```

而写集里明明有 `rtcp_processor.hpp` 和 `rtcp_processor.cpp` 两个文件。

**根因**：`src/core/spec/scope.ts` 的 `normalizeMentionedPath` 过滤了
glob 通配（`*` / `?`），但**没处理花括号**。于是
`rtcp_processor.{hpp,cpp}` 被当成**一个**具体文件名。

**闸门误报比闸门漏报更糟**：漏报让人绕过一次检查；误报让人以为
「规格有问题」，于是去改规格 —— 而规格是对的。

**已修**（`2a1f8d0`）：**展开**而不是丢弃。

```ts
function expandBraces(raw: string): string[] {
  // a{b,c}d → abd + acd
  // 不含逗号的 {x} → 原样返回（不是简写）
  // 嵌套花括号不展开
}
```

展开失败（嵌套、无逗号）的花括号串**不报** —— 报一个多半不存在的文件名
比不报更糟。

不残留花括号、前后缀场景、无逗号不展开、嵌套不展开。

> 「一个路径」。实际上规格提到的是**路径的集合**，而集合有不同的写法
> （逗号分隔、花括号、目录）。**判据要能认出集合的写法。**

### D-27（低）`--agent` 参数值拼错时，错误信息不指向正确命令

### D-28（严重）同版本第二片从主干 HEAD 建 worktree → agent 被迫重造上一片 + 越界误报

**现象**：`v1-engineimpl` 是版本 `v1` 的第二片（第一片 `v1-rtcpprocessor`
已合入 `version/v1`）。运行后切片被退回 `frozen`，报「写集越界」：

```json
{"kind":"write-outside-write-set",
 "violations":["src/engine/src/engine_rtcp_xr.cpp",
               "src/engine/src/rtcp_processor.hpp",
               "tests/acceptance/v1-rtcpprocessor/acceptance.test.cjs"]}
```

**这三条「越界」没有一条是 agent 写的** —— 它们全是**上一片**的产物。

**根因（两层）**：

| 层 | 问题 |
|---|---|
| 基点 | `zelto run <id>`（单片路径）**不解析切片归属**，直接拿主干 HEAD（`489de212`）当基点 —— agent 看不到 `rtcp_processor.hpp` |
| 审计 | `auditWorktreeWrites` 算的是 `baseCommit..HEAD` 的全部文件 —— 分支上的**历史提交**（上一片的）被算成本片的越界 |

agent 被放在一个「信息不完整的世界」里：规格要求它接线一个**不存在的协作者**，
它唯一能做的就是**造一个** —— 于是重写了 `rtcp_processor.cpp`（716 行）。

**已修**（`712041f`，ADR-067）：

1. `resolveSliceBaseCommit`：基点解析改为
   `override → pinned → 归属版本分支 tip → 主干 HEAD`
2. `auditWorktreeWrites`：按 `Refs-Slice:` trailer 过滤提交归属，
   只把**本片自己产出的提交**算进审计范围

**真实验证**：重跑 `v1-engineimpl`，基点 = `720d47ab`（`version/v1` tip），
agent 正常看到 `rtcp_processor.hpp`，只改写集内 5 个文件，
门禁②一次通过，审计零越界。详见 §六。

> **教训**：同一个概念（版本切片基点）在**两条路径**上实现
> （版本流水线 vs 单片路径），迟早有一路径漏掉。
> ADR-056 §3.3 早就把 `baseCommitOverride` 做出来了，
> 但只接在版本流水线上。代价是 50 分钟 agent 运行 + 一次写入白工
> + 一个**误导性的「越界」结论**。
>
> 另一条教训：**「守卫正确地拦住了」不等于「系统是对的」。**
> 写集守卫生效了（agent 想改 `rtcp_processor.hpp` 被当场拦下），
> 看起来是「C9 有效」—— 但它拦住的其实是一个
> **被基点错误逼出来的合理请求**。

### D-29（低）`zelto set --value ""` 报 MISSING_ARGS → 字段永远清不掉

**现象**：要清掉 `v1-engineimpl` 的钉死基点（`baseCommit`）以让它重新解析，
执行：

```

{"error":{"code":"MISSING_ARGS","message":"Both --field and --value require a value"}}
```

**根因**：`src/cli/commands/slice-detail.ts` 用 `!rawValue` 判定「值缺失」，

**已修**（`3f2febc`）：判定改为「值整个缺失才报错」，空串是合法值。
补 2 条验收测试（能清空 `baseCommit`；完全不给 `--value` 仍报错）。

> **教训**：字段要能「置空」是基本能力。一个只能写不能清的配置接口，
> 人最后一定会绕过它去手改 JSON —— 绕过的那一刻，追溯链就断了。

### 7.1 D-30（新发现，严重）：`policy edit` / `remove` 静默抹掉整个 `arch:` 段

写 `arch` 编辑器时顺手做了一次现状验证，发现：

```console
$ cat policy/policy.yaml
rules:
  - id: keep-me
    ...
arch:
  - kind: cycle
    action: ask
    basis: "ADR-025"

$ zelto policy remove keep-me
✓ Rule "keep-me" removed.

$ cat policy/policy.yaml
rules:
```

**`arch:` 段整个消失了。**

**根因**：`writePolicyYaml(filePath, rules, headerComment)` 的签名里
**没有 `arch` 参数**，而 `serializeRulesToYaml(rules, header, arch)` **有**。
两者不一致 → 所有走 `writePolicyYaml` 的路径（`policy edit` / `policy remove`）
丢掉整个 `arch:` 段。

`policy add` 走另一条路径（自己做字符串插入），所以它**侥幸没丢**。

**为什么这是「严重」**： `arch:` 段是**架构护栏的判定依据**。
人明确写下的 `action: ask`（ADR-025 承认的那两条已知环）会无声消失 ——
**护栏的「已知例外」被一个跟护栏毫无关系的命令静默抹掉**。

**修复不只是补一个参数**。修的时候发现了第二层问题：
即便补上 `arch` 参数，`policy edit` 仍然会抹掉：

- 段落之间的**注释块**（人写下的「为什么」—— nimrtc-zelto 的
  `arch:` 上面有 10 行注释解释 ADR-025 承认的两条环）
- `anchors:` 段（已废弃但仍认，ADR-040 §3.3）
- 解析器**不认识的字段**（真实项目里的 `reason:`）

**所以改用文本级分段编辑**（新增 `core/policy/section-editor.ts`）：
只动目标那一段，其余部分**逐字节保留**。整条重建改成**字段级替换**。

> **教训**：修一个功能时顺手验证现状 —— 成本最低的缺陷发现方式，
> 因为你要动那些文件 anyway。这个 D-30 已经存在了多久、
> 影响过谁，都不会有人知道。

### 7.2 ADR-068：`zelto policy arch` + `validate --update`

```
zelto policy arch list [--json]
zelto policy arch add <kind> --action <action> --basis <basis> [--guidance <text>]
zelto policy arch edit <kind> [--action <action>] [--basis <basis>] [--guidance <text>]
zelto policy arch remove <kind> [--json]
```

**为什么是独立的 `arch` 子命令组**，而不是扩到 `policy add/edit`：

`rules:` 段的标识是**任意的 `id`**（`allow-src-ts`），
`arch:` 段的标识是**固定的 `kind`**（六类硬偏离之一）。
两者标识空间完全不同 —— 塞进同一个命令，就得在参数层面猜
「`<rule-id>` 还是 `<kind>`」。分成两个子命令组，每个命令的参数空间是单一的。

**一体化入口**（用户明确选的）：

```
zelto policy validate              # 报失配，退出码仍为 0（判与报分开）
zelto policy validate --update     # 报失配 → 当场重锚 → 退出码 0
```

**为什么 `validate` 的退出码口径不变**（没有升级成 error）：

| | 升级成 error | 一体化入口 |
|---|---|---|
| 解决 | 「CI 门禁看不见失配」 | 「人改完策略不知道还要跑什么」 |
| 代价 | 接管既有项目每次都要先改锚（仪式） | 门禁仍然看不见失配 |

**用户遇到的是后者** —— 「改完不知道还要跑什么」每次都遇到，
「CI 看不见失配」偶尔遇到。而代价那一栏正好反过来。

**策略本身非法时不重锚** —— 给一个语法都过不了的策略改锚，
等于让「锚点一致」盖住「策略是坏的」。

**改 `arch:` 段不自动改锚**（改锚是人的决定，C5），
但命令输出**必须告诉人下一步跑什么**：

```
✓ arch 规则 "cycle" 已更新。

⚠ 策略锚点已失配 （策略文件变了，锚点没跟上）
  跑 zelto policy validate --update 重锚。
```

### 7.5 ADR-069：Go / Rust 依赖解析

`arch check` 之前只验证 TS/JS / Python / C/C++。现在补上 Go 与 Rust。

| 语言 | 依赖表达 | 关键判据 |
|---|---|---|
| Go | `import "..."` / `import ( ... )` | 以 `go.mod` 的 module path 开头 → 项目内部 |
| Rust | `use ...;` / `extern crate ...;` | `crate::` / `self::` / `super::` → 项目内部 |

**Go 的两个易错点**：

- **别名不是路径的一部分** —— `import alias "x/y"` 的依赖是 `x/y`
- **`//go:build` 是文件级约束** —— 覆盖整个文件的所有 import

**Rust 的三个易错点**：

- **`mod` 声明不产生依赖边** —— 它是「声明」不是「引用」
  （`mod submodule;` 指的是同目录的 `submodule.rs`，
  那是「这个文件属于那个模块」，不是「这个模块依赖那个模块」）
- **嵌套花括号要展开** —— `use crate::{a, b::c};` 是两条依赖
- **`#[cfg(...)]` 只影响紧跟的那一个 item**

**约定法的取舍**（同 ADR-062 §7）：

- Go 的 `require` / `replace` 语义复杂，**只读 `go.mod` 的 module 一行**
- Rust 的 workspace / `#[path]` / `super::` 层级解析，**判不准时宁可漏**

后果都是**漏边**（不是假边）—— 漏边让人去补声明，假边让人去改对的代码。

**顺带修掉两处「锁旧事实」的测试断言**：它们锁的是
「Go/Rust 读不懂」这个在 ADR-069 之前为真的事实，不是永远成立的不变量。
「有代码但验不了」的代表改成了 **Java / Kotlin**（那块盲区还没补）。

### 7.6 回归

`npm test` → **1998/1998 通过**（新增 55 条 Go/Rust 用例 + 34 条 ADR-068 用例 + 6 条 D-27 用例）；
`npx biome check src tests` → 干净；编码检查 → 干净。

## 九、第四轮：D-31 —— 段标题判据被 BOM 打穿

**日期**：2026-11-16（接第三轮之后）

第三轮的实现全部落地后做端到端复验。**复验脚本自己踩出了一个新缺陷。**

### 9.1 现象

复验脚本在 PowerShell 里用 `Set-Content -Encoding UTF8` 造 `policy.yaml`
—— **Windows PowerShell 5.1 的 `UTF8` 就是「带 BOM 的 UTF-8」**。

```console
$ zelto policy edit other --action deny
✓ Rule "other" updated.
  action: deny

$ cat policy/policy.yaml
  - id: other
    action: allow      # ← 没变！
```

第一反应是「我的测试文件有问题」。把文件换成无 BOM 后一切正常。

**但那不是测试问题 —— 那是真缺陷。**

### 9.2 根因

ADR-068 引入的 `core/policy/section-editor.ts` 用**长度相等**判定段标题：

```ts
if (lines[i].trim() === header && lines[i].length === header.length) {
```

JS 的 `trim()` 会把 BOM（U+FEFF）当空白去掉（它属于 WhiteSpace），
所以 `trim() === 'rules:'` **成立**；但 `lines[i].length` 比标题多 1，
长度判据**不成立** → **整段找不到**。

**同一个字符，两个判据给出相反的答案。**

### 9.3 为什么这比 D-30 更隐蔽

| | D-30 | D-31 |
|---|---|---|
| 现象 | 抹掉了不该抹的（`arch:` 段） | **什么都没做** |
| 命令表现 | `✓ Rule removed` | `✓ Rule removed` |
| 文件 | `arch:` 段消失了 | **一个字节没变** |
| 人怎么发现 | 看文件，发现护栏没了 | 看 `validate` 说「锚点失配」，而失配明明没发生过 |

D-31 的失败方式**没有任何异常信号**：命令成功、退出码 0、
提示信息正确。只有去看文件才发现。

**它是 D-30 那一族缺陷的极端形态**：工具报告成功、实际什么都没做。

### 9.4 修法（ADR-070）

**两处**：

1. **判据换掉** —— 「去 BOM 后的整行 == 标题」：

   ```ts
   function isSectionHeaderLine(line: string, header: string): boolean {
     const stripped = line.replace(/^\uFEFF/, '').replace(/\s+$/, '');
     return stripped === header;
   }
   ```

   「整行相等」天然排除缩进标题（不需要长度判据），
   「去 BOM」修掉 BOM —— 比原判据**更严**，不是更松。

2. **加结构性防线** —— 承认「两套解析器判据可能分叉」这件事本身：

   ```ts
   if (!hasSection(yaml, 'rules')) {
     return { success: false, message: 'Cannot locate the "rules:" section ...' };
   }
   ```

   覆盖 `policy remove` / `policy edit` / `policy arch edit` / `policy arch remove`
   四条编辑路径。段缺失 → 报错，**绝不报告成功**。

   防线放在 handler 层而不是 core 层：`appendToSection` 的
   「段不存在就创建」是**新增**路径的正常行为，不是错误 ——
   「这个命令要求段必须存在」是**命令语义**层的事。

3. **BOM 保留不抹** —— 工具没资格改文件的编码标记；
   仓库既有惯例（`core/design/store.ts`、`core/version/branch.ts`）
   也是读时容错、写时不动。

### 9.5 端到端复验

带 BOM 的 `policy.yaml`，四条编辑命令全部真正生效：

```console
$ zelto policy arch list
Arch Guard Rules:
  ? [cycle] ask   ADR-025

$ zelto policy arch edit cycle --action deny
✓ arch 规则 "cycle" 已更新。

$ zelto policy edit keep-me --action deny
✓ Rule "keep-me" updated.

$ zelto policy remove keep-me
✓ Rule "keep-me" removed.

$ cat policy/policy.yaml
rules:

arch:
  - kind: cycle
    action: deny        # ← 真改了
    basis: "ADR-025"
```

### 9.6 回归测试的写法 —— 一条教训

D-31 这一组的测试断言全部落在**副作用**上，不是**返回值**上：

```ts
it('policy remove 真的删掉了规则（不是只报成功）', async () => {
  const { code } = await runCommand('policy', 'remove', 'keep-me');
  assert.equal(code, 0);
  assert.ok(!readPolicy().includes('id: keep-me'), 'remove 报告成功但规则还在');
});
```

> **「命令成功」不等于「事情做成了」。**
> 如果断言只写 `assert.equal(code, 0)`，D-31 这个缺陷**根本测不出来** ——
> 它返回的正是 0。
>
> 这条对写测试的人是硬要求：**断言必须落在副作用上。**

回归：`npm test` → **2007/2007 通过**；`npx biome check` → 干净。

## 十、第五轮：跑完两个冻结切片 —— 暴露「合并路径」的两个缺陷

**日期**：2026-11-16（接第四轮之后）
**目标**：把 `nimrtc-zelto` 里两个已冻结的切片（`v1-fix-arch-guard-cycle`、
`v1-fix-plugin-test-placement`）真正跑完并合入，做一次端到端钻。
**用户决策**：C5 保护域规则**保留** —— 人提交 `policy/**` 允许，agent 提交不允许。

### 10.1 第一处硬墙：保护域挡在 agent 前面

`v1-fix-arch-guard-cycle` 要改 `policy/policy.yaml`（架构护栏本身）。
`policy/**` 在 C5 保护域里，所以：

- **agent 路走不通** —— 门禁①（`zelto check`）会拦下越界写。
- **人路走得通** —— pre-commit hook 按发起人身份判（D-24 已修）。

于是这个切片**只能由人执行**。这不是缺陷，是设计：`policy/**` 的变更
本来就不该由 agent 提。

> **但这暴露了一个真实的流程事实**：切片流程假设「产物在 agent 的 worktree 里，
> 由 zelto 合并」。产物由人直接提交到 `main` 时，那条假设不成立 ——
> `slice/<id>` 分支根本不存在。

### 10.2 D-32（严重）：产物已由人提交 → `zelto merge` 直接拒绝

**现象**：切片已签字（`zelto sign --approve` 通过），执行 `zelto merge`：

```
❌ 以下切片没有对应的分支，无法合并：
   - v1-fix-arch-guard-cycle
```

而**产物就在 `main` 上**。合并此刻本该是**空操作** ——
产物已经在目标分支里了，没什么可搬的。

**为什么这是严重缺陷**：它逼着人去手工改 `.zelto/` 里的状态文件。
**追溯链就断在这里** —— 事件流里没有这次合并，人也无从知道「它合过了」。

**修法**（ADR-071）：判据从「分支存不存在」改成「**产物是否已在目标 ref 上**」。

```ts
const { missing } = verifyArtifactsInRef(writes, targetRef, repoRoot);
if (missing.length === 0) → 空操作合并
else → 仍然拒绝（并点名缺哪些产物）
```

**为什么不放宽成「分支不存在就跳过」**：D-11 刚把「假成功」当严重缺陷修过一轮。
「分支不存在 + 产物也不在目标分支」= 什么都没做，
放行就是**假成功**。所以判据必须是**产物核实**，不是**分支存在性**。

空操作合并**照样写事件**（`mode: 'noop'` + 核实的产物路径）——
追溯链不因为「这次没搬东西」而断。

### 10.3 D-33（中）：清理分支的报错在撒谎

**现象**：`cleanupMergedSlices` 删分支失败时报「该分支可能有未合并的改动」。
但空操作切片**压根没有分支**，以及「合进 `version/v1` 但 HEAD 在 `main`」——
这两种情况都报同一句话。

**那句话对两种情况都不成立。** 报错不该在描述一个不存在的原因。

**修法**：区分三种情形 —— 分支不存在（跳过，不报警）/
分支没合入目标（报「未合并」）/ 其它 git 错误（报原始错误）。

### 10.4 一个副产物：「空操作切片被无限次列为待合并」

ADR-071 落地后立刻暴露：空操作切片的产物**已经在**目标分支上，
所以「产物在目标分支」这个判据**永远成立** —— 每次 `zelto merge`
都会把它重新列一遍。人会以为它一直没合过。

**修法**：判据加一条 —— 事件流里已有 `mode: 'noop'` 的 `merge.completed` 就不再列。
**只读事件流，不做新判定**（C4：事件是追溯的唯一证据载体）。

### 10.5 验收测试的 `test.todo` 骨架被门禁②挡下

两个切片的验收测试都是 `test.todo` 骨架 —— 门禁②按「`pass 0 / todo N`」拒绝。
**这是对的**：一个只有骨架的验收测试，验不了任何东西。

补成真实断言后：

- `v1-fix-arch-guard-cycle`：**5 条**。含一条在临时目录里造迷你工程、
  埋一个**未声明的** `#include <nimrtc/a.hpp>`，验 `arch check --strict`
  真的以退出码 1 拦下。
- `v1-fix-plugin-test-placement`：**7 条**。含真实跑一次 CTest，
  验 3 个 target 真的被 CTest 发现并执行。

**顺带发现一处规格自相矛盾**：`v1-fix-plugin-test-placement` 的判据 2 说
「plugin 目录下不许出现 `video_frame` 引用」，而「不做范围」里又说
「不许动 plugin 公开头文件」（那些头文件合法地 re-export `video_frame` 类型）。
把断言收敛到 `src/plugins/tests/` 目录，并在测试注释里记下这个规格缺陷。

### 10.6 回归测试的连带修正

ADR-071 改的是**判据**，两条既有测试的断言随之要改 ——
它们原本断言「缺分支 = 失败」，现在要区分两种缺分支：

| 情形 | 处置 |
|---|---|
| 缺分支 + 产物已在目标分支 | 空操作合并，成功 |
| 缺分支 + 产物不在目标分支 | 拒绝，退出码非 0，点名缺哪些产物 |

`tests/merge-false-success.test.ts` 的切片写集原本正好是 `src/feature.ts`
（init 提交里就有）—— 于是它从「拒绝」变成了「空操作成功」。
**改成一条目标分支上不存在的路径**，让断言重新对准「真的合不了」这一情形。

### 10.7 回归

`npm test` → **2014/2014 通过**；`npm run lint` → 干净；编码检查 → 干净。

### 10.8 本轮的方法论观察

**「产物在哪」比「分支叫什么」更接近事实。**
D-32 的修法之所以自然，是因为「产物已经在目标分支上了」本来就是事实，
而「`slice/<id>` 分支存在」只是**实现手段**。
拿实现手段当判据，就会在实现手段不成立时卡住。

**D-32 和 D-11 是同一个家族的两面。**
D-11 修的是「什么都没做却报成功」，D-32 修的是「做过了却报失败」。
两个都要修 —— 只修一个，工具就在另一个方向上骗人。

**日期**：2026-11-16（接第五轮之后）
**目标**：实现 `docs/adr-010-web-ui-adapter.md`（ADR-010，2026-10-30，状态「提案」）。

ADR-010 是一份写了三个月从未落地的提案。用户要求「按 ADR 实现可用的 UI」——
于是这一轮不是写新东西，是**把一份过时的提案落地**，并修掉它里的洞。

### 11.1 ADR-010 过期在哪

ADR-010 写于 2026-10-30。三个月里代码走得很远：

| ADR-010 写的 | 现在的实际 |
|---|---|
| §5.3 端点表（含 run/gate/freeze/admit/abandon/resume/create） | 多数动作在 CLI 侧已有完整实现，Web 侧再做一份 = **分叉判定** |
| §13.3 示例代码里自己拼 `store.transit(id, 'FREEZE')` | 状态迁移的唯一判据是 `core/slice/state.ts` 的 `transitionSlice` |

### 11.2 硬伤一：ADR-010 §9 的 CSRF 缓解措施把因果说反了

ADR-010 §9 原文：

| 风险 | 缓解措施 |
|---|---|
| CSRF | 无 session/cookie，fetch 调用无副作用问题 |

**「无 session/cookie」不是缓解措施 —— 它恰恰是 CSRF 成立的前提。**

CSRF 的机制是浏览器对目标站自动附带凭据。目标站**不要求**任何浏览器猜不到的凭据时，
**任何第三方网页**都能让访问者的浏览器向 `127.0.0.1:4321` 发请求，
而浏览器认为这是同源请求（Same-Origin-Policy 只拦**读**响应，不拦**发**请求）。

按 ADR-010 §5.3 照做的话：

```html
<!-- 攻击者网页上的任意一行 -->
<script>fetch('http://127.0.0.1:4321/api/sign-requests/<某片>/approve',{method:'POST'})</script>
```

访问者一打开那个网页，**这一片就被签了字**。而签字是 zelto 里唯一「人行使的权力」，
签完字 `zelto merge` 就能合入主干。

> **只绑 `127.0.0.1` 防不住这个。** 绑定面防的是**网络可达性**，
> 攻击者不需要能连你的机器 —— 他只需要让**你的浏览器**替他连。

**修法（ADR-072 §3）**：写操作双因子 ——
① 启动时 `randomBytes(32)` 生成的会话 token，注入 HTML，前端放 `X-Zelto-Token` 头；
② `Origin` 头必须为空或等于本服务。
第三方网页读不到本页内容（SOP 拦读）→ 拿不到 token；
且本服务**从不发** `Access-Control-Allow-Origin` → 跨源脚本连 token 都读不出来。

### 11.3 硬伤二：写操作范围撞「一键批准」禁区

ADR-010 §5.4 的签名审批页长这样：

```
┌─ slice-001 ────────────────────────────────┐
│  [✓ 批准]  [✗ 拒绝]                          │
└──────────────────────────────────────────────┘
```

**在浏览器里这就是一键批准** —— AGENTS.md 负向清单明列。

**收窄（ADR-072 §4）**：Web UI 只保留**签字**这一个写操作，其余全砍：

| 被砍的端点 | 理由 |
|---|---|
| `run` | 会启动 agent 进程 —— HTTP 请求不该有副作用地启动另一个进程 |
| `admit` / `gate` | 触发门禁 = 发起一次执行；CLI 侧已有完整实现，Web 侧再做一份会分叉判定 |
| `freeze` / `clarify` | 改切片状态；状态变更必须走同一条代码路径 |
| `abandon` / `resume` | 状态机变更，唯一判据是 `transitionSlice` |
| 创建切片 | 要过 D-4「规格与写集一致性」判定 |
| `approve` / `reject` | **保留** —— 但见下节 |

### 11.4 「看完事实再签」：怎么让它不是一键批准

签字要在浏览器里做（否则驾驶舱只是好看的看板），但不能是「点一下就签」。

**双端防线**：

- **前端**：签字页先渲染完整的四项确认项（追溯链 / 验收 / 写集 / 产物），
  批准按钮初始 `disabled`。
- **服务端**：`POST /api/sign-requests/:id/approve` **自己重新算一遍**四项判定，
  四项全绿才签；任一不过 → `409` + 回传是哪一项不过。
  **前端传来的判定结果一概不信** —— 只当「人确认过了」的凭据。

> 只有前端那道是自欺欺人（改个 DOM 就能绕过）；
> 只有服务端那道是「暗室里批准」。两者合起来才是「人真的看过了」。

测试里专门有一条：**前端声称四项全过、服务端重算发现不过 → 必须被拒**。

### 11.5 一个位置错误：事实收集本该在 core/，却在 CLI 层

ADR-070 把签字复查的事实收集放在 `src/cli/sign-review/collect-facts.ts`。
它跑 git、读 `.zelto` —— 这类活儿 core/ 里已有先例
（`core/sched/audit.ts` 跑 git 拿写集审计证据、`core/worktree/manager.ts` 跑 git 管 worktree）。

当时的理由是「core/ 不跑 git」，但那条约定**本来就不存在** ——
是 ADR-070 选位置的偶然。结果就是 Web UI **没法复用同一份事实**。

**修法（ADR-072 §5.1）**：下沉到 `core/sign-review/collect.ts`，依赖注入
（`readSlice` / `readEvents` / `worktreePath` / `repoRoot`），
CLI 与 Web 各装配各的依赖，共用一份实现。

> **两处判定一旦漂移，就会重演 D-11**（合并的两条路径判据不一致 ——
> 那次修的也是「同一个判据散在两处」）。

### 11.6 端到端复验

真实仓库（113 片切片）里起服务、浏览器打开：

### 11.9 本轮的方法论观察

**一份过时的提案比没有提案更危险。**
ADR-010 写得很详细、看着很完备 —— 但它是在 2026-10-30 的代码上写的。
直接照做，会同时踩三个坑：端点表过时、判定分叉、CSRF 洞。
**提案的价值在实现时会被时间稀释** —— 落地时必须逐条核对。

**「无凭据」不是安全措施，「无凭据」是最危险的状态。**
ADR-010 那句「无 session/cookie」听起来像安全设计，实际是**把门拆了还挂了块
「此处无门」的牌子**。CSRF 的判据永远是：**第三方能不能让你的浏览器替你做事？**

**收窄范围不是偷工减料。**
ADR-010 列了 20 多个端点。真正实现下来，只有 8 个 ——
而砍掉的那 12 个**不是「没时间做」，是「不该在浏览器里做」**：
它们要么会分叉判定，要么会启动进程，要么是状态机迁移。
写清楚为什么不做的理由，比多写 12 个端点更有价值。

**「看过了」这件事必须由服务端验证。**
前端的 `disabled` 属性挡不住任何人。但服务端重算一遍判定，
至少能保证「签的时候，这四项确实是绿的」——
人有没有真的读，那是流程问题，工具只能保证事实没被跳过。

### 11.10 落地后的 UI 自查：三个实测出来的缺陷

落地不等于对。第七轮专门回头查 UI —— 起服务、开浏览器、逐个视图点、
用探针模拟人签字。**查出三个真缺陷**，都是「看代码看不出来、点几下才发现」的那类。

#### 缺陷一：切片详情页被 5 秒轮询刷掉

**现象**：从总览点进切片详情，**4 秒后页面自动跳回总览**。人正在看的东西被抢走。

**根因**：轮询守卫写成了

```js
if (currentView !== 'overview' && main.querySelector('.back')) return;
```

它想表达「在详情页就别轮询」，但**从总览点进详情时 `currentView` 仍然是 `'overview'`**
（`showSliceDetail` 不改它）。第一条件为 false → 不 return → 轮询把详情页整个换掉。

**修法**：详情页状态用**独立变量** `inDetail` 跟踪，守卫只看它。
「当前在哪个视图」和「当前是否在看某片的详情」是**两件事** ——
前者是导航状态，后者是阅读状态，混在一个变量里就会这样判错。

#### 缺陷二：签字成功了，但人什么都看不到

**现象**：点「确认签字」→ 服务端确实签了（`sign.approved` 与 `slice.state.changed` 事件都写了），
但页面**什么提示都没有**。人以为失败了。

**根因**：`doApprove` 里先 `appendChild(提示)` 再 `render('signs')`，
而 `render()` 会 `clear(main)` —— **提示被自己刚调用的视图切换清掉了**。

**修法**：提示走**独立横幅容器**（`#banner`，在主区域外面），
且必须在视图切换**之后**追加。横幅在主区域外 → 轮询碰不到它 → 提示活得过一轮。

> **第一次修复只做了一半**：改用横幅后仍然只剩一条 ——
> 因为 `showBanner` 每次都 `clear(banner)`，第二条把第一条冲掉了。
> 一次签字要显示两条（已签字 + 签字不等于合并），所以横幅必须**追加**而不是覆盖。

#### 缺陷三：轮询时页面每 5 秒塌陷成「加载中…」再重建

**现象**：MutationObserver 抓到每 5 秒一次「加载中」闪现。表格行会跳、滚动位置会丢。

**根因**：轮询复用了 `render()`，而 `render()` 是「先清空、显示加载中、加载完再填」。
用于首次导航没问题，用于**轮询刷新**就是每 5 秒闪一次。

**修法**：轮询走 `refreshSilently()` —— 先渲染到**离屏容器**，成功了再整体替换；
失败就保留原内容（一次网络抖动不该把屏幕清空）。

> **这里踩到了一个更深的坑**：第一版修法把 `main` 从 `const` 改成可变的 `let`，
> 轮询时临时把它指向离屏容器。结果**缺陷二反而更严重了** ——
> 视图函数往哪个容器渲染取决于时序，签字提示写进了已被丢弃的容器。
>
> 修法：视图函数改成**显式接收 `target` 参数**（`viewOverview(target)`），
> `main` 保持 `const`。**可变的全局容器 = 渲染竞态**，这个教训值得记住。

#### 三个缺陷的共同点

**它们都发生在「异步完成之后」这个边界上。**
页面渲染、视图切换、轮询刷新、签字回执 —— 全都是「先发请求，拿到结果再改屏幕」。
而**改屏幕**这一步里，「什么时候改」「改到哪」「改完谁说了算」三件事全都能错。

**静态检查抓不到这类缺陷。** 三个都是「读代码觉得没问题」——
直到真的开浏览器、真的点、真的等 5 秒。

#### 回归测试

三个缺陷都补了**前端回归测试**（对发出去的脚本做断言）：
轮询守卫必须用 `inDetail`、视图函数必须接收 `target`、`main` 必须是 `const`、
`refreshSilently` 里 `clear(main)` 必须在 catch 的 return 之后、
`showBanner` 必须是追加、脚本里**一处 `innerHTML` 都不许有**。

回归：**2036/2036 全绿**（比上一轮多 6 条 Web 测试）。

### 11.12 D-34：事件流读不懂带 BOM 的首行 —— 证据凭空消失

**发现经过**：写 Web 驾驶舱的 UI 自查时，用 PowerShell 造探针事件文件，
签字按钮**永远解锁不了**。查下来是 `gate.result` 事件读不到 ——
「验收真跑过」判据因此判不过。

**根因**：`EventStream.read()` 逐行 `JSON.parse`，但**第一行带 BOM**。
`JSON.parse` 不接受带 BOM 的字符串（BOM 不是 JSON 语法的一部分），
于是整行解析失败，被 `catch` 掉、返回 `null`、被 `filter` 掉。

**为什么这是严重缺陷，不是一个小 bug**：

C4 说事件流是「追溯的**唯一证据载体**」。一行读不懂就被静默丢掉，
等于**证据凭空消失** —— 而且**没有任何报错**。人看到的是「这条切片没跑过验收」，
真相是「验收跑过了，但证据没读出来」。**工具把「没有证据」和「证据是坏的」混为一谈。**

顺带查出同族问题：带 BOM 的事件文件还会让 `restoreSeq()` 读不出 `runSeq`，
重启后序号从头开始，**与既有事件撞号** —— 追溯链直接乱掉。

**修法**：读时容错、写时不动（仓库既有惯例，8 处都是这个写法）。
抽出 `stripBom()`，覆盖 `read()` 与 `restoreSeq()` 两处；
同样处理 `slice/store.ts`、`gate/sign.ts`、`sched/reservation.ts`、
`question/store.ts`、`contracts/registry.ts` 五个读点。

> **注意 `trim()` 救不了这个场景**：U+FEFF 属于 JS 的 WhiteSpace，
> `trim()` 确实会去掉它，但 `JSON.parse` 要求的是**整个字符串**不带 BOM ——
> 必须显式剥，不能指望 trim 顺手带过。

**修法二（同样重要）：不主动抹，也不主动加。**
工具没资格改文件的编码标记 —— BOM 是外部工具留下的痕迹，
抹掉它就是在**篡改证据**。所以只读时容错，写出去的文件仍然不带 BOM
（测试里也断言了这一点）。

**回归测试**：新增 `tests/bom-tolerance.test.ts`（7 条），覆盖事件流首行/中间行、
重启序号不撞号、写时不带 BOM，以及五个状态文件的同族容错。
另做对照验证：修复前读到 **0** 条事件（证据丢了），修复后读到 **1** 条。

回归：**2043/2043 全绿**。

### 11.13 D-35：「Failed to fetch」—— 人该看到的话被浏览器吃了

**发现经过**：人问「UI 总览为啥显示『加载失败：Failed to fetch』」。

**根因不是代码 bug**：浏览器标签页开在 **4406**，那个服务早停了
（`zelto web` 是**前台进程**，ADR-072 §10 —— Ctrl+C 就停）。
`fetch` 连不上时抛的是 `TypeError: Failed to fetch` ——
**连接根本没建立起来**，页面当然拿不到数据。

**但排查过程中挖出两个真缺陷**：

**缺陷一：那句提示对人毫无帮助。**
`Failed to fetch` 只说明「失败了」，不说明**该做什么**。
人得自己推理出「哦那个服务可能已经关了」——
而这恰恰是最容易踩的坑：**浏览器还开着上一个会话的页面，服务却早就退了**。
改成翻译成人能直接行动的话：
「连不上 zelto 服务（Failed to fetch）。多半是服务已经停了 —— 回到终端重新跑 zelto web，然后刷新本页。」

**缺陷二（更危险）：轮询把错误全吞了。**
`refreshSilently()` 的 catch 里直接 `return` —— 服务挂了之后，
页面**纹丝不动**，还是上一次渲染的内容。
人看着一个「看起来正常但其实早已不更新」的页面，
会以为那就是当前状态 —— **这比直接报错更危险**，
因为错误至少会让人停下，而「看起来正常」不会。

修法：加独立的连接状态条（`#conn`），**连续失败 3 次**才判定为断开
（一次网络抖动不该报），恢复后自动消失。

> **为什么状态条要与动作横幅分开**：
> 动作横幅（签字提示）是**追加**语义 —— 一次签字要显示两条；
> 断连提示是**独占**语义 —— 一条状态，反复更新。
> 混在一个容器里，断连提示的 `textContent` 赋值会把动作横幅冲掉
> —— 这正是缺陷二修法自己踩的坑（第一版用了同一个 `#banner`）。

**实测验证**：浏览器开着页面 → 杀掉服务 → 等 3 轮轮询 →
状态条出现「⚠️ 与 zelto 服务的连接已断开：连不上 zelto 服务…」→
重启服务 → 提示自动消失。

回归：新增 3 条前端测试，**2046/2046 全绿**。

### 11.14 D-36：文档写了、代码里没有 —— 三个缺口（D-36）

**发现经过**：人问「文档定义的 UI 内容都实现了吗？」——
于是把 ADR-072（当前绑定规格）逐条对照实现。

**方法论**：**逐条对照文档与代码**，而不是靠「我记得写过了」。
对照下来 15 项里 12 项没问题，3 项有缺口 —— 全部是**「文档写了、代码里没有」**。

**缺口一：`/api/slices/:id/audit` 端点实现了，但前端从不调用。**
ADR-072 §1 摘要明写驾驶舱含「审计」，§6 端点表也列了它。
router 里 `sliceAudit()` 实现得好好的，但前端 `apiGet` 的调用列表里**根本没有 audit**。
→ ADR-010 §5.4 详情页设计的「📋 审计」按钮，ADR-072 收窄后**没人能用**。

> **「端点实现了却没人用」= 没实现。**
> 端点能通 ≠ 功能对人可用 —— 中间隔着「前端有没有调」这一步。

**缺口二：ADR-072 §5.2 要求的「人确认过了这四项」凭据没传。**
原文：「POST 必须带四项判定结果」+「只把前端传的当作
『人确认过了这四项』的凭据」。前端 `apiPost(..., {})` 传的是**空对象**。

服务端自己重算那半条是对的（也是安全的关键），但「必须带」这半条没实现。

**为什么「带」本身有意义**（这是设计上最微妙的一点）：
服务端**不信任**前端传的内容（自己重算一遍），
所以内容真假完全不影响安全 —— 那「必须带」防的是什么？
防的是**流程绕过**：有人绕过前端直接调 API，或者前端没渲染出那四项。
「没带」这个事实本身就说明**人没在页面上看过这四项**。
这不是「多一次点击的形式主义」—— 是把「人看过了」这个前提**变成可验证的**。

修法：`parseClientChecks()` 只校验**形状**（是数组、≥4 项、每项有 label/ok），
**刻意不校验「四项都 ok」** —— 那是服务端重算后才知道的事。
前端报「有一项没过」也是**有效凭据**（说明人确实看到了失败项）。

**缺口三：`/api/slices` 的「追溯」只给条目数，`/api/summary` 完全没有「成本」。**
ADR-072 §6 端点表明写「切片总览（… 追溯 …）」与
「概况（切片数 / 状态分布 / 待签字数 / **成本**）」。

追溯只给数量的问题是：**列表页排不下**只是表象，
实质是「替人决定该看什么」—— 追溯链是签字四项确认之一，
列表页看不到明细，人就得逐片点进去，且**点进去也只看到详情页那一处的**。

补法：追溯给**明细 + 计数**（计数保留给列表页排序用）。
成本接 `core/budget/collector.ts`（`budget.spent` 事件是权威成本来源），
上限从 `config.yaml` 的 `budgetLimitUsd` 读。

> **踩到一个 JSON 的坑**：预算上限可能是 `Infinity`（ADR-035 §3.6：
> `budgetLimitUsd: 0` = 不限），而 `JSON.stringify(Infinity)` 得到的是 `null`。
> 前端照着 null 显示就会变成「$null」。
> 修法：对外用 `null` 表示不限，另给一个 `unlimited: true` 标志。

**回归**：新增 7 条测试（含 API 层与前端源码断言），
`npm test` → **2053/2053 全绿**。

### 11.15 本轮（第八轮）的方法论观察
**「跑通了」和「是对的」是两件事。**
第一轮实现完，2030 条测试全绿、端到端点得动 —— 但那只是在验证
「它能跑」。**验证它「对不对」需要另一套动作**：开浏览器、逐个视图点、
用探针造出真实场景、等它自己跑几个轮询周期。

**测试全绿 ≠ UI 没问题。**
三个缺陷里没有一个是后端逻辑错 —— 全是前端时序与状态归属。
后端测试再全也照不到它们。**前端的缺陷只能靠真的驱动前端来发现。**

**缺陷二暴露了一个更深的问题：我第一版的修法引入了竞态。**
把 `main` 改成可变全局来「支持离屏渲染」—— 表面修好了，
实际制造了一个新的、更隐蔽的问题（视图函数往哪渲染取决于时序）。
**修 bug 时引入的新机制，本身要经得起同样的检验。**

### 11.16 补记：只读面板没补齐（D-37）

**现象**：人问「都在驾驶舱里能看到吧」。
ADR-010 §5.3 的端点表里有度量、停机、策略、预算、pipeline，
但 ADR-072 §6 只列了切片/事件/签字三类 —— **五个只读面板没人做**。

**为什么这不是「文档没写全」，是设计漏洞**：

ADR-072 §4 砍掉的是**写操作**（run/gate/freeze/admit/abandon/resume/create），
理由是「CLI 侧有完整实现，Web 侧再实现一份会分叉判定（C3 的隐患）」。
这条理由**只对写操作成立**。度量、停机、策略、预算、pipeline 全是只读 ——
只读不会分叉判定，CLI 侧也根本没提供 Web 想要的形态（`zelto summary --metrics`
是终端表格，不是给人扫读的看板）。

**当时为什么没发现**：ADR-072 §1 的摘要写「只读驾驶舱（切片总览 / 切片详情 /
事件流 / 审计 / 签字复查）」，这句话读起来像是**穷举**了只读面板。
我写 ADR 时把它当成了范围定义，实现时照着做 —— 一致，但都漏了。
**摘要是范围定义，不是范围清单**；漏了不会有人报错，因为没人对着 ADR-010 逐条核。

**修法**：补 5 个端点 + 5 个视图，判据一律复用 core 的既有实现：

| 面板 | 复用 | 对应 CLI |
|---|---|---|
| 度量 | `core/metrics/collector.ts` | `zelto summary --metrics` |
| 停机 | `core/stall/classifier.ts` | `zelto stall` |
| 策略 | `core/policy/data-access.ts` | `zelto policy list` |
| 预算 | `core/budget/collector.ts` | `zelto budget` |
| 全链 | `core/version/branch.ts` 的 `resolveSliceOwnership()` | `zelto merge`（归属判定） |

**关键约束：复用而不是重写。**
新写一份停机判定 = Web 与 CLI 报不同的停机列表 = 人不知道该信哪个（D-11 同族）。
归属判定尤其不能重写：CLI 判「这片归 v2」、Web 判「这片归 v1」，
人看到两套说法就无从判断。所以 `/api/pipeline` 的版本归属
直接调 `core/version/branch.ts` 的 `resolveSliceOwnership()`。

**两个「诚实性」决定**：

1. **未归属的切片要列出来**（`slices.unassigned`）。
   本仓实测 113 片中 40 片不属于任何版本。少列一份看起来更清爽，
   但人看到「v1 有 14 片」会以为其余都归了别处 ——
   直说「这 40 片没进任何版本计划」才是事实。
2. **策略的 `arch:` 段也要给**。
   只给 `rules:` 会让人以为策略只有一条规则 ——
   而 `arch:` 是架构护栏的判据依据，漏掉它等于让人漏看一半策略。

### 11.17 补记：Refs-Slice trailer 的 83 种取值（D-38）

**现象**：人问「统一修改」—— 指提交历史里 `Refs-Slice: <id>` trailer 写法混乱。

**实测数据**：全库 83 种 trailer 取值，只有 17 种对应真实存在的切片；
其余是 `adr-072` / `adr-069` / `drill-*` / `zelto-self` 这类**伪 id**。

**为什么这事不能当「格式问题」糊过去**：
`Refs-Slice` 不是纯标签 —— 它有**功能**。
`core/sched/audit.ts` 的 `hasRefsSlice()` 靠它判定
「这条提交是不是本片 agent 产出的」（ADR-067 D3）。
写集审计因此才能把「不是本片产出的提交」排除掉（实测 D-28）。

**伪 id 的真实危害**：审计按 trailer 过滤时，
一条 trailer 指向不存在的切片 = **这条提交永远不会被任何切片认领**。
不是「算错」，是「查不到」—— 追溯链在这里断了一节。

**为什么不全改成同一个值**：trailer 有功能，
统一到同一个 id 等于把 41 个提交都算成那一片的产出 ——
审计会认为「本片改了 41 个提交的文件」，越界判定立刻失真。

**修法（判据三条，同时满足才改）**：

1. 目标切片**真实存在**（`.zelto/slices/<id>.json`）且 `state === 'completed'`；
2. 其写集覆盖该提交的**代码类文件**（src/ tests/ contracts/ scripts/ specs/）——
   判据用 core 自己的 `pathInWriteSet`，不另写 glob 规则；
3. 覆盖数最多者胜出。

**为什么只要求覆盖「代码类文件」**：ADR 与演练记录是**开发过程的文档记录**，
不是切片产物。ADR 的引用保留在 commit message 正文里（本来就写着「ADR-072」），
trailer 只管「这段代码是谁写的」。

**结果**：41 个待改提交里 37 个可映射到真切片，
其余 4 个是纯文档提交 → `v0-docs`（写集 `docs/**` 正好覆盖）。

**一个工具坑**：git 默认把中文路径转义成八进制
（`"docs/zelto-\345\256\236..."`），直接拿去匹配必然失败。
必须 `git -c core.quotePath=false`。第一版脚本没加，
算出「只有 1/41 全覆盖」的荒谬结论 —— **工具的输出要验证，不要直接采信**。

### 11.18 补记：钱花了但账上没记（D-39）

**现象**：人问「为啥还有 3 个切片没有记账」。

**先查清「几个」**：界面上的「未记账切片」显示 111 个，
但那统计的是**所有无成本证据的切片**（含 117 个从没跑过的历史切片）——
不是人问的那个数。按「有 `run.started`/`run.finished` 证据、
却一条成本证据都没有」重查，真相是 **6 个**：

| 切片 | 性质 |
|---|---|
| `v2-sign-review-fix` | 真实切片（已签字合并） |
| `v3-sign-review-acceptance-spec` | 真实切片（已签字合并） |
| `admit-acceptance-tests` / `fail-test` / `run-via-scheduler` / `test-fail-retry` | 演练切片 |

**「3 个」这个数从哪来的**：4 个演练切片的 agent 是 `cmd /c exit 1`
之类，输出为空，本来就没用量可测 —— 剩 2 个真实切片。
数字对不上多半是人在看另一个口径（界面 111 / 真·没记账 6 / 演练 4）。
**这提醒一件事**：报数要说清口径，否则「3」和「6」会变成各说各话。

**根因（真 bug，不是设计如此）**：
`run.finished` 里写的是 `costUsd: null` —— 记账入口走到了，
但**金额取不到**。真实 stdout 长这样：

```
[claude-code:unrecognized_model] {"model":"deepseek-v4-flash-anthropic","query_source":"sdk"}
{"duration_api_ms":202574,"stop_reason":"end_turn","total_cost_usd":1.215272,"result":"..."}
```

第一行是**适配器自己打的告警前缀**，第二行才是 Claude 的结果对象。
`extractClaudeJson()` 的两种切法全废：

- 整体 parse —— 前缀不是 JSON
- 「第一个 `{` 到最后一个 `}`」—— 截出**两段 JSON 拼在一起**，
  `JSON.parse` 报 `Unexpected non-whitespace character after JSON at position 61`

于是 `total_cost_usd` 被丢掉 → `getUsage()` 返回 null →
`budget.spent` 事件写不出来 → `run.finished.costUsd = null` →
预算页显示「未记账」。**钱其实花了**：
`v2-sign-review-fix` 是 $1.2153，`v3-sign-review-acceptance-spec` 是 $3.5151，
**合计 $4.73 白丢**。这就是 ADR-035 §3.5 说的「假账」。

**修法**：`extractClaudeJson` 加第三种切法 ——
**按括号配对逐个切出 JSON 对象**（手工扫，跟住字符串字面量，
只在字符串外数花括号 —— 不能用正则，JSON 里有嵌套和转义引号），
然后按明确优先级挑：

1. 含 `total_cost_usd` 的（成本证据的唯一载体）
2. 含 `result` 字符串的（回答在这里）
3. 只有一个候选时就它
4. 都不满足且有多个 → **不猜，返回 null**（宁可退回原始 stdout 让人自己看）

**顺带发现的一个隐患**：`getOutput()` 与 `getUsage()` 原来共用
`extractClaudeJson()`。修好之后前者挑「含成本的」、后者挑「含结果的」，
两个需求会互相挤掉。所以**拆成两个提取器**：
新增 `extractClaudeResult()` 专门取回答，`getOutput()` 改用它。
「拿到了成本、丢了答案」也是假账的一种。

**实测**：拿真实的历史会话文件回放 ——
`v2-sign-review-fix` 取回 $1.215272（50364 / 14044 tokens），
`v3-sign-review-acceptance-spec` 取回 $3.515086（128709 / 55869 tokens），
两者的回答文本也都完整取回。

**回归**：新增 8 条测试（真实形状解析 / 成本段优先 / 回答独立取 /
只有告警段时不误判 / 多段都不含关键字段时不猜 / 字符串里的花括号不破坏配对 /
端到端走完适配器读到花费）。`npm test` **2100/2100 全绿**；lint 干净；编码检查通过。

**一处测试上的坑**：端到端那条用例最初用 `node -e "process.stdout.write('...')"`
伪造多行 stdout —— 但**换行在 shell 语法里是命令分隔符**，
多行文本塞进单引号会被拆断，测出来的 stdout 根本不是要验证的形状，
测试成了自欺欺人。改成**用文件承载 stdout** 才是真的。

### 11.19 补记：回填历史账 + 成本的第三态（D-41）

**起因**：人问「为啥还有 3 个切片没有记账」→「回填呀」。

**第一步先查清「几个」**（这一步不能跳）：
| 口径 | 数字 |
|---|---|
| 界面「未记账切片」 | 111 |
| 有 `runs` 记录但无成本证据 | 2 |
| 事件流里有 `run.*` 但无成本证据 | 19 |
| 有成本证据的切片 | 5 |

真·没记账的就是 **2 个**：`v2-sign-review-fix`、`v3-sign-review-acceptance-spec`。
其余 126 片**会话文件里根本没有成本数据**（输出为空或 31 字节的失败信息）——
它们的真相是「**核查过，但 agent 没报出用量**」，不是「没花钱」。

**第二步撞上一个真问题**：回填要给那 126 片写「零额」事件，
但 `BudgetCollector` 的判据是「**见过 `budget.spent` 就 measured**」——
写 `amount: 0` 会让界面显示「$0.0000」，等于宣称「测过了，确实没花钱」。
而 ADR-035 §3.5 恰恰说**「没测到」不能显示成金额**。

反方向也一样：「测到 0」显示成「未记账」也不对。
真相有**三态**，布尔装不下：

| 状态 | 含义 | 界面 |
|---|---|---|
| `unmeasured` | 压根没核查 | 「未记账」 |
| `unavailable` | 核查过，但拿不到金额 | 「未测到」 |
| `measured` | 测到了（金额可能就是 0） | 「$X.XXXX」 |

**实现**：`budget.spent` 的 payload 加 `measured: false` 表示「核查过但拿不到」。
`BudgetCollector.getSpentDetail()` 返回三态 `CostMeasurement`，
`dashboard-cost.ts` 相应拆成 `measuredSlices` / `checkedNoUsageSlices` / `unmeasuredSlices`。

**回填脚本**：`scripts/backfill-cost.mjs`，三条硬规矩：
1. **只追加**（C4）—— 已有事件一个字节不动。
2. **金额必须来自真实会话文件** —— 拿不到就写「拿不到」的标记，绝不写 0 冒充。
3. **时间戳用原始会话时间**，不是补记时刻 —— 事件时间就是事实发生的时间。

默认干跑，`--apply` 才真写。

**实测**：
- 2 片真实金额：`v2-sign-review-fix` $1.215272（50364/14044 tokens）、
  `v3-sign-review-acceptance-spec` $3.515086（128709/55869 tokens），**合计 $4.730358**。
- 126 片零额标记（`measured: false`）。
- 事件流 1276 行 → 1404 行，正好 +128。**前缀一致性检查全过**（已有事件零改动）。
- 总花费 $0.01116 → **$4.741518**。三态分布：measured 4 / unavailable 109。

**顺带发现的既有洞（没修，另记）**：17 片老状态文件 `stall: null`，
`SliceStore.read()` 读 `slice.stall.class` 直接抛异常，
`listSlices()` 的 `catch` 把它们**整个跳过** —— 驾驶舱显示「113 切片」，
实际状态文件有 130 个。那 17 片在驾驶舱里**根本看不见**。
这跟回填无关（回填按状态文件遍历，不走 `store.read()`，绕开了它），
但它是「113」这个数字的来源。**另开一条修。**

**回归**：新增 6 条三态测试 + 8 条解析测试。`npm test` **2106/2106 全绿**；
lint 干净；编码检查通过。

但 `tests/merge-branch-cleanup.test.ts`（未提交，nimrtc-zelto 靶子上

### 11.21 补记：CI 红了，根因在测试自己（D-42）

**现象**：推上去的 ADR-073 提交，CI 直接失败（run 44030218205）。
本机 `npm test` 同样失败（2108/2109）。

**第一层直觉**：新并进来的 `tests/merge-branch-cleanup.test.ts` 从没跑过，
所以是它坏了。但**为什么坏**才是重点 —— 直觉会把你引到错误的地方。

**根因一：`.zelto/` 被 `git add -A` 当成嵌入式仓库提交了**

测试在 `.zelto/worktrees/` 与 `.zelto/version-worktrees/` 下建了两个
`git worktree` —— 每一个都是**独立的 git 仓库**。测试里有一次 `git add -A`，
git 于是把它们作为 gitlink（mode 160000）提交进分支。

于是：目标分支与待合分支在 `.zelto/**` 上「有差异」→ 合并守卫判定
「合并会真冲突」→ 不豁免 → `.zelto/` 被算成「工作区脏」→ 合并中止。

**而这个差异纯粹是测试自己造出来的**。真实项目里 `.zelto/` 是被
`.gitignore` 忽略的（nimrtc-zelto .gitignore:78），这个坑不会发生。

这里要记一条方法论：**gitlink（mode 160000）是「嵌套 git 仓库」被
`git add` 后的正常形态**，不是 bug。看到 porcelain 里出现 `?? .zelto/`
却发现某个 ref 里有 `.zelto/xxx` 的条目，先查 `git ls-tree <ref> .zelto/` ——
mode 是 160000 就说明是 gitlink，不是普通文件。

**根因二：「合并成功但分支没并入目标」这件事在正常流程里到不了**

第三个用例想验「分支没合入目标 → 不删分支，如实说还有未合入的内容」。
但这个状态**通过 `zelto merge` 根本产生不了**：

- 分支是从 `main` 长出来的 → `main` 是它的祖先 → fast-forward 成功
- 合并成功后该分支**确实**是目标分支的祖先 → 删掉它完全正确

所以测试实际测到的是「合并被工作区脏拦下」，输出里自然没有
「not merged / 未合入」—— 断言失败，但**失败的原因跟被测的逻辑无关**。

修法：这条**直接调被测函数** `cleanupMergedSlices`，构造出
「分支确实还没并入目标」的状态。那段「没合入就不删」的防御代码守的是
**别的情况**：分支被人手动改过、目标 ref 不是合并时用的那个、
或仓库状态在合并与清理之间被外部改动。

**教训（这才是值钱的部分）**：

1. **测试要复现真实项目的环境，不是理想化的环境。** 真实项目 `.zelto/`
   被 gitignore，测试却没 ignore —— 于是测试测的是一个真实世界不存在的
   故障形态。写测试前先问「真实项目长什么样」。
2. **「测试失败」不等于「代码有 bug」。** 这次产品代码是对的，坏的是测试
   造出的前提。**先证明失败与被测逻辑无关**，再去改代码 ——
   否则会把一个「如实报告工作区脏」的正确行为改成「放宽豁免」的错误行为
   （那正是 D-11 假成功缺陷的反面）。
3. **有些状态通过正常流程到不了，就必须直接调被测函数构造。**
   「合并成功但分支没并入目标」在 `zelto merge` 的流程里不存在 ——
   这种情形只可能来自「合并与清理之间被外部改动」。
4. **断言要指向真正要守的东西。** 原来的断言盯着「not merged / 未合入」
   这句文案；真正该守的是「**不该出现「merged elsewhere」**」——
   那句话对两种情形都不成立，人照着它去 `git branch -D`
   就等于绕过 git 的安全检查。

**回归**：2125/2125 全绿；lint 干净。

**另**：ADR-073 提交与 budget 修复提交在本地被拆成两个（原先是 amend 压成的一个），
推送时用了 `--force-with-lease`。拆分前逐文件比对过：远程没有本地缺失的内容，
本地是严格超集（多出测试修复与文档更新），强制推送安全。

### 11.22 补记：CI 第二次红 —— 又是测试自己，而且**早就坏了**（D-43）

第一次 CI 失败（44030218205）修掉后，第二次（44035290667）又红。
这次的报错是：

    Command failed: git commit -q -m legacy state
    Author identity unknown
    *** Please tell you who you are.

**根因**：`adr-056-adopt.test.ts` 与 `adr-056-migration.test.ts`
建了 git 仓库就直接 `git commit`，**没设仓库内的提交身份**。

**为什么本机过、CI 不过**：本地 git 有全局 `user.email` / `user.name`；
CI runner 是干净容器，**没有全局身份**。于是前者的 5 个用例全部
cascade 成「test did not finish before its parent and was cancelled」。

**这不是本轮改动引入的**。这两个测试文件是 2026-11-13 引入的
（`2f4a3c9 feat(version): 老项目迁移命令 zelto version adopt`），
而**上一次绿的 CI 是 2026-11-12** —— 也就是说这些提交**从没被推过**，
CI 从没见过它们。**一直红着，只是没人看见。**

这个事实值得单独记一笔：**「上次 CI 绿」不等于「这批提交是绿的」**。
中间攒了 8 个没推过的提交，CI 一旦跑起来就全暴露了。

**修法**：照仓库里其余 20 多个测试的既有做法，`git init` 之后补
`git config user.email` / `user.name`（**仓库内**，不是全局）。

**验证方式（这条最值钱）**：本机有全局身份，所以本地**永远复现不出来**。
用环境变量模拟 CI 即可：

```powershell
$env:GIT_CONFIG_GLOBAL="NUL"; $env:GIT_CONFIG_NOSYSTEM="1"
node --test "dist-test/tests/**/*.test.js"
```

改前：这两个文件全红。改后：**2125/2125 全绿**。

**教训**：
1. **本机绿 ≠ CI 绿。** 环境差异（git 全局配置、locale、路径大小写、
   换行符、8.3 短名）都是隐形差异。要在本地复现 CI，就**显式抹平环境**。
2. **仓库内身份优于全局身份** —— 测试建自己的仓库，就必须自己配齐身份，
   不能依赖跑测试那台机器的全局设置。这不是「补个环境变量」，
   是**测试不该假设宿主机状态**。
3. **提交积压是风险**。攒 8 个提交不推，CI 的第一次运行就变成
   「8 个提交的集体体检」。推送应该是**每个提交都过 CI**，不是攒一批再说。

### 11.23 补记：agent 空转 30 分钟 —— 「写集不在 policy 覆盖内」（D-44）

**现象**：nimrtc-zelto 的 v2 两个切片卡在 `running`，worktree 里
**agent 一个字节代码都没写**（只有 zelto 自己放的规格副本和验收骨架）。
会话文件 `status: running` 但进程早已死掉。

**排查顺序**（每一步都要**排除**，不能跳）：

| 检查 | 结果 |
|---|---|
| agent 本身 | ✅ 探针 7 秒返回 `result: "OK"`，`total_cost_usd: 0.023445` |
| 网关 `api.haimacloud.com` | ✅ HTTP 200，正常返回 |
| claude-code CLI | ✅ 2.1.318 可用 |
| `v2-input-binder` 写集 | ✅ 三条全在 `src/**` / `tests/**` 允许清单内 |
| **`v2-ai-decision` 写集** | ❌ **`demo-agent-realtime/**` 不在允许清单** → 落到 `default` 规则 → 拒绝 |
| 事件流 | ✅ 直接给出答案：`deny demo-agent-realtime/package.json（规则 default）` |

**根因**：policy 的允许清单是自动生成的（`src/**`、`cmake/**`、
`examples/**`…），`demo-agent-realtime/**` 不在其中 →
agent 第一次写文件就被 `default` 规则拒 → **换个路径再试 → 又被拒** →
30 分钟超时耗尽。

**这件事 zelto 其实已经提前算出来了**（06:29:40 的 `spec.checked`）：

> 写集 "demo-agent-realtime/**" 不在 policy.yaml 的任何允许规则覆盖范围内
> —— agent 第一次写文件就会被拒（policy.yaml#default）

**但它算出来了，却没有拦住 run** —— agent 仍然开跑、反复撞墙、
把 30 分钟超时耗光。这才是真正的问题：**判定有，闸门没接上**。

**顺带发现两件事**：

1. **「写集」有三层，可能互不一致**：
   - 已提交并冻结的规格（哈希 = 切片状态的 `frozenHash`）—— **权威**
   - 工作区里未提交的规格（人改的，哈希已失配）
   - 切片状态文件的 `writes` 字段
   改规格而不改切片状态（或反之）就会脱节。**判断哪份权威的方法：比哈希**，
   不是比内容「看起来对不对」。

2. **`[claude-code:unrecognized_model]` 告警无害但会误导**：
   agent 请求的模型名 `deepseek-v4-flash-anthropic`，
   网关实际返回 `deepseek-v4-flash-ga-260731` —— 名字对不上，
   claude-code 就打这行告警。**它不是错误**，但它和 D-39 的多段 JSON
   是同一个 stdout 形状（告警前缀 + 真正的 JSON），正好被 D-39 的解析器覆盖。

**这一轮做的事**（nimrtc-zelto，提交 `1fdb5da2`）：
1. 加规则 `allow-write-demo-agent` → `demo-agent-realtime/**` 放行。
2. **建立 `policy/lock.json` 锚点** —— 之前**根本没有这个文件**，
   策略哈希无锚点，改策略不可检出（C5 形同虚设）。
3. 删掉 `policy.yaml` 里废弃的 `anchors` 段（validate 一直在警告）。

**锚点机制实测有效**：删废弃段 → 哈希变化 → 立刻被检出失配
（「策略被改过而锚点没动」）→ 重新锚定才一致。**这正是 C5 要的效果**，
而且是第一次在真实项目上看到它拦下真东西。

**教训**：
1. **「agent 没产出」的第一嫌疑不是 agent 挂了，是 agent 被挡住了。**
   先看事件流里的 `policy.decision` —— 那里有每一次写入的判定，
   比任何外部探测都直接。
2. **判定算出来了 ≠ 拦住你了。** zelto 已经有「写集不在 policy 覆盖内」
   的检查，但它没接到 run 的入口。**这是下一步该修的**（不是产品 bug，
   是闸门没接上）。
3. **锚点必须真的存在。** C5 写了「锚点独立存于 `policy/lock.json`」，
   但真实项目里那个文件**压根不存在** —— 约束写在文档里，
   落地时漏了，就等于没有这条约束。**约束要靠「它有没有真的在工作」
   来验证，不是靠文档写了没有。**

### 11.24 补记：判定有、闸门没接上（D-44 的后半段）

上一节说 zelto「已经能算出写集不在 policy 覆盖内」，但**它没接到 run 的入口**。
这一节把这段补完。

**先分清三个位置**（这是当时没分清、导致判断偏差的地方）：

| 命令 | 性质 | 改状态？ |
|---|---|---|
| `zelto check` | **一个命令** —— 人不跑它，它就只是屏幕上的一段字 | 否 |
| `zelto freeze` | 把规格钉成「基线」 | 是 |
| `zelto run` | agent 真正开跑（最贵的一道） | 是 |

**真正的闸门在会改变状态的路径上。** `check` 有判据但不是闸门 ——
`freeze` 和 `run` 都不查它。修法是让三处共用**同一个判据**
（`core/spec/write-set-policy.ts`），不各写一份（各写一份必然漂移）。

**顺序也有讲究**（这不是洁癖，是信息量的问题）：

- `run` 里放在 `admit` **之前**：写集策略比「状态对不对」更根本 ——
  一个 draft 的切片，和一个 frozen 但注定跑不起来的切片，
  **后者的信息量更大**（它已经被人批准过了，却被策略挡住）。
- `freeze` 里放在 D-4 检查**之前**：写集整体被策略挡住时，
  D-4 报「某文件不在写集里」只是**症状**，病根在策略。
  顺序反了会让人去改写集，而真正该改的是策略。

**顺带发现一个更隐蔽的缺陷**（比原病灶更值得记）：

项目**没有** `policy/policy.yaml` 时，`loadPolicyConfig` 回落到
**zelto 自己的兜底策略**（`src/**/*.ts` 等，给 TypeScript 项目用的）。
拿它去判一个 C++ 项目的写集（`src/engine/src/foo.cpp`）会得出
「不在任何允许规则覆盖范围内」—— **一个纯误判**：
那个路径在项目自己的策略里很可能被允许，只是这个项目还没写策略而已。

> **「还没写策略」和「策略不允许」是两件事。前者不该拦人。**

所以 `loadPolicyConfig` 现在返回 `source: 'project' | 'fallback'`，
**阻断性判定只认项目自己的策略**。兜底策略只够用来回答
「读总是允许」「保护域是什么」这类不依赖项目语义的问题。

**这个缺陷是被测试逮住的，不是想出来的** —— 它先让
`tests/write-set-coverage.test.ts` 红了。**测试红的时候先问
「失败与被测逻辑有关吗」**，别急着改产品代码：这次红的表面症状是
「我的新闸门误伤」，追下去才发现真正的缺陷在
「兜底策略被当成项目策略」这个更早的地方。

**验收测试**（`tests/acceptance/write-set-policy-gate/`，11 个用例）锁的是
「闸门真的接上了」，不是「判据算得对」：

- `run` / `freeze` / `check` 三处都拦得住（真实 CLI 进程，不 mock）
- 拒绝信息说清「第一次写文件就会被拒」，并给出**可执行的**修法
- 拒绝发生在**预算扣除之前** —— 不占额度
- 被拒的 `freeze` **不会**把切片置为 frozen（状态没被改）
- 判定写进事件流（事后可查「为什么没跑」）
- 「没有 policy.yaml 的项目」不被误拦（上面那个缺陷的回归）

**教训**：
1. **「判定有」不等于「闸门接上了」。** 判定在某个命令里，
   而闸门在**会改变状态的路径**上 —— 这两件事必须分开看。
2. **兜底策略不能用来阻断。** 兜底是「暂时没有判据」，
   拿它当判据会把「没配置」误判成「不允许」。**判不了 ≠ 判为坏。**
3. **闸门之间要共用判据，也要共用顺序。** 三处各写一份判据，
   迟早漂移；三处顺序不同，会让人去修错的东西。

### 11.25 补记：两个人同时改一个仓库，会踩哪些坑（D-45）

这一轮是**人（我）和另一个 agent 同时在 `D:\MyOpen\Zelto` 工作**。
听起来是效率增益，实际上踩了四个坑 —— 每个都值得记。

**坑一：提交会把别人的半成品一起带走。**

我改了 `src/cli/commands/core-slice.ts`（接写集策略闸门），
他改了同一个文件（ADR-074 的 watchdog）。`git diff` 里我的 hunk 和他的 hunk
**交织在同一个文件**，无法用 `git add -p` 干净分开。

更麻烦的是依赖闭合：他新建的 `src/core/spec/reference.ts` 被
`core-slice.ts` import，我的新闸门 import 他写的
`src/core/spec/write-set-policy.ts`。**任何一边单独提交都会编译不过。**

> **两个 agent 同时改一个仓库，「按文件分开提交」这个假设不成立。**
> 依赖是跨文件的，提交是按仓库的。要么等对方收工，
> 要么一起提交（前提是**工作树自洽**：全量测试过、lint 过）。
> 本次选了后者 —— 先跑通 2184 个测试再一起提交。

**坑二：全量测试的失败可能不是你的代码。**

我的新闸门让 `tests/write-set-coverage.test.ts` 红了 2 个用例。
第一反应是「我改错了」。但复现不出来：
- 单独跑该文件：24/24 过
- 与另一个文件一起跑：过
- 串行跑：过

最后发现：**并发 agent 正在给那个测试文件加 fixture**（`policy.yaml`），
我的测试跑在它改到一半的时刻。**「失败的测试」和「不稳定的测试」
必须分开**，而区分的办法只有一个：**复现**。

> **测试红了先复现，再改代码。** 复现不了 = 不是你的问题（或者说是竞态）。
> 直接改产品代码去迎合一个复现不出来的失败，
> 是在给一个不存在的问题打补丁。

**坑三：两个 agent 抢 `dist/`。**

`npm run build` 会先 `rm -rf dist/`。我跑全量测试的 80 秒里，
他跑了一次 build —— **144 个用例因为 `Cannot find module 'dist/hook/index.js'`
而失败**。这些失败和我的改动毫无关系，纯粹是构建目录被抽走了。

> **两个 agent 共享一个构建目录时，「测试失败」要先怀疑构建产物。**
> `Cannot find module 'dist/...'` 这一类失败不是逻辑失败，是**基础设施失败**。
> 判据：失败消息里出现模块找不到 → 先重新构建再复跑，别改代码。

**坑四：注释里的 glob 会炸。**

我在 JSDoc 里写了 `` `src/**/*.ts` `` —— 里面的 `*/` **提前闭合了注释**，
编译直接报 `TS1443: Module declaration names may only use ' or " quoted strings`，
报错位置还指向几行之外（因为注释被吃掉后语法全乱了）。

> **注释里不要写含 `**/` 的 glob 字面量。** 这是个非常隐蔽的坑：
> 编译错误指向的位置和真正的病因**差了十几行**。
> 排查时如果报错位置在一条看起来完全正常的注释里 —— 先怀疑它。

**一个反直觉的收获**：`loadPolicyConfig` 的兜底策略缺陷
（项目没有 `policy.yaml` 时，拿 zelto 自己的兜底策略去判 C++ 项目）
**是被测试逮住的，不是我想出来的**。如果我先写测试再写实现，
这个缺陷根本不会出现 —— 因为我会从「项目没有策略」这个场景开始设计，
而不是从「有策略」开始。

> **先写「边界场景」的测试，再写实现。** 正常路径的实现谁都会写；
> 边界场景的测试才是发现设计缺陷的东西。

### 11.26 补记：第一次完整闭环（D-46）

`v2-input-binder` 走完了 zelto 设计以来的**完整路径**：

```
agent 在隔离 worktree 里产出代码
  → 记账（$0.673，73049 输入 / 13268 输出 token）
  → 门禁①：追溯、写集、规格一致性 —— 通过
  → 门禁②：build（60.8s）+ ctest —— passed: true
  → 状态变更 → 发出签字请求 → 停在「等人签字」
```

**为什么这件事值得单独记一节**：前面十几轮里，zelto 验证过
「越界当场拦下」「追溯不合格拒冻结」「agent 崩了能定责」——
但那些都是**「拦住」**的验证。**「放行」**的这一侧，
在真实 C++ 大项目（848 个构建目标、1998 个 ctest 用例）上，
是第一次走完。

之前一次「看起来成功」其实是假的：`v2-input-binder` 的 agent 自述
「No code changes were needed — the worktree already satisfied every
acceptance regex」。乍看是成功，细看是**它什么都没做** ——
那批代码早在 `efc1c2bc` 里就有了，agent 只是跑了一遍验收确认。

> **「agent 说做完了」和「agent 做了事」是两件事。**
> 判据不在 agent 的自述里，在 **git diff** 里。
> 一个零改动的 run 也是「成功退出」，但它没有交付任何东西 ——
> 而这种「假成功」比失败更危险：流程一路绿灯，人以为进度在推进。

**另一个值得记的：规格被重写后，代码就「过期」了。**

并发 agent 把 `v2-ai-decision` 的规格从 4 条空洞指标
（「决策响应时间≤50ms」「决策准确率≥90%」—— 这类指标**没法验证**）
改写成 9 条可验证的断言（字段齐备、`partial`/`barge_in` 可解析、
`agent-control` 标签、`framed` 模式、`IASR`/`ILLM` 可插拔…）。

但**代码还是按旧规格写的** —— 有 `LatencyInstrument`/`percentile_ns`，
没有那六项。规格与代码之间出现了一道**没人写下来的债**。

于是：
- 冻结哈希对不上 → 漂移告警（这正是它的用处）
- 重跑 agent 会按新规格重做 → 但预算已超（$1.85 / $1.00）
- 预算闸门拦住 → 交回给人

**这一连串全是闸门在正常工作**，而且每一道都拦在了对的地方。
唯一「不像故障」的地方是：**人差点忘了预算上限可以调**，
是另一次演练顺手把 `budgetLimitUsd` 从默认 1.0 提到了 6。

> **闸门拦住 ≠ 出故障。** 大多数时候它拦住的是**一个还没被决定的问题**
> （这次是「要不要为新规格再花一次 agent 的钱」）。
> 这种拦截是设计意图，不是缺陷 —— 但它要求人能看见那个待决问题，
> 所以拦截信息必须说清「为什么拦」和「怎么解」。

**一条串起来的因果链**（这一轮最有价值的部分）：

```
规格写成不可验证的指标
  → agent 照着实现（性能监控工具、专家 oracle —— 但都验证不了）
  → 规格被重写成可验证的断言
    → 代码过期（规格与实现的债）
      → 漂移告警（人看得见）
        → 重跑需要钱 → 预算闸门（人拍板）
          → 提预算 → 重跑 → 新代码对上新规格
```

**每一环都不是 bug，每一环都是闸门。** 这一轮真正验证的是：
**这些闸门串在一起时，能不能把人带到「该做决定的地方」，而不是
把人困住或者让人误以为一切正常。**

### 11.27 补记：「看起来全绿」的两片里有两片根本没被验证过（D-47 / D-48）

这一节是本轮最重要的记录 —— 它记的不是 zelto 挡住了什么，
而是**zelto 差点放过了什么**。

**第一片：`v2-input-binder`（已完成、gate 通过、等待签字）**

乍看是本轮最成功的一片：agent 跑完 → gate 通过 → 签字请求已发出。
细看：

| 规格要求的 5 条验收标准 | 实现情况 |
|---|---|
| `ref_frame_binder.hpp` / `.cpp` | **文件根本不存在** |
| `rd_device.cpp` 消费侧（反查采集时刻、帧龄） | **一行都没写** |
| 验收测试 3 条用例 | **全是 `test.todo`** —— 零真断言 |

agent 的自述是：「No code changes were needed — the worktree already
satisfied every acceptance regex」。

**这句话是真的，但它是关于「旧代码」的。** 那批 `include_ref_frame`
代码早在 `efc1c2bc` 里就有了 —— agent 跑了一遍验收正则，确认它们还在，
于是报告「无需改动」。而**规格要的是新东西**（消费侧反查 + 帧龄展示）。

worktree 的全部改动：**两个未跟踪文件（规格 + 验收骨架），零行代码改动**。

**第二片：`v2-ai-decision`（已完成、gate 通过、等待签字）**

agent 跑成功了（1043s），代码也真写了。但它的产出对着的是**旧规格**：

```
规格在 09:04 被重写（4 条空洞指标 → 9 条可验证断言）
worktree 在 05:12 创建，里面拷的是当时的旧规格
10:00 重跑 agent —— agent 读的是 worktree 里的旧副本
```

于是产出的代码有 `LatencyInstrument`/`percentile_ns`（旧规格要的），
没有 `partial`/`barge_in`/`agent-control`/`framed`/`IASR`/`ILLM`
（新规格要的）。

**两个病根，一个在上游，一个在下游。**

#### 上游：worktree 里的规格副本永不更新（D-47）

`syncContext`（规格 + 验收目录的复制）**只在 worktree 创建时跑一次**。
之后规格改了、副本不跟着改。

**判据分裂**：门禁按**新**规格判（冻结哈希算的是主仓当前规格），
agent 按**旧**规格干。拦住的不是「实现有 bug」，而是
「实现的是另一个需求」。

**每一道闸门单独看都在正常工作** —— 这才是它难查的原因。
漂移告警响了（哈希对不上），但没人把「漂移告警」和「agent 读的是哪份规格」
连起来。

修法（`src/core/worktree/manager.ts`）：复用已有 worktree 时**也**同步
规格与验收目录。规格是 agent 的**输入**，输入必须在每次开跑前对齐到当前真源。

#### 下游：签字路径绕过了审查（D-48）

修好上游之后，两片还是**不能签** —— 因为它们根本没被验证过。

而 zelto 这时给出了一片绿灯：

```
gate: build ✅ exit 0 (80.8s) + ctest ✅ exit 0 (218.1s) → passed: true
acceptance: skipped（未配置切片级验收）
sign.requested ✅
```

**注意 `acceptance: skipped`。** 项目的 `config.yaml` 没配 `gate.acceptance`
段 → ADR-033 的 fail-closed（没有真断言就算没验证）**压根没被触发** →
验收测试文件里那三条 `test.todo` 从头到尾没被执行过。

**规格的 5 条验收标准，由谁验证？没人。**

而 ADR-070 的 `sign --review` 其实**抓到了**。实测：

```
签字前请确认四件：
  ❌ 追溯链未断    需求/契约/测试三条追溯均非空，冻结准入判据通过
  ❌ 验收真跑过本片  gate.result 事件没有 acceptance 记录——本片没有真正被验收过
  ✅ 改动在写集内   写集审计无越界写入
  ✅ 产物真落地     产物已在主干找到：src/modules/rd_input/include/...
```

**四项里两项不过。** 但 `zelto sign <id> --approve` **不经过 review** ——
审查工具存在，签字路径绕过审查。

修法：`--approve` 先跑四项确认，任何一项不过就**拦下**（退出码 1）。
`--force` 留给人一个显式出口 —— 明知故犯可以，但要明着做。

#### 这一节真正要记的东西

> **「gate 通过」和「这片东西被验证过」是两件事。**
> 门禁②跑的是**项目级**命令（build + ctest）—— 它们验证的是
> 「项目没被改坏」，不是「这片东西做到了规格」。
> 把前者当成后者，是这一轮踩到的最深的一个坑。

> **审查工具和执行路径必须同一条路。**
> 有一个「签字前确认」的 review 功能，但它只挂在 `sign --review` 上，
> 而人实际签字走的是 `sign --approve` ——
> 审查做得再好，只要执行路径不经过它，它就只是「一个可选功能」。

> **「skipped」和「passed」在人的眼里长得一模一样。**
> 界面上都是一片绿。区别只在事件流的一行 JSON 里。
> zelto 的整个设计是为了「把判定变成可判定的约束」，
> 但**约束没接上执行路径**的时候，它就退化成了一份记录。

最后这一条，其实是 D-44 那句教训的翻版：
**判定有、闸门没接上** —— 上一次是「写集不在 policy 覆盖内」，
这一次是「签字前确认项」。同一个形状，同一个教训，
但这次是在**签字**这条路上 —— 也就是最后一道闸门。
