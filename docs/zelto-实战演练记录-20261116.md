## 一、这一轮与上一轮的差别

上一轮的目标是「**从空白需求到 `version ship`**」—— 验证 zelto 的骨架能不能撑起
一次完整交付。这一轮的目标不同：**验证 zelto 在一个「已经在维护中的真实项目」
上能不能做增量的、可并行的开发**。

具体差别：

| 维度 | 第一轮 | 第二轮 |
|---|---|---|
| 起点 | 空白（`reset --hard github/main`） | 已有 20+ 个切片、已有版本分支 |
| 切片来源 | LLM 生成（`zelto plan`） | **人工撰写规格**（两片都手写） |
| 并发性 | 单片串行 | **两片写集重叠 → 调度器降级为串行** |
| 靶子代码 | 新建 | 改动**既有**生产代码（`engine_media.cpp` / `engine_rtcp.cpp` / `engine_rtcp_xr.cpp`） |

**规格人写**这一条是本轮最重要的变化。第一轮的规格是 LLM 起草的，
问题藏在措辞里；这一轮手写规格，能更精确地测「规格与写集的一致性」
（ADR-059 §3 的判据到底准不准）。

## 三、本轮发现的 zelto 缺陷目录

### D-24（中）人改保护域也被 hook 拦住

**现象**：`policy/policy.yaml` 改了之后 `git commit` 被 pre-commit hook 拦下：

```
policy/** 是保护域 —— 策略的修改必须由人直接完成，
并通过 `zelto policy lock --update` 重新锚定。
```

**为什么这是缺陷而不是正确行为**：C5 说「保护域硬编码、不可被任何策略规则覆盖」
—— 保护域防的是 **agent**。但 hook 不区分**谁**在提交：

- agent 提交 → 必须拦（C5 的本意）
- 人提交 → 必须放行（否则 C5 的配套流程 `policy lock --update` 走不通）

现状是两者都拦。演练中只能 `--no-verify` 绕过。

**修复方向**（待实施）：hook 判据要看**是不是 agent 在提交** ——
zelto 在 agent 运行时往环境里注入标记（类似 `ZELTO_SLICE_ID`），
hook 据此区分。没有标记 → 是人 → 放行。

> 顺带暴露：**演练记录里写「用 `--no-verify` 绕过」是权宜之计**，
> 它让「策略被改过」这件事在 git 历史里没有钩子痕迹。

### D-25（严重）超时的重试在适配器内部「从头再来」，短路了 ADR-055 的续跑

**现象**：`v1-rtcpprocessor` 的 agent 跑了 30 分钟被超时杀掉，然后：

| 会话 | agent 会话 id | 说明 |
|---|---|---|
| `claude-agent-v1-rtcpprocessor-1794796572264` | `bd4e6295-...` | 第一次，`status=timeout` |
| `claude-agent-v1-rtcpprocessor-1794798375472-retry-1` | `d6944875-...` | **新的 agent 会话 id** |

**agent 会话 id 变了** → 不是续跑，是**从头再跑**：agent 的上下文被清零，
它已经摸清的东西（改到一半的代码、跑了一半的测试、读过的一堆源码）全部作废。

**根因**：`src/adapters/claude-agent/index.ts` 的 `waitForExit` 里，
非零退出 → 适配器**内部** `startWithRetry` → 用**原始 bundle** +
**新的 agentSessionId** 重启。这条路径把 CLI 层的
`resumeForRetry`（真正的 ADR-055 续跑）**完全短路**了 ——
适配器内部已经把重试链跑完（实测跑到 `-retry-2`），CLI 层根本没机会执行。

**关键的隐蔽点：退出码分不出超时。**

ADR-055 决策 B 假设「超时时 exitCode 是 `null`」（POSIX 上确实如此）。
但 **Windows 上 `taskkill` 杀掉进程树后，shell 包装返回的是非零码（1）** ——
实测确认。所以 `waitForExit` 里的 `code !== null` 判断在 Windows 上
**永远成立**，超时与「agent 报错退出」在退出码上完全一样。

唯一可靠的超时信号是适配器**自己**记的 `status === 'timeout'`
（`handleTimeout` 在杀进程树之前就写好了，ADR-055 决策 B）。

**已修**（`c07df3f`）：

```ts
const data = loadSession(sessionId);

// 超时 → 不在这里重试。交给 CLI 层走 ADR-055 的续跑路径
// （`continueSession`）—— 见上面那段说明。
if (data?.status === 'timeout') {
  resolve(code);
  return;
}
```

**回归测试**（`tests/adr-055-timeout-kills-tree-and-continues.test.ts`，+5 条）：

1. 超时的退出码不是 0（**锁住「退出码分不出超时」这个事实**）
2. 超时后适配器**没有**起第二个 agent（会话数增量 == 1）
3. agent 报错退出（`failed`）**仍会**起内部重试（增量 == 2）
   —— **两条必须不同**，否则修复就是把「重来一遍」这个正当行为也砍了
4. 超时后 CLI 层能续同一个 agent 会话（`agentSessionId` 相同）
5. 非零退出码的状态是 `failed` 不是 `timeout`

> **教训**：ADR-055 写于 Windows 环境，却把 POSIX 的退出码语义
> （信号杀 → `null`）当成了通用事实。**跨平台的语义差异必须在 ADR 里写明，
> 或者干脆不用它做判据。**

### D-26（中）花括号简写被当成一个文件名 → 写集覆盖判据误报

**现象**：规格里写「新建 `src/engine/src/rtcp_processor.{hpp,cpp}`」，
门禁①报：

```
规格提到「src/engine/src/rtcp_processor.{hpp,cpp}」，但它不在写集里 —— agent 改不了它
```

而写集里明明有 `rtcp_processor.hpp` 和 `rtcp_processor.cpp` 两个文件。

**根因**：`src/core/spec/scope.ts` 的 `normalizeMentionedPath` 过滤了
glob 通配（`*` / `?`），但**没处理花括号**。于是
`rtcp_processor.{hpp,cpp}` 被当成**一个**具体文件名。

**闸门误报比闸门漏报更糟**：漏报让人绕过一次检查；误报让人以为
「规格有问题」，于是去改规格 —— 而规格是对的。

**已修**（`2a1f8d0`）：**展开**而不是丢弃。

```ts
function expandBraces(raw: string): string[] {
  // a{b,c}d → abd + acd
  // 不含逗号的 {x} → 原样返回（不是简写）
  // 嵌套花括号不展开
}
```

展开失败（嵌套、无逗号）的花括号串**不报** —— 报一个多半不存在的文件名
比不报更糟。

**回归测试**（`tests/write-set-coverage.test.ts`，+6 条）：展开正确性、
不残留花括号、前后缀场景、无逗号不展开、嵌套不展开。

**真实验证**：`v1-engineimpl` 的门禁①从 ❌ 变 ✅。

> **教训**：D-4 引入「规格全文路径提取」时，把「提到的路径」理解成了
> 「一个路径」。实际上规格提到的是**路径的集合**，而集合有不同的写法
> （逗号分隔、花括号、目录）。**判据要能认出集合的写法。**

### D-27（低）`--agent` 参数值拼错时，错误信息不指向正确命令

**现象**：`zelto run v1-rtcpprocessor --agent claude-code` 直接失败，
但错误信息没有说「命令不存在」或「配置里是 `npx @anthropic-ai/claude-code`」。

**性质**：**不是 zelto 的缺陷** —— 是演练时我传错了参数。
配置 `.zelto/config.yaml` 里的 `agent.command` 是 `npx @anthropic-ai/claude-code`。

**但暴露了一个真问题**：agent 命令名（`claude-code`）与真实可执行命令
（`npx @anthropic-ai/claude-code`）**长得不一样**，而工具没有在预检失败时
把「你想要的」与「实际用的」并排列出来。人只能自己去翻 `config.yaml`。

**处置**：列为改进项（预检失败时附上「当前配置的命令」），不单独开 ADR。

### D-28（严重）同版本第二片从主干 HEAD 建 worktree → agent 被迫重造上一片 + 越界误报

**现象**：`v1-engineimpl` 是版本 `v1` 的第二片（第一片 `v1-rtcpprocessor`
已合入 `version/v1`）。运行后切片被退回 `frozen`，报「写集越界」：

```json
{"kind":"write-outside-write-set",
 "violations":["src/engine/src/engine_rtcp_xr.cpp",
               "src/engine/src/rtcp_processor.hpp",
               "tests/acceptance/v1-rtcpprocessor/acceptance.test.cjs"]}
```

**这三条「越界」没有一条是 agent 写的** —— 它们全是**上一片**的产物。

**根因（两层）**：

| 层 | 问题 |
|---|---|
| 基点 | `zelto run <id>`（单片路径）**不解析切片归属**，直接拿主干 HEAD（`489de212`）当基点 —— agent 看不到 `rtcp_processor.hpp` |
| 审计 | `auditWorktreeWrites` 算的是 `baseCommit..HEAD` 的全部文件 —— 分支上的**历史提交**（上一片的）被算成本片的越界 |

agent 被放在一个「信息不完整的世界」里：规格要求它接线一个**不存在的协作者**，
它唯一能做的就是**造一个** —— 于是重写了 `rtcp_processor.cpp`（716 行）。

1. `resolveSliceBaseCommit`：基点解析改为
   `override → pinned → 归属版本分支 tip → 主干 HEAD`
2. `auditWorktreeWrites`：按 `Refs-Slice:` trailer 过滤提交归属，
   只把**本片自己产出的提交**算进审计范围

agent 正常看到 `rtcp_processor.hpp`，只改写集内 5 个文件，
门禁②一次通过，审计零越界。详见 §六。

> **教训**：同一个概念（版本切片基点）在**两条路径**上实现
> （版本流水线 vs 单片路径），迟早有一路径漏掉。
> ADR-056 §3.3 早就把 `baseCommitOverride` 做出来了，
> 但只接在版本流水线上。代价是 50 分钟 agent 运行 + 一次写入白工
> + 一个**误导性的「越界」结论**。
>
> 另一条教训：**「守卫正确地拦住了」不等于「系统是对的」。**
> 写集守卫生效了（agent 想改 `rtcp_processor.hpp` 被当场拦下），
> 看起来是「C9 有效」—— 但它拦住的其实是一个
> **被基点错误逼出来的合理请求**。

### D-29（低）`zelto set --value ""` 报 MISSING_ARGS → 字段永远清不掉

**现象**：要清掉 `v1-engineimpl` 的钉死基点（`baseCommit`）以让它重新解析，
执行：

```
$ zelto set v1-engineimpl --field baseCommit --value ""
{"error":{"code":"MISSING_ARGS","message":"Both --field and --value require a value"}}
```

**根因**：`src/cli/commands/slice-detail.ts` 用 `!rawValue` 判定「值缺失」，
把**空串**和 `undefined` 混为一谈。结果是 `baseCommit` / `traceWaiver`
这类字段**永远清不掉**，只能手改切片 JSON。

**已修**（`3f2febc`）：判定改为「值整个缺失才报错」，空串是合法值。
补 2 条验收测试（能清空 `baseCommit`；完全不给 `--value` 仍报错）。

> **教训**：字段要能「置空」是基本能力。一个只能写不能清的配置接口，
> 人最后一定会绕过它去手改 JSON —— 绕过的那一刻，追溯链就断了。

### 7.1 D-30（新发现，严重）：`policy edit` / `remove` 静默抹掉整个 `arch:` 段

写 `arch` 编辑器时顺手做了一次现状验证，发现：

```console
$ cat policy/policy.yaml
rules:
  - id: keep-me
    ...
arch:
  - kind: cycle
    action: ask
    basis: "ADR-025"

$ zelto policy remove keep-me
✓ Rule "keep-me" removed.

$ cat policy/policy.yaml
rules:
```

**`arch:` 段整个消失了。**

**根因**：`writePolicyYaml(filePath, rules, headerComment)` 的签名里
**没有 `arch` 参数**，而 `serializeRulesToYaml(rules, header, arch)` **有**。
两者不一致 → 所有走 `writePolicyYaml` 的路径（`policy edit` / `policy remove`）
丢掉整个 `arch:` 段。

`policy add` 走另一条路径（自己做字符串插入），所以它**侥幸没丢**。

**为什么这是「严重」**： `arch:` 段是**架构护栏的判定依据**。
人明确写下的 `action: ask`（ADR-025 承认的那两条已知环）会无声消失 ——
**护栏的「已知例外」被一个跟护栏毫无关系的命令静默抹掉**。

**修复不只是补一个参数**。修的时候发现了第二层问题：
即便补上 `arch` 参数，`policy edit` 仍然会抹掉：

- 段落之间的**注释块**（人写下的「为什么」—— nimrtc-zelto 的
  `arch:` 上面有 10 行注释解释 ADR-025 承认的两条环）
- `anchors:` 段（已废弃但仍认，ADR-040 §3.3）
- 解析器**不认识的字段**（真实项目里的 `reason:`）

**所以改用文本级分段编辑**（新增 `core/policy/section-editor.ts`）：
只动目标那一段，其余部分**逐字节保留**。整条重建改成**字段级替换**。

> **教训**：修一个功能时顺手验证现状 —— 成本最低的缺陷发现方式，
> 因为你要动那些文件 anyway。这个 D-30 已经存在了多久、
> 影响过谁，都不会有人知道。

### 7.2 ADR-068：`zelto policy arch` + `validate --update`

```
zelto policy arch list [--json]
zelto policy arch add <kind> --action <action> --basis <basis> [--guidance <text>]
zelto policy arch edit <kind> [--action <action>] [--basis <basis>] [--guidance <text>]
zelto policy arch remove <kind> [--json]
```

**为什么是独立的 `arch` 子命令组**，而不是扩到 `policy add/edit`：

`rules:` 段的标识是**任意的 `id`**（`allow-src-ts`），
`arch:` 段的标识是**固定的 `kind`**（六类硬偏离之一）。
两者标识空间完全不同 —— 塞进同一个命令，就得在参数层面猜
「`<rule-id>` 还是 `<kind>`」。分成两个子命令组，每个命令的参数空间是单一的。

**一体化入口**（用户明确选的）：

```
zelto policy validate              # 报失配，退出码仍为 0（判与报分开）
zelto policy validate --update     # 报失配 → 当场重锚 → 退出码 0
```

**为什么 `validate` 的退出码口径不变**（没有升级成 error）：

| | 升级成 error | 一体化入口 |
|---|---|---|
| 解决 | 「CI 门禁看不见失配」 | 「人改完策略不知道还要跑什么」 |
| 代价 | 接管既有项目每次都要先改锚（仪式） | 门禁仍然看不见失配 |

**用户遇到的是后者** —— 「改完不知道还要跑什么」每次都遇到，
「CI 看不见失配」偶尔遇到。而代价那一栏正好反过来。

**策略本身非法时不重锚** —— 给一个语法都过不了的策略改锚，
等于让「锚点一致」盖住「策略是坏的」。

**改 `arch:` 段不自动改锚**（改锚是人的决定，C5），
但命令输出**必须告诉人下一步跑什么**：

```
✓ arch 规则 "cycle" 已更新。

⚠ 策略锚点已失配 （策略文件变了，锚点没跟上）
  跑 zelto policy validate --update 重锚。
```

### 7.5 ADR-069：Go / Rust 依赖解析

`arch check` 之前只验证 TS/JS / Python / C/C++。现在补上 Go 与 Rust。

| 语言 | 依赖表达 | 关键判据 |
|---|---|---|
| Go | `import "..."` / `import ( ... )` | 以 `go.mod` 的 module path 开头 → 项目内部 |
| Rust | `use ...;` / `extern crate ...;` | `crate::` / `self::` / `super::` → 项目内部 |

**Go 的两个易错点**：

- **别名不是路径的一部分** —— `import alias "x/y"` 的依赖是 `x/y`
- **`//go:build` 是文件级约束** —— 覆盖整个文件的所有 import

**Rust 的三个易错点**：

- **`mod` 声明不产生依赖边** —— 它是「声明」不是「引用」
  （`mod submodule;` 指的是同目录的 `submodule.rs`，
  那是「这个文件属于那个模块」，不是「这个模块依赖那个模块」）
- **嵌套花括号要展开** —— `use crate::{a, b::c};` 是两条依赖
- **`#[cfg(...)]` 只影响紧跟的那一个 item**

**约定法的取舍**（同 ADR-062 §7）：

- Go 的 `require` / `replace` 语义复杂，**只读 `go.mod` 的 module 一行**
- Rust 的 workspace / `#[path]` / `super::` 层级解析，**判不准时宁可漏**

后果都是**漏边**（不是假边）—— 漏边让人去补声明，假边让人去改对的代码。

**顺带修掉两处「锁旧事实」的测试断言**：它们锁的是
「Go/Rust 读不懂」这个在 ADR-069 之前为真的事实，不是永远成立的不变量。
「有代码但验不了」的代表改成了 **Java / Kotlin**（那块盲区还没补）。

### 9.1 现象

复验脚本在 PowerShell 里用 `Set-Content -Encoding UTF8` 造 `policy.yaml`
—— **Windows PowerShell 5.1 的 `UTF8` 就是「带 BOM 的 UTF-8」**。

```console
$ zelto policy edit other --action deny
✓ Rule "other" updated.
  action: deny

$ cat policy/policy.yaml
  - id: other
    action: allow      # ← 没变！
```

第一反应是「我的测试文件有问题」。把文件换成无 BOM 后一切正常。

**但那不是测试问题 —— 那是真缺陷。**

### 9.2 根因

ADR-068 引入的 `core/policy/section-editor.ts` 用**长度相等**判定段标题：

```ts
if (lines[i].trim() === header && lines[i].length === header.length) {
```

JS 的 `trim()` 会把 BOM（U+FEFF）当空白去掉（它属于 WhiteSpace），
所以 `trim() === 'rules:'` **成立**；但 `lines[i].length` 比标题多 1，
长度判据**不成立** → **整段找不到**。

**同一个字符，两个判据给出相反的答案。**

### 9.3 为什么这比 D-30 更隐蔽

| | D-30 | D-31 |
|---|---|---|
| 现象 | 抹掉了不该抹的（`arch:` 段） | **什么都没做** |
| 命令表现 | `✓ Rule removed` | `✓ Rule removed` |
| 文件 | `arch:` 段消失了 | **一个字节没变** |
| 人怎么发现 | 看文件，发现护栏没了 | 看 `validate` 说「锚点失配」，而失配明明没发生过 |

D-31 的失败方式**没有任何异常信号**：命令成功、退出码 0、
提示信息正确。只有去看文件才发现。

**它是 D-30 那一族缺陷的极端形态**：工具报告成功、实际什么都没做。

### 9.4 修法（ADR-070）

**两处**：

1. **判据换掉** —— 「去 BOM 后的整行 == 标题」：

   ```ts
   function isSectionHeaderLine(line: string, header: string): boolean {
     const stripped = line.replace(/^\uFEFF/, '').replace(/\s+$/, '');
     return stripped === header;
   }
   ```

   「整行相等」天然排除缩进标题（不需要长度判据），
   「去 BOM」修掉 BOM —— 比原判据**更严**，不是更松。

2. **加结构性防线** —— 承认「两套解析器判据可能分叉」这件事本身：

   ```ts
   if (!hasSection(yaml, 'rules')) {
     return { success: false, message: 'Cannot locate the "rules:" section ...' };
   }
   ```

   覆盖 `policy remove` / `policy edit` / `policy arch edit` / `policy arch remove`
   四条编辑路径。段缺失 → 报错，**绝不报告成功**。

   防线放在 handler 层而不是 core 层：`appendToSection` 的
   「段不存在就创建」是**新增**路径的正常行为，不是错误 ——
   「这个命令要求段必须存在」是**命令语义**层的事。

3. **BOM 保留不抹** —— 工具没资格改文件的编码标记；
   仓库既有惯例（`core/design/store.ts`、`core/version/branch.ts`）
   也是读时容错、写时不动。

### 9.5 端到端复验

带 BOM 的 `policy.yaml`，四条编辑命令全部真正生效：

```console
$ zelto policy arch list
Arch Guard Rules:
  ? [cycle] ask   ADR-025

$ zelto policy arch edit cycle --action deny
✓ arch 规则 "cycle" 已更新。

$ zelto policy edit keep-me --action deny
✓ Rule "keep-me" updated.

$ zelto policy remove keep-me
✓ Rule "keep-me" removed.

$ cat policy/policy.yaml
rules:

arch:
  - kind: cycle
    action: deny        # ← 真改了
    basis: "ADR-025"
```

### 9.6 回归测试的写法 —— 一条教训

D-31 这一组的测试断言全部落在**副作用**上，不是**返回值**上：

```ts
it('policy remove 真的删掉了规则（不是只报成功）', async () => {
  const { code } = await runCommand('policy', 'remove', 'keep-me');
  assert.equal(code, 0);
  assert.ok(!readPolicy().includes('id: keep-me'), 'remove 报告成功但规则还在');
});
```

> **「命令成功」不等于「事情做成了」。**
> 如果断言只写 `assert.equal(code, 0)`，D-31 这个缺陷**根本测不出来** ——
> 它返回的正是 0。
>
> 这条对写测试的人是硬要求：**断言必须落在副作用上。**

回归：`npm test` → **2007/2007 通过**；`npx biome check` → 干净。

## 十、第五轮：跑完两个冻结切片 —— 暴露「合并路径」的两个缺陷

**日期**：2026-11-16（接第四轮之后）
**目标**：把 `nimrtc-zelto` 里两个已冻结的切片（`v1-fix-arch-guard-cycle`、
`v1-fix-plugin-test-placement`）真正跑完并合入，做一次端到端钻。
**用户决策**：C5 保护域规则**保留** —— 人提交 `policy/**` 允许，agent 提交不允许。

### 10.1 第一处硬墙：保护域挡在 agent 前面

`v1-fix-arch-guard-cycle` 要改 `policy/policy.yaml`（架构护栏本身）。
`policy/**` 在 C5 保护域里，所以：

- **agent 路走不通** —— 门禁①（`zelto check`）会拦下越界写。
- **人路走得通** —— pre-commit hook 按发起人身份判（D-24 已修）。

于是这个切片**只能由人执行**。这不是缺陷，是设计：`policy/**` 的变更
本来就不该由 agent 提。

> **但这暴露了一个真实的流程事实**：切片流程假设「产物在 agent 的 worktree 里，
> 由 zelto 合并」。产物由人直接提交到 `main` 时，那条假设不成立 ——
> `slice/<id>` 分支根本不存在。

### 10.2 D-32（严重）：产物已由人提交 → `zelto merge` 直接拒绝

**现象**：切片已签字（`zelto sign --approve` 通过），执行 `zelto merge`：

```
❌ 以下切片没有对应的分支，无法合并：
   - v1-fix-arch-guard-cycle
```

而**产物就在 `main` 上**。合并此刻本该是**空操作** ——
产物已经在目标分支里了，没什么可搬的。

**为什么这是严重缺陷**：它逼着人去手工改 `.zelto/` 里的状态文件。
**追溯链就断在这里** —— 事件流里没有这次合并，人也无从知道「它合过了」。

**修法**（ADR-071）：判据从「分支存不存在」改成「**产物是否已在目标 ref 上**」。

```ts
const { missing } = verifyArtifactsInRef(writes, targetRef, repoRoot);
if (missing.length === 0) → 空操作合并
else → 仍然拒绝（并点名缺哪些产物）
```

**为什么不放宽成「分支不存在就跳过」**：D-11 刚把「假成功」当严重缺陷修过一轮。
「分支不存在 + 产物也不在目标分支」= 什么都没做，
放行就是**假成功**。所以判据必须是**产物核实**，不是**分支存在性**。

空操作合并**照样写事件**（`mode: 'noop'` + 核实的产物路径）——
追溯链不因为「这次没搬东西」而断。

### 10.3 D-33（中）：清理分支的报错在撒谎

**现象**：`cleanupMergedSlices` 删分支失败时报「该分支可能有未合并的改动」。
但空操作切片**压根没有分支**，以及「合进 `version/v1` 但 HEAD 在 `main`」——
这两种情况都报同一句话。

**那句话对两种情况都不成立。** 报错不该在描述一个不存在的原因。

**修法**：区分三种情形 —— 分支不存在（跳过，不报警）/
分支没合入目标（报「未合并」）/ 其它 git 错误（报原始错误）。

### 10.4 一个副产物：「空操作切片被无限次列为待合并」

ADR-071 落地后立刻暴露：空操作切片的产物**已经在**目标分支上，
所以「产物在目标分支」这个判据**永远成立** —— 每次 `zelto merge`
都会把它重新列一遍。人会以为它一直没合过。

**修法**：判据加一条 —— 事件流里已有 `mode: 'noop'` 的 `merge.completed` 就不再列。
**只读事件流，不做新判定**（C4：事件是追溯的唯一证据载体）。

### 10.5 验收测试的 `test.todo` 骨架被门禁②挡下

两个切片的验收测试都是 `test.todo` 骨架 —— 门禁②按「`pass 0 / todo N`」拒绝。
**这是对的**：一个只有骨架的验收测试，验不了任何东西。

补成真实断言后：

- `v1-fix-arch-guard-cycle`：**5 条**。含一条在临时目录里造迷你工程、
  埋一个**未声明的** `#include <nimrtc/a.hpp>`，验 `arch check --strict`
  真的以退出码 1 拦下。
- `v1-fix-plugin-test-placement`：**7 条**。含真实跑一次 CTest，
  验 3 个 target 真的被 CTest 发现并执行。

**顺带发现一处规格自相矛盾**：`v1-fix-plugin-test-placement` 的判据 2 说
「plugin 目录下不许出现 `video_frame` 引用」，而「不做范围」里又说
「不许动 plugin 公开头文件」（那些头文件合法地 re-export `video_frame` 类型）。
把断言收敛到 `src/plugins/tests/` 目录，并在测试注释里记下这个规格缺陷。

### 10.6 回归测试的连带修正

ADR-071 改的是**判据**，两条既有测试的断言随之要改 ——
它们原本断言「缺分支 = 失败」，现在要区分两种缺分支：

| 情形 | 处置 |
|---|---|
| 缺分支 + 产物已在目标分支 | 空操作合并，成功 |
| 缺分支 + 产物不在目标分支 | 拒绝，退出码非 0，点名缺哪些产物 |

`tests/merge-false-success.test.ts` 的切片写集原本正好是 `src/feature.ts`
（init 提交里就有）—— 于是它从「拒绝」变成了「空操作成功」。
**改成一条目标分支上不存在的路径**，让断言重新对准「真的合不了」这一情形。

### 10.7 回归

`npm test` → **2014/2014 通过**；`npm run lint` → 干净；编码检查 → 干净。

### 10.8 本轮的方法论观察

**「产物在哪」比「分支叫什么」更接近事实。**
D-32 的修法之所以自然，是因为「产物已经在目标分支上了」本来就是事实，
而「`slice/<id>` 分支存在」只是**实现手段**。
拿实现手段当判据，就会在实现手段不成立时卡住。

**D-32 和 D-11 是同一个家族的两面。**
D-11 修的是「什么都没做却报成功」，D-32 修的是「做过了却报失败」。
两个都要修 —— 只修一个，工具就在另一个方向上骗人。

### 11.2 硬伤一：ADR-010 §9 的 CSRF 缓解措施把因果说反了

ADR-010 §9 原文：

| 风险 | 缓解措施 |
|---|---|
| CSRF | 无 session/cookie，fetch 调用无副作用问题 |

**「无 session/cookie」不是缓解措施 —— 它恰恰是 CSRF 成立的前提。**

CSRF 的机制是浏览器对目标站自动附带凭据。目标站**不要求**任何浏览器猜不到的凭据时，
**任何第三方网页**都能让访问者的浏览器向 `127.0.0.1:4321` 发请求，
而浏览器认为这是同源请求（Same-Origin-Policy 只拦**读**响应，不拦**发**请求）。

按 ADR-010 §5.3 照做的话：

```html
<!-- 攻击者网页上的任意一行 -->
<script>fetch('http://127.0.0.1:4321/api/sign-requests/<某片>/approve',{method:'POST'})</script>
```

访问者一打开那个网页，**这一片就被签了字**。而签字是 zelto 里唯一「人行使的权力」，
签完字 `zelto merge` 就能合入主干。

> **只绑 `127.0.0.1` 防不住这个。** 绑定面防的是**网络可达性**，
> 攻击者不需要能连你的机器 —— 他只需要让**你的浏览器**替他连。

**修法（ADR-072 §3）**：写操作双因子 ——
① 启动时 `randomBytes(32)` 生成的会话 token，注入 HTML，前端放 `X-Zelto-Token` 头；
② `Origin` 头必须为空或等于本服务。
第三方网页读不到本页内容（SOP 拦读）→ 拿不到 token；
且本服务**从不发** `Access-Control-Allow-Origin` → 跨源脚本连 token 都读不出来。

### 11.3 硬伤二：写操作范围撞「一键批准」禁区

ADR-010 §5.4 的签名审批页长这样：

```
┌─ slice-001 ────────────────────────────────┐
│  [✓ 批准]  [✗ 拒绝]                          │
└──────────────────────────────────────────────┘
```

**在浏览器里这就是一键批准** —— AGENTS.md 负向清单明列。

**收窄（ADR-072 §4）**：Web UI 只保留**签字**这一个写操作，其余全砍：

| 被砍的端点 | 理由 |
|---|---|
| `run` | 会启动 agent 进程 —— HTTP 请求不该有副作用地启动另一个进程 |
| `admit` / `gate` | 触发门禁 = 发起一次执行；CLI 侧已有完整实现，Web 侧再做一份会分叉判定 |
| `freeze` / `clarify` | 改切片状态；状态变更必须走同一条代码路径 |
| `abandon` / `resume` | 状态机变更，唯一判据是 `transitionSlice` |
| 创建切片 | 要过 D-4「规格与写集一致性」判定 |
| `approve` / `reject` | **保留** —— 但见下节 |

### 11.4 「看完事实再签」：怎么让它不是一键批准

签字要在浏览器里做（否则驾驶舱只是好看的看板），但不能是「点一下就签」。

**双端防线**：

- **前端**：签字页先渲染完整的四项确认项（追溯链 / 验收 / 写集 / 产物），
  批准按钮初始 `disabled`。
- **服务端**：`POST /api/sign-requests/:id/approve` **自己重新算一遍**四项判定，
  四项全绿才签；任一不过 → `409` + 回传是哪一项不过。
  **前端传来的判定结果一概不信** —— 只当「人确认过了」的凭据。

> 只有前端那道是自欺欺人（改个 DOM 就能绕过）；
> 只有服务端那道是「暗室里批准」。两者合起来才是「人真的看过了」。

测试里专门有一条：**前端声称四项全过、服务端重算发现不过 → 必须被拒**。

### 11.5 一个位置错误：事实收集本该在 core/，却在 CLI 层

ADR-070 把签字复查的事实收集放在 `src/cli/sign-review/collect-facts.ts`。
它跑 git、读 `.zelto` —— 这类活儿 core/ 里已有先例

当时的理由是「core/ 不跑 git」，但那条约定**本来就不存在** ——
是 ADR-070 选位置的偶然。结果就是 Web UI **没法复用同一份事实**。

**修法（ADR-072 §5.1）**：下沉到 `core/sign-review/collect.ts`，依赖注入
（`readSlice` / `readEvents` / `worktreePath` / `repoRoot`），
CLI 与 Web 各装配各的依赖，共用一份实现。

### 11.9 本轮的方法论观察

**一份过时的提案比没有提案更危险。**
ADR-010 写得很详细、看着很完备 —— 但它是在 2026-10-30 的代码上写的。
直接照做，会同时踩三个坑：端点表过时、判定分叉、CSRF 洞。
**提案的价值在实现时会被时间稀释** —— 落地时必须逐条核对。

**「无凭据」不是安全措施，「无凭据」是最危险的状态。**
ADR-010 那句「无 session/cookie」听起来像安全设计，实际是**把门拆了还挂了块
「此处无门」的牌子**。CSRF 的判据永远是：**第三方能不能让你的浏览器替你做事？**

**收窄范围不是偷工减料。**
ADR-010 列了 20 多个端点。真正实现下来，只有 8 个 ——
而砍掉的那 12 个**不是「没时间做」，是「不该在浏览器里做」**：
它们要么会分叉判定，要么会启动进程，要么是状态机迁移。
写清楚为什么不做的理由，比多写 12 个端点更有价值。

**「看过了」这件事必须由服务端验证。**
前端的 `disabled` 属性挡不住任何人。但服务端重算一遍判定，
至少能保证「签的时候，这四项确实是绿的」——
人有没有真的读，那是流程问题，工具只能保证事实没被跳过。

### 11.10 落地后的 UI 自查：三个实测出来的缺陷

落地不等于对。第七轮专门回头查 UI —— 起服务、开浏览器、逐个视图点、
用探针模拟人签字。**查出三个真缺陷**，都是「看代码看不出来、点几下才发现」的那类。

#### 缺陷一：切片详情页被 5 秒轮询刷掉

**现象**：从总览点进切片详情，**4 秒后页面自动跳回总览**。人正在看的东西被抢走。

**根因**：轮询守卫写成了

```js
if (currentView !== 'overview' && main.querySelector('.back')) return;
```

它想表达「在详情页就别轮询」，但**从总览点进详情时 `currentView` 仍然是 `'overview'`**
（`showSliceDetail` 不改它）。第一条件为 false → 不 return → 轮询把详情页整个换掉。

**修法**：详情页状态用**独立变量** `inDetail` 跟踪，守卫只看它。
「当前在哪个视图」和「当前是否在看某片的详情」是**两件事** ——
前者是导航状态，后者是阅读状态，混在一个变量里就会这样判错。

#### 缺陷二：签字成功了，但人什么都看不到

**现象**：点「确认签字」→ 服务端确实签了（`sign.approved` 与 `slice.state.changed` 事件都写了），
但页面**什么提示都没有**。人以为失败了。

**根因**：`doApprove` 里先 `appendChild(提示)` 再 `render('signs')`，
而 `render()` 会 `clear(main)` —— **提示被自己刚调用的视图切换清掉了**。

**修法**：提示走**独立横幅容器**（`#banner`，在主区域外面），
且必须在视图切换**之后**追加。横幅在主区域外 → 轮询碰不到它 → 提示活得过一轮。

> **第一次修复只做了一半**：改用横幅后仍然只剩一条 ——
> 因为 `showBanner` 每次都 `clear(banner)`，第二条把第一条冲掉了。
> 一次签字要显示两条（已签字 + 签字不等于合并），所以横幅必须**追加**而不是覆盖。

#### 缺陷三：轮询时页面每 5 秒塌陷成「加载中…」再重建

**现象**：MutationObserver 抓到每 5 秒一次「加载中」闪现。表格行会跳、滚动位置会丢。

**根因**：轮询复用了 `render()`，而 `render()` 是「先清空、显示加载中、加载完再填」。
用于首次导航没问题，用于**轮询刷新**就是每 5 秒闪一次。

**修法**：轮询走 `refreshSilently()` —— 先渲染到**离屏容器**，成功了再整体替换；
失败就保留原内容（一次网络抖动不该把屏幕清空）。

> **这里踩到了一个更深的坑**：第一版修法把 `main` 从 `const` 改成可变的 `let`，
> 轮询时临时把它指向离屏容器。结果**缺陷二反而更严重了** ——
> 视图函数往哪个容器渲染取决于时序，签字提示写进了已被丢弃的容器。
>
> 修法：视图函数改成**显式接收 `target` 参数**（`viewOverview(target)`），
> `main` 保持 `const`。**可变的全局容器 = 渲染竞态**，这个教训值得记住。

#### 三个缺陷的共同点

**它们都发生在「异步完成之后」这个边界上。**
页面渲染、视图切换、轮询刷新、签字回执 —— 全都是「先发请求，拿到结果再改屏幕」。
而**改屏幕**这一步里，「什么时候改」「改到哪」「改完谁说了算」三件事全都能错。

**静态检查抓不到这类缺陷。** 三个都是「读代码觉得没问题」——
直到真的开浏览器、真的点、真的等 5 秒。

#### 回归测试

三个缺陷都补了**前端回归测试**（对发出去的脚本做断言）：
轮询守卫必须用 `inDetail`、视图函数必须接收 `target`、`main` 必须是 `const`、
`refreshSilently` 里 `clear(main)` 必须在 catch 的 return 之后、
`showBanner` 必须是追加、脚本里**一处 `innerHTML` 都不许有**。

回归：**2036/2036 全绿**（比上一轮多 6 条 Web 测试）。

### 11.12 D-34：事件流读不懂带 BOM 的首行 —— 证据凭空消失

**发现经过**：写 Web 驾驶舱的 UI 自查时，用 PowerShell 造探针事件文件，
签字按钮**永远解锁不了**。查下来是 `gate.result` 事件读不到 ——
「验收真跑过」判据因此判不过。

**根因**：`EventStream.read()` 逐行 `JSON.parse`，但**第一行带 BOM**。
`JSON.parse` 不接受带 BOM 的字符串（BOM 不是 JSON 语法的一部分），
于是整行解析失败，被 `catch` 掉、返回 `null`、被 `filter` 掉。

**为什么这是严重缺陷，不是一个小 bug**：

C4 说事件流是「追溯的**唯一证据载体**」。一行读不懂就被静默丢掉，
等于**证据凭空消失** —— 而且**没有任何报错**。人看到的是「这条切片没跑过验收」，
真相是「验收跑过了，但证据没读出来」。**工具把「没有证据」和「证据是坏的」混为一谈。**

顺带查出同族问题：带 BOM 的事件文件还会让 `restoreSeq()` 读不出 `runSeq`，
重启后序号从头开始，**与既有事件撞号** —— 追溯链直接乱掉。

**修法**：读时容错、写时不动（仓库既有惯例，8 处都是这个写法）。
抽出 `stripBom()`，覆盖 `read()` 与 `restoreSeq()` 两处；
同样处理 `slice/store.ts`、`gate/sign.ts`、`sched/reservation.ts`、
`question/store.ts`、`contracts/registry.ts` 五个读点。

> **注意 `trim()` 救不了这个场景**：U+FEFF 属于 JS 的 WhiteSpace，
> `trim()` 确实会去掉它，但 `JSON.parse` 要求的是**整个字符串**不带 BOM ——
> 必须显式剥，不能指望 trim 顺手带过。

**修法二（同样重要）：不主动抹，也不主动加。**
工具没资格改文件的编码标记 —— BOM 是外部工具留下的痕迹，
抹掉它就是在**篡改证据**。所以只读时容错，写出去的文件仍然不带 BOM
（测试里也断言了这一点）。

**回归测试**：新增 `tests/bom-tolerance.test.ts`（7 条），覆盖事件流首行/中间行、
重启序号不撞号、写时不带 BOM，以及五个状态文件的同族容错。
另做对照验证：修复前读到 **0** 条事件（证据丢了），修复后读到 **1** 条。

回归：**2043/2043 全绿**。

### 11.13 本轮（第七轮）的方法论观察
**「跑通了」和「是对的」是两件事。**
第一轮实现完，2030 条测试全绿、端到端点得动 —— 但那只是在验证
「它能跑」。**验证它「对不对」需要另一套动作**：开浏览器、逐个视图点、
用探针造出真实场景、等它自己跑几个轮询周期。

**测试全绿 ≠ UI 没问题。**
三个缺陷里没有一个是后端逻辑错 —— 全是前端时序与状态归属。
后端测试再全也照不到它们。**前端的缺陷只能靠真的驱动前端来发现。**

**缺陷二暴露了一个更深的问题：我第一版的修法引入了竞态。**
把 `main` 改成可变全局来「支持离屏渲染」—— 表面修好了，
实际制造了一个新的、更隐蔽的问题（视图函数往哪渲染取决于时序）。
**修 bug 时引入的新机制，本身要经得起同样的检验。**
