## 一、这一轮与上一轮的差别

上一轮的目标是「**从空白需求到 `version ship`**」—— 验证 zelto 的骨架能不能撑起
一次完整交付。这一轮的目标不同：**验证 zelto 在一个「已经在维护中的真实项目」
上能不能做增量的、可并行的开发**。

具体差别：

| 维度 | 第一轮 | 第二轮 |
|---|---|---|
| 起点 | 空白（`reset --hard github/main`） | 已有 20+ 个切片、已有版本分支 |
| 切片来源 | LLM 生成（`zelto plan`） | **人工撰写规格**（两片都手写） |
| 并发性 | 单片串行 | **两片写集重叠 → 调度器降级为串行** |
| 靶子代码 | 新建 | 改动**既有**生产代码（`engine_media.cpp` / `engine_rtcp.cpp` / `engine_rtcp_xr.cpp`） |

**规格人写**这一条是本轮最重要的变化。第一轮的规格是 LLM 起草的，
问题藏在措辞里；这一轮手写规格，能更精确地测「规格与写集的一致性」
（ADR-059 §3 的判据到底准不准）。

## 三、本轮发现的 zelto 缺陷目录

### D-24（中）人改保护域也被 hook 拦住

**现象**：`policy/policy.yaml` 改了之后 `git commit` 被 pre-commit hook 拦下：

```
policy/** 是保护域 —— 策略的修改必须由人直接完成，
并通过 `zelto policy lock --update` 重新锚定。
```

**为什么这是缺陷而不是正确行为**：C5 说「保护域硬编码、不可被任何策略规则覆盖」
—— 保护域防的是 **agent**。但 hook 不区分**谁**在提交：

- agent 提交 → 必须拦（C5 的本意）
- 人提交 → 必须放行（否则 C5 的配套流程 `policy lock --update` 走不通）

现状是两者都拦。演练中只能 `--no-verify` 绕过。

**修复方向**（待实施）：hook 判据要看**是不是 agent 在提交** ——
zelto 在 agent 运行时往环境里注入标记（类似 `ZELTO_SLICE_ID`），
hook 据此区分。没有标记 → 是人 → 放行。

> 顺带暴露：**演练记录里写「用 `--no-verify` 绕过」是权宜之计**，
> 它让「策略被改过」这件事在 git 历史里没有钩子痕迹。

### D-25（严重）超时的重试在适配器内部「从头再来」，短路了 ADR-055 的续跑

**现象**：`v1-rtcpprocessor` 的 agent 跑了 30 分钟被超时杀掉，然后：

| 会话 | agent 会话 id | 说明 |
|---|---|---|
| `claude-agent-v1-rtcpprocessor-1794796572264` | `bd4e6295-...` | 第一次，`status=timeout` |
| `claude-agent-v1-rtcpprocessor-1794798375472-retry-1` | `d6944875-...` | **新的 agent 会话 id** |

**agent 会话 id 变了** → 不是续跑，是**从头再跑**：agent 的上下文被清零，
它已经摸清的东西（改到一半的代码、跑了一半的测试、读过的一堆源码）全部作废。

**根因**：`src/adapters/claude-agent/index.ts` 的 `waitForExit` 里，
非零退出 → 适配器**内部** `startWithRetry` → 用**原始 bundle** +
**新的 agentSessionId** 重启。这条路径把 CLI 层的
`resumeForRetry`（真正的 ADR-055 续跑）**完全短路**了 ——
适配器内部已经把重试链跑完（实测跑到 `-retry-2`），CLI 层根本没机会执行。

**关键的隐蔽点：退出码分不出超时。**

ADR-055 决策 B 假设「超时时 exitCode 是 `null`」（POSIX 上确实如此）。
但 **Windows 上 `taskkill` 杀掉进程树后，shell 包装返回的是非零码（1）** ——
实测确认。所以 `waitForExit` 里的 `code !== null` 判断在 Windows 上
**永远成立**，超时与「agent 报错退出」在退出码上完全一样。

唯一可靠的超时信号是适配器**自己**记的 `status === 'timeout'`
（`handleTimeout` 在杀进程树之前就写好了，ADR-055 决策 B）。

**已修**（`c07df3f`）：

```ts
const data = loadSession(sessionId);

// 超时 → 不在这里重试。交给 CLI 层走 ADR-055 的续跑路径
// （`continueSession`）—— 见上面那段说明。
if (data?.status === 'timeout') {
  resolve(code);
  return;
}
```

**回归测试**（`tests/adr-055-timeout-kills-tree-and-continues.test.ts`，+5 条）：

1. 超时的退出码不是 0（**锁住「退出码分不出超时」这个事实**）
2. 超时后适配器**没有**起第二个 agent（会话数增量 == 1）
3. agent 报错退出（`failed`）**仍会**起内部重试（增量 == 2）
   —— **两条必须不同**，否则修复就是把「重来一遍」这个正当行为也砍了
4. 超时后 CLI 层能续同一个 agent 会话（`agentSessionId` 相同）
5. 非零退出码的状态是 `failed` 不是 `timeout`

> **教训**：ADR-055 写于 Windows 环境，却把 POSIX 的退出码语义
> （信号杀 → `null`）当成了通用事实。**跨平台的语义差异必须在 ADR 里写明，
> 或者干脆不用它做判据。**

### D-26（中）花括号简写被当成一个文件名 → 写集覆盖判据误报

**现象**：规格里写「新建 `src/engine/src/rtcp_processor.{hpp,cpp}`」，
门禁①报：

```
规格提到「src/engine/src/rtcp_processor.{hpp,cpp}」，但它不在写集里 —— agent 改不了它
```

而写集里明明有 `rtcp_processor.hpp` 和 `rtcp_processor.cpp` 两个文件。

**根因**：`src/core/spec/scope.ts` 的 `normalizeMentionedPath` 过滤了
glob 通配（`*` / `?`），但**没处理花括号**。于是
`rtcp_processor.{hpp,cpp}` 被当成**一个**具体文件名。

**闸门误报比闸门漏报更糟**：漏报让人绕过一次检查；误报让人以为
「规格有问题」，于是去改规格 —— 而规格是对的。

**已修**（`2a1f8d0`）：**展开**而不是丢弃。

```ts
function expandBraces(raw: string): string[] {
  // a{b,c}d → abd + acd
  // 不含逗号的 {x} → 原样返回（不是简写）
  // 嵌套花括号不展开
}
```

展开失败（嵌套、无逗号）的花括号串**不报** —— 报一个多半不存在的文件名
比不报更糟。

**回归测试**（`tests/write-set-coverage.test.ts`，+6 条）：展开正确性、
不残留花括号、前后缀场景、无逗号不展开、嵌套不展开。

**真实验证**：`v1-engineimpl` 的门禁①从 ❌ 变 ✅。

> **教训**：D-4 引入「规格全文路径提取」时，把「提到的路径」理解成了
> 「一个路径」。实际上规格提到的是**路径的集合**，而集合有不同的写法
> （逗号分隔、花括号、目录）。**判据要能认出集合的写法。**

### D-27（低）`--agent` 参数值拼错时，错误信息不指向正确命令

**现象**：`zelto run v1-rtcpprocessor --agent claude-code` 直接失败，
但错误信息没有说「命令不存在」或「配置里是 `npx @anthropic-ai/claude-code`」。

**性质**：**不是 zelto 的缺陷** —— 是演练时我传错了参数。
配置 `.zelto/config.yaml` 里的 `agent.command` 是 `npx @anthropic-ai/claude-code`。

**但暴露了一个真问题**：agent 命令名（`claude-code`）与真实可执行命令
（`npx @anthropic-ai/claude-code`）**长得不一样**，而工具没有在预检失败时
把「你想要的」与「实际用的」并排列出来。人只能自己去翻 `config.yaml`。

**处置**：列为改进项（预检失败时附上「当前配置的命令」），不单独开 ADR。

### D-28（严重）同版本第二片从主干 HEAD 建 worktree → agent 被迫重造上一片 + 越界误报

**现象**：`v1-engineimpl` 是版本 `v1` 的第二片（第一片 `v1-rtcpprocessor`
已合入 `version/v1`）。运行后切片被退回 `frozen`，报「写集越界」：

```json
{"kind":"write-outside-write-set",
 "violations":["src/engine/src/engine_rtcp_xr.cpp",
               "src/engine/src/rtcp_processor.hpp",
               "tests/acceptance/v1-rtcpprocessor/acceptance.test.cjs"]}
```

**这三条「越界」没有一条是 agent 写的** —— 它们全是**上一片**的产物。

**根因（两层）**：

| 层 | 问题 |
|---|---|
| 基点 | `zelto run <id>`（单片路径）**不解析切片归属**，直接拿主干 HEAD（`489de212`）当基点 —— agent 看不到 `rtcp_processor.hpp` |
| 审计 | `auditWorktreeWrites` 算的是 `baseCommit..HEAD` 的全部文件 —— 分支上的**历史提交**（上一片的）被算成本片的越界 |

agent 被放在一个「信息不完整的世界」里：规格要求它接线一个**不存在的协作者**，
它唯一能做的就是**造一个** —— 于是重写了 `rtcp_processor.cpp`（716 行）。

**已修**（`712041f`，ADR-067）：

1. `resolveSliceBaseCommit`：基点解析改为
   `override → pinned → 归属版本分支 tip → 主干 HEAD`
2. `auditWorktreeWrites`：按 `Refs-Slice:` trailer 过滤提交归属，
   只把**本片自己产出的提交**算进审计范围

**真实验证**：重跑 `v1-engineimpl`，基点 = `720d47ab`（`version/v1` tip），
agent 正常看到 `rtcp_processor.hpp`，只改写集内 5 个文件，
门禁②一次通过，审计零越界。详见 §六。

> **教训**：同一个概念（版本切片基点）在**两条路径**上实现
> （版本流水线 vs 单片路径），迟早有一路径漏掉。
> ADR-056 §3.3 早就把 `baseCommitOverride` 做出来了，
> 但只接在版本流水线上。代价是 50 分钟 agent 运行 + 一次写入白工
> + 一个**误导性的「越界」结论**。
>
> 另一条教训：**「守卫正确地拦住了」不等于「系统是对的」。**
> 写集守卫生效了（agent 想改 `rtcp_processor.hpp` 被当场拦下），
> 看起来是「C9 有效」—— 但它拦住的其实是一个
> **被基点错误逼出来的合理请求**。

### D-29（低）`zelto set --value ""` 报 MISSING_ARGS → 字段永远清不掉

**现象**：要清掉 `v1-engineimpl` 的钉死基点（`baseCommit`）以让它重新解析，
执行：

```
$ zelto set v1-engineimpl --field baseCommit --value ""
{"error":{"code":"MISSING_ARGS","message":"Both --field and --value require a value"}}
```

**根因**：`src/cli/commands/slice-detail.ts` 用 `!rawValue` 判定「值缺失」，
把**空串**和 `undefined` 混为一谈。结果是 `baseCommit` / `traceWaiver`
这类字段**永远清不掉**，只能手改切片 JSON。

**已修**（`3f2febc`）：判定改为「值整个缺失才报错」，空串是合法值。
补 2 条验收测试（能清空 `baseCommit`；完全不给 `--value` 仍报错）。

> **教训**：字段要能「置空」是基本能力。一个只能写不能清的配置接口，
> 人最后一定会绕过它去手改 JSON —— 绕过的那一刻，追溯链就断了。

## 四、本轮的方法论观察

### 4.1 调度器的写集重叠检测在真实项目上生效了

`zelto batch v1-rtcpprocessor v1-engineimpl`：

```
执行阶段：2 个
  Phase 1: v1-engineimpl （单独跑）
  Phase 2: v1-rtcpprocessor （单独跑）
  ⚠️  v1-rtcpprocessor 与 v1-engineimpl 写集重叠 —— 已降级为串行
```

两片共享 `engine_media.cpp` / `engine_rtcp.cpp` / `rtcp_processor.cpp` /
`CMakeLists.txt` 四个文件 —— **检测准确**，并正确降级为串行。

这是 ADR-024（亲和调度）在真实项目上的第一次验证。

### 4.2 「签字不自动合并」被真的执行了

```
$ zelto sign v1-rtcpprocessor --approve
zelto sign v1-rtcpprocessor -- ✅ Approved
下一步：zelto merge v1-rtcpprocessor
```

签字**只改状态**，不碰分支。合并必须显式跑 `zelto merge`（ADR-018）。

### 4.3 合并时的两条 git 报错不影响结论，但值得记一笔

```
error: the branch 'slice/v1-rtcpprocessor' is not fully merged
error: cannot delete branch 'version/v1' used by worktree at '.../version-worktrees/v1'
ℹ️  Could not delete branch "slice/v1-rtcpprocessor" (may have unmerged changes)
```

合并**实际成功了**（`version/v1` 含 merge commit `720d47ab`，
`git branch --contains slice/v1-rtcpprocessor` 同时列出两者）。

但报错信息误导：分支**已经被合并进** `version/v1` 了，git 说「not fully merged」
是因为它合并的目标是 `version/v1` 而不是当前的 `main`。
**清理失败的报错应该区分「合不上」与「没合到当前分支」。**

### 4.4 agent 的 49 分钟里有 30 分钟在「重新摸索」

第一次运行超时被杀 → 从头再跑 → 又花了 30 分钟。

**如果 D-25 的修复在位**，第二次运行会是「接着做」：
agent 记得自己改到哪、记得编译报什么错、记得哪些测试过了。

**这是 D-25 最实际的影响：一半的执行时间被浪费了。**

### 7.1 D-30（新发现，严重）：`policy edit` / `remove` 静默抹掉整个 `arch:` 段

写 `arch` 编辑器时顺手做了一次现状验证，发现：

```console
$ cat policy/policy.yaml
rules:
  - id: keep-me
    ...
arch:
  - kind: cycle
    action: ask
    basis: "ADR-025"

$ zelto policy remove keep-me
✓ Rule "keep-me" removed.

$ cat policy/policy.yaml
rules:
```

**`arch:` 段整个消失了。**

**根因**：`writePolicyYaml(filePath, rules, headerComment)` 的签名里
**没有 `arch` 参数**，而 `serializeRulesToYaml(rules, header, arch)` **有**。
两者不一致 → 所有走 `writePolicyYaml` 的路径（`policy edit` / `policy remove`）
丢掉整个 `arch:` 段。

`policy add` 走另一条路径（自己做字符串插入），所以它**侥幸没丢**。

**为什么这是「严重」**： `arch:` 段是**架构护栏的判定依据**。
人明确写下的 `action: ask`（ADR-025 承认的那两条已知环）会无声消失 ——
**护栏的「已知例外」被一个跟护栏毫无关系的命令静默抹掉**。

**修复不只是补一个参数**。修的时候发现了第二层问题：
即便补上 `arch` 参数，`policy edit` 仍然会抹掉：

- 段落之间的**注释块**（人写下的「为什么」—— nimrtc-zelto 的
  `arch:` 上面有 10 行注释解释 ADR-025 承认的两条环）
- `anchors:` 段（已废弃但仍认，ADR-040 §3.3）
- 解析器**不认识的字段**（真实项目里的 `reason:`）

**所以改用文本级分段编辑**（新增 `core/policy/section-editor.ts`）：
只动目标那一段，其余部分**逐字节保留**。整条重建改成**字段级替换**。

> **教训**：修一个功能时顺手验证现状 —— 成本最低的缺陷发现方式，
> 因为你要动那些文件 anyway。这个 D-30 已经存在了多久、
> 影响过谁，都不会有人知道。

### 7.2 ADR-068：`zelto policy arch` + `validate --update`

```
zelto policy arch list [--json]
zelto policy arch add <kind> --action <action> --basis <basis> [--guidance <text>]
zelto policy arch edit <kind> [--action <action>] [--basis <basis>] [--guidance <text>]
zelto policy arch remove <kind> [--json]
```

**为什么是独立的 `arch` 子命令组**，而不是扩到 `policy add/edit`：

`rules:` 段的标识是**任意的 `id`**（`allow-src-ts`），
`arch:` 段的标识是**固定的 `kind`**（六类硬偏离之一）。
两者标识空间完全不同 —— 塞进同一个命令，就得在参数层面猜
「`<rule-id>` 还是 `<kind>`」。分成两个子命令组，每个命令的参数空间是单一的。

**一体化入口**（用户明确选的）：

```
zelto policy validate              # 报失配，退出码仍为 0（判与报分开）
zelto policy validate --update     # 报失配 → 当场重锚 → 退出码 0
```

**为什么 `validate` 的退出码口径不变**（没有升级成 error）：

| | 升级成 error | 一体化入口 |
|---|---|---|
| 解决 | 「CI 门禁看不见失配」 | 「人改完策略不知道还要跑什么」 |
| 代价 | 接管既有项目每次都要先改锚（仪式） | 门禁仍然看不见失配 |

**用户遇到的是后者** —— 「改完不知道还要跑什么」每次都遇到，
「CI 看不见失配」偶尔遇到。而代价那一栏正好反过来。

**策略本身非法时不重锚** —— 给一个语法都过不了的策略改锚，
等于让「锚点一致」盖住「策略是坏的」。

**改 `arch:` 段不自动改锚**（改锚是人的决定，C5），
但命令输出**必须告诉人下一步跑什么**：

```
✓ arch 规则 "cycle" 已更新。

⚠ 策略锚点已失配 （策略文件变了，锚点没跟上）
  跑 zelto policy validate --update 重锚。
```

### 7.5 ADR-069：Go / Rust 依赖解析

`arch check` 之前只验证 TS/JS / Python / C/C++。现在补上 Go 与 Rust。

| 语言 | 依赖表达 | 关键判据 |
|---|---|---|
| Go | `import "..."` / `import ( ... )` | 以 `go.mod` 的 module path 开头 → 项目内部 |
| Rust | `use ...;` / `extern crate ...;` | `crate::` / `self::` / `super::` → 项目内部 |

**Go 的两个易错点**：

- **别名不是路径的一部分** —— `import alias "x/y"` 的依赖是 `x/y`
- **`//go:build` 是文件级约束** —— 覆盖整个文件的所有 import

**Rust 的三个易错点**：

- **`mod` 声明不产生依赖边** —— 它是「声明」不是「引用」
  （`mod submodule;` 指的是同目录的 `submodule.rs`，
  那是「这个文件属于那个模块」，不是「这个模块依赖那个模块」）
- **嵌套花括号要展开** —— `use crate::{a, b::c};` 是两条依赖
- **`#[cfg(...)]` 只影响紧跟的那一个 item**

**约定法的取舍**（同 ADR-062 §7）：

- Go 的 `require` / `replace` 语义复杂，**只读 `go.mod` 的 module 一行**
- Rust 的 workspace / `#[path]` / `super::` 层级解析，**判不准时宁可漏**

后果都是**漏边**（不是假边）—— 漏边让人去补声明，假边让人去改对的代码。

**顺带修掉两处「锁旧事实」的测试断言**：它们锁的是
「Go/Rust 读不懂」这个在 ADR-069 之前为真的事实，不是永远成立的不变量。
「有代码但验不了」的代表改成了 **Java / Kotlin**（那块盲区还没补）。

## 九、第四轮：D-31 —— 段标题判据被 BOM 打穿

**日期**：2026-11-16（接第三轮之后）

第三轮的实现全部落地后做端到端复验。**复验脚本自己踩出了一个新缺陷。**

### 9.1 现象

复验脚本在 PowerShell 里用 `Set-Content -Encoding UTF8` 造 `policy.yaml`
—— **Windows PowerShell 5.1 的 `UTF8` 就是「带 BOM 的 UTF-8」**。

```console
$ zelto policy edit other --action deny
✓ Rule "other" updated.
  action: deny

$ cat policy/policy.yaml
  - id: other
    action: allow      # ← 没变！
```

第一反应是「我的测试文件有问题」。把文件换成无 BOM 后一切正常。

**但那不是测试问题 —— 那是真缺陷。**

### 9.2 根因

ADR-068 引入的 `core/policy/section-editor.ts` 用**长度相等**判定段标题：

```ts
if (lines[i].trim() === header && lines[i].length === header.length) {
```

JS 的 `trim()` 会把 BOM（U+FEFF）当空白去掉（它属于 WhiteSpace），
所以 `trim() === 'rules:'` **成立**；但 `lines[i].length` 比标题多 1，
长度判据**不成立** → **整段找不到**。

**同一个字符，两个判据给出相反的答案。**

### 9.3 为什么这比 D-30 更隐蔽

| | D-30 | D-31 |
|---|---|---|
| 现象 | 抹掉了不该抹的（`arch:` 段） | **什么都没做** |
| 命令表现 | `✓ Rule removed` | `✓ Rule removed` |
| 文件 | `arch:` 段消失了 | **一个字节没变** |
| 人怎么发现 | 看文件，发现护栏没了 | 看 `validate` 说「锚点失配」，而失配明明没发生过 |

D-31 的失败方式**没有任何异常信号**：命令成功、退出码 0、
提示信息正确。只有去看文件才发现。

**它是 D-30 那一族缺陷的极端形态**：工具报告成功、实际什么都没做。

### 9.4 修法（ADR-070）

**两处**：

1. **判据换掉** —— 「去 BOM 后的整行 == 标题」：

   ```ts
   function isSectionHeaderLine(line: string, header: string): boolean {
     const stripped = line.replace(/^\uFEFF/, '').replace(/\s+$/, '');
     return stripped === header;
   }
   ```

   「整行相等」天然排除缩进标题（不需要长度判据），
   「去 BOM」修掉 BOM —— 比原判据**更严**，不是更松。

2. **加结构性防线** —— 承认「两套解析器判据可能分叉」这件事本身：

   ```ts
   if (!hasSection(yaml, 'rules')) {
     return { success: false, message: 'Cannot locate the "rules:" section ...' };
   }
   ```

   覆盖 `policy remove` / `policy edit` / `policy arch edit` / `policy arch remove`
   四条编辑路径。段缺失 → 报错，**绝不报告成功**。

   防线放在 handler 层而不是 core 层：`appendToSection` 的
   「段不存在就创建」是**新增**路径的正常行为，不是错误 ——
   「这个命令要求段必须存在」是**命令语义**层的事。

3. **BOM 保留不抹** —— 工具没资格改文件的编码标记；
   仓库既有惯例（`core/design/store.ts`、`core/version/branch.ts`）
   也是读时容错、写时不动。

### 9.5 端到端复验

带 BOM 的 `policy.yaml`，四条编辑命令全部真正生效：

```console
$ zelto policy arch list
Arch Guard Rules:
  ? [cycle] ask   ADR-025

$ zelto policy arch edit cycle --action deny
✓ arch 规则 "cycle" 已更新。

$ zelto policy edit keep-me --action deny
✓ Rule "keep-me" updated.

$ zelto policy remove keep-me
✓ Rule "keep-me" removed.

$ cat policy/policy.yaml

  - kind: cycle
    action: deny        # ← 真改了
    basis: "ADR-025"
```

### 9.6 回归测试的写法 —— 一条教训

D-31 这一组的测试断言全部落在**副作用**上，不是**返回值**上：

```ts
it('policy remove 真的删掉了规则（不是只报成功）', async () => {
  const { code } = await runCommand('policy', 'remove', 'keep-me');
  assert.equal(code, 0);
  assert.ok(!readPolicy().includes('id: keep-me'), 'remove 报告成功但规则还在');
});
```

> **「命令成功」不等于「事情做成了」。**
> 如果断言只写 `assert.equal(code, 0)`，D-31 这个缺陷**根本测不出来** ——
> 它返回的正是 0。
>
> 这条对写测试的人是硬要求：**断言必须落在副作用上。**

回归：`npm test` → **2007/2007 通过**；`npx biome check` → 干净。
