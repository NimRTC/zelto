## 三、演练中发现的 zelto 缺陷目录

### D-1（严重）脏构建产物留在 `dist/`，比 `main` 新

**现象**：`dist/` 里有 `src/cli/commands/agent-preflight.ts` 的编译产物，但
`main` 的 `src/` 里**根本没有这个文件** —— 它只存在于备份分支
`backup/dirty-20261114`。

后果：`zelto run` 直接崩在 agent 预检：

```
❌ Agent 预检未通过：agent 预检失败：Cannot read properties of undefined (reading 'trim')
   命令：undefined
```

`tsc` **不删旧产物**，所以从备份分支构建过的 `dist/` 会一直留在磁盘上。

**处置**：本次手工 `Remove-Item -Recurse -Force dist, dist-test` 后重新 `npm run build`。
**已修**：新增 `scripts/clean-dist.mjs`，`npm run build` 先清 `dist/`（不动 `dist-test/`）。

### D-2（中）`--agent` 缺值时把 `undefined` 当成「用户指定的值」

`src/cli/commands/core-slice.ts`：

```ts
const agentName = args.includes('--agent') ? args[args.indexOf('--agent') + 1] : agentCmd;
```

`--agent` 是**带值选项**（usage 写的是 `--agent <name>`）。
问题出在它是**最后一个参数**时：`args[indexOf('--agent') + 1]` 是 `undefined`，
而 `undefined` 被当成了「用户指定的值」传下去 —— 打印出 `Agent: undefined`，
`checkAgentAvailable(undefined)` 拿着 undefined 去检查。

本次没炸，是因为 `createExecutorAdapter` 对 undefined 又兜了一层
回退到 `cfg.agent.command` —— **兜底掩盖了 bug**，征兆只剩日志里的
`Agent: undefined`。

**已修**：新增 `shared.ts` 的 `optionValue` / `optionValueStrict`，
三处调用点（`run` / `run --parallel` / `start`）统一走它。

> 演练记录初稿把这个缺陷写成了「`--agent` 是布尔标志」—— **那是记录错误**。
> 真正的缺陷是「带值选项缺值时的回退缺失」。教训：缺陷描述本身也会错，
> 修的时候要回到代码确认，别信记录。

### D-3（中）提示词模板的占位符标题被当成真标题

`.zelto/requirements/<id>.md` 的 `title:` 停在占位符「需求标题」，
追溯链上全是「需求标题」。

**根因不是 `refine` 不更新标题**（它确实写了 `doc.title = result.title`），
而是**提示词模板里写的就是 `# 需求标题`**：

```
请按以下格式输出：

# 需求标题        ← 模型有时会原样照抄
```

模型照抄模板时，解析器就把「需求标题」当成了真标题。

**已修**（两条同时做）：

1. 五个提示词模板的占位符改成 `<需求标题>` / `<设计标题>` 填空槽，
   并明确写「这是占位符，请替换」
2. 新增 `llm/generators/placeholder-title.ts`，
   解析侧独立判一次占位符（历史格式、尖括号格式、中文括号格式、
   默认回退串），占位符不算标题

> 教训：提示词模板里的占位符是**内容的一部分**。模型有可能原样照抄，
> 解析侧不能信任模型填了。

### D-4（中）切片规格的「范围」与「写集」可能不一致，人工才看得出来

规格需求 6 写着「`src/engine/CMakeLists.txt` 如需登记新 `.cpp` 文件，只加一行」，
但**写集里没有这个文件**。

结果：agent 建了新 `.cpp` 却无法登记 → 链接期才炸：

```
error LNK2019: 无法解析的外部符号 "nimrtc::engine::build_rtp_packet(...)"
```

写集守卫（C9）**正确拦住了越界**（agent 想改也改不了），但代价是
「规格要说改 + 写集不允许改」这种矛盾要靠人去 spec 和 write-set 里比对才能发现。

**已修**（ADR-059 §3）：冻结准入增加一条判据 ——

1. `parseMentionedPaths` 解析规格**全文**提到的路径（不只「范围」章节）
2. `evaluateWriteSetCoverage` 判「写集是否覆盖该路径」（glob / 目录都算覆盖）
3. 有未覆盖路径 → **拒绝冻结**，逐个点名，给出两条出路

比对的是**有效写集**（`resolveWriteSet`），不是 `slice.writes` ——
写集有三级来源，只看 `slice.writes` 会误伤「写集由规格推导出来」的正常切片。
这是实现时踩到的真坑（`tests/acceptance/refreeze.test.ts` 因此红了 10 个用例）。

### D-5（低）`require list` 之外的自然语言会掉进 LLM 通路

`zelto requirement list`（`require` 的复数形式）没有对应命令，被 LLM 通路接住，
返回一段「需求似乎不够明确」的提示。人会以为自己拼错了。

**已修**：`cli/commands/index.ts` 加 `COMMAND_ALIASES` 别名表，
合并前先查表，命中直接跑真命令（`requirement`/`requirements`/`req` → `require`，
以及 `designs`/`plans`/`slices`/`versions` 等 20 余个近形词）。

> 教训：LLM 路由的成本不只是「调一次模型」—— 它给出的答案还比一条明确的
> 提示更糟，因为它让人以为工具「懂了但没找到」，而不是「命令名不对」。
> **近形命令不该动用 LLM。**

### D-6（严重）`zelto merge <id> --plan` 越过签字门

**现象**：在切片尚未签字时调用 `zelto merge v1-rtp-packetizer-core --plan`，
zelto **直接提交并合并了**，没有拦住。

**根因**：`zelto merge` 有两条路径，判据不一致：

| 路径 | 判据 |
|---|---|
| 不带 id | `collectMergeCandidates()` —— 只收 `status=approved` 的签字请求 |
| **带 id** | 直接 `store.read(id)` —— **不查签字状态** |

`--plan` 参数（ADR-056 §3.2 的归属消歧）被当成了「这条路径已验证过」的信号。

**已修**（ADR-059 §2）：合并路径**无条件**校验签字状态，
判据放在 ownership 解析与 `commitPendingWorktrees` 之前 ——
合并有副作用（提交 worktree 改动），必须在任何副作用之前拒绝。
批次里只要有一片未签字，整批拒绝。

判据用**签字记录**而不是切片状态：`revoked` 之后切片状态仍是 `completed`，
只有签字记录能区分。

### D-7（严重）版本交付被废弃切片永久阻塞

**现象**：`zelto version deliver v1` 失败：

```
❌ 验收前置条件不满足：
   - v1-adapter-layer：状态是 abandoned，还没到「已完成」
```

**死路**：废弃的切片 ID 不可复用（`zelto create` 报「Slice already exists」），
`abandoned` 是终态不可复活，而 `zelto plan` 也不能删切片 —— 三条路全堵死。

**根因**：`version deliver` 的判据要求每个切片都是 `completed`，
但同仓库的 `src/core/report/report-analyzer.ts`（版本进度统计）用的是
`completed || abandoned`。**同一件事两套判据，报表说「都了结了」，
交付说「没完」。**

**修复**：已实施 **ADR-057** —— `abandoned` 切片不阻塞交付，但必须
在交付输出里显式列出（`⚠️ 本版本有 N 个切片被放弃（不阻塞交付）`），
不静默吞掉。

```ts
if (data.state === 'abandoned') {
  abandonedSlices.push(s.id);
  continue;
}
if (data.state !== 'completed') {
  problems.push(`${s.id}：状态是 ${data.state}，还没到「已完成」`);
}
```

### D-8（中）验收骨架全 `test.todo`，门禁② fail closed

**现象**：agent 交付的 `tests/acceptance/v1-rtp-packetizer-core/acceptance.test.cjs`
里 8 条验收标准全是 `test.todo`。门禁②判 failed。

**这是正确行为**（ADR-033/034：无通过断言 ≠ 验收通过）。但暴露一个
演练流程上的事实：**门禁②拦住的是「没写测试」，不是「测试写错了」**，
两者的失败信息长得一样，人分不清。

**处置**：补齐 8 条真实断言（见下文「验收断言」）。

- 「验收文件里全是 test.todo 占位符 —— 一条断言都没写」
- 「验收断言不成立（有用例通过，也有用例失败）」
- 「验收命令执行失败（读不出测试统计）」

> 教训：「没写断言」与「断言写错了」的修法完全不同
> （前者要写测试，后者要改实现）。失败信息不该长得都一样。

### D-9（中）`arch check` 对 C++ 项目误报硬性「缺依赖」

**现象**：`zelto arch check` 输出 `❌ 架构偏离 377 项（硬性 2 项）`，
两项硬性偏离指向 `src/third_party`（googletest / msquic 源码）。

**根因**：arch 扫描器的 `detectLang` 只识别 JS/TS 与 Python。C++ 文件
全部落入「有代码但不可读」状态，而旧判据只看「目标模块有没有代码」，
不看「代码能不能被扫描」，于是把第三方模块误判为缺 import。

**后果严重性**：这是**硬性偏离**（直接拒绝），意味着任何 C++ / Go / Rust
项目的 `arch check` 基本跑不过。

**修复**：已实施 **ADR-058** —— 引入「可扫描性」判据：目标模块中
可被扫描器识别的文件占比 ≥ 0.5 才可能构成 `missing_dependency`；
否则降级为警告级 `unverifiable_dependency`。

```ts
const totalFiles = (scan.moduleFiles.get(to) ?? []).length;
const readableFiles = (scan.moduleCodeFiles.get(to) ?? []).length;
const readableRatio = totalFiles > 0 ? readableFiles / totalFiles : 1;
const scannable = readableRatio >= 0.5;

deviations.push({
  kind: targetHasCode && scannable ? 'missing_dependency' : 'unverifiable_dependency',
  from,
  to,
  detail: targetHasCode && scannable
    ? '设计声明了依赖，代码里没有对应的 import'
    : '目标模块没有源文件（契约 / 规格一类），无法用 import 验证',
});
```

### D-10（中）`policy/lock.json` 被保护域挡住提交，永久污染工作区

**现象**：`policy/lock.json` 被 hook 的 `protect-policy` 规则拦在提交之外

## 三之二、演练收尾阶段发现的两个缺陷

### D-11（严重）合并的假成功 —— 什么都没做，却报「✅ Merge complete」

**发现路径**：ADR-059 §6 的遗留项 —— 验证 `collectMergeCandidates`
（不带 id 的合并路径）与新签字门（带 id 的路径）之间有没有判据漂移。

**现象**：

```
$ zelto merge dirty-workspace-slice

Merge Plan: 1 slices
Overall Strategy: sequential_ff
Phases: 1

  Phase 0 (sequential_ff):
    - dirty-workspace-slice

Executing merge (strategy: sequential_ff)...
  ⚠️  目标工作区有未提交改动，已跳过自动合并。
     ?? .zelto/
     先提交（git commit）或暂存（git stash）这些改动，再重新跑 zelto merge。
     签字已经过了，不用重新签。

✅ Merge complete (1 phases, 0 slices)
```

**退出码 0。合并一步都没做。**

**根因**：`MergeExecutionResult.aborted` 的语义被写成「是否因冲突而中止」，
但工作区脏的守卫也用它返回 —— 且返回 `aborted: false`：

```ts
// 修复前
if (dirty.length > 0) {
  log('  ⚠️  目标工作区有未提交改动，已跳过自动合并。');
  return { merged, conflicts, staleBase, aborted: false };  // ← 这里
}
```

上层只看 `aborted`：`false` → 打印 ✅ → 退出 0。

**为什么这是最严重的一类缺陷**：误报（该拦的没拦）的问题是「漏了防线」；
假成功（没做却报做了）的问题是「**结论与事实相反**」。

具体后果：

1. **人被骗**。看到 ✅ 就以为合完了，去做下游的事（版本交付、发版）。
   真正的问题（工作区脏）被一句 ✅ 完全盖住。
2. **`--push` 会跟着跑** —— 推的是一条**没变过**的分支，远端看起来一切正常。
3. **下游判定基于假成功**。`version deliver` 读的是 git 状态（正确），
   所以会失败 —— 但人已经花时间在错误的方向上了。

**已修**（ADR-060 §2）：

1. `aborted` 的语义改成「合并没有完成」，新增 `abortReason` 区分原因
2. 工作区脏的守卫返回 `aborted: true`
3. **兜底**：合并完但 `merged.length === 0` 时报警告并退出 1 ——
   判据不依赖单一标志位

```ts
if (result.merged.length === 0) {
  console.log(`⚠️  Merge finished but no slice was merged (${plan.phases.length} phases, 0 slices).`);
  console.log(`   目标分支未被修改。`);
  return 1;
}
```

**顺带修的判据漂移**：显式 id 路径原先**不查分支存在性**，
而 `collectMergeCandidates` 会查。分支不存在时合并根本无从下手，
但计划会照列 —— 到执行阶段才发现，而那时 `commitPendingWorktrees`
（**有副作用**）已经跑过了。

修法：显式 id 路径在 `commitPendingWorktrees` **之前**查分支存在性，
缺失就拒绝并点名。

### D-12（中）编码守卫对着干净文件报假警

**现象**：全量测试时编码守卫报错：

```
[zelto] 编码检查失败：1 个文件疑似乱码污染。
  tests\write-set-coverage.test.ts:293  U+6B22
```

但那个文件**完全干净** —— 第 293 行是：

```ts
const paths = parseMentionedPaths('这个功能应该很快，用户会喜欢这个体验。');
```

`U+6B22` 是「**欢**」。

**根因**：编码守卫的 `MOJIBAKE_MARKERS` 名单里混进了常用汉字。
名单的原始推导标准是「污染语料中频次 >= 200、干净语料中出现 <= 2 次」——
那个「干净语料」是仓库当时的语料，不含「喜欢」这个组合。
**语料一换，判据就失效了。**

**为什么误伤比漏检更严重**：编码守卫是**最后一道防线** ——
其它工具坏了它还能拦住，它自己坏了就是没人拦。

而一个开始报假警的检测器会**迅速失去可信度**：
人看到它对着干净文件报错，第一反应是「这玩意儿不可靠」，
然后就绕过它 —— 那它对**真污染**也失效了。

**漏检一个污染**：人写坏了一个文件，编译期报错，能查出来。
**误伤一次**：人开始不信这个守卫，之后所有真污染都放过。后者更糟。

**已修**（ADR-060 §5）：

1. 把 `欢` 移出名单，并写明入选标准（两条都要满足）：
   - 在 GBK 误解码语料里出现频次 >= 20
   - **本身不是常用汉字**
2. 守卫**不查自己** —— 它的源码里必然含特征字（它们是数据）
3. 给守卫写回归测试，且是**双向**的：
   - 测「不误伤」（特征字表里没有常用汉字）
   - 测「还抓得住」（特征字表仍包含典型误解码产物）

第 3 条的关键：**只测「不误伤」不够**，
还得测「还抓得住」—— 否则最省事的修法是**清空名单**，
守卫就彻底瞎了，而所有测试还都是绿的。

## 三之三、两项遗留的处置

### `parseMentionedPaths` 的无扩展名文件白名单

`Makefile` / `Dockerfile` / `CMakeLists.txt` 这类文件识别不到 ——
D-4 的写集覆盖判据因此会漏检它们。

**已修**：

1. 新增 `KNOWN_EXTENSIONLESS_FILENAMES`（`makefile` / `dockerfile` /
   `license` / `readme` / `changelog` 等）
2. **扩展名清单合并成一份** `KNOWN_EXTENSIONS` —— 原来有两份，是漂移的温床
3. 加负向后视断言 `(?<![/:\\w.])` —— 防止 URL 主机名与绝对路径漏进来

## 五、关于「为什么要跑全量测试」——一次真实教训

**规格原文的表述把 agent 带偏了。** 初版规格里写了「既有 ctest 全绿」
「全量 ctest 通过」，于是 agent 在 worktree 里跑起了 **1400+ 个测试套件**
的全量 `ctest` —— 一个只改了 RTP 打包集中层的切片，触发了整个项目的
全量测试矩阵。

**修正**：规格改为显式限定 scoped 目标，并在「不做」章节写明
「不要跑全量 ctest」：

```
ctest --test-dir build -R "engine_dtmf|engine_audio_send|engine_timeline|hotpath_zero_allocs"
```

**教训（可推广）**：

1. **规格里的「全量」「既有」「都」这类词会被 agent 当成硬性验收标准。**
   规格是 agent 的唯一权威输入，写「全量 ctest 通过」等于下令跑全量。
2. **验收标准要写「跑什么」，不能只写「跑过什么」。** 只说「通过」不给命令，
   agent 就会自己选最保险（最贵）的解释。
3. **「不做」章节是有效防线**，但要写成可执行的具体否定
   （点名命令 + 目标正则），不是泛泛的「不要跑全量测试」。

修正后，全部 4 个 scoped 目标在 `main` 上通过：

- `test_engine_timeline`
- `test_engine_audio_send`
- `test_engine_dtmf`
- `hotpath_zero_allocs`

### 演练后补修（D-16）：C/C++ 的 `#include` 依赖解析（ADR-062）

ADR-061 把「代码」与「扫描器读得懂」分开了，但**盲区本身没缩小**。
这一轮补上盲区里最大的那块：**C/C++**。

调研在真实项目上做（扫 401 个 C/C++ 文件、108 条引号 include）：

| 形态 | 数量 | 例子 |
|---|---|---|
| 裸文件名 | 72 | `engine_impl.hpp` |
| 带目录 | 36 | `nimrtc/core/registry.hpp` |

**两种形态在同一个项目里并存** —— 所以需要两套解析策略。
另外发现 **44 个 include 根目录，全部叫 `include`**（C++ 世界惯例）。

**关键取舍：不读 CMakeLists，用「约定法」**（找叫 `include/` 的目录）。
理由是**失败方向**：

| | 约定法 | 解析 CMake |
|---|---|---|
| 假边风险 | **零**（只漏不错） | 有（解析错就假边） |
| core/ 复杂度 | 低 | 高（要实现半个构建系统） |

架构检查的价值在于「报出来的偏离都是真的」。
一个会误报的检查器，人用两次就不信了 —— 那它对真问题也失效了。

**实施效果**（nimrtc-zelto，14439 个文件）：

| | 实施前 | 实施后 |
|---|---|---|
| 已验证文件 | 462 | **4939**（10.7 倍） |
| 覆盖率 | 3.2% | **34.2%** |
| 剩余盲区 | 4557 个代码文件 | **76** 个（Rust） |

**D-16 附带发现：工具报出了设计的错。**

新引入 `empty_module` 偏离（软偏离）：**模块声明了，但一个文件都没匹配上**。
真实项目里一次抓出 **5 处**：

```
● 模块无文件    src/dtls → src/dtls
  模块 "src/dtls" 声明了文件路径，但一个文件都没匹配上
  （src/dtls/*、src/dtls/**/*）—— 路径写错了，或目录还不存在
```

真相：代码实际在 `src/modules/dtls/` —— **设计文档里的路径写错了**。

不报出来的话，这个错误会飘到「依赖无法验证」里，
人看到的是「`src/dtls` 验不了」，而真相是「**`src/dtls` 根本不存在**」。

> **这是这套架构检查第一次能指出设计本身的问题**，而不只是代码与设计的差异。

### 演练后补修（D-18）：`<>` 不等于「系统头」（ADR-062 §3.2 修正）

核对偏离时发现一条 `src/engine → src/dtls`，但 `engine_impl.hpp` 里
明明没有 include `nimrtc/dtls/...`。查下去发现：

```cpp
#include <nimrtc/dtls/dtls_session_iface.hpp>   ← 尖括号！
```

**实测：2716 条尖括号 include 里，1081 条是项目内部的**（占 40%）。

C++ 的 `<>` 与 `""` 的区别**不是「内部 vs 外部」**，而是「**搜索顺序的约定**」：
`<>` 跳过当前目录、直接搜 `-I` 列表 —— 而 `-I` 列表里既有系统路径，
也有项目的公共头文件目录。**公共头文件用 `<>` 是正常且推荐的写法。**

**修正**：两种都解析，**解析不到的自然就是外部依赖**。
外部依赖靠「在不在 include 根里」这个**可判定的事实**识别，不需要猜。

> **教训：「排除外部依赖」不如「识别内部依赖」。**
> 遇到「要判断 X 是不是 Y」时，先找有没有一个可直接判定的事实。
> 这条在 D-15（区分不可验证的三种原因）里已经出现过一次。

### 演练暴露的流程缺口：已确认的设计改不了

```
$ zelto design refine prj-1792993843912 "修正文件路径"
INVALID_STATE: Design "prj-1792993843912" is already confirmed.
```

工具报出了设计的错，却**没有修正的路径** ——
`DesignDoc.supersedes` 字段预留了「新版取代旧版」的机制，
但**没有任何命令设置它**（一直是 `null`）。

本轮先手改 JSON（用户确认），把「实现修正命令」记为遗留。
将来该做一个走**确定性替换**（不经 LLM）的命令 ——
这里的修改是文本替换，走 LLM 反而有把别的东西改坏的风险。

### 演练后补修（D-19）：`zelto design patch` —— 确定性修正设计（ADR-063）

上面那条「流程缺口」已经补上了。

**不走 LLM，走确定性文本替换**：

```
zelto design patch <id> --module <name> --path <glob> [--dep <module>] [--yes]
```

**为什么不让 LLM 做**：LLM 会「顺手」改别的东西。修正一个路径，
结果它重写了整个职责描述 —— 那不是修正，是**未授权的创作**，
而创作需要人从头重新确认，违背了命令的意图。

**正文与 modules 两处同步** —— 根治了「手改 JSON 只改一处会不一致」的陷阱：
改完正文后**重新推导** `modules`（用 `modules: []` 强制走推导路径，
不会退回旧快照）。调用方不需要知道有两份，只改正文即可。

**改已确认的设计 → 必须人确认**：TTY 下交互确认；
非 TTY 下拒绝并要求 `--yes`（不静默跳过）。
事件写 `draft.revised`（**已有事件类型，契约不用改**），payload 带完整 before/after。

**真实项目端到端验证**（闭环成立）：

1. 故意把 `src/dtls` 的路径改回错的
2. `arch check` 报出 `src/dtls 0 个文件` + `模块无文件`
3. `design patch` 修
4. `arch check` 恢复 `src/dtls 21 个文件（19 代码）`，偏离回到 26
5. `body` / `modules` 两处都改了，事件带完整 before/after

**踩到一个隐蔽的坑**：在 JSDoc 里写 glob（`src/core/**/*`）——
连续的星号加斜杠会**提前结束块注释**，报错位置离真正原因很远。
**在 JSDoc 里写 glob 模式时，星号是危险的。**

另一个教训：**解析规则已经存在时，不要重写**。
我本来自己实现了一遍字段值的清理（没剥反引号），测试直接抓到不一致 ——
改成直接调 `parse.ts` 的 `parseFieldList`（单一实源）。

### 演练后补修（D-20）：条件编译（`#ifdef`）的依赖边（ADR-064）

ADR-062 §9 留的尾巴：「条件编译可能产生假边」。**先测，再决定要不要修**。

**实测**（nimrtc-zelto，项目代码 491 个 C/C++ 文件，3770 条 include）：

| 类别 | 数量 | 占比 |
|---|---|---|
| 条件编译块外 | 3090 | 82.0% |
| **include 守卫内** | 431 | 11.4% ← 永远为真，**不是**条件 |
| **真条件编译内** | 249 | 6.6% |

**「假边」其实不存在**：真条件里的 249 条 include，
219 条指向系统头 / 第三方 SDK（本来就是外部依赖），
只有 **30 条（0.8%）指向项目内部代码**。

**include 守卫占了将近一半** —— 这是第一轮调研被误导的原因：
`NIMRTC_ENGINE_ENGINE_HPP` 看着像条件，其实是守卫。
判据：「`#ifndef X` 紧跟 `#define X`」→ 守卫，**永远为真**。
不区分的话，11.4% 的 include 全被误标成条件依赖，标记就没意义了。

**决策：条件边仍是依赖，只标记、不隐藏、不报违规**

条件编译不是「这段代码不存在」，是「这段代码在某些配置下存在」。
开启那个特性时依赖就在 —— 设计该声明就得声明。
隐藏它，等于把**真问题**放过（开启特性后代码里有依赖、设计里没写）。

**区分两种情况**：
- **纯条件边**（整条边都来自条件编译）—— 「关闭对应特性时这条边不存在」
- **混合边**（有无条件来源，也有条件来源）—— 「依赖本身一直存在，但有 N 处来源只在特定构建配置下生效」

真实项目结果：**0 条纯条件边，5 条混合边**。

**一个重要的负面结论**：演练报的两个依赖环
（`src/engine → src/dtls → src/plugins → src/modules`）**是真的环** ——
`src/modules/* → src/plugins` 有 88 处无条件来源。
**不是**「条件编译造成的假环」。
这条结论重要 —— 否则会误以为是工具的问题，去改工具。

**报告输出的实际价值**：把「特性开关」在依赖图上的痕迹显出来了。
读者能看出 `src/modules → src/core` 的依赖有一部分是
「Windows 平台的 AMF/DXVA 编码器后端带来的」。

新增 ADR：

- **ADR-057** —— 被放弃的切片不阻塞版本交付
- **ADR-058** —— 架构守卫对不可扫描目标不再报硬性缺失依赖
- **ADR-059** —— 签字门与写集覆盖判据（D-4 + D-6 + 四个小缺陷）
- **ADR-060** —— 合并的假成功（D-11）、架构扫描的语言覆盖面、
  编码守卫的误伤（D-12）
- **ADR-061** —— C++ 项目上的架构报告：「代码」与「扫描器读得懂」要分开
  （D-13 / D-14 / D-15）
- **ADR-062** —— C/C++ 的 `#include` 依赖解析（D-16）
  —— 覆盖率 3.2% → 34.2%，并报出设计文档里的 5 处路径错误
- **ADR-063** —— 确定性修正设计（`zelto design patch`，D-19）
  —— 走文本替换不经 LLM，正文与 modules 两处同步
- **ADR-064** —— 条件编译（`#ifdef`）的依赖边（D-20）
  —— 条件边仍是依赖，只标记不隐藏；区分 include 守卫与真条件

ADR-060 同时实施了「架构扫描语言覆盖面」的第一档方案：
`arch check` 现在会**显式报告**本次验证了哪些语言、
哪些代码文件**没有**被验证过 ——

```
扫描覆盖：
  ✔ TypeScript / JavaScript     142 个文件（依赖已验证）
  ✔ Python                       38 个文件（依赖已验证）
  ⚠ C / C++                     377 个文件（代码 —— 无 import 语义，依赖未验证）
  · 构建脚本                     12 个文件（不产生依赖边）

  ⚠ 本次只验证了 180/569 个文件的依赖关系。
    377 个代码文件没有可用的依赖语义 —— 它们的依赖关系**没有被检查过**。
    上面的偏离只涉及已验证的部分；未验证部分的偏离本次查不出来。
```

C++ / Go / Rust 的**依赖解析**本身（方案 B / C）仍待单独 ADR。

## 九、结论

zelto 在真实项目上的**主链路是通的**：需求 → 设计 → 计划 → 切片 → 冻结 →
隔离 worktree → agent 真实执行 → 写集强制 → 门禁 → 失败即停 → 签字 →
显式合并 → 版本交付 → 版本合主干，全程没有一步绕过护栏。

演练暴露的问题集中在三类：

1. **zelto 自己的工程卫生**（D-1 脏 `dist/`、D-2 `--agent` 解析、D-3 占位符标题）
2. **护栏判据的漏判与误判**（D-6 签字门漏判、D-9 arch 误判、D-10 工作区误判）
3. **规格与写集的一致性无人校验**（D-4 —— 本次唯一一次真正卡住流程的地方）

第 3 类才是「越界在发生的那一刻暴露」这条主张的薄弱处：写集守住了
「不该写的没写」，但**没守住「该写的写了」**。
护栏只管住了越界，没管住**授权不足**。

D-6 是同一类问题的另一个方向：护栏只管住了「签字之后必须显式合并」，
没管住「合并之前必须签过字」。**解耦不等于不管。**

这两条合起来说明一件事：zelto 的闸门倾向于「拦住明显的」，
而**漏判往往发生在闸门之间** —— 一条命令有两条路径时，
两条路径的判据很容易不一致（D-6），一条判据涉及两个文件时，
两个文件的内容很容易不一致（D-4）。

D-11 是同一个模式的第三种形态，而且是最严重的一种：
**闸门自己放行了，但闸门后面什么都没做**。
判据不一致只是「两次判断给出不同答案」；
判据一致但**结果判据缺失**（「合并了 0 个切片也算成功」）
是「判断给出了与事实相反的答案」。

**最根本的遗留问题**：zelto 的 arch check 目前只对 JS/TS/Python 有判定能力。
C++/Go/Rust 的「依赖是否真被引用」验证能力缺失 —— 这不是误报一个第三方目录的问题，
而是**整个语言覆盖面**的问题。

ADR-060 的方案 A 已把这个缺口**显式化**：
`arch check` 现在会说清「哪些文件验过、哪些没验过」，
不再用「无偏离」这种结论盖住根本没验证过的代码。
但**验证能力本身**（方案 B / C）仍待单独 ADR。

### 遗留清单

- `zelto plan` 仍不能删切片 / 改切片归属（ADR-057 已记录）
- ADR-057 §5 记录的「`plan add-version` 靠 LLM 自动生成切片，容易产生幻觉规格」
  仍需单独一条 ADR 处理
- **Go / Rust 的依赖解析**（ADR-060 §4 方案 B / C）待单独 ADR
  —— C++ 已由 ADR-062 / ADR-064 覆盖
  —— 两者同样有条件编译（Go 的 `//go:build`、Rust 的 `#[cfg]`），
  实施时要一并处理「include 守卫 vs 真条件」这个问题
- ADR-060 §4.5 的「模块归属要先在设计里说清楚」是**实践问题**，
  需要文档跟进 —— 即使补齐了解析，模块划分没跟上，扫出来的图也是噪声
