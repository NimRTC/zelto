## 三、演练中发现的 zelto 缺陷目录

### D-1（严重）脏构建产物留在 `dist/`，比 `main` 新

**现象**：`dist/` 里有 `src/cli/commands/agent-preflight.ts` 的编译产物，但
`main` 的 `src/` 里**根本没有这个文件** —— 它只存在于备份分支
`backup/dirty-20261114`。

后果：`zelto run` 直接崩在 agent 预检：

```
❌ Agent 预检未通过：agent 预检失败：Cannot read properties of undefined (reading 'trim')
   命令：undefined
```

`tsc` **不删旧产物**，所以从备份分支构建过的 `dist/` 会一直留在磁盘上。

**处置**：本次手工 `Remove-Item -Recurse -Force dist, dist-test` 后重新 `npm run build`。
**待办**：应写进 zelto 自己的开发流程，或让 `npm run build` 先清目录。

---

### D-2（中）`--agent` 是布尔标志，实现却按「后跟命令名」解析

`src/cli/commands/core-slice.ts`：

```ts
const agentName = args.includes('--agent') ? args[args.indexOf('--agent') + 1] : agentCmd;
```

`zelto run <id> --agent`（help 里明确写 `--agent` 是布尔标志）会让
`agentName` 变成 `undefined`。

本次没炸，是因为 `createExecutorAdapter` 对 undefined 回退到了
`cfg.agent.command` —— **靠兜底掩盖了 bug**。日志里打印的
`Agent: undefined` 就是征兆。

**修复方向**：布尔标志只做存在性判断；「指定 agent 名」应另设参数（如
`--agent <name>` 与 `--use-default-agent` 分开，或 `--agent=name` 语法）。

---

### D-3（中）`refine` 不更新 frontmatter 的 `title`

`zelto require refine <id> "标题改为：..."` 更新了正文，但
`.zelto/requirements/<id>.md` 的 `title:` 仍是占位符「需求标题」。

结果：需求 / 设计 /计划的标题永久停在占位符，追溯链上全是「需求标题」。

**修复方向**：`refine` 若在反馈里识别出标题意图，应同步写 frontmatter。

---

### D-4（中）切片规格的「范围」与「写集」可能不一致，人工才看得出来

规格需求 6 写着「`src/engine/CMakeLists.txt` 如需登记新 `.cpp` 文件，只加一行」，
但**写集里没有这个文件**。

结果：agent 建了新 `.cpp` 却无法登记 → 链接期才炸：

```
error LNK2019: 无法解析的外部符号 "nimrtc::engine::build_rtp_packet(...)"
```

写集守卫（C9）**正确拦住了越界**（agent 想改也改不了），但代价是
「规格说要改 + 写集不允许改」这种矛盾要靠人去 spec 和 write-set 里比对才能发现。

**修复方向**：冻结时校验「规格里点名的文件」是否都在写集里；或从规格「范围」
章节自动推导写集。

---

### D-5（低）`require list` 之外的自然语言会掉进 LLM 通路

`zelto requirement list`（`require` 的复数形式）没有对应命令，被 LLM 通路接住，
返回一段「需求似乎不够明确」的提示。人会以为自己拼错了。

**修复方向**：常见近形词给一条「你是不是想用 `zelto require list`」的提示。

---

### D-6（严重）`zelto merge <id> --plan` 越过签字门

**现象**：在切片尚未签字时调用 `zelto merge v1-rtp-packetizer-core --plan`，
zelto **直接提交并合并了**，没有拦住。

**问题**：签字不自动合并（ADR-018）是硬约束 —— `--plan` 参数让 merge
路径绕过了「必须先 `sign --approve`」的前置检查。签字与合并两条命令
必须彻底解耦，不能因为一个透传参数就恢复成「一条命令全干」。

**处置**：本次以显式 `zelto sign v1-rtp-packetizer-core --approve`
补齐签字状态，随后手工核对合并结果。
**修复方向**：`merge` 路径无条件校验切片已批准，`--plan` 只应影响
「合到哪里」（版本分支 vs 主干），不应影响「能不能合」。

---

### D-7（严重）版本交付被废弃切片永久阻塞

**现象**：`zelto version deliver v1` 失败：

```
❌ 验收前置条件不满足：
   - v1-adapter-layer：状态是 abandoned，还没到「已完成」
```

**死路**：废弃的切片 ID 不可复用（`zelto create` 报「Slice already exists」），
`abandoned` 是终态不可复活，而 `zelto plan` 也不能删切片 —— 三条路全堵死。

**根因**：`version deliver` 的判据要求每个切片都是 `completed`，
但同仓库的 `src/core/report/report-analyzer.ts`（版本进度统计）用的是
`completed || abandoned`。**同一件事两套判据，报表说「都了结了」，
交付说「没完」。**

**修复**：已实施 **ADR-057** —— `abandoned` 切片不阻塞交付，但必须
在交付输出里显式列出（`⚠️ 本版本有 N 个切片被放弃（不阻塞交付）`），
不静默吞掉。

```ts
if (data.state === 'abandoned') {
  abandonedSlices.push(s.id);
  continue;
}
if (data.state !== 'completed') {
  problems.push(`${s.id}：状态是 ${data.state}，还没到「已完成」`);
}
```

**现象**：agent 交付的 `tests/acceptance/v1-rtp-packetizer-core/acceptance.test.cjs`

**处置**：补齐 8 条真实断言（见下文「验收断言」）。
**修复方向**：门禁②的失败输出应区分「零通过断言（fail closed）」与
「有断言但失败」两类。

### D-9（中）`arch check` 对 C++ 项目误报硬性「缺依赖」

**现象**：`zelto arch check` 输出 `❌ 架构偏离 377 项（硬性 2 项）`，
两项硬性偏离指向 `src/third_party`（googletest / msquic 源码）。

**根因**：arch 扫描器的 `detectLang` 只识别 JS/TS 与 Python。C++ 文件
全部落入「有代码但不可读」状态，而旧判据只看「目标模块有没有代码」，
不看「代码能不能被扫描」，于是把第三方模块误判为缺 import。

**后果严重性**：这是**硬性偏离**（直接拒绝），意味着任何 C++ / Go / Rust
项目的 `arch check` 基本跑不过。

**修复**：已实施 **ADR-058** —— 引入「可扫描性」判据：目标模块中
可被扫描器识别的文件占比 ≥ 0.5 才可能构成 `missing_dependency`；
否则降级为警告级 `unverifiable_dependency`。

```ts
const totalFiles = (scan.moduleFiles.get(to) ?? []).length;
const readableFiles = (scan.moduleCodeFiles.get(to) ?? []).length;
const readableRatio = totalFiles > 0 ? readableFiles / totalFiles : 1;
const scannable = readableRatio >= 0.5;

deviations.push({
  kind: targetHasCode && scannable ? 'missing_dependency' : 'unverifiable_dependency',
  from,
  to,
  detail: targetHasCode && scannable
    ? '设计声明了依赖，代码里没有对应的 import'
    : '目标模块没有源文件（契约 / 规格一类），无法用 import 验证',
});
```

### D-10（中）`policy/lock.json` 被保护域挡住提交，永久污染工作区

**现象**：`policy/lock.json` 被 hook 的 `protect-policy` 规则拦在提交之外
（保护域 `policy/**` 硬编码，不可被策略覆盖 —— C5 的正确执行），
但它**不在 `.gitignore`**。于是这个文件永久是「未跟踪」状态。

**后果**：`zelto version ship v1` 的工作区干净检查永远失败 —— **版本
永远发不出去**，且错误信息只是「工作区不干净」，不指出是哪个文件。

**修复**：把 `policy/lock.json` 加入 `src/core/project/initializer.ts` 的
`GITIGNORE_ENTRIES`（新建项目自动忽略），并更新已存在项目的 `.gitignore`。

## 五、关于「为什么要跑全量测试」——一次真实教训

**规格原文的表述把 agent 带偏了。** 初版规格里写了「既有 ctest 全绿」
「全量 ctest 通过」，于是 agent 在 worktree 里跑起了 **1400+ 个测试套件**
的全量 `ctest` —— 一个只改了 RTP 打包集中层的切片，触发了整个项目的
全量测试矩阵。

**修正**：规格改为显式限定 scoped 目标，并在「不做」章节写明
「不要跑全量 ctest」：

```
ctest --test-dir build -R "engine_dtmf|engine_audio_send|engine_timeline|hotpath_zero_allocs"
```

**教训（可推广）**：

1. **规格里的「全量」「既有」「都」这类词会被 agent 当成硬性验收标准。**
   规格是 agent 的唯一权威输入，写「全量 ctest 通过」等于下令跑全量。
2. **验收标准要写「跑什么」，不能只写「跑过什么」。** 只说「通过」不给命令，
   agent 就会自己选最保险（最贵）的解释。
3. **「不做」章节是有效防线**，但要写成可执行的具体否定
   （点名命令 + 目标正则），不是泛泛的「不要跑全量测试」。

修正后，全部 4 个 scoped 目标在 `main` 上通过：

- `test_engine_timeline`
- `test_engine_audio_send`
- `test_engine_dtmf`
- `hotpath_zero_allocs`

### Windows DLL 暂存（环境适配）

首次跑 scoped 测试时，测试可执行文件全部 `0xC0000135 (STATUS_DLL_NOT_FOUND)` ——
`msquic.dll` 构建在 `build/src/third_party/msquic/bin/Debug/`，既不在 PATH 也不在
`build/tests/Debug/`。

但它说明**跨语言项目的门禁配置需要模板化支持**，否则每次都要手写。

## 九、结论

zelto 在真实项目上的**主链路是通的**：需求 → 设计 → 计划 → 切片 → 冻结 →
隔离 worktree → agent 真实执行 → 写集强制 → 门禁 → 失败即停 → 签字 →
显式合并 → 版本交付 → 版本合主干，全程没有一步绕过护栏。

演练暴露的问题集中在三类：

1. **zelto 自己的工程卫生**（D-1 脏 `dist/`、D-2 `--agent` 解析、D-3 `refine` 标题）
2. **护栏判据的漏判与误判**（D-6 签字门漏判、D-9 arch 误判、D-10 工作区误判）
3. **规格与写集的一致性无人校验**（D-4 —— 本次唯一一次真正卡住流程的地方）

第 3 类才是「越界在发生的那一刻暴露」这条主张的薄弱处：写集守住了，
但**「该写的东西没被授权」**这件事要靠人先看出来。

另外，**D-9 暴露了一个更根本的问题**：zelto 的 arch check 目前只对
JS/TS / Python 项目有判定能力。C++ / Go / Rust 项目的「依赖是否真的被引用」
验证能力缺失 —— 这不是误报一个第三方目录的问题，而是**整个语言覆盖面**的问题，
需要独立议题。
