# ADR-034: 切片规格的生成与人工确认 + 验收测试骨架生成

**状态**: 已实施
**日期**: 2026-11-07
**作者**: 系统架构
**关联约束**: C1, C2, C3, C4, C7
**关联文档**: `docs/adr-032-trace-judgment-enforcement.md`, `docs/adr-033-slice-level-acceptance.md`,
`docs/zelto-项目目标.md` §3.1, `src/llm/generators/slice-spec.ts`, `src/core/spec/skeleton.ts`,
`src/core/gate/acceptance.ts`, `src/cli/commands/slice-spec.ts`

---

## 1. 摘要

切片规格此前由 `generateSliceSpecContent()` 生成，内容是固定四段：

```
## 验收标准
1. 完成 XXX
2. 全部测试通过
```

这两条不是验收标准，是**废话**：不可判定、无法核对、且与「这一片到底做成什么样」无关。
agent 拿到这样的规格，照规格实现的依据接近于零 —— 规格这一环在整个流程里是空的。

同时还有两处断链：

1. **规格的「验收标准」与「验收测试」之间没有桥**。规格写了验收标准，
   但没有任何东西把它落成能跑的断言；`slice.acceptance.dir` 只是个路径提示，
   门禁②（ADR-033）去跑的时候只会得到「验收目标不存在」。
2. **规格是人批准的这件事没有落点**。ADR-032 §4 已经指出：工具自动写的
   验收标准会**物化成本片的需求追溯**，于是「追溯合格」变成 zelto 替人批准的需求；
   当时的处理是「占位规格故意留空验收标准，宁可让人被拦住」。
   那是对的，但它只堵住了「不许造假」，没回答「人怎么才能拿到一份能用的规格」。

本次定案：

1. **规格生成器**（`src/llm/generators/slice-spec.ts`）：有 LLM 走模型，没有则确定性降级；
   产出**永远是草稿**，进下游须经人 `confirm`（C7）。
2. **草稿 → 确认闭环**（`zelto spec draft|show|confirm`）：草稿落 `.zelto/drafts/specs/`，
   确认后才写进 `specs/slices/`；没确认过的规格不会被冻结。
3. **验收测试骨架生成**（`src/core/spec/skeleton.ts`）：把规格里的验收标准
   逐条落成 `test.todo(...)` 骨架；门禁②补一条判定：**全是 todo/skip 的验收文件不算验证**。

---

## 2. 为什么现在做

ADR-032 把追溯接进了冻结准入，ADR-033 把切片级验收接进了门禁②。
这两条一落地，「追溯」与「验收」都变成了真闸门 —— 于是规格本身的质量立刻变成瓶颈：

- 追溯闸门要求「人批准的出处」，而规格是工具写的；
- 验收闸门要求「这片真的被验证过」，而根本没有验收测试可跑。

结果是流程跑不通：`zelto version start` 会在追溯闸门前停住（因为规格没有可物化的出处），
`zelto gate` 会因为找不到验收目标而判 failed。**工具在自己承诺的两件事上是空的**，
而这正是 ADR-032/033 之后必须补的最后一环。

---

## 3. 决策

### 3.1 规格生成器：LLM 优先，确定性降级

`src/llm/generators/slice-spec.ts`：

- **有 LLM**：把切片信息（id / 标题 / 模块 / 写集 / 需求条目 / 前置切片）交给模型，
  要求输出结构固定的 Markdown（目的 / 范围 / 需求 / 验收标准 / 风险）。
- **模型输出不可用时**（空、缺必备章节、验收标准全是套话）→ 退回确定性降级。
  规格的结构完整性不能靠模型心情。
- **没有 LLM** → 直接走确定性降级。

模型输出的可用性判定（`isUsableSpec`）：必备章节齐全，且验收标准**不是空壳**
（「完成 XXX」「全部测试通过」这类套话一律判不可用）。

### 3.2 确定性降级**不自己编验收标准**

这是本次最关键的一条边界。

降级路径下，规格里的验收标准**只能来自人已批准的需求条目**
（切片记录里的 `trace.requirements`，来自 `zelto create --requirement` 或人写的规格）。
没有需求条目时，验收标准章节只留一句明确的占位说明，**不写编号条目**。

原因：编号条目会被 `core/spec/trace-extract.ts` 物化成本片的需求追溯。
工具自己写的条目一旦被物化，「追溯合格」就变成 zelto 替人批准的需求 ——
和 ADR-032 §4 方案四（「1. 完成 XXX」）是同一个病，只是换了措辞。

**没有需求 → 没有可物化的验收条目 → 追溯为空 → 冻结被拦**。
宁可让人被拦住，也不制造看着完整的空追溯链。

### 3.3 草稿 → 确认闭环

新增命令组 `zelto spec`（`src/cli/commands/slice-spec.ts`）：

| 命令 | 做什么 | 落在哪 |
|---|---|---|
| `zelto spec draft <id>` | 生成规格草稿（有 LLM 走模型，没有则降级）+ 生成验收骨架 | `.zelto/drafts/specs/<id>.md` |
| `zelto spec show <id>` | 看草稿；没有草稿就看正式规格 | 只读 |
| `zelto spec confirm <id>` | 人确认 → 草稿内容写进正式规格 | `specs/slices/<id>.md`（切片自己的 `spec.path`） |

配套规则：

- **草稿与正式规格分目录**。`.zelto/drafts/` 下的东西不参与任何判定。
- **已有草稿不重新生成**（`createSpecDraft` 复用已有文件）：草稿是人正在审的东西，
  工具擅自覆盖等于抹掉人的工作，也会白花一次模型调用。
- **事件**：沿用既有事件类型 `draft.created` / `draft.confirmed`，payload 里带
  `kind: 'spec'`。**不新增事件类型** —— 契约面不变大。
- **确认后才谈冻结**：`zelto version start` 发现某片没有正式规格时，
  自动生成草稿、把这一片列进「待确认」，**本轮不启动执行**，并提示
  `zelto spec confirm <id>`。确认完重跑 `version start` 才冻结、才进调度。

`zelto plan confirm` 相应地**不再代填规格**：计划确认只确认计划，
规格一律走「生成草稿 → 人确认」。

### 3.4 验收测试骨架

`src/core/spec/skeleton.ts` 按规格正文的验收标准逐条生成骨架：

```
// 验收测试骨架 —— 由 `zelto spec draft` 生成（ADR-034）
const { test } = require('node:test');

test.todo("登录接口在密码错误时返回 401；验证方式：有对应测试");
```

- 落点：本片的验收目录（`slice.acceptance.dir`），文件固定叫 `acceptance.test.cjs`
  （`.cjs` 是为了跟目标项目的模块类型无关：ESM 与 CJS 项目都能直接跑）。
- 验收目标本来就是**单个文件**形态时（`create --from-spec` 登记的
  `tests/acceptance/<id>.test.ts`）→ **不覆盖**，那是人自己的文件。
- 规格里没有可用的验收条目 → 如实报告「没生成」，不硬造。

骨架存在的意义：门禁②找得到目标、命令真的能跑起来。
**但骨架不假装通过** —— 见下条。

### 3.5 门禁②：退出码 0 不等于验收通过

`node --test` 对一个**全是 todo** 的文件，退出码是 0。
也就是说：骨架生成之后，门禁②会看到「命令成功」→ 判 passed → 签字放行。
「这片验证过」这句话就变成了假的。

补一条判定（`core/gate/acceptance.ts` 的 `parseTestRunnerStats` +
`verifyAcceptanceRanTests`）：

- 从测试运行器的 TAP 汇总行里读 `pass / fail / todo / skipped`；
- **读不出统计就不做判断**（不同运行器输出格式不同，猜不得）；
- 读得出且 `pass == 0`（无论 todo / skip 有多少）→ 判 **failed**，理由写明
  「todo 与 skip 不算验证」。

这条与 ADR-033 的 fail-closed 语义一致：跑起来了不等于验证过了。

## 4. 被否决的方案

**方案一：继续让工具代填验收标准（「1. 完成 XXX」），只是把措辞改好。**
否决理由：ADR-032 §4 方案四已经否决过一次。措辞改好不改变性质 ——
工具写的条目会被物化成需求追溯，于是「追溯合格」变成 zelto 替人批准的需求。
问题的根不是措辞，是**出处**。

**方案二：把需求追溯从规格里物化，改为只认 `--requirement` 显式声明。**
否决理由：会让人写规格这件事变得没有意义。人写的规格正文里的「验收标准」
本来就是最贴近实现的出处（ADR-032 §3.3 已经把它排第一）。
而且这个方案没有回答「规格里没有需求条目怎么办」—— 只是把问题推给纪律。

**方案三：`version start` 继续自动写正式规格，只是加个「未确认」标记。**
否决理由：需要给切片状态加字段（契约面变大），而且「文件存在但未确认」这种状态
比「文件不存在」更难判断 —— 后面每个读规格的地方都得记得看标记。
用**目录**区分草稿与正式规格，判定只看「正式规格在不在」，比状态标记更不容易漂移。

**方案四：验收骨架直接写成会通过的占位断言（`assert.ok(true)`）。**
否决理由：那是骗人。骨架必须以 todo 形式存在，让门禁②能看见「没写」，
再由 §3.5 的判定把「没写」变成 failed。骨架的作用是让「没写」可见，不是让它变绿。

**方案五：门禁②不补「真跑过用例」判定，靠骨架里的 todo 自己让命令失败。**
否决理由：`node --test` 对全是 todo 的文件退出码是 0（这是测试运行器的既定行为，
不是 bug）。要让 todo 变成失败，就得在生成骨架时故意写错 —— 那是把「未完成」
伪装成「失败」，报告里会出现看不懂的失败信息。判定放在门禁侧更诚实。

## 5. 影响与迁移

**破坏性变更**：

1. **`zelto plan confirm` 不再生成 `specs/slices/<id>.md`**。
   依赖「计划确认后规格文件就在那儿」的脚本会失效。
   替代流程：`zelto spec draft <id>` → `zelto spec confirm <id>`。
2. **`zelto version start` 在有切片缺正式规格时不再开跑**（退出码 1），
   会先生成草稿并列出待确认的切片。这是刻意的：追溯的出处必须是人确认过的规格。
3. **门禁②多一条判定**：验收文件里一条用例都没真正执行 → 判 failed（此前是 passed）。
   已有的、真正跑过用例的验收文件不受影响。
4. **`generateSliceSpecContent()` 的产出变了**：
   此前产出「1. 完成 XXX / 2. 全部测试通过」，现在产出结构完整、
   但**没有需求条目时不含任何编号验收条目**的规格。

**契约面变化**：

- 事件类型集合**没变**（沿用 `draft.created` / `draft.confirmed`）；
- `contracts/schemas/**` **没变**；
- 切片状态机、事件流结构、policy 配置格式**都没变**；
- CLI 新增命令组 `zelto spec draft|show|confirm`；
- 新增目录 `.zelto/drafts/specs/`（工具产物，人可改可删）。

**没有改的东西**：`core/` 的零依赖与依赖方向（新增的 `core/spec/skeleton.ts`
只用 Node 内置）、门禁①的追溯判定、ADR-033 的切片级验收定位逻辑。

---

## 6. 验证方式

- 新增单元测试 `tests/adr-034-spec-draft.test.ts`：
  - 确定性降级规格：无需求 → 物化不出验收条目；有需求 → 验收条目来自需求原文；
  - 模型产出缺章节 / 全是套话 → 判不可用；
  - 验收骨架：每条验收标准一条 todo；目录形态落盘正确；文件形态不覆盖人自己的文件；
  - 门禁判定：读不出统计不判断；全是 todo 判 failed；有真正跑过的用例才放行；
  - CLI 闭环：draft → 草稿在 `.zelto/drafts/specs/` 且此时**没有**正式规格 →
    confirm → 正式规格与草稿逐字一致 → 冻结成功；没有草稿时 confirm 拒绝。
- 全量 `pnpm build` + `pnpm test` 全绿（1299 个用例），`pnpm lint` 无错。

## 7. 与 ADR-032 / ADR-033 的关系

- **ADR-032** 保证了「追溯不合格不许冻结」，但当时留下的占位规格是**空的**。
  本 ADR 补上了空的那一半：让规格有内容，且内容经过人确认。
- **ADR-033** 保证了「门禁②要真的跑本片的验收」，但本片**没有验收测试可跑**。
  本 ADR 补上骨架生成，并补上「骨架不算验证」的判定。

两份 ADR 合起来的闭环是：

```
人确认需求 → 设计 → 计划（人确认）
   ↓
zelto spec draft      生成规格草稿（LLM）+ 验收测试骨架
   ↓  人审阅、按需修改
zelto spec confirm    写进正式规格 —— 这份规格从此是「人批准的出处」
   ↓
zelto version start   冻结（追溯物化出人批准的出处）+ 调度
   ↓
agent 实现（把骨架里的 todo 换成真断言）
   ↓
门禁②                 跑本片验收；一条都没真跑 → failed
   ↓
人签字 → zelto merge
```
