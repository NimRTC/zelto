## 1. 一句话

**zelto 是「AI 编程驾驶舱」——一个人 + 一组 agent 做中大型项目时的驾驶舱。**

它不写一行业务代码。它做的是**在项目从想法到主干的全过程中当那个方向盘和刹车**：

```
人做规划（方案设计 → 版本规划 → 模块划分 → 切片设置）
   ↓  规划确认完，zelto 把工作切成互不冲突的作业
zelto 控制并行 agent 进入高速开发（隔离 worktree + 写集守卫 + 门禁）
   ↓  出错时
拉闸 —— 越界当场拦下、卡住会来问人、预算耗尽停机，人被交还控制权
   ↓  验收通过
逐片签字 → 显式合并 → 版本交付 → 下一个版本
```

**目标用户是「一个人 + 一组 agent」**。zelto 的存在，是为了让一个人也能把中大型项目
做得**可控**、**可维护**、**不变成垃圾代码**——并且比直接用 Cursor 更快、更省心。

一句话说清它跟其它 AI 编程工具的区别：

> 其它工具是「把上下文喂给模型，让模型写对」；
> zelto 是「把上下文变成**可判定的约束**，让越界在发生的那一刻就暴露，
> 同时让一个人的规划能变成 N 个 agent 的高速并行」。

前半句是**可追溯**（§3）——这是 zelto 区别于其它编程工具的本质特征，不能丢；
后半句是**驾驶舱**——这是 zelto 真正要交付的产品形态。

## 2. 目标是什么（以及不是什么）

### 2.1 是

| # | 目标 | 具体含义 | 怎么验收 |
|---|---|---|---|
| G1 | **规划先行** | 方案设计、版本规划、模块划分、切片设置在写代码**之前**完成，并且由人确认 | 需求→设计→计划→版本→切片，每一级都有 `confirm` 状态位 |
| G2 | **高速并行** | 规划确认后，zelto 把切片拆成互不冲突的写集，并行拉起多个 agent | 一次命令拉起 N 个 agent，各自隔离 worktree 跑 |
| G3 | **可控可刹** | 出错时能拉闸，人被交还控制权，而不是 agent 自己跑偏 | 越界写入当场被 hook 拦下；停机分类 9 类；agent 提问可挂起可回答 |
| G4 | **可追溯** | 每行代码 → 测试 → 契约 → 规格 → 人批准的意图 | `zelto trace` 打通需求到切片；切片带 `trace` 字段；append-only 事件流 |
| G5 | **长期可维护** | 合起来是一个能长期演化的项目，不是一堆能跑的补丁 | 模块边界不被破坏；契约演进有检查；版本级验收守主干健康 |
| G6 | **比 Cursor 顺手** | 日常交互密度不输 Cursor，规划质量与并行速度明显超过 Cursor | 规划确认不用通读长文；日常操作命令少、路径短、结果可读 |

G1–G3 是**驾驶舱的三段**（规划 → 并行 → 拉闸），
G4 是让这三段可信的**底座**，G5 是最终要交付的结果，G6 是竞争力标准。

### 2.2 规划层：zelto 到底帮人做什么

这一段是整个驾驶舱的**上游**，也是最容易被做成「AI 随便生成一坨东西」的地方。
zelto 在规划层做四件事，每一件都是**「生成草案 → 人确认 → 才往下走」**：

| 阶段 | zelto 做什么 | 人做什么 | 产出落在哪 |
|---|---|---|---|
| **方案设计** | 从需求生成设计草案，含**模块划分**（模块名 / 文件 / 依赖） | 确认或细化设计 | `.zelto/designs/<id>.json`，`draft → confirmed` |
| **版本规划** | 把设计切成**版本**，每个版本挂一批切片 | 确认版本顺序与切法 | `.zelto/versions/<id>.json`，`draft → confirmed` |
| **模块划分** | 在设计阶段就把模块边界和依赖写进结构化字段（`modules[].dependencies`） | 决定模块边界对不对 | 同上 |
| **切片设置** | 把版本拆成可独立交付的**切片**，每个切片带写集与追溯字段 | 确认切片粒度 | `specs/slices/<id>.md` + `.zelto/slices/<id>.json` |

**关键点：规划层产出的是「可判定的约束」，不是「一段给人看的文字」。**
模块依赖写进字段，才能在后面被校验；切片写集写进规格，才能被 hook 逐写判定；
追溯写进字段，才能被门禁①检查。规划层如果只产出 markdown，
后面所有机器判定都无从谈起。

规划层也**不是** zelto 替人做决定——LLM 产出的永远是草稿（C7），
每一级都要人 `confirm` 才进入下游。

### 2.3 执行层：高速并行为什么是「高速」

规划确认之后，zelto 要让 N 个 agent **同时**跑，且互不干扰。这靠四件事：

| 机制 | 解决什么 | 约束 |
|---|---|---|
| **写集解析与冲突检测** | 两个 agent 不写同一批文件 | C3 确定性判定 |
| **隔离 worktree** | 主仓工作树不被切换分支、不被 agent 写入 | ADR-011 |
| **写集预约 + PreToolUse 钩子** | agent 越界写入**当场**被拒 | C9 |
| **门禁② + 签名请求** | 每个 agent 跑完立刻验、立刻请求签字，不等人 | C3 |

**并行度算错了，「高速」就是伪命题**——不是跑得不够快，
而是 N 个 agent 里有两个在抢同一批文件，结果整批 abort，一个都没跑成。
§6 里的 G-1 与 G-2 正是这件事，现已闭环：并行度由 zelto **算**出来，
而不是让人去猜。

### 2.4 拉闸层：出错时人怎么拿回控制权

「高速」与「可控」是一对，代价是必须有刹车。zelto 的刹车有五种形态：

| 触发 | zelto 的动作 | 人怎么接手 |
|---|---|---|
| agent 越界写入 | hook 当场拒绝，写 `policy.decision` 事件 | 看事件流 → 决定改规格还是改 agent |
| agent 提了个问题 | 挂起该切片，批次里其它切片继续 | `zelto ask` 看 → `zelto answer <id> "..."` 续跑 |
| agent 反复失败 | 停机分类（9 类），分清「可自愈」与「要人管」 | `zelto stall` 看分类 → `zelto resume` |
| 批次跑偏了 | 人喊停拉闸，安全点收手，现场交回给人（ADR-020） | `zelto halt` → 处理现场 → `zelto halt --clear` |
| 预算耗尽 | 切片停在待签字前，不进 gate（ADR-035） | 加预算还是砍范围，人决定 |

**停机分类的价值在于区分责任**：环境故障该自动重试，
`cognitive_stuck`（想不通）必须交回给人——这两类混在一起，
就会变成「agent 一直失败但不知道为什么」的黑箱。

### 2.5 不是

- **不是代码生成器**。zelto 自己不写业务代码，它写的是「让 agent 安全地写代码」的那套约束。
- **不是审计器**。只做事后检查的工具在这个位置没价值——**约束必须发生在 agent 写文件的那一刻**。
- **不是自动批准器**。签字必须由人行使（AGENTS.md 禁区：「一键批准」「自动合并」）。
  签字只改状态，合入主干必须人显式跑 `zelto merge`（ADR-018）。
- **不是 GUI 产品**。当前形态是 CLI + 一个可选的 HTML 看板。完整 GUI 在负向清单里。
- **不是 agent 编排引擎的替代品**。zelto 不自己实现 agent 循环，
  它做的是「给 agent 套上约束与闸门」（AGENTS.md 禁区：「重造 agent 编排引擎」）。

## 3. 核心特色：可追溯

这是 zelto 与其它 AI 编程工具**最本质的区别**，不能因为功能变多而丢掉。

其它工具的思路是「把上下文喂给模型，让模型写对」。
zelto 的思路是「把上下文变成**可判定的约束**，让越界在发生的那一刻就暴露」。

具体差别：

| 维度 | 其它 AI 编程工具 | zelto |
|---|---|---|
| 代码为什么这么写 | 靠模型记住上下文 | 追溯到一条**人批准的规格** |
| 越界怎么发现 | 事后 review，人眼看 | **运行时** hook 逐写判定，当场拦下 |
| 谁说了算 | 模型 | **人**（模型产出只是可覆盖的草稿，C7） |
| 事后能不能查 | 靠 git blame 和聊天记录 | append-only 事件流，每个动作留痕 |
| 出错时 | 模型继续跑 | 停机分类 + 拉闸交回给人 |

**追溯不是第四个功能，它是前三段的共同底座。**
规划层靠它把「模块边界」「切片写集」变成可判定的字段，
执行层靠它让越界当场暴露，拉闸层靠它让人事后查得到「当时谁批的、依据什么」。
没有追溯，规划层产出的约束无法校验、拉闸时无法定责、交付后无法复盘。

追溯链的完整形态：

```
需求 (require)  →  设计 (design)  →  版本计划 (plan)  →  版本 (version)
   →  切片 (slice)  →  规格 (spec)  →  测试 (acceptance)  →  代码
                              ↑
                    每个切片带 trace: { requirements, contracts, tests }
```

`zelto trace <req-id>` 打印这条链，`zelto trace <slice-id> --slice` 打印单片的追溯与事件。

**这条链上任何一个环节断开，都是 zelto 判定失败**——
门禁①（`zelto check`）查的就是它。这不是附加功能，是 zelto 存在的前提。

### 3.1 追溯靠什么落地

追溯不是文档里的一句话，它由三样东西共同保证，缺一不可：

| 环节 | 实现 | 断了会怎样 |
|---|---|---|
| **链的载体** | 切片文件的 `trace: { requirements, contracts, tests }`，外加 `traceWaiver`（豁免必须写明理由） | 门禁① 拒绝冻结 |
| **链的校验** | 门禁① 确定性检查：追溯项不得为空、契约与测试必须落到具体文件 | 切片进不了 `frozen`，也就跑不起来 |
| **链的证据** | 57 种 append-only 事件，版本级事件用 `version-<label>` 作归属键 | 事后查不到「当时谁批的、依据什么」 |

三者的分工是：**载体**存关系、**校验**在写代码前拦住断链、**证据**在事后可查。
只有载体没有校验，追溯链会随时间腐化；只有校验没有证据，出了事说不清责任。

### 3.2 追溯也是并行安全的前提

并行开发的难点不是「拉起 N 个 agent」，而是「N 个 agent 同时改一个仓库」。
zelto 的并行安全性不是靠 agent 自觉，而是靠追溯链上的三样约束：

- **写集预约**（C9）：每个切片只能写自己规格声明的路径，运行时由 hook 逐写判定
- **隔离 worktree**（ADR-011）：每个切片在独立工作目录里跑，主仓工作树不被切换分支
- **事件留痕**（C4）：每个判定、每次拒绝、每次合并都写事件

所以追溯与并行不是两件事：**能说清「这行代码从哪来」，才敢说「这行代码只碰了该碰的」。**

### 3.3 追溯链一直延伸到合并之后

追溯最容易被「合并」这一步打断：代码进主干之后，规格、测试、签字记录
都留在了分支和 worktree 里，主干上只剩一个 commit，说不清它凭什么进来。

zelto 把追溯链穿过合并这一步：

| 合并阶段 | 追溯证据 | 查得到什么 |
|---|---|---|
| 签字 | `sign.requested` / `sign.approved` 事件 | 谁批的、批的是哪一片 |
| 计划 | `merge.planned` 事件（含依赖、阶段、策略） | 按什么顺序合、为什么是这个顺序 |
| 阶段完成 | `merge.phase_complete` 事件 | 每一阶段合了哪几片、有没有冲突 |
| 冲突 | `merge.conflict` 事件（含冲突文件） | 冲突发生在哪片哪个文件 |
| 完成 | `merge.completed` 事件 | 合成了什么 commit |
| 基线过期 | `merge.stale_base` 事件 | 哪个切片的基线已经落后 |

这就是为什么「签字」与「合并」必须分成两步（ADR-018）：
**签字把批准写进事件流，合并把归并写进事件流。**
如果签字顺手把代码合进主干，事件流里就只有「批准」，
没有「合了什么、按什么顺序合、撞了哪些文件」——追溯链在这里就断了。

## 4. 三大角色的分工

| 角色 | 是谁 | 做什么 | 不做什么 |
|---|---|---|---|
| **主用户** | 开发者（一个人） | 定意图、做设计、划分模块、排版本、确认切片、**签字**、**显式合并** | 不亲手写每行代码 |
| **执行者** | agent 群（Claude Code 等） | 由 zelto 拉起，按约束包实现切片 | 不做判定、不自己批准 |
| **看守者** | **zelto** | 校验追溯、分层并行、隔离执行、门禁验收、停机分类、事件留痕、派发作业 | **不替人签字** |

关键点：**zelto 的自动化止步于「待签字」**。这是它与「全自动编程 agent」的根本分歧。

把三个角色映射到驾驶舱的三段：

```
规划段：主用户想清楚 + zelto 落成结构化约束
              ↓
执行段：zelto 拉起 agent 群并行干活
              ↓
拉闸段：zelto 判定并拦截，人做最终决定
```

**驾驶舱的隐喻就落在这里**：驾驶舱不替人开车（那是 agent 的活），
也不替人看路（那是规划层人做的事），
它负责的是「仪表盘 + 刹车 + 护栏」——让人在高速运行时仍然知道自己在哪、能随时接管。

## 5. 主流程

```
              ┌───── 驾驶舱第一段：规划（人主导，zelto 落成约束） ─────┐
                          ┌──────────────── 规划层（人主导，zelto 记录） ─────────────────┐
  一个想法 ──► require ──► design ──► plan ──► version
              需求        设计/模块     版本计划    版本 + 切片
               ▲confirm    ▲confirm     ▲confirm     ▲confirm
                          （每一次 confirm 都是人点头；未确认不往下走）
                          └───────────────────────────┬──────────────────────────────┘
                                                          ▼
              ┌───── 驾驶舱第二段：高速并行（zelto 主导） ──────────────────┐
                          ┌──────────────── 执行层（zelto 主导） ────────────────────────┐
                          │  版本级准备：建切片 → 写规格 → 冻结（哈希 + 事件）        │
                          │  排阶段：依赖分层 + 写集冲突降级（阶段间串行/阶段内并行）│
                          │  并行准入：准入检查 → 写集解析 → 预算检查              │
                          │  隔离执行：每片一份 worktree + 一份写集预约 + 一份钩子     │
                          │  实时守卫：agent 每写一个文件 → hook 逐写判定            │
                          └───────────────────────────┬──────────────────────────────┘
                                                          ▼
              ┌───── 驾驶舱第三段：门禁与拉闸（机器判定 + 人接手） ────┐
                          ┌──────────────── 门禁层（机器判定） ─────────────────────────┐
                          │  写集审计 → 门禁②（验收测试）→ 自动发起签名请求          │
                          │  版本级验收（deliver 时）：主仓跑项目自己的门禁命令        │
                          └───────────────────────────┬──────────────────────────────┘
                                                          ▼
                          ┌──────────────── 交付层（人主导） ───────────────────────────┐
                          │  人签字 → 显式合并（zelto merge）→ 版本交付 → 下一个版本   │
                          └──────────────────────────────────────────────────────────┘
```

**签字 ≠ 合并**（ADR-018）：签字回答「这份改动可不可以合入主线」，
合并回答「现在就合」。前者是批准，后者是动作，所以分成两步，
而且合并这一步永远由人显式发起——zelto 不替人写主干，也不替人推远端。

**出错时的路径**（拉闸）：

```
agent 越界写入   → hook 当场拒绝 → policy.decision 事件 → 人来处理
agent 提了个问题 → 挂起该切片 → 批次里其它切片继续 → zelto answer <id> "..." → 续跑
agent 反复失败   → 停机分类 → cognitive_stuck 不可自动恢复 → zelto resume
预算耗尽        → 批次停在待签字 → 人决定加预算还是砍范围
版本验收不过    → 版本状态保持 in_progress → zelto version start <ver> --retry-failed
```

## 6. 现状与目标的差距

三大段的骨架都立起来了，但**衔接有缺口**。这是当前最需要投入的地方。

按驾驶舱三段归位：

| # | 差距 | 属于 | 现状 | 目标 | 影响 |
|---|---|---|---|---|---|
| **G-1** | ~~版本内并行不认依赖~~ | 高速并行 | ✅ **已落地**：`version start` / `run --parallel` 先排阶段再按阶段跑，依赖来自规格「前置切片」章节（D1=A） | 按依赖分层：同 phase 内并行，phase 之间串行 | 依赖 B→A 时 B 不再抢跑，**「高速」的并行度是算出来的** |
| **G-2** | ~~写集冲突 = 整批不跑~~ | 高速并行 | ✅ **已落地**：同阶段写集重叠自动降级为串行，批次继续跑（D2=A） | 自动把冲突切片降级为串行 / 分层 | 写集重叠是可预期的（都碰 `types.ts`），整批 abort 太脆 |
| **G-3** | ~~**没有「拉闸」这个动作」~~ | 拉闸 | ✅ **已落地**：`zelto halt` 一键暂停批次并交回控制权（ADR-020）；签字可撤销（ADR-021） | 一键暂停 → 快照现场 → 人处理 → 继续；签错可回退 | 出错时不再只能靠 Ctrl-C，半成品 worktree 与预约可清理 |
| **G-4** | **防垃圾代码的机制缺位** | 长期可维护 | ✅ **已闭环**：G-4/B（`zelto arch check` 只读偏离报告）+ G-4/A（ADR-027：`policy.yaml` 的 `arch:` 段给六类硬偏离定级，`arch check --strict` / `version deliver` / `batch` 准入 / 单片 `gate` 四处执行）+ 契约演进检查与跨版本回归基线（ADR-036） | 模块依赖方向可校验；契约演进有检查；跨版本回归基线 | 这是 G5（长期可维护）的直接缺口 |
| **G-5** | ~~**规划确认的体验重**~~ | 规划 | ✅ **已落地**（ADR-023）：`require/design/plan show <id>` 输出**摘要 + diff + 只看决策点**；refine 前留快照，差异看得见 | 摘要 + diff + 只看决策点 | 规划确认不再需要通读长文档 |

**G-1 / G-2 / G-3 / G-5 已闭环**。现在只有一份排法：`core/sched/batch.ts` 的 `planExecutionPhases()`
同时做依赖分层与写集降级；`src/cli/commands/execution-plan.ts` 是 CLI 侧的唯一入口，
`zelto batch`（只查）、`version start` 与 `run --parallel`（要跑）消费的是同一份计划——
两处各排一次，早晚得出不同结论。排阶段是纯计算（C3），不调模型、不触网；
计划只落在文件里（C1）。

执行时若某个阶段没过（失守 / 停机 / 提问），**后面的阶段不会启动**：
依赖没满足就跑下去，跑出来的多半也是错的，不如把控制权交回给人。

### 6.0 主路径的五处断点：已闭环

这一轮盘点的是「zelto 拿到一个真实项目后，主路径上还差什么」。
结论是**骨架与护栏都齐了，但主路径上有五处断点**——
其中最要命的那处是：门禁①在所有执行路径上都是「建议」而非「闸门」。
现在五处都已落地：

| # | 断点 | 现状 | 对应 ADR |
|---|---|---|---|
| 1 | **追溯判定接不进冻结与准入** —— `judgeTrace` 是唯一判据，但 `freeze` / `version start` / `scheduler.admit` 三个调用点没有一个在开跑前拦人。追溯为空的切片照样能冻结、跑 agent、过门禁②、进签字队列 | ✅ **已落地**：三个入口都接了追溯准入；`freeze` 与 `version start` 走同一条 `evaluateFreezeTrace`，规格里的「验收标准」会物化成需求追溯 | ADR-032 |
| 2 | **`zelto check` 在文本模式下永远返回退出码 0** —— 作为门禁①没法被脚本或 hook 串联；规格引擎的 `validateDeterministic` / `analyzeSemantic` 只被测试引用，CLI 里没有调用点 | ✅ **已落地**：文本模式与 json 模式退出码一致（有阻断项 = 1）；规格引擎接进 `check`，确定性判据 error 阻断、语义启发式只提示（C7） | ADR-032 |
| 3 | **验收测试没有骨架生成，门禁②跑的是全项目测试** —— agent 交回半成品，只要别的测试还绿就放行；`changedLineCoverage` 是个没人读的空壳 | ✅ **已落地**：`zelto spec draft` 生成验收测试骨架；门禁②按 `slice.acceptance.dir` 跑**本片**的验收文件（没配则显式记 `skipped`，配了则 fail closed） | ADR-033 |
| 4 | **agent 拿到的是半空规格** —— 规格生成器只产出「完成 XXX / 全部测试通过」，规划期生成的意图在落地时被压扁 | ✅ **已落地**：`zelto spec draft` 走 LLM 生成草稿（无 LLM 时确定性降级），人 `confirm` 后才写进正式规格（C7：草稿不参与判定） | ADR-034 |
| 5 | **预算对 agent 执行不生效** —— `budget.spent` 只有规划期的 LLM 通路写，执行适配器不回传实际花费，`BudgetCollector.getSpent()` 永远是 0，预算闸门是一道永远敞开的门 | ✅ **已落地**：两个 executor 适配器实现 `getUsage` 上报真实花费；CLI 在 agent 退出后记账（`budget.spent`，`source: 'agent'`）并复判预算——超预算则**不进 gate、不发签字请求**，切片停在 `frozen` 等人 | ADR-035 |

**这五处补上之后，zelto 从「能演示的驾驶舱」变成了「能托管一个真实项目开发的驾驶舱」。**
剩下的缺口集中在两处，都不在这条主路径上：
契约演进检查与跨版本回归基线（§6.1 G-4 剩余项 —— **已于 ADR-036 落地**），
以及日常交互密度（59 个命令的学习成本，§6.2）。

### 6.1 G-4 展开：为什么「不产垃圾代码」需要三样东西

| 需要的能力 | 现状 | 缺什么 |
|---|---|---|
| 架构护栏 | ✅ **已落地**：G-4/B（`zelto arch check` 只读偏离报告）+ G-4/A（ADR-027：六类硬偏离做成 `policy.yaml` 的 `arch:` 段，`deny` / `ask` / `allow` 逐类可配，四处执行点全部接通） | —— |
| 契约演进检查 | ✅ **已落地**（ADR-036）：`zelto contract check` 把当前契约与**人工确认过的基线**对比，算出破坏性变化并分清方向（写入方 = 新契约不再接受旧数据；读取方 = 新数据旧程序读不懂）；基线由人显式 `zelto contract baseline` 更新；`version deliver` 把契约检查作为前置闸门 | —— |
| 跨版本回归基线 | ✅ **已落地**（ADR-036）：版本交付时记录 TAP 用例状态，与上一个已交付版本对比，检出「用例消失 / 退化成空壳 / 直接变红」三类回归；检出即阻断交付（`--accept-regression` 可显式放行） | —— |

### 6.2 G-5 展开：与 Cursor 的关系

zelto 不与 Cursor 竞争「写代码」这件事——它比不过，也不该比。
zelto 赢在**并行度 + 闸门 + 追溯**三件事上，这三件事 Cursor 都不提供。

代价是**交互成本**：当前 59 个命令（`src/cli/commands/catalog.ts` 是唯一真源），
且规划确认要通读长文档。
所以「比 Cursor 方便高效」这个目标（G6），准确说是：

> 在**规划质量**和**并行开发速度**上明显超过 Cursor，
> 在**日常交互密度**上做到不输给 Cursor。

拆开看「方便」和「高效」分别指什么：

| 维度 | Cursor 的强项 | zelto 要达到的 | 怎么比 |
|---|---|---|---|
| **高效** | 单 agent 写代码很快 | **N 个 agent 并行**写，各自隔离、互不干扰 | 一个人维护 3–5 个并发 agent，产出是 Cursor 单线的数倍 |
| **规划质量** | 有上下文，但边界靠模型自觉 | 模块边界与切片写集**结构化落盘**，可校验 | `zelto check` 冻结前拦住断链与越界写集 |
| **可控** | 跑偏要人回头看 | 越界**当场**拦下、卡住会来问人 | hook 逐写判定 + 停机分类 |
| **方便** | 对话式，几乎零学习成本 | 命令式，59 个命令有学习成本 | 日常路径要短：`next` / `suggest` / `inbox` / `ask` 一把梭 |

**G-5 是这条路上最硬的一块**。规划确认是整个驾驶舱的入口，
入口体验重，人就会绕过 zelto 直接开写——那 zelto 就没有价值了。
所以「摘要 + diff + 只看决策点」不是锦上添花，是**能不能用起来的前提**。

**G-5 已落地**（ADR-023）：`zelto require/design/plan show <id>` 给出
摘要、决策点清单（新增 / 移除 / 变更逐条标出）与相对上一版的 diff；
refine 前自动留快照，所以「改了什么」永远看得见。
`zelto pipeline status` 末尾列出待确认的草稿与下一步命令，入口不让人猜。

要达成 G6，还要继续压「日常交互密度」这条：59 个命令对一个人仍然是学习成本，
下一步的方向是把这三条规划命令接进 `next` / `suggest` 的推荐流。

## 8. 不变量

不管功能怎么加，这七条永远不破（与是否走切片流程无关）。
保留 C1–C9 编号以兼容历史引用：C6 是 C2 的依赖方向分面，C8 是 C5 的落地分面，新文档优先引用 C2 / C5。

| ID | 约束 | 说明 |
|---|---|---|
| C1 | 状态只在文件里 | 无数据库、无内存状态、无常驻 daemon；状态变更只经文件读写 |
| C2 | `core/` 核心纯洁性 | 零第三方运行时依赖（只用 Node 内置），且不得 import `adapters/`（含原 C6 的单向依赖） |
| C3 | 判定必须确定性 | `core/policy/`、`core/gate/`、`core/sched/` 不调模型、不触网；只读文件、纯计算 |
| C4 | append-only 事件流 | 每个动作都记录，不可改不可删；事件是追溯的唯一证据载体 |
| C5 | 保护域与锚点外部化 | 保护域硬编码、不可被策略规则覆盖；策略哈希锚点存于 `policy/lock.json`（含原 C8） |

| C9 | 写集预约运行时强制 | 以 PreToolUse 钩子逐写判定为主、运行后 git 审计兜底；预约缺失时 fail closed |

**约束优先于功能。** 宁可少一个功能，也不许破一条不变量。

## 9. 负向清单

以下明确**不做**，即使看起来很有价值：

- 完整 GUI（当前只有 CLI + 一个 HTML 看板）
- 一键批准 / 自动合并（签字必须由人行使；合入主干必须显式跑 `zelto merge`）
- 常驻 daemon（不引入常驻进程与内存状态）
- 自动改规格（规格改了就重新冻结，不偷偷改）
- 重造 agent 编排引擎（不自己实现 agent 循环）
- 路由自动学习

## 10. 一句话验收标准

> 一个人拿着 zelto，能独立完成一个中等规模项目：
> 先想清楚——需求、设计、模块、版本、切片，每一步都落成能校验的结构，
> 都由自己点头确认；
> 然后放手让一组 agent 并行写，各自隔离、互不干扰；
> 期间 agent 跑偏会被当场拦下，agent 卡住会来问人；
> 最后逐片签字、显式合并、整体验收、合入主干——
> **全程心里有数，代码三年后还看得懂。**
>
> 并且每一行代码都能被回答三个问题：**它来自哪条人批准的规格**、
> **它是否越界**、**它是何时、被谁批准并合入的**。

### 10.1 三条判据

按驾驶舱三段各取一条，作为「做成了没有」的检验：

| 段 | 判据 | 怎么验 |
|---|---|---|
| **规划** | 一个人能独立完成从需求到切片的全部规划，且每一步都有据可查 | 走完 `require → design → plan → version`，每次 `confirm` 前看到的是结构化摘要而不是长 markdown |
| **并行** | 3 个以上 agent 同时跑，互不干扰，产出是单线的数倍 | `version start` 拉起 N 个切片，各自 worktree，无写集冲突、无互相覆盖 |
| **拉闸** | 出错时能当场刹住，且人知道为什么、怎么接 | 越界被拒、提问被挂起、停机有分类，每一种都能一条命令接手 |

**三条同时成立，zelto 才算做成了。** 只做到「可追溯」，
那是个审计工具；只做到「能并行」，那是个调度器；只做到「能刹车」，
那是个 lint 工具。三段合起来才是一个人能用的驾驶舱。
