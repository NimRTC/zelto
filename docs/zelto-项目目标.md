## 1. 一句话

**zelto 是"人做架构、agent 干体力活、机器当刹车和交警"的三方分工系统。**

目标用户是**一个人 + 一组 agent**。zelto 的存在，是为了让一个人也能把中大型项目
做得**可控**、**可维护**、**不变成垃圾代码**——并且比直接用 Cursor 更快、更省心。

## 2. 目标是什么（以及不是什么）

### 2.1 是

| # | 目标 | 具体含义 | 怎么验收 |
|---|---|---|---|
| G1 | **规划先行** | 方案设计、版本规划、模块划分、切片设置在写代码**之前**完成，并且由人确认 | 需求→设计→计划→版本→切片，每一级都有 `confirm` 状态位 |
| G2 | **高速并行** | 规划确认后，zelto 把切片拆成互不冲突的写集，并行拉起多个 agent | 一次命令拉起 N 个 agent，各自隔离 worktree 跑 |
| G3 | **可控可刹** | 出错时能拉闸，人被交还控制权，而不是 agent 自己跑偏 | 越界写入当场被 hook 拦下；停机分类 6 类；agent 提问可挂起可回答 |
| G4 | **可追溯** | 每行代码 → 测试 → 契约 → 规格 → 人批准的意图 | `zelto trace` 打通需求到切片；切片带 `trace` 字段；append-only 事件流 |
| G5 | **长期可维护** | 合起来是一个能长期演化的项目，不是一堆能跑的补丁 | 模块边界不被破坏；契约演进有检查；版本级验收守主干健康 |

### 2.2 不是

- **不是代码生成器**。zelto 自己不写业务代码，它写的是「让 agent 安全地写代码」的那套约束。
- **不是审计器**。只做事后检查的工具在这个位置没价值——**约束必须发生在 agent 写文件的那一刻**。
- **不是自动批准器**。签字必须由人行使（AGENTS.md 禁区：「一键批准」「自动合并」）。
  签字只改状态，合入主干必须人显式跑 `zelto merge`（ADR-018）。
- **不是 GUI 产品**。当前形态是 CLI + 一个可选的 HTML 看板。完整 GUI 在负向清单里。

## 3. 核心特色：可追溯

这是 zelto 与其它 AI 编程工具**最本质的区别**，不能因为功能变多而丢掉。

其它工具的思路是「把上下文喂给模型，让模型写对」。
zelto 的思路是「把上下文变成**可判定的约束**，让越界在发生的那一刻就暴露」。

具体差别：

| 维度 | 其它 AI 编程工具 | zelto |
|---|---|---|
| 代码为什么这么写 | 靠模型记住上下文 | 追溯到一条**人批准的规格** |
| 越界怎么发现 | 事后 review，人眼看 | **运行时** hook 逐写判定，当场拦下 |
| 谁说了算 | 模型 | **人**（模型产出只是可覆盖的草稿，C7） |
| 事后能不能查 | 靠 git blame 和聊天记录 | append-only 事件流，每个动作留痕 |
| 出错时 | 模型继续跑 | 停机分类 + 拉闸交回给人 |

追溯链的完整形态：

```
需求 (require)  →  设计 (design)  →  版本计划 (plan)  →  版本 (version)
   →  切片 (slice)  →  规格 (spec)  →  测试 (acceptance)  →  代码
                              ↑
                    每个切片带 trace: { requirements, contracts, tests }
```

`zelto trace <req-id>` 打印这条链，`zelto trace <slice-id> --slice` 打印单片的追溯与事件。

**这条链上任何一个环节断开，都是 zelto 判定失败**——
门禁①（`zelto check`）查的就是它。这不是附加功能，是 zelto 存在的前提。

### 3.1 追溯靠什么落地

追溯不是文档里的一句话，它由三样东西共同保证，缺一不可：

| 环节 | 实现 | 断了会怎样 |
|---|---|---|
| **链的载体** | 切片文件的 `trace: { requirements, contracts, tests }`，外加 `traceWaiver`（豁免必须写明理由） | 门禁① 拒绝冻结 |
| **链的校验** | 门禁① 确定性检查：追溯项不得为空、契约与测试必须落到具体文件 | 切片进不了 `frozen`，也就跑不起来 |
| **链的证据** | 47 种 append-only 事件，版本级事件用 `version-<label>` 作归属键 | 事后查不到「当时谁批的、依据什么」 |

三者的分工是：**载体**存关系、**校验**在写代码前拦住断链、**证据**在事后可查。
只有载体没有校验，追溯链会随时间腐化；只有校验没有证据，出了事说不清责任。

### 3.2 追溯也是并行安全的前提

并行开发的难点不是「拉起 N 个 agent」，而是「N 个 agent 同时改一个仓库」。
zelto 的并行安全性不是靠 agent 自觉，而是靠追溯链上的三样约束：

- **写集预约**（C9）：每个切片只能写自己规格声明的路径，运行时由 hook 逐写判定
- **隔离 worktree**（ADR-011）：每个切片在独立工作目录里跑，主仓工作树不被切换分支
- **事件留痕**（C4）：每个判定、每次拒绝、每次合并都写事件

所以追溯与并行不是两件事：**能说清「这行代码从哪来」，才敢说「这行代码只碰了该碰的」。**

### 3.3 追溯链一直延伸到合并之后

追溯最容易被「合并」这一步打断：代码进主干之后，规格、测试、签字记录
都留在了分支和 worktree 里，主干上只剩一个 commit，说不清它凭什么进来。

zelto 把追溯链穿过合并这一步：

| 合并阶段 | 追溯证据 | 查得到什么 |
|---|---|---|
| 签字 | `sign.requested` / `sign.approved` 事件 | 谁批的、批的是哪一片 |
| 计划 | `merge.planned` 事件（含依赖、阶段、策略） | 按什么顺序合、为什么是这个顺序 |
| 阶段完成 | `merge.phase_complete` 事件 | 每一阶段合了哪几片、有没有冲突 |
| 冲突 | `merge.conflict` 事件（含冲突文件） | 冲突发生在哪片哪个文件 |
| 完成 | `merge.completed` 事件 | 合成了什么 commit |
| 基线过期 | `merge.stale_base` 事件 | 哪个切片的基线已经落后 |

这就是为什么「签字」与「合并」必须分成两步（ADR-018）：
**签字把批准写进事件流，合并把归并写进事件流。**
如果签字顺手把代码合进主干，事件流里就只有「批准」，
没有「合了什么、按什么顺序合、撞了哪些文件」——追溯链在这里就断了。

## 4. 三大角色的分工

| 角色 | 是谁 | 做什么 | 不做什么 |
|---|---|---|---|
| **主用户** | 开发者（一个人） | 定意图、做设计、划分模块、排版本、确认切片、**签字**、**显式合并** | 不亲手写每行代码 |
| **执行者** | agent 群（Claude Code 等） | 由 zelto 拉起，按约束包实现切片 | 不做判定、不自己批准 |
| **看守者** | **zelto** | 校验追溯、分层并行、隔离执行、门禁验收、停机分类、事件留痕、派发作业 | **不替人签字** |

关键点：**zelto 的自动化止步于「待签字」**。这是它与「全自动编程 agent」的根本分歧。

## 5. 主流程

```
                          ┌──────────────── 规划层（人主导，zelto 记录） ─────────────────┐
  一个想法 ──► require ──► design ──► plan ──► version
              需求        设计/模块     版本计划    版本 + 切片
               ▲confirm    ▲confirm     ▲confirm     ▲confirm
                          （每一次 confirm 都是人点头；未确认不往下走）
                          └───────────────────────────┬──────────────────────────────┘
                                                          ▼
                          ┌──────────────── 执行层（zelto 主导） ────────────────────────┐
                          │  版本级准备：建切片 → 写规格 → 冻结（哈希 + 事件）        │
                          │  并行准入：准入检查 → 写集解析 → 冲突检测 → 预算检查      │
                          │  隔离执行：每片一份 worktree + 一份写集预约 + 一份钩子     │
                          │  实时守卫：agent 每写一个文件 → hook 逐写判定            │
                          └───────────────────────────┬──────────────────────────────┘
                                                          ▼
                          ┌──────────────── 门禁层（机器判定） ─────────────────────────┐
                          │  写集审计 → 门禁②（验收测试）→ 自动发起签名请求          │
                          │  版本级验收（deliver 时）：主仓跑项目自己的门禁命令        │
                          └───────────────────────────┬──────────────────────────────┘
                                                          ▼
                          ┌──────────────── 交付层（人主导） ───────────────────────────┐
                          │  人签字 → 显式合并（zelto merge）→ 版本交付 → 下一个版本   │
                          └──────────────────────────────────────────────────────────┘
```

**签字 ≠ 合并**（ADR-018）：签字回答「这份改动可不可以合入主线」，
合并回答「现在就合」。前者是批准，后者是动作，所以分成两步，
而且合并这一步永远由人显式发起——zelto 不替人写主干，也不替人推远端。

**出错时的路径**（拉闸）：

```
agent 越界写入   → hook 当场拒绝 → policy.decision 事件 → 人来处理
agent 提了个问题 → 挂起该切片 → 批次里其它切片继续 → zelto answer <id> "..." → 续跑
agent 反复失败   → 停机分类 → cognitive_stuck 不可自动恢复 → zelto resume
预算耗尽        → 批次停在待签字 → 人决定加预算还是砍范围
版本验收不过    → 版本状态保持 in_progress → zelto version start <ver> --retry-failed
```

## 6. 现状与目标的差距

代码里六大能力都有对应实现，但**衔接有缺口**。这是当前最需要投入的地方。

| # | 差距 | 现状 | 目标 | 影响 |
|---|---|---|---|---|
| **G-1** | **版本内并行不认依赖** | `version start` 把版本里所有切片一次性全并行，不看切片之间的依赖 | 按依赖分层：同 phase 内并行，phase 之间串行 | 依赖 B→A 时 B 会抢跑，必然失败。**「高速」目前是伪命题**——不是跑得不够快，是并行度算错了 |
| **G-2** | **写集冲突 = 整批不跑** | 两个切片写集撞了 → 整个版本一个 agent 都不启动 | 自动把冲突切片降级为串行 / 分层 | 写集本来就来自 LLM 生成的重叠路径，整批 abort 太脆 |
| **G-3** | **没有「拉闸」这个动作** | 只有被动停机（agent 自己挂了、被 hook 拦了）；没有批次级主动刹车 | 一键暂停 → 快照现场 → 人处理 → 继续；签错可回退 | 「出错时拉闸人工确认」目前只能靠 Ctrl-C，半成品 worktree 与预约留在磁盘上 |
| **G-4** | **防垃圾代码的机制缺位** | 只管「单片有没有越界」，管不了「项目架构有没有烂掉」 | 模块依赖方向可校验；契约演进有检查；跨版本回归基线 | 这是 G5（长期可维护）的直接缺口 |
| **G-5** | **规划确认的体验重** | `require`/`design`/`plan` 每次吐一大坨 markdown，人要通读才能 confirm | 摘要 + diff + 只看决策点 | 与「比 Cursor 方便高效」这条目标直接冲突 |

### 6.1 G-4 展开：为什么「不产垃圾代码」需要三样东西

| 需要的能力 | 现状 | 缺什么 |
|---|---|---|
| 架构护栏 | zelto 自身有 C2/C6（`core/` 不依赖 `adapters/`），但**被 zelto 管理的项目没有对应机制** | `DesignDoc.modules[].dependencies` 只写在文档里，没有被编译期/门禁期检查过 |
| 契约演进检查 | `contracts/schemas/` 只在 zelto 内部用 | 管理第三方项目时，接口改坏了没有东西会发现 |
| 跨版本回归基线 | 版本级验收只跑 `gate.commands` | 没有「这个版本把上个版本的哪些行为弄坏了」的对比 |

### 6.2 G-5 展开：与 Cursor 的关系

zelto 不与 Cursor 竞争「写代码」这件事——它比不过，也不该比。
zelto 赢在**并行度 + 闸门 + 追溯**三件事上，这三件事 Cursor 都不提供。

代价是**交互成本**：当前 50+ 个命令，且规划确认要通读长文档。
所以「比 Cursor 方便高效」这个目标，准确说是：

> 在**规划质量**和**并行开发速度**上明显超过 Cursor，
> 在**日常交互密度**上做到不输给 Cursor。

要达成它，G-5（规划确认体验）必须解决。

## 7. 待决策

以下三处「规格里没写的行为」，按 AGENTS.md 的规矩**停下来问，不自己选**：

### D1 版本内切片的依赖从哪来？

现状：规格里有「前置切片」章节，`core/sched/batch.ts` 已有 `planBatchPhases()` 能做拓扑分层，
但 `version start` 完全没用它。

- **选项 A**：`version start` 改成按规格「前置切片」章节读依赖、分层并行。**不动 schema。**
- **选项 B**：把依赖提到版本计划的 `VersionSlice` 上显式声明。**要改 schema → 写 ADR。**

推荐 A：依赖信息已经存在于规格里，B 是重复表达。

### D2 写集冲突的降级策略

- **选项 A**：自动把冲突的切片串行化（拆成两个 phase），批次继续跑
- **选项 B**：让 agent 重新算写集后重试
- **选项 C**：仍然整批 abort，但给出更清晰的原因与修复建议

推荐 A：写集重叠是可预期的（都碰 `types.ts`），把它变成串行是确定性判定，符合 C3。

### D3 架构护栏怎么落地

- **选项 A**：做成 zelto 可配置的规则（policy.yaml 加 import 类规则 → **改 schema → 写 ADR**）
- **选项 B**：先只做「设计里的模块图 vs 实际 import 图」的报告（只读、不拦）
- **选项 C**：两者都做，先 B 后 A

推荐 C：B 能立刻给出可维护性报告，A 才是长期护栏。
但 A 涉及 policy 契约扩展，得先写 ADR。

## 8. 不变量

不管功能怎么加，这九条永远不破（与是否走切片流程无关）：

| ID | 约束 | 说明 |
|---|---|---|
| C1 | 状态只在文件里 | 无数据库、无内存状态、无常驻 daemon |
| C2 | `core/` 零 SDK 依赖 | 只用 Node 内置 |
| C3 | 判定必须确定性 | `core/policy/`、`core/gate/`、`core/sched/` 不调模型、不触网 |
| C4 | append-only 事件流 | 每个动作都记录，不可改不可删 |
| C5 | 约束自身在管辖范围之外 | 保护域不可被策略规则覆盖 |
| C6 | 依赖单向向下 | `core/` 不得 import `adapters/` |
| C7 | `llm/` 只产出草稿 | 永远只是可被覆盖的建议，不参与任何判定 |
| C8 | 保护域不可被策略自身覆盖 | 策略锚点外部化 |
| C9 | 写集预约运行时强制 | 由 hook 在 agent 写文件的那一刻执行，不只是提交时检查 |

**约束优先于功能。** 宁可少一个功能，也不许破一条不变量。

## 9. 负向清单

以下明确**不做**，即使看起来很有价值：

- 完整 GUI（当前只有 CLI + 一个 HTML 看板）
- 一键批准 / 自动合并（签字必须由人行使；合入主干必须显式跑 `zelto merge`）
- 常驻 daemon（不引入常驻进程与内存状态）
- 自动改规格（规格改了就重新冻结，不偷偷改）
- 重造 agent 编排引擎（不自己实现 agent 循环）
- 路由自动学习

## 10. 一句话验收标准

> 一个人拿着 zelto，能独立完成一个中等规模项目：
> 先想清楚、分好模块、排好版本，然后放手让一组 agent 并行写；
> 期间 agent 跑偏会被当场拦下，agent 卡住会来问人；
> 最后逐片签字、显式合并、整体验收、合入主干——
> **全程心里有数，代码三年后还看得懂。**
>
> 并且每一行代码都能被回答三个问题：**它来自哪条人批准的规格**、
> **它是否越界**、**它是何时、被谁批准并合入的**。
