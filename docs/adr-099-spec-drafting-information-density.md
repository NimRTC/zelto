# ADR-099：规格起草的信息量 —— 让草稿带上「需求全貌」与「模块事实」

## 状态

已接受（2026-11-23）

## 背景

### 战场数据（nimrtc-v14 实测，2026-11-21 ~ 11-22）

五片的**规格阶段**（首个事件 → `spec.frozen`）墙钟：

| 切片 | 规格阶段 | `spec.drafted` 次数 | `spec.checked` 失败轮次 |
| --- | --- | --- | --- |
| v1-audio-p2 | 8.14h | 2 | 1 |
| v1-device-policy | 14.70h | 6 | 2 |
| v1-n5-turn-server | 0.26h | 1 | 1 |
| v2-ice | 0.74h | 2 | 1 |
| v3-n4-d6-connectivity | 0.09h | 1 | 2 |
| **合计** | **23.93h** | 12 | 7 |

### 关键结论一：**慢的不是模型**

| 环节 | 实测耗时 | 占比 |
| --- | --- | --- |
| 全部 LLM 调用（10 次 spec 草稿） | **1908s ≈ 32 分钟** | **2.2%** |
| 规格阶段总墙钟 | 86144s ≈ 23.93h | 100% |
| 人在改规格与改写集 | **22.23h** | **97.8%** |

**「LLM 起草慢」这个假设不成立。** 提速的杠杆不在模型，
而在**给模型的信息量**与**报错给不给出路**。

### 关键结论二：草稿的输入**信息量极低**

实测 `zelto spec draft` 送进模型的 prompt：

| 切片 | prompt 字符数 | ≈ token |
| --- | --- | --- |
| v2-ice | 1026 | 513 |
| v1-n5-turn-server | 939 | 470 |
| v1-device-policy | 1410 | 705 |

里面只有：切片 id / 标题 / 模块名 / 写集路径 / 需求条目的**一行**正文 /
前置切片 id。

**没有任何模块事实、没有任何文件路径的来由、没有需求的验收口径。**

而人要写出一份**能判定的**规格，恰恰需要这些。

### 关键结论三：需求条目的正文被**压成一行**

需求文档里一条需求往往**散落多行** —— 主体、验收口径、测试形态、子条目。

实测 nimrtc v1.4 的 `N2`：需求文档里有 **16 行**不同描述，
而 `extractCriteria` 只装下**其中 1 行**：

```
丢掉的：
- SDP writer 发出 a=candidate:… tcp <pri> <host> <port> typ host tcptype passive
- 验收：两个只能通过 TCP 互通的 peer 选出 TCP 候选对，被选中对的 protocol 读作 "tcp"
- 测试形态：环回测试里让 UDP socket 绑到互相不可路由的地址，TCP 是唯一通路
- N2-1：TCP 在 UDP 失败之后才尝试，不是和 UDP 赛跑
```

丢的**恰恰是规格里「可判定的验收标准」最该照抄的东西** ——
验收口径（「protocol 读作 "tcp"」）与测试形态（「UDP 绑到不可路由的地址」）。

模型看不到，就只能自己编一条 —— 于是人又得回去改。
**这就是 22.23h 的去向。**

### 关键结论四：模块事实**已经在仓库里，却没被读**

已确认的设计文档（`.zelto/design/dsg-*.json`）里写着：

```json
{
  "name": "网络适配层 (ice)",
  "description": "实现ICE-over-TCP穿透、TURN-over-TLS连接管理和网络状态监测",
  "filePatterns": ["src/modules/ice/**"],
  "dependencies": ["core", "engine"]
}
```

**这正是规格需要的**：写集该落在哪、哪些模块只读参考。

而 `zelto spec draft` 这条路**根本没读设计文档** ——
模型只能凭空猜目录，或者写出一份空泛骨架。

### 关键结论五：报错**没给出路**

97% 的闸门失败是同一句：

```
规格提到「X」，但它不在写集里 —— agent 改不了它
```

人得自己判断 X 是「要改的」还是「只读参考的」——
两条修法方向**完全相反**（加写集 vs 标只读），猜错就再等几小时被打回。

## 决策

### 决策一：需求条目要给出**全部侧面**，不只主体那一行

`extractCriteria` 的返回值加一个 `aspects` 字段（`string[]`），
装这条需求在文档里的**所有**去重后的侧面。
`text` 保持向后兼容（仍是主体描述）。

**去重要保守**：只剥列表 / 勾选标记 / markdown 强调标记 / 引号风格，
**不动正文** —— 「N2：主体」与「N2 验收：口径」只差三个字，
而那正是必须区分的信息。

**子条目并入父需求**：`N2-1` 是 `N2` 的一个约束条件（不是独立需求），
必须跟着 `N2` 一起给模型看 —— 它是一条「负向」纪律
（「TCP 在 UDP 失败之后才尝试」），模型看不到就一定会实现错。

**父需求没正文但有子条目时**，主体取第一个侧面 ——
否则下游会报「找不到这一条的正文」，而明明有内容。

### 决策二：把**已确认设计**的模块事实喂进 prompt

新增 `src/llm/design-context.ts`：

- 只取**已确认**的设计（draft 状态的设计是模型草稿，人没批准，
  拿它当事实就是把「模型的猜测」升级成「输入的真相」）；
- 只取**与本片相关**的模块（模块名匹配 / 路径与写集有交集 / **依赖闭包**）；
- 模块分两种**角色**：
  - `write` —— 本片所属模块（「归的路径」就是写集该落的位置）；
  - `readonly` —— 依赖闭包里的模块（本片要**对接 / 仿照**的对象）。

**依赖闭包要算传递依赖**：设计的依赖名可能指向中间模块
（`ice` → `sdp` → `core`），只取一层的话 `core` 不会出现在只读参考里，
而它恰恰是最常被参考的那个。

模块名匹配有个细节：设计的依赖名是**短名**（`core`），
模块名是**带括号的标题**（`核心基础层 (core)`）—— 两者字面不相等，
判据要认括号里的短名。

**降级不阻断**：读不到设计就照旧走（信息少一点，不是不能干活）。

### 决策三：prompt 要把「要改的」与「只读参考的」**分开写**

规格的「范围」章节分成两段：

```markdown
## 范围

要改的（这些是 agent 会去改的文件）：
- 路径

只读参考（**不得修改**，agent 只许读）：
- 只读 路径 —— 为什么需要读它
```

**为什么必须分开**：写集是「agent 允许改动什么」的边界。
把只读参考的文件混进「要改的」那一段，等于要求 agent 去改一份
人批准的规划文档或第三方源码 —— 门禁会拦下它，但那时人已经等了几小时。

这一条同时与 ADR-098 的「只读前缀」识别对齐：
规格里写「只读 `path`」→ `parseReferencedPaths` 认它 → 不进「要改」集合。

### 决策四：验收标准要**照抄需求里的验收口径与测试形态**

prompt 里明说：需求里写「验收：……」就写成一条验收标准，
不要另编一条更容易做的。

### 决策五：报「不在写集里」时**给出两条出路**

改动在**编排层**（`core/lifecycle/freeze.ts`）而不是 CLI 侧 ——
CLI 与 Web 共用同一份判定（C3），两份说法不一致人更懵。

```
每个路径都要选一条出路（先想清楚它是「要改的」还是「只读参考的」）：
  ① 本片确实要改它 → 加进写集：zelto set <id> --field writes --value '["路径", …]'
  ② 只是拿来参考 / 仿照 → 在规格的「范围」章节写成「只读 <路径>」
两种改法方向相反，选错会被门禁打回 —— 判据：「这行代码本片会不会改？」
```

**工具不自动改写集**（ADR-098 决策五）：写集是人批准的边界（C9），
工具替人扩边界 = 追溯链上「agent 改哪些文件」这一环的批准权从人手里滑走。

## 影响面

### 判定住在 `core/` 与 `llm/`（C3 / C2）

- `core/requirements/criteria.ts` —— `extractCriteria` 加 `aspects`；
  `renderCriteriaSection` 渲染多侧面。**纯文本计算**，不调模型。
- `llm/design-context.ts`（新）—— 读已确认设计、算依赖闭包、渲染上下文。
  只依赖 `core/`，不 import `adapters/`。
- `llm/generators/slice-spec.ts` —— `SliceSpecInput` 加 `requirementAspects`
  与 `designContext`；确定性降级路径每个侧面一条验收标准。
- `llm/prompts/slice-spec.ts` —— 加 `{{DESIGN_CONTEXT}}` 段与「只读」语义要求。
- `cli/commands/slice-spec.ts` —— `buildSpecInput` 组装上述两份输入。
- `core/lifecycle/freeze.ts` —— D-4 失败时写两条出路进 `advisories`。
- `cli/commands/core-slice.ts` —— 打印 `advisories`；删掉与编排层重复的
  「写集」分支（**一份说法**）。

### 不改的地方

- **不改写集的批准权**（决策五）；
- **不改 policy 判定**（C5）；
- **不改冻结闸门的严格性** —— 只是把「要改」集合算准、给足出路；
- **不改事件类型**（`spec.checked` 的 payload 是自由对象，
  加 `advisories` 字段不需要改契约）；
- **不改追溯判据**（`trace.requirements` 的物化逻辑不变）。

## 后果

- **收益**：规格草稿的输入从 **470~705 token** 涨到 **2000~2800 字符**
  （含模块路径与依赖事实）；需求信息从「1 行」变成「4~6 个侧面」；
  闸门报错从「你有问题」变成「两条出路 + 判据」。
  按 ADR-098 实测的 22.23h 人工作业估算，这三处合计有望把规格阶段的
  **往返次数**（12 次 `spec.drafted`）压到接近**每片一次**。
- **代价**：prompt 变长（成本上升，且更容易超上下文）；
  规格起草**依赖已确认的设计**存在（没有设计时降级到旧行为）。
- **风险**：把只读参考写进「要改」段 → 冻结被拦。
  对策：prompt 明确要求分两段写；ADR-098 的「只读前缀」识别兜底。
- **不做的**：不引入自动改写集；不改 policy；不引入依赖图推导；
  不做「按改动历史增量」。

## 备选方案

**A. 让模型自己写得更长更细就行。** 否决 —— 模型不知道需求文档里
有验收口径（那部分**根本没喂给它**），写得再细也是编的。

**B. 靠提示词让模型去读需求文档 / 设计文档。** 否决 ——
`llm/` 不该有文件 IO 之外的自由探索（且模型读文件路径不可靠）；
事实该由工具**确定性地**喂进去。

**C. 工具自动把规格提到的路径加进写集，省掉人这一轮。** 否决 ——
写集是人批准的边界（C9），工具扩边界就是替人批准。

**D. 把需求文档整篇塞进 prompt。** 部分有效，但**信噪比太低** ——
需求文档里 101 条验收标准大多与本片无关。选「与本片关联的条目 + 全部侧面」
才是信噪比对的取法。

## 实现要点（踩坑备忘）

1. **`aspects` 的去重只能剥排版** —— 剥正文就把「验收口径」与「测试形态」合并了，
   回到「一条需求只给一行」的老问题。
2. **子条目要并入父需求** —— `N2-1` 是 `N2` 的约束，不是独立需求。
   但 `N2-1` 被**直接**关联时它也是独立需求 —— 两种情况不冲突。
3. **父需求没正文但有子条目**时，主体取第一个侧面 ——
   否则下游报「找不到正文」，而明明有内容（假报也是误报）。
4. **依赖名是短名、模块名带括号** —— 匹配要认括号里的短名。
5. **依赖闭包要算传递依赖** —— `ice → sdp → core`，只取一层会漏掉 `core`。
6. **报错出路写在编排层** —— CLI 与 Web 共用（C3）。CLI 侧**删掉**重复分支，
   两份说法不一致比没出路更糟。
