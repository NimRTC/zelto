# ADR-033: 切片级验收（门禁②里「这一片自己有没有被验证过」）

**状态**: 已实施
**日期**: 2026-11-07
**作者**: 系统架构
**关联约束**: C1, C2, C3, C4, C9
**关联文档**: `docs/zelto-技术架构.md`, `docs/adr-018-no-auto-merge-on-sign.md`,
`docs/adr-014-runtime-policy-enforcement.md`, `docs/adr-030-baseline-rebuild-and-arch-policy.md`

---

## 1. 摘要

门禁②（gate）原本只跑 `config.yaml` 里的 `gate.commands` —— 默认是
`pnpm test` / `pnpm lint`，也就是**全项目**命令。

后果是：agent 交回来一片半成品，只要项目里**别的**测试还绿，门禁就放行。
于是「签字 = 门禁通过」这句话，在门禁②这一环上并不成立 ——
签字只说明「项目整体没被弄坏」，不说明「这一片东西被验证过」。

本次定案：

- 门禁②**多走一步**「切片级验收」：定位本片的验收目标、真的把它跑起来、把结论记下来；
- 这一步 **fail closed**：跑不起来 = 失败，不是跳过。只有配置显式声明
  `required: false` 且本片确实没有验收目标时，才判 `skipped`；
- `skipped` 也**显式记录**（事件流 + CLI 输出）—— 静默跳过等于骗人；
- 顺手修掉一个更隐蔽的**假绿**：验收命令继承 `NODE_TEST_CONTEXT=child-v8` 时，
  `node --test` 会认为「我已经是测试子进程」，于是**跳过所有用例直接 exit 0**。

---

## 2. 为什么现在做

「可追溯是 zelto 区别于其它 AI 编程工具的本质特征」——这是本项目的立身之本。
而 ADR-032 把追溯从「建议」变成「硬闸门」之后，「追溯」这条链的最后一环暴露出缺口：

```
人批准的规格 → agent 写的代码 → 门禁判定 → 人签字
                                ↑
                    这一环只验证了「项目没坏」
                    没验证「这一片对不对」
```

门禁是签字前的最后一道闸。它放行 = 「我确认这一片是对的」，
但它实际确认的只是「我确认项目整体还是绿的」。这两句话之间的距离，
就是本 ADR 要填的。

---

## 3. 决策

### 3.1 验收目标怎么定位

切片记录里的 `acceptance.dir` 在既有代码里有两种真实形态：

- **目录**：`tests/acceptance/<id>/`（`store.create` 的默认值）
- **文件**：`tests/acceptance/<id>.test.ts`（`create --from-spec` 设的）

两种都要支持。新增 `src/core/gate/acceptance.ts` 负责定位，规则：

1. 目标路径不存在 → `验收目标不存在：<path>`
2. 目标存在但是个目录，里面**一个测试文件都没有** → `验收目录存在但里面没有测试文件：<path>`
3. TypeScript 源路径 → 先去编译产物目录（默认 `dist-test/`）找同名 `.js` 产物，
   找到就跑产物，找不到就跑源路径（让运行器去失败，并把原因说清楚）

第 2 条必须与第 1 条分开报：「目录压根没建」和「目录建了但里面没东西」
是两种不同的病，报成同一句话，人就没法判断该补测试还是该修路径。

### 3.2 目录必须展开成文件列表

`node --test <目录>` 在 Node 24 上**不展开目录**：它把目录当模块加载，
报 `Cannot find module` 直接失败。

所以目标不能停在「目录」这一层，必须落到**具体文件**。
`acceptance.ts` 自己递归展开目录，收集测试文件，规则与 node 测试运行器一致
（`test.js` / `test-foo.js` / `foo.test.js` / `foo-test.js` / `foo_test.js`，
以及任意 `test/` 目录下的文件），并**按路径排序** —— 同样的输入永远得到同样的命令（C3）。

### 3.3 命令模板

```yaml
gate:
  acceptance:
    command: "node --test {acceptance}"
    required: true
```

`{acceptance}` 占位符会被替换成**文件列表**；模板没有占位符时，文件列表作为末尾参数追加。
这样 `pnpm vitest run`、`node --test {acceptance}` 两种写法都能用。

### 3.4 fail closed

三种情况判 `failed`：

- 配了验收，但本片没有验收目标
- 命令跑不起来（spawn 失败 / 非零退出）
- 命令跑了但失败

只有一种判 `skipped`：配置显式声明 `required: false` **且**本片确实没有验收目标。

`required` 只管**有没有**，不管**结果** —— 跑了但失败的，永远是 `failed`。

### 3.5 假绿修复：`NODE_TEST_CONTEXT`

这是本次发现的最隐蔽的一个问题。

当门禁自己跑在 `node --test` 里面时（也就是在 zelto 的**测试**里跑门禁），
父进程带着 `NODE_TEST_CONTEXT=child-v8`。这个环境变量会被子进程继承。
而 `node --test` 看到它，就认为「我已经是测试运行器的子进程了」，
于是**跳过所有用例，直接 exit 0**。

于是：验收测试里的每个断言都会失败 → 但门禁看到 exit 0 → 判 `passed` → **假绿**。

修法：验收命令派生前从环境里摘掉 `NODE_TEST_CONTEXT`（`runCommand` 的
`stripTestContext` 选项）。普通门禁命令不做这个处理 —— 它们是 `pnpm test`
之类的全项目命令，本来就期望在测试环境里跑。

回归测试见 `tests/core/gate/acceptance.test.ts` 的
「验收命令不继承 NODE_TEST_CONTEXT（防止假绿）」：它先断言
`process.env.NODE_TEST_CONTEXT === 'child-v8'`（确认前置条件成立），
再跑一个**故意失败**的验收，要求门禁判 `failed`。

### 3.6 结论落到事件流

`gate.result` 事件里带上 `acceptance` 字段（状态 / 目标 / 命令 / 原因 / 退出码 / 文件列表）。

理由：追溯链要求「事后可查」（C4）。「这一片验没验、验的什么、结果是什么」
必须能从事件流里翻出来，而不是只存在于当时的终端输出里。

## 4. 约束合规检查

| 约束 | 检查 | 合规 |
|---|---|---|
| **C1** | 无新增常驻进程、无内存状态；结论落在事件流文件里 | ✅ |
| **C2** | `core/gate/acceptance.ts` 只用 `node:fs` / `node:path`，零第三方依赖，不 import `adapters/` | ✅ |
| **C3** | 定位与判定全是确定性计算（文件枚举按路径排序），不调模型、不触网 | ✅ |
| **C4** | `gate.result` 事件追加 `acceptance` 结论，只追加不改 | ✅ |
| **C9** | 本 ADR 不涉及写集预约逻辑；验收命令的越界审计照常走 | ✅ |

禁区检查：未新增自动批准、自动合并、自动改规格；未新增事件类型；
签字仍不自动合并（ADR-018 不变）。

## 5. 后果

**好的**

- 门禁②第一次真正回答「这一片自己有没有被验证过」；
- 假绿（`NODE_TEST_CONTEXT`）被修掉并有回归测试锁住；
- 「没有验收目标」和「目录里没有测试文件」报成两种不同的原因，人能对症下药。

**代价与边界**

- 配置多了一段 `gate.acceptance`（**默认关闭**）—— 不开这个功能的项目行为不变；
- 门禁多跑一个进程，开销可忽略；
- 本次仍然只是「zelto 检 zelto 自己」：能验证「验收步骤确实跑了、结论确实记下来了」，
  不能独立验证「这一片的验收目标选得对不对」——那是选目标的人的判断。

**明确不做**

- 不自动生成验收目标（人定）；
- 不自动把失败重试成成功（`required` 只管有没有）；
- 不把 `skipped` 当成 `passed`（两者在事件流里分得清清楚楚）。

---

## 6. 验收标准

1. `npm test` 全绿（1265 用例，0 失败）
2. `npm run lint` 通过
3. `tests/core/gate/acceptance.test.ts` 覆盖：定位三种结果、目录展开、命令模板、
   三种结论边界、**假绿回归**
4. `tests/core/gate/acceptance.test.ts` 的配置解析用例覆盖：
   `acceptance:` 段在 `profiles:` 之后不被吞、`acceptance` 段之后的 gate 顶层键不被误吞
5. `zelto gate` 的 CLI 输出显式打印验收结论（passed / failed / skipped 都要说）
