# zelto 下一步优化方向

> 基于 v0.7.1 交付完成后的项目状态梳理
> 更新时间：2026-11-25

---

## 概述

v0.7.1 已完成并交付（三个版本 tag 在位、事件链完整、追溯链闭合）。
下一阶段的优化方向分为三类：**核心能力补齐、开发体验改进、可维护性强化**。

---

## 第一类：核心能力补齐

### 1. 🔴 多工作区驾驶舱支持（相关：ADR-112 / ADR-114 / ADR-115）

**现状**：`zelto web` 已能按「根」扫描（ADR-112：仓库根 + 每个版本集成目录），也能把「计划 / 盘上 / 分支」三个口径并排显示（ADR-114）。剩下的缺口是**同一批次里的跨根合入进度**：一个版本分支上到底合进了哪些切片、和盘上差多少，仍要人自己对。

**优化方向**：
- 驾驶舱可同时监控**版本集成目录**（`.zelto/version-worktrees/`）内的切片状态 ✅（ADR-112）
- 切片卡住时能直观看到「卡在哪个工作树、什么原因」✅（ADR-112 分组 + 活性/停机列）
- 支持跨工作树的「当前进度总览」和「瓶颈分析」✅ 部分（ADR-114 计划对照：计划 N 片 / 盘上 M 片 / 分支上完成 B 片，并标注「N 片仅在盘上」）
- 剩余：版本分支上**已合入哪些切片**逐版列出（现在只给计数），以及「未合入的完成片」一键列出处理入口

**预期收益**：一个浏览器标签就能管整个并行批次，不用频繁 `cd` 或开多个窗口。

**涉及文件**：`src/adapters/web/api.ts`、`src/adapters/web/frontend/`

---

### 2. 🟡 高可用的拉闸机制（相关：ADR-020）

**现状**：`zelto halt` 能停机，但「停在哪」「怎么继续」的信息还不够清晰。

**优化方向**：
- 拉闸时自动保存「当前切片执行位置」快照（哪个 agent，跑到第几行提示词）
- 恢复时能**从上次卡住的地方**继续，而不用全部重跑
- 拉闸事件里记录「当时的 stderr / stdout / 最后一条消息」，便于离线复现

**预期收益**：
- 长运行任务意外中断时损失最小
- 人能更快定位问题（有现场上下文）
- 重跑次数减少 → 整体时间更短

**涉及文件**：`src/core/halt/store.ts`、`src/cli/commands/halt.ts`、`.zelto/slices/` schema

---

### 3. 🟡 规格自动分解（需求层面）

**现状**：规格由人手写，大规格容易遗漏细节或冗余。

**优化方向**：
- `zelto spec-analyze <slice-id>` 对现有规格做一次**结构化分解**
  - 提取「功能需求」「非功能需求」「边界条件」「测试场景」
  - 检测「规格承诺 vs 实现」的缝隙（见 ADR-057）
- LLM 可在 clarify 阶段自动生成「规格检查清单」（作为草稿）

**预期收益**：
- 规格质量更稳定，细节不易遗漏
- agent 有明确的「要验证哪些点」清单，不用自己推测
- 规格评审时间短

**涉及文件**：新建 `src/core/spec/analyzer.ts`、`src/cli/commands/spec-analyze.ts`

## 第二类：开发体验改进

### 4. 🟡 本地 hook 预检加速

**现状**：`git commit` 时 PreToolUse hook 需要遍历所有规格和写集，新增文件较多时会卡。

**优化方向**：
- Hook 加缓存：记录「上次扫描的文件列表 hash」，只增量检查新增/改动部分
- 并行化：一次提交里的多个文件写集检查可并行执行
- 分档：
  - 本地 `git commit` → 轻量检查（只看本次改动的文件）
  - CI 里 `git push` → 完整检查（全量写集扫描）

**预期收益**：
- 本地 commit 反应时间从秒级降到毫秒级
- 开发不用因为 hook 等待而打断思路
- CI 仍然保持完整检查的准确性

**涉及文件**：`src/hook/write-set-check.ts`、`src/core/policy/write-set.ts`

---

### 5. 🟡 更好的错误报告

**现状**：agent 失败或停机时，错误分类（10 类）准确，但人看到的信息还不够聚焦。

**优化方向**：
- `zelto stall --verbose` 显示**关键路径**：
  - 是哪一行改动触发的写集冲突
  - 是哪条 gate 命令失败的
  - 是在验收的第几个测试卡住的
- 生成「可复现的最小化用例」（如可能的话）
- 对常见错误提供**快速修复建议**

**预期收益**：
- 人定位问题的时间减少 50%
- 更多问题能自己修、不用靠 LLM 重新分析

**涉及文件**：`src/core/sched/stall.ts`、`src/cli/commands/stall.ts`

---

### 6. 🟢 命令补全和 help 优化

**现状**：`zelto help` 已有三层（v3-help-system），但 shell 补全还需手工配置。

**优化方向**：
- 生成 `zsh / bash / fish / PowerShell` 的自动补全脚本
- 补全包括：
  - 命令名（`version`, `merge`, `run` 等）
  - 子命令（`version deliver`, `version start` 等）
  - 常用标志（`--plan`, `--dry-run` 等）
  - slice id（从 `.zelto/slices/` 动态读）
- 一条命令安装：`zelto completion install`

**预期收益**：
- 熟练用户能更快敲命令
- 新手能通过补全学习命令结构

**涉及文件**：新建 `src/cli/commands/completion.ts`、`scripts/gen-completion.mjs`

## 第三类：可维护性强化

### 7. 🔴 架构 guard 自动化验证（相关：ADR-056）

**现状**：`zelto arch check` 要手跑，CI 里还没集成。

**优化方向**：
- `npm test` 或 CI 自动执行架构检查（作为验收门禁的一部分）
- 检查结果写进事件流（`architecture.checked`）
- Baseline 文件更新时自动比对新旧设计，报告「模块依赖何时变了」

**预期收益**：
- 不会无意中违反 C2/C6（`core/` 不 import `adapters/`）
- 新人清晰地看到「哪些改动改变了架构」
- 累积的架构变更历史可追溯

**涉及文件**：`src/core/arch/guard.ts`、`scripts/test.mjs`、`.zelto/design/`

---

### 8. 🟡 规格版本化与快照（相关：ADR-054）

**现状**：规格改了就改了，不保留历史版本。

**优化方向**：
- 切片开始执行时自动**快照当前规格**到 `.zelto/snapshots/slice-<id>-<run>.md`
- agent 执行完毕后对比「实际提交的规格」vs「当时快照」
  - 如果不同 → 写进事件、提醒人复核
  - 如果相同 → 确认「实现忠实于当时的需求」
- 便于「这个切片做的时候，规格是什么」的事后查询

**预期收益**：
- 规格漂移一目了然（不会有「我记得规格写的是…」的争议）
- 追溯链更完整（从规格快照 → 代码改动 → 测试通过）
- 便于复盘：「为什么当时选这个方案」

**涉及文件**：新建 `src/core/slice/snapshot.ts`、改 `src/core/slice/index.ts`

---

### 9. 🟢 事件流压缩与归档（相关：C4）

**现状**：`.zelto/events/` 随着运行次数线性增长，单个 `events.jsonl` 可能很大。

**优化方向**：
- 旧事件（>30 天）自动迁移到 `.zelto/archive/events-<date>.jsonl.gz`
- 查询时仍能跨越新旧文件（`zelto trace` 自动扫全量）
- 保留本月的事件在工作区内快速访问

**预期收益**：
- 工作区大小保持稳定（不会因为长期运行而膨胀）
- 追溯链仍然完整且可查询
- 新手不会被巨大的 events 文件吓到

**涉及文件**：`src/core/events/stream.ts`、新建 `src/core/events/archive.ts`

---

### 10. 🟡 契约演进检查强化（相关：ADR-054）

**现状**：`zelto contract check` 只检查「breaking change」。

**优化方向**：
- 增加**兼容性分析**：
  - 新增的可选字段 ✅
  - 删除的必需字段 ❌ breaking
  - 类型收窄（`string` → `enum`) ⚠️ 需评估
  - 新增的可选 API ✅
- 生成「升级指南」（如果有 breaking change）
- 对比历史 schema 版本，显示「这次改动的影响范围」

**预期收益**：
- 不会无意中破坏下游的 API 消费者
- 契约改动时有明确的风险评估
- 新 schema 版本上线前清晰知道「要通知谁」

**涉及文件**：`src/core/contract/check.ts`

### ZD-041 🔴 构建锁的「持有者已死」检测缺失

**实证（2026-11-25，nimrtc v1.4 驾驶舱联调时）**

`scripts/build-lock.mjs` 的 `acquireBuildLock()` 只用 **mtime 10 分钟**判定锁是否过期：

```js
const age = Date.now() - statSync(lockDir).mtimeMs;
if (age > staleMs) { rmSync(lockDir, { recursive: true, force: true }); continue; }
```

目录一旦由某个进程 `mkdirSync` 创建后该进程就死了，锁目录的 mtime 就**再也
不会变**——它不再代表「有人在干活」，只代表「曾经有人来过」。

**实测后果**：4 个 `test.mjs` 进程在 `21:19:51` 之后再无任何子进程（全部
0 children，即没在跑任何测试），纯粹空转在 `sleepSync(200)` 的轮询里；
它们的父 `cmd` 都还活着，所以从进程树上看不出异常。要不是有人盯着，
它们会一直等到 `timeoutMs = 15 分钟` 才抛错——而 15 分钟里工作树完全停滞。

**为什么不能只靠 mtime**：一次真实的全量测试可能跑满十几分钟，期间目录
mtime 也不变；所以「mtime 旧」既可能是死锁，也可能是长任务。判据不足。

**建议**：
- 锁目录里写 `owner.json`（`{pid, startedAt, hostname}`），抢锁前
  `process.kill(pid, 0)` 探活——ESRCH 即判死、立即接管；
- 心跳：持有者在 `fn()` 期间每 30 s 触摸一次锁目录 mtime，把「长任务
  静止」和「死锁」区分开；
- 拿不到锁时**打印持有者信息**（pid / 何时开始 / 已等多久），而不是静默轮询。

**涉及文件**：`scripts/build-lock.mjs`、`scripts/test.mjs`、`scripts/build.mjs`

### ZD-042 🟡 并发测试互抢锁，等待过程完全静默

**实证**：同一次联调里出现 4 个并行的 `npm test`（不同终端/会话），它们全都
`mkdirSync` 失败 → 空转等锁，**没有任何一行输出**（既不说「在等谁」，也不说
「等了多久」）。人看到的现象是「测试卡住了」，而不是「测试在排队」。

**建议**：
- `acquireBuildLock` 支持 `onWait(checkpoint)` 回调，`test.mjs` / `build.mjs`
  在等到 5 s / 30 s 时各打一行：`⏳ 已在等待构建锁 30s（持有者 pid 12345，
  已持有 8m12s）`；
- 同一仓库同时只允许一份测试排队（排队者发现队列 > 1 时提示「已有 N 份
  在等，建议串行化」）。

**与 ZD-041 的关系**：这是同一处机制的两个面——ZD-041 修「死锁识别」，
本条修「可见性」。可以一起做。

**涉及文件**：`scripts/build-lock.mjs`、`scripts/test.mjs`

---

### ZD-043 🟢 缺少自助诊断命令

**实证**：今晚排查上述问题时，需要的证据全部要靠手拼 PowerShell：
`Win32_Process` 找 `scripts/test.mjs` → 再看每个的 `ParentProcessId` →
看 children 是否为 0 → `mkdirSync` 试抢锁判断是否 EEXIST → 读锁目录 mtime。
这套流程重复了 5 次，且每次都要人肉判断「0 子进程 = 空转」。

**建议**：新增 `zelto doctor`（名字待定），一条命令输出：

| 检查项 | 判据 |
|---|---|
| 构建锁状态 | 存在与否 / 持有者 pid / 已持有多久 / 探活结果 |
| 在跑的测试/构建进程 | pid / 启动时间 / **是否有子进程** / 是否在等锁 |
| 依赖完整性 | junction 是否悬空（`ensure-deps.mjs` 已会修，这里只报告） |
| 工作树状态 | 是否有未解决冲突 / 是否有 `.tmp` 残骸 / 是否有中间态索引 |
| 事件链 | 各流的 `verifyChain` 三态汇总（ADR-105） |

**为什么值得做**：这些证据**全部是确定性可读的**（C1/C3 的纯计算），
没有一条需要模型。写成一个命令，等于把今晚这张排查表固化下来。

**涉及文件**：新建 `src/cli/commands/doctor.ts`、`src/core/health/`

## 决策记录

### 为什么不先做 "GUI 完整化"

**原因**（见 AGENTS.md 负向清单）：
- 完整 GUI（多窗格、编辑器、插件系统）不在范畴
- 当前形态（CLI + Web 驾驶舱）已足够驱动工作流
- 过早的 GUI 铺装会削弱 CLI 的快速迭代

### 为什么不先做 "性能优化"

**原因**：
- 当前性能瓶颈主要在 I/O（文件读写）和 LLM 调用，不在 zelto 本身
- Hook 预检加速（#4）是优化项，但不影响核心功能
- 等到 v0.8.0 核心稳定后，性能优化的 ROI 会更高

### 为什么优先做 "多工作区驾驶舱" 而不是 "GUI 完整化"

**原因**：
- 多工作区是当前**真实痛点**：已有 N 个 agent 并行跑，需要中央观测
- 完整 GUI 是**未来方向**，不是当前阻塞
- 优先解决真实痛点，才能快速验证产品方向
