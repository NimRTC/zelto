# ADR-038: 接管既有项目的三道闸门（可接管、可追溯、确认前预演）

**状态**: 已实施
**日期**: 2026-11-08
**作者**: 系统架构
**关联约束**: C1, C2, C3, C4, C5, C7
**关联文档**: `docs/adr-032-trace-judgment-enforcement.md`, `docs/adr-034-spec-generation-and-confirmation.md`,
`docs/zelto-项目目标.md`, `src/core/project/initializer.ts`, `src/core/project/scanner.ts`,
`src/core/project/baseline.ts`, `src/cli/commands/slice-spec.ts`, `src/cli/commands/panoramic-project.ts`

---

## 1. 摘要

zelto 对外的头号场景是「接管一个既有项目」。这条路径此前有三处断链，
每一处都会让人在**第一次真正用 zelto** 时撞墙：

| 断链 | 症状 | 本次处置 |
|---|---|---|
| **① `project init` 静默失败** | 人先跑 `zelto init`（建目录）再跑 `project init`（接管），后者看到 `.zelto/` 已存在就跳过 —— 门禁命令还是通用的 `pnpm test`，写集规则也没按实际模块生成 | 接管改为**按内容判定**：zelto 生成且未被改过的文件按真实探测结果重建，人手写的一个字不动 |
| **② 追溯链没有起点** | 接管之后一片基线切片都没有 —— 追溯链从「现状」开始才有意义，后续切片才知道该对齐哪块写集 | `project init` 生成**基线切片**（确定性、不依赖 LLM），状态直接 `completed` |
| **③ `spec confirm` 确认废规格** | 草稿里没有可物化的需求条目，确认之后 `freeze` 必被追溯闸门拒掉 —— 人被引导确认一份注定不能用的规格，然后卡在下一步 | 拦在「确认」这一道：确认前用**冻结准入的同一个判据**预演 |

三件事共用一条主线：**判定必须确定性，且要拦在「人还能改内容的最后那一刻」。**

---

## 2. 为什么现在做

这三处不是新功能，是**主路径上的洞**。此前没有暴露，是因为 zelto 一直是被
「先自己写规格、再开跑」的方式使用（99 个切片全部 `completed`，
`run.started` 只有 5 次）—— 接管既有项目这条对外主场景从未被真正走通过。

走一遍就全撞上了：

```
zelto init          →  .zelto/ 建好，config.yaml 写死通用命令
zelto project init  →  "Already initialized"（什么都没接管）
zelto project design→  要 LLM，没配就卡住
```

于是「接管既有项目」在没配 LLM 的机器上**完全走不通**。

---

## 3. 决策

### 3.1 接管的判据：内容哈希，不是「文件存在」

旧实现只问「文件在不在」。在不在，回答不了「能不能改」：

- zelto 自己生成的 → **可以安全更新**（接管就该用真实探测结果）
- 人手写的 → **必须尊重**，一个字都不改

怎么区分？生成时把**生成内容的哈希**记进文件里：

```yaml
# zelto project configuration
# Auto-generated for "demo"
# zelto:generated:6d9b8bebf00edea6
```

接管时重新算一遍当前内容（去掉标记行）的哈希，与记录的比对：

- 一致 → 文件还是 zelto 留下的原样 → **重建**（用真实探测结果）
- 不一致 → 人动过了 → **一个字都不动**，并明确告诉人「门禁命令与写集规则请自行核对」

**为什么不能只写「这里是 zelto 生成的」这种标记**：人在 zelto 生成的文件上加一条
自己的规则后，标记还在，但内容已经是人写的了 —— 按标记判断会覆盖掉人的规则。
哈希比对才能真正区分这两种情况。

**哈希口径**：算的是**去掉标记行之后的正文**。标记行自己不能参与自己的哈希
（否则成了自指：标记里记的哈希会因为标记本身的存在而对不上）。
摘掉与插回都按**整行/下标**处理，不能按子串或行的值处理 ——
正文里恰好含有这串文本的行会被误伤（按值过滤还会把内容相同的其它行一起删掉，
导致「没被人改过」被误判成「人改过」）。

**契约面变化**：`config.yaml` 与 `policy/policy.yaml` 多了一行注释标记。
不影响解析（`parseConfigYaml` 跳过 `#` 开头的行），但**确实是文件格式的变化**，
所以本文档就是它的 ADR。

### 3.2 基线切片：追溯链的起点，不依赖 LLM

接管既有项目的第一步不是「写新代码」，而是「把现有代码登记进来」——
否则追溯链没有起点，后续切片无从对齐写集。

基线切片表达的东西很简单：**这个模块现在有哪些文件**。
这个信息 `project scan` 已经拿到了（`ProjectMap.modules[].files`），
是确定性的事实，不需要模型猜。让它依赖 LLM，只会让「接管既有项目」
在没配 LLM 的机器上直接走不通 —— 那是本次要修的东西，不是要加的东西。

基线切片的语义：

- 状态直接 `completed` —— 它不是待办的活，是既成事实；
- `trace.requirements = ['(v0 baseline)']` —— 追溯链的起点是「现状」；
- `traceWaiver` 说明它为什么不需要契约追踪；
- 写集覆盖该模块的**全部文件**（用具体文件而不是目录通配）——
  它标的是「这一片涵盖哪些既有文件」，用 `src/**` 会把整个 src 都算进来。

**只有叶子模块成为基线切片**：父模块的写集是子模块写集的并集，
两边都建会造成写集重叠（并行调度会据此把它们判成冲突，白白降级成串行）。

**zelto 自己的治理目录不进基线切片**：`policy/` 与 `specs/` 是 zelto 的运行时产物，
不是被接管的业务代码。若把它们扫成模块：

- 基线切片会给它们开一片 `v0-policy`，把**保护域登记成可写模块** ——
  追溯链从此说「`policy/policy.yaml` 是某片的写集」，与 C5 直接冲突；
- `policy.yaml` 会给它们生成一条 `allow-write policy/**` 规则，
  与同一文件里的 `protect-policy`（deny）自相矛盾。

所以扫描器在**根层**排除这两个目录；根层之外的同名目录
（`src/core/policy/` 之类）是业务代码，不受影响。

### 3.3 `spec confirm`：确认前预演追溯物化

拦住它的时机应该在「确认」：确认是「人批准这份规格」的瞬间，
也是最后一道能改内容的瞬间。过了这道门，规格就是「人批准的出处」，不该再拒。

判据**复用冻结准入的同一个函数**（`evaluateFreezeTrace`）——
两处各判一套的话，人会遇到「confirm 说行、freeze 说不行」。

拦下时要说清楚三条出路（否则人只看到「拒绝」，不知道怎么继续）：

1. 在「## 验收标准」下写编号条目 → 自动物化成需求追溯；
2. `zelto set <id> --field trace.requirements --value "<需求引用>"`；
3. `zelto set <id> --field traceWaiver --value "<理由>"`。

**契约面变化**：`spec confirm` 在「追溯无法物化」时返回退出码 1 且不写正式规格。
事件类型不变（仍用 `draft.confirmed`，只是不再为被拒的确认写事件）。

## 4. 被否决的方案

**方案一：`project init` 见到已存在的文件就跳过（当前行为）。**
否决理由：接管的意义就是「按真实情况更新」。旧行为让接管静默失败，
人以为接管成了，实际门禁命令还是通用的 `pnpm test` —— 在 npm 项目或
Rust 项目上是错的，等于「配了但不生效」（ADR-027 之后要避免的那种病）。

**方案二：用文件修改时间判断「人改过没有」。**
否决理由：mtime 不可靠 —— `git checkout`、备份恢复、`touch` 都会改它；
而且它说不清「改了哪部分」。内容哈希是唯一可判定的口径（C3）。

**方案三：接管时直接覆盖 config.yaml / policy.yaml，不问来源。**
否决理由：`policy.yaml` 是**保护域的真源**（C5）。覆盖它等于 zelto 单方面
改写了「按什么标准拦的」，事后审计说不清当时的标准是什么。

**方案四：基线切片走 `project design`（需要 LLM）生成。**
否决理由：那正是「接管既有项目走不通」的根因。基线要表达的是
「这个模块现在有哪些文件」——扫描已经拿到了这个事实，引入模型只会增加
不确定性而不增加信息。

**方案五：基线切片状态设为 `draft`，让人去逐片签字。**
否决理由：基线切片描述的是**既成事实**，不是待办的活。
它是追溯链的起点，不需要「人批准」（人批准的是「接下来要做什么」）。
设成 `completed` 与它的事实属性一致。

**方案六：在 `freeze` 时才拦（现状），confirm 不拦。**
否决理由：那样人被引导确认一份废规格，然后卡在下一步，还不知道问题出在哪。
拦在确认这一道，人还来得及改内容 —— 这是「最后能改内容的瞬间」。

## 5. 影响与迁移

**破坏性变更**：

1. `zelto project init` 现在会**创建基线切片**（`.zelto/slices/v0-*.json`
   与 `specs/slices/v0-*.md`）。既有项目重新接管会多出这些切片。
2. `zelto spec confirm` 在追溯无法物化时**返回退出码 1**，此前总是成功。
   依赖「confirm 一定成功」的脚本会失败 —— 这是刻意的：此前确认的是废规格。
3. 生成的 `config.yaml` / `policy.yaml` 多了一行 `# zelto:generated:<hash>`。
   人手写的同名文件不受影响（没有标记行 → 不动）。

**契约面变化**：

- 事件类型集合**没变**（沿用 `draft.created` / `draft.confirmed`）；
- `contracts/schemas/**` **没变**；
- 切片状态机**没变**；
- **变的是**：`.zelto/config.yaml` 与 `policy/policy.yaml` 的生成格式多一行标记；
  `spec confirm` 的退出码语义变了。

**没有改的东西**：`core/` 的零依赖与依赖方向、门禁①的追溯判定、
ADR-033 的切片级验收定位逻辑、policy 的保护域定义。

## 6. 约束合规检查

| 约束 | 检查 | 合规 |
|---|---|---|
| **C1** | 状态仍只在文件里：基线切片在 `.zelto/slices/*.json`、规格在 `specs/slices/*.md`、`.gitignore` 追加 `.zelto/`；未新增内存状态或常驻进程 | ✅ |
| **C2** | `core/project/baseline.ts` 只 import Node 内置与同目录 types；`core/project/initializer.ts` 用 Node 内置 `crypto` 算哈希，未加任何第三方依赖 | ✅ |
| **C3** | 接管判定、基线切片生成、确认前预演全是**纯文件判定 + 纯计算**：不调模型、不触网 | ✅ |
| **C4** | 基线切片的创建经 `SliceStore.write`（写切片状态文件）；`spec confirm` 沿用既有 `draft.confirmed` 事件；本次未新增事件类型 | ✅ |
| **C5** | 保护域（`PROTECTED_PATTERNS`）**完全未动**；人手写的 `policy.yaml` 接管时逐字不动；zelto 自己的治理目录不再被登记成可写模块 | ✅ |
| **C7** | 基线切片生成不经过任何模型（确定性）；`spec confirm` 拦的是「人批准的出处缺失」，不涉及模型产出 | ✅ |
| **C9** | 写集预约与逐写判定完全未动；本次只改了「基线切片的写集内容」，未动判定机制 | ✅ |

禁区检查：未新增自动批准、自动合并、自动改规格。
`project init` 生成基线切片是**登记既成事实**（状态直接 `completed`、
写明豁免理由、留规格文件），不是替人批准待办的活。

## 7. 验证方式

新增单元测试 `tests/project-takeover.test.ts`（12 个用例）：

- **接管判定**：生成的 config 带标记行；探测结果变化后 config 被重建
  （`pnpm test` → `vitest run`）；人改过的 config 逐字不变且被标为「跳过」；
  人手写的 policy 逐字不变；`.gitignore` 补上 `.zelto/`。
- **基线切片**：`src/core` 成为一片基线切片且写集覆盖该模块文件；
  `policy/`、`specs/` **不进**基线切片、写集里不出现保护域路径；
  切片 id 合法不重名；CLI `project init` 生成基线切片且状态 `completed`。
- **确认前预演**：无需求时 `confirm` 退出码 1 且正式规格不落盘；
  有需求时通过且与草稿逐字一致；草稿补编号验收标准后 confirm 与 freeze 都通过。

端到端实测（临时项目，非本仓）：
`zelto init` → `project scan` → `project init` 生成 2 片基线切片；
人改过的 config 显示「人手写的，未改动」；`policy.yaml` 不再出现
`allow-write policy/**` 规则。

全量 `pnpm build` + `pnpm test` + `pnpm lint` 全绿。

## 8. 遗留（需人拍板）

**基线切片的写集用具体文件还是目录通配。**
本次用具体文件（`src/core/a.ts`），理由是基线要精确标「这一片涵盖哪些既有文件」；
但这也意味着：**基线切片建好之后，往该模块新增文件不再属于基线写集**。
若人认为「模块目录级的写集」更合适（新增文件自动落在基线范围内），
需要改 `planBaselineSlices` 的写集口径 —— 这会让基线与后续切片的写集重叠，
并行调度会据此降级成串行（见 §3.2 的叶子模块取舍）。本次未动，留给下一次决定。
