# ADR-104：签字判据要认「门禁跑的是不是本片」—— 收窄门禁的证据闭环

**状态**: 已实现（2026-11-24）
**日期**: 2026-11-24
**作者**: 系统架构
**关联约束**: C1, C3, C4
**关联文档**: `docs/adr-097-gate-scope-by-write-set.md`、
`docs/实战缺陷记录-nimrtc-v14.md`（§ZD-030 剩余问题 ②）

---

## 1. 摘要

ADR-097 让门禁能按写集**收窄**跑哪些用例（实测：`v2-ice` 从 2387 个用例
降到 ~200 个）。收窄这件事在**事件里留了痕**（`scoped` / `scopeLabels` /
`scopeTestCount` / `scopeTotalTestCount`）。

但**签字判据没认这些字段**。

`core/sign-review/evaluate.ts` 的第②项「验收真跑过本片」只看
`acceptanceRan` / `acceptancePassed` —— **看不出这轮跑的是不是本片相关的用例**。

于是收窄之后出现一种**看似合理、实则没闭环**的状态：

- 门禁按写集收窄，只跑了 200 个与本片相关的用例，全绿；
- 签字复查四项确认全过，显示「验收通过 200/200」；
- 但**没有任何一处证据说明「这 200 个就是本片该验的那些」**。

这不是「多跑或少跑」的问题，是**追溯链断在签字这一环**：
zelto 的核心价值主张是「agent 的每一行代码都能追溯到一条人批准的规格」，
而「本片该验的用例真的被验了」是这条链上**签字前的最后一节**。

本 ADR 把它接上。

---

## 2. 动机

### 2.1 现在的判据链路

```
gate.executed / gate.result 事件
    ↓ collectGateFacts()          ← 只取 passed / acceptance / results[]
SignReviewFacts.gate
    ↓ evaluateAcceptanceCheck()  ← 只判 ran && passed
「验收真跑过本片」 ✓
```

作用域字段（`scoped` / `scopeLabels` / `scopeTestCount` /
`scopeTotalTestCount`）在**事件里有、在事实层没有、在判定层更没有**。

### 2.2 为什么「跑过了」不等于「验过本片」

ADR-097 决策里写得很清楚：收窄**不可用时一律退回全量**（宁可慢，不漏验），
且「标签一个都没匹配到」必须**判失败**（假绿防线）。

也就是说：**收窄的每一条路径都已经在门禁侧 fail closed 了**。
门禁过了，**意味着**「跑的是本片相关的用例」（要么收窄成功，
要么退回全量 —— 全量当然也覆盖本片）。

**所以「门禁过了」这句结论本身是成立的。** 缺的是**证据的可见性**：
人签字时看到「验收通过」，但看不到「验的是哪 200 个 / 为什么是这 200 个」。

这不是「判定错了」，是**判定对了但说不清**。

而「说不清」在签字这一环有实际后果：

| 现状 | 后果 |
|---|---|
| 人看到「验收通过 200/200」 | 以为跑了全量 2387 个里的 200 个 |
| 实际是 | 按写集匹配出的 200 个，而**匹配规则是人自己配的** |
| 规则配窄了 | 本片该验的用例没被验 → **静默漏验** |

**规则是人配的**（`gate.scope` 在 `config.yaml` 里），
所以「规则配窄了」是一个**真实存在的**失败模式——
而现在签字复查**没有任何一处能看出规则配得对不对**。

### 2.3 缺的是「可核对」，不是「更严」

关键判断：**这一项不该变成「更严的闸门」**。

如果把「收窄了但说不清验的是哪些」判成**不通过**，
那么每个配了 `gate.scope` 的项目都会签不了字 —— 而门禁侧已经 fail closed 了，
签字侧再 fail closed 一次是**重复**，且没有新信息。

正确的做法是：**把作用域事实接进签字复查的呈现层**，
让人**看得见**「这轮验的是哪一组用例、依据是什么规则」，
并让签字复查在**收窄发生过**时明确标注出来。

判据本身仍然由门禁承担（它已经承担了）。

## 3. 决策

### 决策一：事实层加 `scope` 段，只采**事件里已有的**字段

`SignReviewFacts.gate` 增：

```ts
/** 门禁作用域事实（ADR-097 决策五） */
scope: {
  /** 这轮是不是收窄跑的 */
  scoped: boolean;
  /** 按哪些标签收窄的 */
  labels: string[];
  /** 收窄后实际跑的用例数（没收窄或没枚举时为 null） */
  testCount: number | null;
  /** 全量有多少个用例（对比用） */
  totalTestCount: number | null;
  /** 为什么收窄 / 为什么没收窄 */
  source: 'config' | 'fallback-full' | 'no-config';
  /** 人话说明 */
  reason: string;
};
```

来源是 `gate.result` 事件 payload —— **已经在那里了**（ADR-097 决策五
「留痕」），本决策只是把它**读出来**。

**老事件兼容**：老事件的 `gate.result` 没有这些字段 →
按「没收窄」处理（`scoped: false`, `source: 'no-config'`）。
**为什么这样降级是安全的**：老事件是**收窄功能上线之前**写的，
那时的门禁**必然跑的是全量** —— 「全量」永远覆盖本片。

### 决策二：第②项确认的**佐证文案**要带上作用域

第②项「验收真跑过本片」的 `ok` 判据**不变**（仍是 `ran && passed`）。
变的是**佐证文案**：

| 情形 | 佐证 |
|---|---|
| 没收窄 | `gate.result 事件记录了 acceptance 通过（200/200）`（不变） |
| 收窄了 | `acceptance 通过（200/200）· 按写集收窄跑的（标签 ice、sdp；全量 2387 个里选了 200 个）` |

**为什么只改文案不改判据**：见 §2.3 —— 门禁侧已经 fail closed，
签字侧再判一次是重复。而且**判据加严会让每个配了 `gate.scope` 的项目签不了字**。

### 决策三：呈现层新增一段「门禁作用域」，让人**看得见收窄**

`renderSignReview` 的「验收（门禁②）」段下面加一行：

```
  ✓ 42/42 passed · 按写集收窄跑的（标签 ice）· 全量 2387 个里选了 42 个
```

**为什么要有这一段**：签字是**人**的动作。人需要在签字前知道
「这轮门禁跑的是不是全量」。收窄是**工具的判断**（规则是人配的），
人签字时看不到它 = 人在**不知情**的情况下批准。

这与 ADR-097 决策五「`--full` 是人的出口」是同一件事的两面：
**工具的判断必须对人可见**，人才有「按全量重跑」的机会。

### 决策四：收窄**配得对不对**，靠事件里的 `scopeReason` 与 `scopeLabels` 自证

「规则配窄了漏验本片」这个失败模式，**签字侧不该自己判** ——
判据在**门禁侧**（收窄时用的标签来自 `config.yaml` 的规则，
规则与写集的匹配关系在 `resolveScope` 里已经算过）。

签字侧做的是**呈现**：
- `scopeLabels` → 「按哪些标签收窄的」；
- `scopeTestCount` / `scopeTotalTestCount` → 「全量 N 个里选了 M 个」；
- `scopeReason`（没收窄时）→ 「为什么退回全量」。

人看到「全量 2387 个里选了 42 个」而本片显然不止 42 个用例时，
**他有足够的信息**去查 `config.yaml` 的 `gate.scope` 规则。

**为什么不加一个「收窄比例过大 → 警告」的自动判据**：
比例大小与本片复杂度**无关**（有的片就只碰一个模块），
一个固定的阈值必然误报。**人看数字 + 人看规则**比**阈值**可靠。

### 决策五：**不**加新的事件类型，不改 schema

作用域字段**已经在** `gate.result` / `gate.executed` 的 payload 里
（ADR-097 决策五）。本决策只是**读取**它们。

→ **不改 `contracts/schemas/event-envelope.json`**，
不改事件类型词汇表，不写新事件。

### 决策六：CLI 与 Web 共用同一份

事实收集在 `core/sign-review/collect.ts`（CLI 与 Web 共用，ADR-072 §5.1），
判定在 `core/sign-review/evaluate.ts`（共用），
呈现分两处（`src/cli/sign-review/render.ts` 与 Web 前端）。

**判据与事实必须共用**（D-11 教训：合并的两条路径判据不一致）。
呈现可以各有一份（CLI 是文本，Web 是 HTML），但**内容必须同源**
—— 都从 `facts.gate.scope` 渲染。

## 4. 影响面

### `src/core/sign-review/types.ts`

- `SignReviewFacts.gate` 增 `scope` 段（§决策一）。
- **只加字段，不改已有字段** —— 老消费者（Web 前端、forge）
  读已有字段时不受影响。

### `src/core/sign-review/collect.ts`

- `collectGateFacts` 从 `gate.result` payload 采作用域字段。
- 老事件（无字段）→ 按「没收窄」降级（§决策一）。

### `src/core/sign-review/evaluate.ts`

- 第②项的**佐证文案**带作用域（§决策二）。
- **判据不变**。

### `src/cli/sign-review/render.ts` + Web 前端

- 验收段加一行作用域说明（§决策三）。

### 不改的地方

- 不改 `evaluateSignApprovalGate`（拦不拦还是那四项，§2.3）；
- 不改 `contracts/schemas/*`（§决策五）；
- 不改门禁侧任何判定（收窄的 fail closed 已经在那儿了）；
- 不改写集的批准权（ADR-098 决策五）。

## 5. 后果

### 收益

- 签字复查**看得见**「这轮跑的是不是本片相关的用例」——
  收窄不再是一个**只在事件里、用户看不见**的内部决策；
- 「规则配窄了漏验本片」这个失败模式**变得可发现**：
  人签字前能看到「全量 2387 个里选了 42 个」；
- 与 ADR-097 决策五的 `--full`（人的出口）形成闭环：
  **看得见收窄 → 才有「按全量重跑」这个动作**。

### 代价

- `SignReviewFacts` 多一个字段段 —— **加字段不改字段**，
  消费者向后兼容；
- CLI 与 Web 的呈现各改一处（内容同源）。

### 风险

1. **误以为「收窄 = 少验了」** → 呈现文案必须说清
   「收窄的是**与本片无关**的用例」，而不是只报数字；
2. **老事件降级成「没收窄」** → 这是**安全**的降级
   （§决策一：老事件必然是全量）；
3. **人忽略这个信息** → 呈现放在验收段**紧邻**结论处，
   不单独开一段（那会让人以为它是另一件事）。

## 6. 备选方案

### A. 加「收窄比例过大 → 签字不通过」的自动判据 —— **否决**

比例与本片复杂度无关，固定阈值必然误报。
**人看数字 + 人看规则**比阈值可靠（§决策四）。

### B. 把「验收真跑过本片」的判据改成「ran && passed && (未收窄 || 收窄信息完整)」—— **否决**

收窄信息完整**已经在门禁侧 fail closed** 了（标签没匹配到用例 → 判失败）。
签字侧再判一次是重复，且会让**老事件**（无作用域字段）签名失败 ——
老事件是全量跑的，全量当然完整。

### C. 在 `gate.result` 里新增一个「本片用例清单」字段 —— **否决（本次）**

更彻底（签字能直接列出「本片该验的用例」），但：
- 要在门禁侧维护「本片该验什么」的集合 —— **那是项目侧的知识**
  （ADR-097 决策二：工具不推导，工具不猜）；
- 且清单可能很大（200 个用例名进事件 payload）。

**什么时候值得做**：等项目侧显式声明「模块 → 用例」的映射之后
（ZD-030 剩余问题① 已记：nimrtc 侧还没给用例打标签）。
在那之前，`scopeLabels` + 计数 + 原因**已经足够**让人核对。

### D. 什么都不做 —— **否决**

收窄已经上线（ADR-097），签字侧不认 = 追溯链在签字这一环断开。
「工具具备能力但判据没闭环」是本 ADR 存在的全部理由。

## 7. 实现要点（踩坑备忘）

1. **老事件必须能读** —— `gate.result` payload 的作用域字段是
   **可选**的（ADR-097 决策五就是这么留痕的）。收集层要用
   `?? 默认值` 收敛，**不能**假设字段存在。

2. **`scopeTestCount` 与 `scopeTotalTestCount` 都可能是 `null`** ——
   没收窄、或枚举失败时都是 null。呈现时不能拼出「null 个」。

3. **「全量 N 个里选了 M 个」这个句式只在两个数都在时才有意义** ——
   只有一个时退化成「按写集收窄跑的（标签 ice）」。

4. **标签列表要排序后显示** —— `scopeLabels` 的顺序来自规则匹配顺序，
   而**规则顺序会变**（人改 `config.yaml`）。
   判据不受影响，但**呈现要稳定**（同一组标签两次签字显示成同一个字符串），
   否则「事件里记的和这次显示的不一样」会让人以为出了 bug。

5. **不要在 Web 侧另写一套判据** —— 事实与判定共用 core 的那一份
   （D-11 教训）。Web 呈现可以不同，但**数字与文案必须同源**。
