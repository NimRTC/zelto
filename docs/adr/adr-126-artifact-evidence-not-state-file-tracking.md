# ADR-126 「这版做完没有」要看**产物**在不在分支上，不能看状态文件在不在

- 状态：实施（core 判据 + API + 驾驶舱界面均已落地）
- 日期：2026-11-26
- 关联：ADR-114（分支可见性）、ADR-112（驾驶舱按根扫描）、ADR-121（版本上下文归属 fail-closed）、ADR-056（版本分支归属）

## 背景

实测 nimrtc-v14（2026-11-26）驾驶舱「版本计划」表：

| 版本 | 计划片数 | 盘上有片 | 盘上完成 | **分支上完成** | 分支 |
|---|---|---|---|---|---|
| v1 | 11 | 11 | 11 | **0** | version/v1 |
| v2 | 1  | 1  | 1  | **0** | version/v2 |
| v3 | 14 | 14 | 14 | **0** | version/v3 |
| v4 | 3  | 3  | 3  | **0** | version/v4 |

「分支上完成」**恒为 0**，而且给出的结论是**错的**：

> 「盘上完成 11 / 分支上完成 0」读起来像「v1 版的产物一片都没进分支」。

真相恰好相反 —— 产物**就在**分支上。

### 为什么那列恒为 0

ADR-114 那一列判的是：**切片的状态文件**（`.zelto/slices/<id>.json`）
是否已被提交进所属分支的 git 跟踪。

但 ADR-121 定了「不给 `.zelto/slices/` 进版本控制」，而 `.zelto/` 整体在
`.gitignore` 里 —— 状态文件**永远不会**进版本分支。这不是某个版本的意外，
是**结构性**的：判据问的东西按设计就不可能为真。

于是这列：

1. **没有信息量** —— 所有版本、所有项目都是 0；
2. **给出误导性结论** —— 它把「状态文件没进 git」说成了「这版没做完」；
3. **占着一个看起来最权威的位置** —— 它叫「分支上完成」，
   在「盘上完成」旁边，读者一定会把它当成完成度的另一种量法。

### 事实上产物一直在分支上

按 AGENTS.md 的提交约定（`Refs-Slice: <id>` trailer）实测 nimrtc-v14：

```
version/v1 => 4 片    version/v2 => 5 片
version/v3 => 21 片   version/v4 => 25 片
```

（对照：计划里 v1 有 11 片、v3 有 14 片 —— 差额是**归属错位**与**未合**，
见 ADR-127。这是两回事，不混在这一列里说。）

## 决策

### 一、产物证据 = 该切片 id 在**所属版本分支**上出现过 `Refs-Slice:` 提交

新增 `core/project/artifact-evidence.ts`，判据：

```
artifactOnBranch = true   这一片在所属版本的分支上出现过 Refs-Slice trailer
artifactOnBranch = false  分支上查不到
artifactOnBranch = null   拿不到证据（不是 git 仓库 / 分支不存在）
```

**为什么用 trailer 而不是「提交改了哪些文件」**：

- trailer 是**显式声明** —— 「这个提交属于哪一片」由提交者写明，
  不靠猜文件路径（写集之外的改动会污染文件推断）；
- 一个片可能有多个提交（实现 + 测试 + 文档 + 验收）—— trailer 相同，
  「这一片在分支上」= 分支历史里出现过这个 trailer；
- 它**不依赖 `.zelto/` 是否进 git** —— 正好绕开上面那个死结。

### 二、问的是「**所属版本**的分支」，不是「哪个分支上有就在哪」

所属分支从版本计划算（ADR-121 的归属解析，`branchOfVersion`）。

**为什么不能「哪儿有算哪儿」**：那会把**归属错位**藏起来。
若 v1 的片落到了 v3 的分支上，「哪儿有算哪儿」会让驾驶舱说「完成」，
而版本计划里那一版仍然是空的 —— 错位就再也看不见了。

查所属分支查不到，就是 `false`：那是**事实**（归属错位或还没合），
前端只把事实摆出来，不下结论（ADR-114 决策二的精神）。

### 三、ADR-114 那列**保留**，但改名为「状态文件进分支」

它是事实，只是它恒为 0，且现在诚实地说自己是 0 而不是冒充「完成度」。
删掉它会丢掉 ADR-114 已经建立的事实链（切片级的「分支证据」徽标同）。

### 四、三态口径不变

`null`（拿不到证据）≠ `false`（查到了，没有）——
这是 ADR-081 / ADR-114 一直守的口径，本 ADR 沿用。

### 五（r2，同日实测补正）：栈式版本必须并排给「随祖先版本并入」

nimrtc-v14 的版本是**栈式**的（v3 从 v2 切、v2 从 v1 切）。按「所属分支上」的判据，
v2/v3 **永远不会**有 v1 片的 trailer 提交 —— 实测 v3：本版命中 **1** 片，
祖先分支上另有 **20** 片。只报「本版 0/21」会把「这版没做」当成结论。

所以每行多两列（不合成、不改上面的判据）：

| 列 | 含义 |
|---|---|
| `artifactOnBranch` | 这一片**自己的** Refs-Slice 提交在所属分支上（祖先带来的不算） |
| `artifactOnAncestor` | 不在本版分支、但在**祖先版本分支**（本地 `version/*` 中属于本分支祖先的）上 |

「祖先带来的不算」按**提交**判：同一 id 的首个命中提交若已在祖先分支历史里，
就只算 `artifactOnAncestor`（不用 `git log --not` 排除 —— 那会让「本版提交比祖先提交旧」
的 id 落到祖先去，把归属错位藏起来）。

界面：计划表两列（「本版分支有产物」/「随祖先版本并入」），差的片单独标
「两边都查不到」；切片徽标三态改为「有产物 / 随祖先版本并入 / 分支上查不到」。

## 影响

- **core**：`core/project/artifact-evidence.ts`（新）。零第三方依赖，
  只用 `node:child_process`（C2）；只读 git、纯计算（C3）；不落任何状态（C1）。
- **adapters**：`/api/plan-coverage` 每行多五个字段
  （`artifactOnBranch` / `artifactCommit` / `artifactSubject` /
  `artifactOnAncestor` / `artifactAncestorCommit`），
  每版 `counts` 多 `artifactOnBranch` / `artifactOnAncestor`。
  每个版本问两次 git（本分支一次、祖先分支一次），**不逐片问**。
- **驾驶舱**：计划对照表新增「本版分支有产物」+「随祖先版本并入」两列
  （取代「分支上完成」的展示位）；切片列表新增「产物证据」列；切片详情新增「产物证据」行。

## 被否决的替代方案

- **改 ADR-114 的判据**，让它去查状态文件以外的路径：状态文件被忽略是
  **设计**（ADR-121），「状态文件进不进 git」与「这版做完没有」本来就是
  两件事。硬改只会把两个语义搅在一起。
- **把 `.zelto/slices/` 放进版本控制**：那是 ADR-121 明确否掉的
  （多台机器各自的状态会互相覆盖），不是本 ADR 能推翻的。
- **按文件路径推断产物**（提交碰过这片写集里的文件就算）：
  写集之外的改动会污染判断，且切片之间写集重叠时无法区分归属。
- **让前端自己算**（前端拉 `git log`）：判定必须在服务端（C3），
  前端只做展示。
- **用 `git log <branch> --not <ancestors>` 排除祖先提交**：同一 id 若本版提交比
  祖先提交旧，首个命中会落到「本版有、据此却排除了」上；按 id 的首个命中提交
  逐个判「是否已在祖先历史里」，归属错位才暴露得出来。
