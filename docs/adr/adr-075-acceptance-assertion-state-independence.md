# ADR-075：验收断言必须与「切片是否已合并」无关 —— 写集边界断言的判据重构

**状态**: 已实施
**日期**: 2026-11-18
**作者**: 系统架构
**关联约束**: C1, C3, C4
**关联文档**: `src/core/spec/skeleton.ts`, `src/core/gate/acceptance.ts`,
`src/core/sign-review/collect.ts`, `src/core/project/managed-acceptance.ts`
**关联 ADR**: ADR-033（切片级验收）、ADR-034（骨架生成）、
ADR-046（骨架要落在写集里）、ADR-059（签字前的四项确认）、
ADR-070（静默失败守卫）

## 1. 摘要

第八轮演练（nimrtc-zelto，2026-11-18）暴露一个**判据层**的缺陷：

验收测试里有一类断言叫「写集边界断言」，它断言的是
「**存在未提交的改动**」。这种断言**只在切片尚未合并时成立**：

```javascript
const diff = spawnSync('git', ['diff', '--name-only'], { cwd: ROOT });
assert.ok(changed.length >= 1, '写集内必须存在已追踪文件的改动');
assert.ok(changed.includes('examples/demo-agent-realtime/CMakeLists.txt'),
           '本片必须注册 demo-agent-teammate');
```

门禁在 agent 的 worktree 里跑时，`ROOT` 是 worktree 根，
`git diff` 看到的是 agent 尚未提交的改动 —— 断言成立，门禁绿。
切片合并进版本分支、worktree 被清理之后，在主干上复跑同一份验收，
`git diff` 为空 —— **断言红**。

实测（nimrtc-zelto 主仓，2026-11-18）：

| 切片 | 失败的断言 | 失败性质 |
|---|---|---|
| `v4-voice-agent` | 「本片必须改动 demo-agent-realtime」 | 断言红（3 pass / 5 fail） |
| `v4-ai-teammate` | 「写集内必须存在已追踪文件的改动」 | 断言红（7 pass / 1 fail） |
| `v2-ai-decision` | 「本片必须注册 demo-agent-realtime」 | 断言红（5 pass / 1 fail） |
| `v1-video-processing` | 「build 参数应含 NVENC=ON」等 3 条 | 断言红（1 pass / 3 fail） |

**这四片的门禁当时都是绿的** —— 因为门禁在未合并的 worktree 里跑。
追溯链（C4）没有问题，但**判据本身脆**：同一份验收测试，
在「切片未合并」时绿、在「切片已合并」时红，而两者的产品代码完全一样。

**决策**：

- **A**：把「写集边界断言」的判据从「**有未提交改动**」重构为
  「**写集内的产物在树上存在，且内容符合规格**」——
  这个判据在未合并与已合并两种状态下**同样成立**。
- **B**：ADR-034 的骨架生成器新增一段「写集边界断言的正确写法」说明，
  并在 `core/spec/skeleton.ts` 里落成**可复用的判据**而不是自由文本 ——
  让 agent 不必自己发明这条断言。
- **C**：验收测试**不被自动改写**。既有验收文件由人或 agent 自行修正；
  zelto 不替人改断言（改断言 = 改验证语义，必须经人）。

## 2. 为什么这是判据缺陷而不是实现缺陷

### 2.1 框架侧的判据是稳的

先排除「zelto 自己的判据写错了」这个可能。逐条核对：

| 框架判据 | 位置 | 是否依赖未合并状态 |
|---|---|---|
| 「有没有真跑用例」 | `core/gate/acceptance.ts` 的 `verifyAcceptanceRanTests` | ❌ 只看 pass/todo/skipped 计数 |
| 「改动统计」 | `core/sign-review/collect.ts` 的 `collectDiffFacts` | ❌ 统计 `git diff HEAD --numstat`，**不**断言必须 > 0 |
| 「产物是否落地」 | `core/sign-review/collect.ts` 的 `judgeArtifactEvidence` | ❌ 查 `HEAD` 的 `ls-tree`，「不在主干」是正常态而非失败 |
| 「验收骨架是否豁免」 | `core/project/managed-acceptance.ts` | ❌ 只看内容是不是纯 todo |

框架侧没有一处断言「必须有未提交改动」。
**红的是 agent 自己写的验收断言。**

### 2.2 但框架有一个真空

ADR-034 的骨架生成器（`core/spec/skeleton.ts`）只做一件事：
把规格里的「验收标准」逐条变成 `test.todo(<原文>)`。

它**不生成**「写集边界断言」—— 那条断言是 agent 自己加的。
而 agent 加的时候，**没有任何东西告诉它**：

- 这条断言只在未合并状态下成立；
- 它应该写成什么样子才在两种状态下都成立。

于是 agent 凭直觉写了「`git diff` 必须非空」——在 worktree 里它是对的。
**这不怪 agent**：没人给过它正确写法，ADR-034 的骨架也没有这一段。

### 2.3 为什么「合并后复跑验收」是必须支持的场景

不是「主仓复跑验收」这个动作本身有多重要，而是**追溯链要求结论可复现**：

```
人批准的规格 → agent 写的代码 → 门禁判定 → 人签字 → 合并 → 版本交付
                                                        ↑
                            合并之后，「这片的验收还是不是绿的」必须还能回答
```

追溯链（C4：事后可审计）要求「当初那个绿灯」能被重新验证。
如果验收测试在合并之后就红，那么：

- 人无法复核「我当初签的那一片到底行不行」；
- `zelto version deliver` 的版本级验收在版本 worktree 里跑
  （ADR-056），但版本 worktree 里也是**已合并**状态 —— 同一个坑；
- 每次重新验证都需要人为地「把切片倒回未合并状态」，这不可脚本化。

**结论**：验收测试必须是「状态的函数」，而不是「历史事件的函数」。

## 3. 决策

### 3.1 判据重构：写集边界断言的正确写法

**旧写法**（只在未合并状态成立）：

```javascript
const changed = gitDiff('--name-only');
assert.ok(changed.length >= 1, '写集内必须存在已追踪文件的改动');
assert.ok(changed.includes('examples/demo-agent-realtime/CMakeLists.txt'), '...');
```

**新写法**（任何状态都成立）：

```javascript
// 判据：产物在树上存在（已提交），而不是「有未提交改动」
const tracked = gitLsFiles();
assert.ok(tracked.has('examples/demo-agent-realtime/CMakeLists.txt'),
    '本片必须注册 demo-agent-teammate（CMakeLists.txt 必须在树上）');
```

关键差别：**判据的对象从「工作区状态」换成「仓库树的内容」**。
「这次切片改了哪些文件」是一个**历史事件**（合并前后不一样），
「这次切片的产物在不在树上」是一个**状态**（合并前后一样）。

**边界守卫（防越界）仍要保留**，但同样要改成状态式的：
「不在写集内的文件，不该由本片引入」——
判据是「写集外的文件在本次切片基点之后没有被改动」，
而不是「当前工作区没有任何写集外的改动」
（后者会误伤别的切片留下的合法改动）。

### 3.2 骨架生成器补上这一段（ADR-034 的真空）

`core/spec/skeleton.ts` 的 `buildAcceptanceSkeleton` 生成的骨架里，
新增一节**说明 + 可直接改用的判据模板**，内容就是 §3.1 的新写法。

要点：

- 骨架是**给人看、给 agent 抄**的东西 —— 它必须说清「这条断言怎么写才不出错」；
- 模板必须**直接可用**（给出函数名与调用形态），不能只给散文描述；
- 不自动生成断言本身（断言要结合具体写集路径，骨架不知道它们）。

### 3.3 既有验收文件不被自动改写

**zelto 不替人改断言。** 理由：

- 改断言 = 改验证语义。验证语义是**人批准的那一份**（C4 追溯链的起点），
  工具擅自改它，追溯链就断了；
- ADR-037（越界恢复与重新冻结）确立了「规格/验证要变就得重新 freeze」的先例，
  验收断言同理。

既有验收文件的修正路径：

- 由人改，或由 agent 在**新的切片**里改（那一片的写集覆盖了验收目录）；
- 改完必须重跑门禁，让 `gate.result` 事件记下新的结论。

### 3.4 框架侧要不要新增一道「判据形态」检查？

**不新增。** 理由：

- 「这条断言是否依赖未合并状态」**无法静态判定**——
  `git diff` 出现在断言里既可能是「有改动」（脆）
  也可能是「拿改动做对照」（稳），字面上区分不了；
- 硬要判定就得引入「验收测试的静态分析」，那是新的一套判定口径，
  比它要解决的问题大得多；
- **真正的防线在 §3.1**：判据本身写成状态式的，就不需要额外检查。

**但要留一道「门禁可复现」的自检**：门禁②在 worktree 里跑过一次之后，
**不应该**要求同一份验收在别的状态下再跑一遍。

## 4. 约束合规检查

| 约束 | 检查 | 合规 |
|---|---|---|
| **C1** | 状态只落在文件里；本 ADR 不引入任何常驻进程或内存状态 | ✅ |
| **C2** | `core/spec/skeleton.ts` 只用 `node:fs` / `node:path`，零第三方依赖，不 import `adapters/` | ✅ |
| **C3** | 判据是「产物在不在树上」这类确定性计算（读 git 树），不调模型、不触网 | ✅ |
| **C4** | 不新增事件类型；既有验收的修正通过重跑门禁落进 `gate.result` 事件 | ✅ |
| **C9** | 本 ADR 不涉及写集预约；越界审计照常 | ✅ |

禁区检查：未新增自动批准、自动合并、自动改规格；
**未新增「自动改写验收断言」的能力**（§3.3 明确不做）；
签字仍不自动合并（ADR-018 不变）。

## 5. 后果

**好的**

- 验收测试变成「状态的函数」，合并前后结论一致；
- 追溯链的可复现性补上最后一环 ——
  「当初那个绿灯」现在能被重新验证；
- 骨架生成器说清「写集边界断言怎么写」，下一个 agent 不会再踩同一个坑。

**代价与边界**

- 既有验收文件要逐个修正（nimrtc-zelto 上至少 4 片）；
- 修正本身要重跑门禁 —— 一次性成本，不是持续成本；
- 判据从「改动清单」变成「树的内容」，**丢失了「改了多少」的信息** ——
  但那信息本来就只该在 worktree 里看（ADR-059 的 `collectDiffFacts`
  在签字阶段读的是 worktree，没合并时它是准的）。

**明确不做**

- 不自动改写既有验收断言；
- 不新增「验收断言的静态形态检查」；
- 不改变门禁的执行时机与位置（worktree 优先，主仓退回）——
  那由 ADR-056 的版本 worktree 机制保证。

---

## 6. 验收标准

1. `core/spec/skeleton.ts` 生成的骨架里含「写集边界断言的正确写法」一节，
   其中的判据模板在**未合并与已合并两种状态下都成立**；
2. `tests/` 有用例锁定该模板的形态（骨架里必须出现状态式判据的关键词，
   且不得出现「必须存在未提交改动」这类表述）；
3. `npm test` 全绿；
4. `npm run lint` 通过；
5. nimrtc-zelto 上至少 `v4-voice-agent` / `v4-ai-teammate` 两片：
   合并后在主干复跑验收为绿（这两片已合并，样本现成）；
6. `zelto version deliver` 在版本 worktree（已合并状态）里跑版本级验收为绿。

## 7. 关联 ADR 的状态更新

- **ADR-033**（切片级验收）不变 —— 本 ADR 处理的是「验收**内容**的判据」，
  不是「要不要跑验收」；
- **ADR-034**（骨架生成）**扩写** —— 骨架多了一节「写集边界断言的正确写法」；
- **ADR-046**（骨架要落在写集里）不变；
- **ADR-059**（签字前四项确认）不变 —— 框架侧判据本就稳，
  本 ADR 修的是 agent 自写的验收断言；
- **ADR-070**（静默失败守卫）**扩写** —— 静默失败不只发生在
  「命令跑不起来」，也发生在「判据依赖了会变的状态」；
- **ADR-056**（版本级分支）不变 —— 但它的版本 worktree 正是
  「已合并状态」的第一个真实用例。
