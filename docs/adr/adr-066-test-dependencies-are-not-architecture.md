# ADR-066：架构扫描区分「生产依赖」与「测试依赖」

## 状态

已接受（2026-11-16）

## 背景

实战演练在 nimrtc-zelto 上暴露了架构护栏的一个**根本性缺陷**：
测试文件被当成生产代码参与依赖图计算，导致大量假阳性，并在特定情形下
形成**死锁** —— 想修复违反的切片自己被该违反拦住。

具体证据：

### 证据 1：假「未声明依赖」

`src/plugins/tests/test_zero_copy_surface_path.cpp` 包含 video_frame 模块的
公开头。这条边在设计上从未声明过，于是报「未声明依赖」。

但这条边**不该报** —— 测试引用被测对象是测试的**本职**。设计文档描述的是
**生产架构**：模块 A 的生产代码依赖模块 B。测试为了验证契约而引用 B，
不构成架构耦合。

### 证据 2：假「依赖成环」

同一条边导致两个假环：

```
src/engine → src/dtls → src/plugins → src/modules
src/plugins → src/modules
```

环里 `src/modules → src/engine` 是 ADR-025 明确规定的合法方向
（assembly 桥接配置层到运行时层），`src/engine → src/modules` 是 ADR-025
的 L4 豁免。三者相接必然成环 —— 但这个「环」是**测试污染**造成的，
生产依赖图里并不存在。

### 证据 3：死锁

修复该问题的切片 `v1-fix-plugin-test-placement` 写集包含
`src/plugins/tests/...`，因此**与该环相关**，被架构护栏拦住：

```
❌ v1-fix-plugin-test-placement — frozen
     ❌ 架构护栏拦截：依赖成环×2（deny）
```

护栏拦住了唯一能修它的切片。要开工只能：
1. 把 policy 的 `cycle` 规则从 `deny` 改成 `ask` —— 那是**放弃护栏**，
   不是修复；
2. 不走 zelto 流程直接改代码 —— 那是**绕过护栏**。

两条路都违背 zelto 的立意。**护栏必须能区分「真违反」和「假违反」，
否则它要么误伤、要么形同虚设。**

### 证据 4：覆盖统计把测试算成生产代码

`LangCoverage` 的「验过 / 验不了」统计把测试文件混进生产代码分母，
让「本项目 30% 代码没被验证」这类结论失真。

## 决策

**测试文件不参与依赖图计算，但参与文件归属与覆盖统计。**

具体三条：

### 决策 1：测试文件不产生依赖边

扫描时识别测试文件，测试文件的 import/include **不生成模块依赖边**。

测试文件仍然：
- 归属到模块（用于「文件无归属」检查与覆盖统计）
- 计入模块的文件数

只是不成为依赖边的**来源**。

### 决策 2：测试文件不作为依赖边的**目标**被追究

若 A 的测试引用了 B（且 B 也被测试引用），这条边不存在，因此不会报
「未声明依赖」。

### 决策 3：测试文件与「验不了」统计分开

`LangCoverage` 增加 `testFiles` 计数，把测试文件从生产代码分母里剥出。
未实现扫描器的语言（如 Rust）统计只看生产代码。

## 测试文件如何识别

确定性命名约定（不靠内容猜测）：

1. **路径里含测试目录名**：路径的任一段等于 `test` / `tests` / `testing`
   / `spec` / `specs` / `__tests__` / `test_` 结尾的目录段。
   例：`src/plugins/tests/a.cpp`、`src/__tests__/b.ts`。
2. **文件名本身是测试**：文件名（去扩展名）匹配测试命名约定：
   - 以 `test_` 开头（`test_foo.cpp`）
   - 以 `_test` 结尾（`foo_test.cpp`）
   - 以 `Test` / `Tests` 结尾（`FooTest.cpp`、`FooTests.java`）
   - 整个文件名就是 `test` / `tests`
3. **测试后缀**：`_test.go`、`_test.py`、`_spec.rb`

这些约定覆盖了主流生态的绝大多数实际用法。识别是**目录级 + 文件级**两层：
目录级优先（`tests/` 目录下的文件全部算测试），文件名级兜底。

**不靠内容猜测**：不看文件里有没有 `test(` / `assert` / `TEST_F` 这类
token —— 那会把含断言的普通源文件误判成测试。

## 被否决的方案

### 方案 A：把测试文件整体排除在扫描之外

最简单。但会丢掉「文件无归属」检查对测试文件的覆盖 —— 测试文件也该
有归属，否则会静默漂移。**否决。**

### 方案 B：给 policy 加 `arch.ignoreTests` 开关

保留行为可配置。

但这引入了一个「关掉护栏」的旋钮，而项目当前**没有**这个需求 ——
测试依赖一律不是架构耦合是**普遍规律**，不是项目特例。留一个开关只会
让人有理由把它关掉。**否决。**

### 方案 C：只把测试边标记成软偏离（不拦），但仍显示

保留信息，但边还在图里，成环检测仍会算上它 —— 环还是假环，只是被降级。
「成环」这个结论本身就是错的，降级不够。**否决。**

### 方案 D：把测试文件移到一个统一的顶层测试目录

改动项目布局，改动大，且不是所有项目都这么组织（很多项目按模块就地
放测试）。zelto 应当在**不改用户项目布局**的前提下工作。**否决。**

## 影响

### 对 zelto

- `core/arch/scan.ts`：加测试文件识别 + 跳过依赖边生成
- `core/arch/types.ts`：`LangCoverage` 加 `testFiles`
- `core/arch/report.ts`：覆盖统计口径调整
- `src/cli/commands/architecture.ts`：覆盖统计展示加测试文件数

新增测试：`tests/arch-test-deps.test.ts`

### 对使用 zelto 的项目

- 架构检查的假阳性大幅减少
- 护栏不再有「修复违反的切片被违反本身拦住」的死锁
- 覆盖统计反映真实的生产代码构成
