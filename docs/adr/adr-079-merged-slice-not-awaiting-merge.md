# ADR-079：「合过没有」按事件流判，落点按 git 事实验证 —— 已交付的切片不该再被列为「待合并」

**状态**：实施
**日期**：2026-11-18
**相关**：ADR-056（版本分支与归属解析）、ADR-071（空操作合并）、ADR-076（D-71 合并提交真实性）、D-74

## 背景

`zelto merge`（不带切片 id）会收集「已签字但尚未合入目标」的切片。
收集判据写在 `collectMergeCandidates()` 里。

ADR-071 引入了一条判据，用来处理**没有 `slice/<id>` 分支**的切片：

> 产物由人直接提交到目标分支 → 合并是空操作 →
> 按**写集路径**核实产物是否已在目标 ref 上 → 已就位 = 空操作候选。

这条判据本身是对的，但它被用在了**错误的层级**上。

## 病灶

实测（nimrtc-zelto，2026-11-18）：

```
$ zelto merge --list
待合并的已批准切片：v4-voice-agent, v4-ai-teammate, v3-weaknet-verdict,
                   v3-chrome-waterfall, v2-qoe-feed, v2-input-binder,
                   v1-game-source, v1-video-processing
```

而这 8 个切片**全部已经交付** —— v1 / v2 / v3 / v4 的版本都已 ship，
tag 已打，产物已在主干上。

### 精确对应关系（实测）

| 切片的 `merge.completed` mode | 是否被列为待合并 |
|---------------------------|----------------|
| `merged`（合进版本分支）    | **是** ❌        |
| `noop`（产物已在目标上）     | 否 ✅            |
| 无事件（从没合过）           | 否 ✅            |

规律精确到「有没有 noop 事件」——
因为 `hasNoopMergeEvent()` 恰好把 noop 的排除了，而 `merged` 的没排除。

### 根因（两层）

**第一层：判据本身有漏洞。**

ADR-071 的判据是「产物在不在目标 ref 上」。这条判据的前提是
「产物在目标上 = 还没合过」—— 只在**合并还没发生过**时成立。

但**产物一旦在目标上，就永远在**。切片合过之后产物当然在目标上，
于是判据永远成立 → 永远判成「还没合过」。

**第二层：比的目标不是同一个。**

| | 切片合进的 | 收集候选时判的 |
|---|---|---|
| 切片自己的归属 | `version/v1` / `version/v2` … | 主仓 HEAD（= `main`） |

两个目标对不上，判据就必然失配。

于是流程变成：

1. v1-game-source 合进 `version/v1`；
2. `version/v1` ship 进 main（squash 合并后产物也在 main 上了）；
3. 收集候选时按 **main** 判「产物在不在」→ 在 → 判成「还没合」；
4. 但它明明已经合进版本分支、并且版本已经交付了。

### 危害：假待办比假完成更隐蔽

「假完成」会让人以为活干完了。「假待办」相反 —— 它让人以为**还有活没干**。

具体后果：

- 人看到「待合并 8 个」，以为还有活没干；
- 实际去合，还会撞上「这批切片归属不同的合并目标，不能一次合」；
- 更坏的是，它把人引到「这些切片没合进主干」的错误结论上 ——
  而实际上它们**早就合进去了**。

**追溯链在这里说了假话**（C4）。

## 决策

### 判据一：「合过没有」看事件流

合并动作**必然**写 `merge.completed`（ADR-071 §3 D3：空操作也写 ——
追溯链不因为「这次没搬东西」而断）。

所以「有没有这个事件」就是「合过没有」的事实。

但**只看事件不够** —— 那会把「合进版本分支、还没进主干」的切片
也判成「已合完」。落点必须对齐。

### 判据二：落点对齐 —— 事件记 `target`，历史事件用 git 事实兜

`merge.completed` 事件补记 `target` 字段（合并到哪个分支）。

对齐时按**优先级**降级：

| 情形 | 怎么判落点 |
|------|-----------|
| 事件记了 `target` | 直接比字符串 |
| 历史事件没记 `target`，有 `mergeCommit` | `git merge-base --is-ancestor <mergeCommit> <目标 ref>` |
| 历史事件既没 `target` 也没 `mergeCommit` | 只剩空操作事件可作证（且目标是主干） |
| 以上都对不上（孤儿 commit / 历史重写） | **降级**：按写集核实产物是否在目标 ref 的树上 |

最后那条降级是必要的：实测 nimrtc-zelto 的 v5 切片因为版本分支 rebase，
`mergeCommit` 成了孤儿 commit —— 但它的产物确实在 `version/v5` 上。
纯 git 祖先关系会判成「没合过」，把已交付的切片又列一遍。

**关键差别**：ADR-071 的「产物在不在」是**唯一**判据（所以漏判）；
这里是**降级**判据 —— 前面已经有「合过没有」这个前提把着，
且只在「事件说合过、但 git 祖先关系查不到」时才启用。

### 判据三：目标按切片**自己的归属**解析

收集候选时对每个切片单独解析它的合并目标：

- 显式 `--target` → 按它判（人的显式意图最高）；
- 没给 → 按切片自己的归属（版本计划成员扫描 → 规格 frontmatter → 兜底主干）。

这解决第二层根因：`version/v1` 的切片不再拿 `main` 去比。

## 一条被自己写错的断言（与 ADR-078 同型）

修 D-74 时，我先写的两条用例**互相矛盾**：

```ts
it('已合进版本分支…的切片，不再被列为待合并', ...)   // target=version/v1 → 不该列
it('合到别的目标的切片，对当前目标来说仍然要合', ...) // target=version/v1 → 该列
```

两条用的是**完全相同**的现场（同一个 target、同一个 mode），
却断言相反的结果。

根因是我把「落点」和「归属」当成了同一个东西：

- 「落点」= 这次合并合**到哪**了（事件里的 `target`）；
- 「归属」= 这个切片**属于**哪个版本（版本计划 / 规格）。

D-74 的判据是「**合过它的归属目标没有**」——
不是「合过任意目标没有」。所以第二条用例的现场应该是：

- 切片**不在任何版本计划里** → 归属 = 主干；
- 但它历史上合进的是 `version/v1`；
- 现在要合进 `main` → 对主干来说仍然算「没合到」→ 仍要列。

**教训**（与 ADR-078 §「一条被 D-73 顺手满足的错断言」同型）：
写「负向」用例时，要先问「这条用例的现场与正向用例到底差在哪」——
如果差不出来，说明判据的定义本身没想清楚。

## 影响面

- `src/cli/commands/merge-executor.ts`
  - `merge.completed` 事件补记 `target`（合并到哪个分支）
- `src/cli/commands/merge-runner.ts`
  - 新增 `mergeHistoryFor()` —— 读 `merge.completed` 事件（含 `target` / `mode` / `mergeCommit`）
  - 新增 `ownMergeTargetOf()` —— 按 ADR-056 §3.2 解析切片自己的归属目标
  - 新增 `resolveEffectiveTarget()` —— 显式 `--target` 优先，否则按归属
  - 新增 `alreadyLandedIn()` —— 事件 + git 事实双证判据（含降级链）
  - 新增 `isAncestorOfRef()` / `versionTagRefsFor()` —— git 祖先关系核实
  - 新增 `artifactsPresentOn()` —— 降级用的写集核实
- `tests/d74-merged-slice-not-awaiting-merge.test.ts` —— 5 条用例（新增）
  走**真实 CLI 进程**（`dist/cli/index.js`）—— 病灶本身就是跨进程行为。

## 不变量核查

- **C1**（状态只在文件里）：无影响 —— 判据读事件文件 + git 对象库，都是文件。
- **C2**（core 零第三方依赖）：无影响 —— 改动都在 `cli/` 层。
- **C3**（判定确定性）：`git merge-base --is-ancestor` 是确定性判定，无模型、无网络。
- **C4**（append-only 事件流）：**加强** —— 事件补记 `target`，
  追溯链不再需要靠「产物在不在」这种间接推断来判断落点。
- **C5**（保护域外部化）：无影响。
- **C9**（写集预约运行时强制）：无影响 —— `artifactsPresentOn()`
  只是**读**产物路径来核实，不写任何文件。
