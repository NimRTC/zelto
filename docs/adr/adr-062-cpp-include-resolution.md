## 1. 摘要

ADR-061 把「代码」与「扫描器读得懂的代码」分开了，
但**没有缩小盲区本身** —— C++ 项目仍然只有 3% 的代码被验证。

本文处理盲区里最大的那一块：**C++ / C**。

调研在真实项目（nimrtc-zelto）上做，实测数据支撑每一个设计决策。

## 2. 调研：C++ 的 include 长什么样

### 2.1 两种形态

扫了 `src/` 下（排除 third_party）**401 个 C/C++ 文件**、**108 条引号 include**：

| 形态 | 数量 | 例子 |
|---|---|---|
| 裸文件名 | 72 | `engine_impl.hpp`、`rtp_packetizer.hpp` |
| 带目录 | 36 | `nimrtc/core/registry.hpp`、`nimrtc/dtls/dtls.hpp` |

**同一个项目里两种形态并存**，而且不是「不同项目风格不同」——
是**同一个项目里不同位置不同**。

### 2.2 带目录的那种怎么解析

```
nimrtc/core/registry.hpp   →  src/core/include/nimrtc/core/registry.hpp
nimrtc/dtls/dtls.hpp       →  src/modules/dtls/include/nimrtc/dtls/dtls.hpp
```

规律是：**去掉 include 根目录后，剩下的路径原样对应**。

而 include 根目录从哪来？CMake 里写着：

```cmake
target_include_directories(nimrtc_core_objects
    PUBLIC
    $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
```

`src/core/include/` —— 就是模块自己的 `include/` 目录。

全项目共 **44 个 `include/` 目录**（`src/core/include`、
`src/modules/*/include` 44 个、`src/plugins/include`），
**全部叫 `include`** —— 这是 C++ 世界的惯例。

### 2.3 裸文件名的那种怎么解析

```
engine_impl.hpp  →  src/engine/src/engine_impl.hpp
```

它**不带任何路径**。编译器靠 `-I` 列表逐个目录试，
找到第一个存在的就停。

在这个项目里，它命中的就是**引用文件自己所在目录**
（`src/engine/src/engine.cpp` 引 `src/engine/src/engine_impl.hpp`）。

注意：**这条规则不是 C++ 规范**，它是 `#include "..."` 的
「先在当前目录找，找不到再走 `-I` 列表」这条约定的后半截。

### 2.4 尖括号 include

`#include <mutex>` / `#include <stdio.h>` —— **系统头**。

它们：
- 不属于本项目的任何模块
- 不该产生模块依赖边
- 是「外部依赖」，跟 TS 的 `package` 一样

**必须排除**。否则每个 `.cpp` 都会连到「系统」，整张图变成噪声。

## 3. 决策

### 3.1 三种解析策略

C++ 的 include 需要**三种**解析策略，不能套用 TS 的两种：

| 策略 | 适用 | 怎么解析 |
|---|---|---|
| **相对** | `#include "foo/bar.hpp"`（带目录） | 相对于引用文件所在目录 |
| **裸文件名** | `#include "foo.hpp"`（无目录） | 相对引用文件目录 → 再扫所有 include 根 |
| **系统头** | `#include <foo>` | 不解析，不产生边 |

**裸文件名的解析顺序**（对应 C++ 的实际行为）：

1. 引用文件所在目录
2. 每个 include 根目录

**include 根目录怎么来？** —— 从文件树里找所有名为 `include` 或 `inc` 的目录。

**为什么不读 CMakeLists？** 见 §7。

### 3.2 **修正**：`<>` 不等于「系统头」

> **这一节是实施时改的，原始决策是错的。**

原始决策：**尖括号 = 系统头 = 不解析**。

**实测打脸**：真实项目里 **2716 条尖括号 include 中，1081 条是项目内部的**：

```
150 次  nimrtc/core/api_version.hpp
 79 次  nimrtc/core/log.hpp
 62 次  nimrtc/core/registry.hpp
 49 次  nimrtc/core/bytes.hpp
 39 次  nimrtc/plugins/base.hpp
 ...
```

**占尖括号 include 的 40%。**

原因很简单：C++ 的 `<>` 与 `""` 的区别**不是「内部 vs 外部」**，
而是「**搜索顺序的约定**」——
`<>` 跳过引用文件的当前目录、直接搜 `-I` 列表；
`""` 先搜当前目录。而 `-I` 列表里**既有系统路径，也有项目的公共头文件目录**。

公共头文件用 `<>` 是**正常且推荐**的写法（它明确表示「这是公共接口，不是内部实现」）。

**修正后的决策**：

| | 原始 | 修正后 |
|---|---|---|
| `#include "..."` | 解析（当前目录 → include 根） | 解析（当前目录 → include 根） |
| `#include <...>` | **不解析** | **解析**（**只**搜 include 根，跳过当前目录） |

**外部依赖怎么识别？** —— **解析不到的自然就是外部依赖**。
不需要在解析阶段猜「这是不是系统头」——
「这个文件在不在项目的 include 根里」是**可判定的事实**，猜它才有风险。

**实现**：给 `ImportRef` 加一个 `cppBracket?: '<' | '"'` 字段，
记录括号类型（决定搜索顺序），两种都归为 `relative`（= 需要解析）。

**顺带修掉的问题**：原始代码把解析不到的 C++ include 塞进 `unresolved` ——
但解析不到恰恰意味着「这是外部依赖」，不是「引用解析失败」。
`unresolved` 应该只装**真的解析失败**（TS 的相对路径指向不存在的文件）。

### 3.3 `SourceLang` 加 `'cpp'`

```ts
export type SourceLang = 'ts' | 'python' | 'cpp';
```

`detectLang` 认 C/C++ 扩展名：
`.c` `.h` `.cc` `.cpp` `.cxx` `.hpp` `.hh` `.hxx` `.ipp` `.inl`

**`.h` / `.hpp` 要算** —— C++ 项目里头文件占了相当比例
（真实项目：`src/core` 13 个代码文件里 10 个是 `.hpp`）。

### 3.4 include 根目录的发现：约定优先

```ts
/** include 根目录的目录名 */
const INCLUDE_ROOT_NAMES = ['include', 'inc'];
```

扫描文件树时，**每遇到一个叫 `include`/`inc` 的目录，就把它记为一个 include 根**。

**为什么不解析 CMakeLists / BUILD / meson.build？**

| 方案 | 问题 |
|---|---|
| 解析 CMakeLists | 要实现 CMake 方言；`$ENV{}`、`$()`、生成式配置都很难静态求值 |
| 解析 BUILD（bazel） | 同上，且 bazel 的 `includes` 语义与 CMake 不同 |
| **约定（目录名）** | 44/44 命中真实项目；零解析成本；漏了就漏了（不产生假边） |

**关键性质：约定法只会漏，不会错。**

而「错」比「漏」严重得多 ——
把一个 include 解析到**错误的文件**，会产生一条**假的模块依赖边**，
进而报一条**假的架构偏离**。

**约定法的漏报率**：真实项目 44 个 include 根，约定法全找到。
项目也可能用别的名字（`headers/`、`_include/`）—— 那时会漏，
但漏的表现是「这条依赖验不了」，**方向是安全的**。

### 3.5 顺序无关性

include 根目录的**顺序**理论上影响解析结果（编译器取第一个匹配的）。
但：
- 同一个头文件名在多个 include 根下都存在 —— 极罕见
- 真实项目里 `nimrtc/core/registry.hpp` 与 `nimrtc/plugins/registry.hpp`
  **都存在**，但**完整路径不同**（`nimrtc/core/` vs `nimrtc/plugins/`）——
  带目录的那种解析不受顺序影响

**决策：按路径字典序排序 include 根**（确定性优先，C3）。
若解析到多个候选，取字典序最小者。

**这不是编译器行为** —— 编译器取「`-I` 列表里第一个」。
但我们的 `-I` 列表是**猜的**，所以字典序是唯一诚实的选择：
它至少是**确定的**、**可复现的**。

## 4. 影响

### 4.1 数据契约

- `SourceLang` 新增 `'cpp'`
- `ScanResult` 的语义变化：`cpp` 文件会进入 `files` 与 `moduleVerifiedFiles`
- `LangCoverage.verifiable` 新增 `'cpp'`
- `LangCoverage.counts.cpp` 的含义从「代码但验不了」变成「**已验证**」

**`arch check --json` 的输出会变** —— C++ 文件从「未验证」移到「已验证」。
这是**事实上的接口变更**，明确记下。

### 4.2 判定

C++ 项目上，`missing_dependency`（硬偏离）会**开始出现**。

**这是预期的** —— ADR-058 的降级机制本来就是为了「等有了判据再启用」。

**但要小心**：刚启用判据时，C++ 项目很可能**立刻报一堆偏离**。
那些偏离**可能是真的**（C++ 项目确实可能有多余依赖），
也可能是**解析不准导致的假边**。

**缓解**：
1. include 根用约定法（只漏不错）
2. 系统头一律排除
3. 裸文件名先查当前目录（C++ 规范行为）

### 4.3 回归测试

- `tests/arch-cpp-include.test.ts` —— 17 条用例，覆盖：
  - include 根目录的发现（约定法 + 字典序确定性）
  - 带目录 include 相对 include 根解析
  - 裸文件名优先在引用文件所在目录解析（C++ 规范行为）
  - 裸文件名回退到 include 根
  - `#include <...>` 归为 builtin（不进模块图）
  - `#include "..."` 归为 relative（进模块图）
  - 跨模块依赖边正确产生
  - 模块内部 include 不产生边
  - C++ 文件进入「已验证」
  - 覆盖面报告里 C++ 变成「已验证」
  - 模块概况里 C++ 代码既算「代码」也算「已验证」
  - 确定性（同输入两次结果相同）

## 4.4 实施中发现的额外问题：模块声明了但一个文件都没匹配上

装到真实项目上一跑，立刻冒出**一类新的偏离**：

```
  模块
    src/dtls          0 个文件    声明依赖: src/core, src/third_party
    src/raw_udp       0 个文件    声明依赖: src/core
    src/sctp          0 个文件    声明依赖: src/core, src/third_party
    src/transport     0 个文件    声明依赖: src/core, src/raw_udp
    src/web_transport 0 个文件    声明依赖: src/core, src/transport
```

**5 个模块匹配到 0 个文件。**

真相：代码实际在 `src/modules/dtls/`、`src/modules/sctp/`、
`src/modules/raw_udp/`、`src/modules/transport/`、
`src/modules/web_transport/` —— 而**设计里写的是 `src/dtls/*`**。

**这是设计里的路径写错了。**

### 为什么不报出来

不报的话，这个错误会一路飘到「依赖无法验证」里：

```
● 依赖无法验证   src/modules → src/dtls
  目标模块没有代码文件（契约 / 规格一类），无法用 import 验证
```

人看到的是「`src/dtls` 验不了」—— 而真相是「**`src/dtls` 根本不存在**」。

这是**同一类错误**（ADR-061 §4 D-15）：
错误信息指错了方向。「没有代码文件」让人去查「是不是漏写了」，
「一个文件都没匹配上」直接指向「**路径写错了**」。

### 决策：新增 `empty_module` 偏离（软偏离）

```ts
| 'empty_module'              // 模块声明了，但一个文件都没匹配上（ADR-062 §4.4）
```

**软偏离**（永不拦）：这是**设计侧**的问题，不是代码违反了架构。
硬拦会挡住「设计还没写完」的正常推进。

**说明文案**要点名出错的路径：

```
● 模块无文件    src/dtls → src/dtls
  模块 "src/dtls" 声明了文件路径，但一个文件都没匹配上
  （src/dtls/*、src/dtls/**/*）—— 路径写错了，或目录还不存在
```

**这是工具给设计文档提的第一个「你写错了」** —— 也是这套架构检查
第一次能指出**设计本身**的问题，而不只是代码与设计的差异。

### 4.5 第二轮：修完 5 处后，又冒出 2 类新问题

把 5 处路径修掉后重跑，偏离从 31 降到 27，`empty_module` 全部消失。
但还剩一条诡异的：

```
● 缺失依赖     src/log → src/core
  设计声明了依赖，代码里没有对应的 import
```

**这条依赖真实存在** —— `src/log/src/log.cpp` 里写着
`#include <nimrtc/core/log.hpp>`。

真正的错在别处：`src/log` 模块的设计路径是 **`src/log/*`**（单层），
而代码在 `src/log/src/log.cpp`（两层）。
**模块只认领到了 `CMakeLists.txt`，没认领到代码文件** ——
于是那条依赖扫不到，报成了「缺失依赖」。

**这是第 6 处路径错误**，但它躲过了 `empty_module` 的检测 ——
因为模块**匹配到了 1 个文件**（CMakeLists.txt），不算「一个文件都没匹配上」。

**两处修改**：

1. **设计**：把 `src/log` 的路径改成 `src/log/*, src/log/**/*`
2. **工具**：`missing_dependency` 的说明要区分两种原因 ——
   - 来源模块**有**代码文件 → 「设计声明了依赖，代码里没有对应的 import」（真的没做）
   - 来源模块**没有**代码文件 → 「来源模块没有匹配到任何代码文件 ——
     依赖可能真实存在但扫不到（先查来源模块的文件路径对不对）」

改完之后 `src/log` 显示 `2 个文件（1 代码）`、实际依赖 `src/core`，
与设计声明**一致**，那条偏离自动消失。

**剩余的 26 条偏离逐条核对过，全是真偏离**：

| 偏离 | 核对结果 |
|---|---|
| `interop → src/core` | interop 的 Python 全是标准库 + playwright，**确实没 import 项目代码** |
| `interop → src/dtls` | 同上 |
| `src/web_transport → src/transport` | web_transport 的 include 里**没有任何 `nimrtc/transport/`** |
| 各 `未声明依赖` | 抽查 `src/engine → src/dtls` 等，include 确实存在 |
| `依赖成环` | `engine → dtls → plugins → modules` 环，真实存在 |

**这是工具可信度的关键检验**：改了设计之后剩下的偏离**逐条都站得住** ——
没有假边、没有误报。

## 7. 为什么不读 CMakeLists

这个决策值得单独说 —— 它是本 ADR 最重要的取舍。

**读 CMake 能得到什么**：精确的 include 列表。

**读 CMake 要付什么**：

1. **CMake 是图灵完备的语言**。`include()` 别的文件、
   `if()` 分支、`set()` 变量插值、`$ENV{}` 环境变量 ——
   静态求值要么做不全，要么做错。
2. **做错的后果是假边** —— 一条假的模块依赖边会报假的架构偏离。
   而假的偏离会**让人去改对的代码**。
3. **多构建系统**。CMake / Bazel / Meson / Premake / 自研脚本 ——
   每种都要实现一遍，等于在 core/ 里造半个构建系统。
   而 core/ 的硬约束是**零第三方依赖**。

**约定法（找 `include/` 目录）的性质**：

| | 约定法 | 解析构建系统 |
|---|---|---|
| 覆盖率 | 44/44（真实项目） | ~100% |
| 假边风险 | **零**（只漏不错） | 有（解析错就假边） |
| 依赖 | 无 | 需要构建系统解析器 |
| core/ 复杂度 | 低 | 高 |

**核心权衡：假边比漏边严重得多。**

架构检查的价值在于**报告出来的偏离都是真的**。
一个会误报的检查器，人用两次就不信了 —— 那它对真问题也失效了
（这与 ADR-060 §5 D-12 的教训是同一条）。

**将来如果需要**：可以加一个**可选的**「从 CMakeLists 读 include 目录」开关，
但它必须：
- **默认关闭**
- **明确标注**「用了构建配置，解析可能有误」
- **只增加候选，不减少** —— 约定法的候选永远保留

这样它只能**增加**验证能力，不能**制造**假边。

## 8. 实施中发现的流程缺口：已确认的设计改不了

工具报出了设计的错，但**没有修正的路径**：

```
$ zelto design refine prj-1792993843912 "修正文件路径"
{
  "error": {
    "code": "INVALID_STATE",
    "message": "Design \"prj-1792993843912\" is already confirmed. Can only refine draft designs."
  }
}
```

`design refine` 只接受 `draft`。**已确认的设计无法修正。**

而 `DesignDoc` 里有个 `supersedes` 字段 —— **预留了「新版取代旧版」的机制，
但没有任何命令设置它**（一直是 `null`）。

**这条流程缺口是本轮演练暴露的**：

1. 工具报出设计的错（`empty_module`）
2. 人想把路径改对
3. **发现没有命令可用** —— 只能手改 JSON

手改 JSON 有个隐患：`body` 是真源，`modules` 是缓存快照 ——
**只改一个会不一致**。本轮修的时候两处都改了。

**决策**：本轮**先手改**（用户确认），把「实现修正命令」记为遗留。
理由是：改 `body` 需要走 LLM（`refine` 的实现是调模型重新生成），
而这里的修改是**确定性的文本替换** —— 走 LLM 反而有把别的东西改坏的风险。

将来该做的可能是一个新命令（比如 `zelto design patch <id> --module <name> --path <glob>`），
走确定性替换 + 人确认，不经过 LLM。

## 9. 遗留

- **Go / Rust / Java 的依赖解析**仍待处理（ADR-060 §4 方案 C 的可插拔方向）
  - 真实项目实测：**Rust 76 个文件**是当前唯一剩下的盲区
- **条件编译**（`#ifdef _WIN32`）会让 include 解析依赖构建配置 ——
  本 ADR 接受这个不精确性：解析**所有**分支的 include，
  可能产生「在某个配置下不存在的依赖」这条边。
  它比漏边多，但漏边更危险。
  极端情况下会产生假边 —— 缓解办法是引入 **「条件编译依赖」** 这个新的偏离种类
  （软偏离，永不拦），单独列出来让人判断。**本轮先不做**，
  等真实数据说明它有多常见。
- `src/third_party` 的 11943 个文件（ADR-061 §7 遗留）——
  启用 C++ 解析后，third_party 的 C++ 文件也会进 import 图。
  实施后实测：third_party **4355 / 4434 个代码文件已验证**，
  它本身没有声明依赖也没有实际依赖，所以**暂时没有产生假偏离**。
  但它的体量仍然让整张图的统计失真 —— 将来需要「第三方模块」的单独处理。
- **设计里的路径写错**（本 ADR §4.4 实测发现 5 处 + §4.5 又发现 1 处）——
  已在 nimrtc-zelto 项目里修掉（6 处，body 与 modules 两处都改）。
  但**新设计仍可能犯同样的错** —— 工具能报出来，但修正得手改 JSON（§8）。
- **「修正已确认设计」的命令缺失**（§8）——
  `supersedes` 字段已预留但没人用；该做一个走**确定性替换**（不经 LLM）的命令。

## 10. 给后续的教训

### 10.1 「启用判据」和「工具一直有用」是两回事

ADR-058 让 C++ 项目不再被硬偏离拦住时，那只是「不再误报」。
真正让工具有用的是 ADR-062 —— **有了判据才能查出真问题**。

实施后真实项目的偏离从 23 条涨到 31 条 —— 看起来是「退步」，
实际是**从 8% 的覆盖率涨到 34%**。

**判据的价值不在于让报告变干净，在于让报告变准。**

### 10.2 工具的第一条真发现，往往是关于**设计**的

这次报出的偏离，有 6 条指向「模块的文件路径写错了」——
**设计文档的问题**。

这类问题此前没人发现，因为：
- 人肉核对 19 个模块的路径太累
- 工具没有「一个文件都没匹配上」这个概念

**架构检查的第一价值不是抓代码的偏离，是抓设计本身的错。**

### 10.3 约定法的价值在于它的**失败方向**

include 根用「找 `include/` 目录」的约定法：
- 项目用别的名字（`headers/`）→ 漏 → 表现为「验不了」→ **安全**
- 解析构建系统出错 → 假边 → 报假偏离 → **危险**

选一个**只会往安全方向失败**的方案，比选一个「更准」的方案更重要 ——
尤其当它的输出会被人当作「代码违反了架构」来处置的时候。

### 10.4 **「排除外部依赖」不如「识别内部依赖」**

原始决策是「尖括号 = 外部 = 排除」。实测打脸：
**2716 条尖括号里 1081 条是项目内部的**（40%）。

改成「**两种都解析，解析不到的自然就是外部**」之后：
- 该报的报了（40% 的漏报消失）
- 外部依赖仍然不进模块图（解析不到）
- **不需要猜**「这是不是系统头」

**「用可判定的事实替代猜测」** —— 这条在 ADR-061 D-15
（区分不可验证的三种原因）里已经出现过一次。
**遇到「要判断 X 是不是 Y」时，先找有没有一个可直接判定的事实。**

### 10.5 改完设计后，剩下的偏离要**逐条核对**

这是工具可信度的关键检验。改完 6 处路径后剩下的 26 条偏离，
逐条核对过 —— 抽查 `src/web_transport → src/transport`（确实没有
`nimrtc/transport/` 的 include）、`interop → src/core`（确实只 import 标准库）、
`src/engine → src/dtls` 的 include 确实存在。

**没有假边、没有误报** —— 工具这才真的可用。

只报「看起来对」的数字是不够的：**要能说出每一条偏离的证据。**
