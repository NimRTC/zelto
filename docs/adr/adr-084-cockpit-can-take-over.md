# ADR-084：驾驶舱从「只读 + 签字」扩展为「可接管的驾驶舱」

**状态**：实施（部分被 ADR-086 取代 —— 见文末「关联缺陷」）
**日期**：2026-11-18
**相关**：ADR-072（Web 驾驶舱：只读 + 签字）、ADR-086（驾驶舱装上油门：freeze/gate/run/resume）、
ADR-018（签字不自动合并）、
ADR-020（拉闸）、ADR-021（签字可撤销）、D-48（签字前的确认项）、
项目目标 §2.5、负向清单「完整 GUI」

## 背景

用户看了 `zelto web` 驾驶舱后问：

> **现在的 UI 是不是太弱了，感觉更像个看板，没有操作的内容**

核实的结果比预想的复杂 —— **「只读」这个描述已经不准确了**：

| | ADR-072 承诺 | 实际 |
|---|---|---|
| 只读视图 | ✅ | ✅ 11 个 GET 端点 |
| **+ 一个签字动作** | ✅ 承诺了 | ✅ **已实现**（`POST /api/sign-requests/:id/approve` + 前端按钮） |

所以「驾驶舱是只读的」这句话**本身是过时的**。

但用户的感受是对的 —— **可操作的面太窄**：

| 动作 | CLI | Web |
|---|---|---|
| 签字 | ✅ `zelto sign <id> --approve` | ✅ 已有 |
| **回答 agent 的提问** | ✅ `zelto answer <id> "..."` | ❌ **没有** |
| **拉闸（交回控制权）** | ✅ `zelto halt` | ❌ **没有** |
| **续跑停机切片** | ✅ `zelto resume <id>` | ❌ **没有** |

而这几个动作恰恰是**驾驶舱最有价值的时刻**：

> **agent 卡住来问人 → 驾驶舱是「被问的那一方」该待的地方。**
>
> 现在 agent 提问了，人得**切回终端**去回答 ——
> 「驾驶舱」在最需要它的时候，把人赶走了。

## 决策

### 1. 扩展「可操作」的定义，但守住边界

驾驶舱提供**四个动作**，全部对应「人接管」：

| 动作 | 端点 | 语义 |
|---|---|---|
| 签字 | `POST /api/sign-requests/:id/approve` | 已有（D-48 的确认项照旧） |
| **拒签** | `POST /api/sign-requests/:id/reject` | **新增** |
| **回答提问** | `POST /api/slices/:id/answer` | **新增** —— 只**记录**答案，不续跑 |
| **拉闸** | `POST /api/halt` | **新增** |

### 1.1 「回答提问」只记录答案，**不续跑**

核实 CLI 侧 `zelto answer` 的实现时发现：它会**调 `adapter.resume()` 续跑 agent 会话**。

那是「推进」不是「接管」—— 而且它要拉起 agent 进程、可能长时间阻塞 HTTP 请求。

**所以 Web 侧的 `answer` 只做两件事**：

1. 记录答案（文件 + `question.answered` 事件）；
2. **明确告诉人下一步**：在终端里跑 `zelto answer <qid> "..."` 完成续跑。

> **为什么不让 Web 侧续跑**：
> 一个 HTTP 请求里挂着一个 agent 会话，会带来三个问题：
> 请求超时、断连丢会话、驾驶舱进程被杀则 agent 孤儿进程。
> 而 CLI 侧本来就有完整实现（`adapter.resume`）——
> **Web 侧再实现一份，就会分叉判定与状态机（C3 的隐患）。**
>
> **分工**：驾驶舱负责「把答案记下来」，CLI 负责「让 agent 接着跑」。

**明确不做**（仍在 ADR-072 §4 的排除清单里）：

- `run` / `gate` / `freeze` / `admit` / `abandon` / `resume` ——
  理由不变：**那些动作在 CLI 侧有完整实现，Web 侧再实现一份会分叉判定（C3 的隐患）**。

> ⚠️ **本段已被 ADR-086 部分取代**（2026-11-18）：
> `run` / `gate` / `freeze` / `resume` 改为**做** ——
> 但方式仍是「不重写判定」：**freeze / gate / resume 的编排下沉到 `core/lifecycle/`，
> CLI 与 Web 调同一份；`run` 拉起 CLI 进程本身**。
> 理由（那三个动作 CLI-only 的那条）经核实**仍然成立**，
> 变的是「怎么复用」而不是「要不要做」。
> `admit` / `abandon` 仍然不做。

> **为什么 `resume` 也不做**：
> `resume` 会改切片状态机、走重试预算、可能触发 gate ——
> 它不是「接管」动作，是「推进」动作。
> 驾驶舱的定位是**人在被交还控制权时的那几个动作**，
> 不是「另一个 CLI」。
>
> **而 `halt` 与 `resume` 是一对**：
> `halt` 是「交回控制权」，`resume` 是「把控制权给回 agent」。
> 但 `resume` 的语义（重试预算、跳过、放弃）比 `halt` 复杂得多，
> Web 侧只提供 `halt` 是**刻意的取舍** ——
> 驾驶舱负责「刹车」，不负责「油门」。
>
> ⚠️ 上面这段「只提供 `halt`」也已被 ADR-086 取代 ——
> 驾驶舱现在刹车油门都有（但 `resume` 仍然**复用 core 的编排**，不重写）。

### 2. Web 侧**不重写判定**，只调 core

每条写操作都直接调用 CLI 侧同一个 core 实现：

| Web 端点 | 复用 |
|---|---|
| approve / reject | `core/gate/sign.ts` 的 `approve()` / `reject()` |
| answer | `core/.../question.ts` 的回答路径（与 `zelto answer` 同一条） |
| halt | `core/halt/` 的暂停逻辑（与 `zelto halt` 同一条） |

**理由（ADR-072 §4 的纪律，保留）**：
Web 侧再实现一份判定，等于**同一件事有两个实现** ——
两边不一致时，人在浏览器里点的和人在终端里跑的会有不同结果。
而「签字」尤其危险：**签字是全流程唯一只能由人做的动作**，
判定一旦分叉，就可能出现「浏览器里能签、终端里不让签」。

### 3. 每个写操作都必须写事件流（C4）

签字/拒签已有事件。**新增的两个动作也要写**：

- 回答提问 → `question.answered`（或复用现有事件名）
- 拉闸 → `halt.triggered`

**理由**：驾驶舱里的操作**也是「人做的决定」** ——
追溯链要能回答「当时是谁在浏览器里回答了这个问题」。

### 4. 身份：`decidedBy` 用什么

事件里要记「谁做的」。CLI 侧写 `'human'`。

Web 侧**没有登录体系**（负向清单不允许常驻 daemon / 账号体系），
所以也写 `'human'` —— 但**额外记一个 `via: 'web'`**：

```json
{ "type": "sign.approved", "actor": "human", "payload": { "via": "web" } }
```

**理由**：`actor: 'human'` 说的是「人做的」，
`via: 'web'` 说的是「在哪儿做的」——
两个维度，不该混成一个字段。

### 5. 安全边界：复用已有的双因子校验，不新开一条

ADR-072 §3 已经把写操作的安全做完了：

| 机制 | 作用 |
|---|---|
| **会话 token**（`X-Zelto-Token`） | 每次启动随机生成 32 字节；写操作必须带 |
| **Origin 校验** | 浏览器发起的必须同源；空 Origin（非浏览器）放行 |
| **不发 `Access-Control-Allow-Origin`** | 第三方网页读不到本页 → 拿不到 token → CSRF 失效 |
| **`validId()`** | 路径参数过白名单字符集，挡 `..` 与路径分隔符 |

**所以新增的三个写操作自动继承这套校验** ——
`server.ts` 的 `handleApi()` 在**分发之前**统一校验，
新增端点不需要（也不许）自己再实现一遍。

> **顺序不能改**：先校验，后分发。
> 校验没过就绝不能碰到任何 handler。

**唯一要补的一条**：`readJsonBody()` 现在**不检查 Content-Type**。
跨站表单提交（`application/x-www-form-urlencoded`）能被解析成合法 JSON 吗？
不能 —— 但它能提交 `text/plain` 型的 JSON 体（`fetch` 的 `no-cors` 模式）。
所以**必须显式要求 `Content-Type: application/json`**。

**为什么这道防线是必需的**：驾驶舱**持有项目目录的写权限**。
一个恶意网页如果能让它跨站 POST，就等于拿到了「在你的项目里签字」的权限。
token + Origin 是双保险，Content-Type 是第三道。

**仍然没有 DELETE 端点** —— 签字可以撤销（`--revoke`），但没有「删除签字记录」。

### 6. `halt` 的范围

`zelto halt` 在 CLI 侧是「暂停批次 + 交回控制权」。
Web 侧**只提供 halt，不提供 resume**（§1 已述）。

而且 `halt` 的语义必须是**可逆的**：
它不改切片状态机，只是**暂停并留现场** ——
这与 ADR-020 的设计一致。

## 影响面

- `src/adapters/web/router.ts`：新增 3 个 POST 端点 + Origin/CSRF 校验
- `src/adapters/web/api.ts`：新增 `rejectSign()` / `answerQuestion()` / `haltBatch()`
- `src/adapters/web/server.ts`：POST 体解析加固（只接受 JSON）
- `src/adapters/web/frontend-assets.ts`：待签卡片加「拒签」、切片详情加「回答」、顶栏加「拉闸」
- `tests/web-cockpit-actions.test.ts`（**新增**）：四个动作的端到端判据

## 不变量核查

- **C1**（状态只在文件里）：**无影响** —— 四个动作都是**文件写**
  （切片状态、事件流），不引入内存状态。
- **C2**（core 零第三方依赖）：**无影响** —— 新代码在 `adapters/web/`，
  调用 `core/` 已有实现。
- **C3**（判定确定性）：**加强** —— Web 侧**不重写判定**，只调 core。
  这是本 ADR 最需要守住的一条。
- **C4**（append-only 事件流）：**加强** —— 新增的两个动作也写事件。
- **C5**（保护域外部化）：无影响。
- **C7**（llm 只产草稿）：无影响。
- **C9**（写集预约运行时强制）：无影响 —— 这四个动作都不写 agent 的工作目录。

## 验收标准

1. ✅ 四个动作在 Web 端可用，且**复用 CLI 的同一套 core 实现**；
2. ✅ 拒签 / 回答 / 拉闸**都写事件流**；
3. ✅ 事件里 `actor: 'human'` + `via: 'web'`（两个维度分开）；
4. ✅ 跨站表单提交（无 JSON Content-Type）被拒；
5. ✅ `Origin` 不匹配的 POST 被拒；
6. ✅ 非法 id 被拒（400）；
7. ✅ **签字仍然不等于合并** —— 响应里明确告知下一步是 `zelto merge`；
8. ⚠️ **本条已被 ADR-086 取代** —— Web 端现在**有** run/gate/freeze/resume 端点
   （复用 core 编排，不是重写判定）。ADR-086 的验收标准取代本条；
   `admit` / `abandon` 仍然没有。
9. ✅ `npm test` 全绿。

## 关联缺陷

- ADR-072 §4 的排除清单**部分被 ADR-086 取代** ——
  `run` / `gate` / `freeze` / `resume` 改为做（复用 core 编排），
  `admit` / `abandon` 仍不做。
- **「看板」还是「驾驶舱」的分界线**：
  看板是「看」，驾驶舱是「能接管」。
  分界不在 UI 复杂度，在于**人能不能在被交还控制权的那一刻就地接管**。
