# ADR-071：合并目标已含产物时的空操作合并

**状态**: 已实施
**日期**: 2026-11-16
**作者**: 系统架构
**关联约束**: C1, C3, C9
**关联缺陷**: D-32（第四轮端到端复验新发现）
**关联文档**: `src/cli/commands/merge.ts`,
`src/cli/commands/merge-executor.ts`,
`src/cli/commands/merge-runner.ts`

---

## 1. 摘要

`zelto merge` 硬性要求每个切片都有 `slice/<id>` 分支，没有就拒绝：

```console
❌ 以下切片没有对应的分支，无法合并：
   - v1-fix-arch-guard-cycle（缺分支 slice/v1-fix-arch-guard-cycle）
```

但有一类切片**天然没有这个分支**：产物由人直接提交到目标分支的切片。

第四轮复验（靶子项目 nimrtc-zelto）撞上两个这样的切片：
`v1-fix-arch-guard-cycle` 与 `v1-fix-plugin-test-placement`。
它们的产物（`policy.yaml` 的 `arch:` 段、测试文件搬迁）由人工直接提交到
`main`，从未跑过 agent —— 所以没有 `slice/<id>` 分支。

**合并此时是空操作**：产物已经在目标分支里，没什么可合的。
zelto 却把它当硬错误拒绝，人只能去手工改状态 —— 追溯链断在这里。

**决策**：合并的判据从「**分支存在**」改成「**产物是否已在目标分支**」。
产物已在 → 空操作合并（记事件，不报错）；产物不在且无分支 → 仍然拒绝。

---

## 2. 背景

### 2.1 「分支存在」这个判据从哪来

`merge.ts` 的前置守卫：

```ts
const missingBranches = ids.filter((id) => !branchExists(`slice/${id}`, process.cwd()));
if (missingBranches.length > 0) { /* 拒绝 */ }
```

它的**用意**是对的（ADR-011 / ADR-059 §6）：分支不存在时合并无从下手，
等到执行阶段才发现合不了，已经跑了 `commitPendingWorktrees`（有副作用）。
**提前拒绝**是好的设计。

**问题不在「提前拒绝」，在「拒绝的理由只认分支」。**

### 2.2 判据漏掉的那一类

切片产物进目标分支有两条路：

| 路径 | 产出 | 有 `slice/<id>` 分支吗 |
|---|---|---|
| agent 跑完 → `zelto merge` | 分支 + worktree | 有 |
| **人直接提交到目标分支** | 直接在目标分支上 | **没有** |

第二条路不是「绕过流程的野路子」，它是**合法路径**：

- 人自己改了代码并提交（这就是人的本职工作）
- 写集撞保护域时（比如要改 `policy/policy.yaml`），
  agent **本来也过不了门禁①** —— 保护域防的就是 agent（ADR-070 / D-24）
- 接管既有项目时，产物本来就在主干上

对这类切片，`zelto merge` 的语义是「**确认产物已在目标分支**」，
不是「把分支合过去」。

### 2.3 为什么不能简单放行

「分支不存在就跳过」是错的 —— 那会让**真正合不了的切片**也悄悄通过
（产物既不在目标分支、又没分支 = 什么都没做）。
D-11 刚把「假成功」当严重缺陷修过一轮（合并了 0 片却报
「✅ Merge complete」）。不能重蹈覆辙。

**判据必须落到「产物在不在目标分支」这个事实问题上。**

---

## 3. 决策

### D1：判据改为「产物是否已在目标分支」

对缺分支的切片，按**写集路径**逐一核实：这些路径的内容是否已经存在于
目标分支？

- **全部存在** → 空操作合并（记 `merge.completed` 事件 + 说明「产物已在目标分支」）
- **有缺失** → 仍然拒绝，并说清「缺分支 **且** 产物不在目标分支」

**为什么按写集路径核实，而不是按 commit 追溯**：commit 追溯需要切片有
基点与分支，而这类切片两样都没有。写集路径是**切片自己声明的产物清单**，
是唯一在「无分支」情形下仍然存在的证据。

### D2：核实用「路径存在于目标 ref」而不是「路径在工作区」

判据是「产物在**目标分支**里」，不是「文件在磁盘上」——
后者会把未提交的本地改动算成已合入。

对已删除的路径（测试搬迁类切片会把旧路径删掉），判据是
「该路径在目标 ref 上**不存在**」也算通过 ——
旧路径的消失正是搬迁的产物。

### D3：空操作合并写 `merge.completed` 事件

追溯链不能因为「这次合并没搬东西」就断。
事件里记明这是空操作（`mode: 'noop'`）与核实方式。

**新增事件类型**：不需要。`merge.completed` 加一个 `mode` 字段即可
（`mode: 'noop' | 'merged'`）—— 事件类型集合不动，schema 不用改。

### D4：门禁不变

「分支缺失且产物不在目标分支」仍然**硬拒绝**，退出码 1。
「产物已在目标分支」→ 退出码 0。

---

## 5. 验证

1. 产物已在目标分支 + 无分支 → 合并成功（退出码 0），记 `merge.completed`
2. 产物不在目标分支 + 无分支 → 拒绝（退出码 1），说清原因
3. 有分支 + 产物不在目标分支 → 正常合并（既有行为不变）
4. 旧路径已删除（搬迁类）→ 算产物已就位
5. 未提交的本地改动**不算**已合入

---

## 6. 已知局限

- **只核实路径存在，不核实内容**。产物路径在目标分支上但内容与切片预期不同
  （比如人改过），zelto 认不出来 —— 那需要切片级的期望摘要，
  而切片没有（无分支、无基点）。
- **多切片混合合并**时，逐片核实 —— 一片空操作、一片真合，都是允许的。
