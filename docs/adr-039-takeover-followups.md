## 1. 摘要

ADR-038 修好了「接管既有项目」的三处断链（静默失败、无追溯起点、确认废规格）。
本文补的是它的**五处收尾** —— 每一处都是「人第一次真用 zelto 接管自己的项目」时
会撞上、而 ADR-038 之后仍然会撞上的：

| # | 缺口 | 症状 | 本次处置 |
|---|---|---|---|
| 1 | **基线登记不留痕** | 现状被登记成基线切片，但事件流里没有任何记录 —— 「谁在什么时候把哪些文件登记成了现状」查不到 | 每登记一片基线切片，追加一条 `slice.baseline_registered` 事件（C4） |
| 2 | **策略锚点是自证的** | 锚点写在 `policy.yaml` 自己体内，改策略的人顺手把哈希也改掉，事后看不出「当时按什么标准拦的」被换过 | 锚点外部化到 `policy/lock.json`，独立于策略本身；失配可检出（C5） |
| 3 | **规格文件挡住合并** | 合并守卫拦的是「人改了代码还没提交」，但它把 zelto 自己生成的规格文件也算成「工作区不干净」—— 接管既有项目时基线规格是新建文件，人还没来得及提交，合并就永远过不去 | 守卫区分「代码改动」与「zelto 管理的规格文件」；后者照实提示但不挡路 |
| 4 | **两条初始化入口不一致** | `zelto init` 与 `zelto project init` 各自登记基线，产出**两份不同**的登记记录（切片 id 相同、内容不同），追溯链说不清 | 登记收敛到 `registerBaselineSlices` 一个函数，两条入口走同一条路径 |
| 5 | **基线写集用具体文件** | 基线标的是「这一片涵盖哪些既有代码」；用具体文件的话，模块里此后新增的文件就落在基线范围之外 | 基线写集改用**目录通配**（`src/core/**`），新增文件自动落在基线范围内 |

---

## 2. 为什么现在做

这五处有一个共同的成因：**ADR-038 之前的代码里，「登记现状」这件事只发生在
`project init` 一条路径上，且只写状态文件**。于是：

- 别的路径（`zelto init`）压根不登记 —— 缺 #4；
- 登记了也不留痕 —— 缺 #1；
- 保护域的真源是策略文件，而策略文件自己声明自己的哈希 —— 缺 #2；
- 合并守卫的判据是「工作区干不干净」，而它不知道 zelto 自己也在写文件 —— 缺 #3；
- 写集口径在 ADR-038 §8 里被明确留成「待人拍板」—— 缺 #5。

ADR-038 §8 的那条遗留，正好是 #5。其余四处在实现 ADR-038 的过程中被撞见。

## 3. 决策

### 3.1 登记现状要落事件（C4）

C4 说「每个动作写 append-only 事件」，事件是追溯的**唯一证据载体**。
「把现状登记成基线切片」是一个动作 —— 它决定了追溯链从哪儿起、
哪些文件被算作「已完成的、不用再做的事」。
这个动作没留痕，就等于这段登记没发生过：事后看到一片 `completed` 的基线切片，
无法判断它是**接管时登记的现状**，还是**某次运行真做完了**。

事件类型：`slice.baseline_registered`，payload 带 `module` / `writes` /
`fileCount` / `reason`。

**为什么抽成函数**：基线切片有两条产生路径（`zelto init` / `project init`，
见 §3.4），两条路径都必须留痕。漏一条就等于这条路径上的登记没发生过。

### 3.2 策略锚点外部化到 `policy/lock.json`（C5）

**为什么原来不行**：策略文件体内写着 `anchors: policy: "sha256:..."`。
改策略的人只要顺手改掉这一行，事后就看不出「当时按什么标准拦的」被换过 ——
锚点自己证明自己，证词无效。

**口径**：

| 情形 | 行为 |
|---|---|
| 策略是 zelto 生成的 | 锚点跟着重建（策略变了锚点必须跟着变，否则每次接管都被自己判成「被人改过」） |
| 策略是人手写的、还没有锚点 | 锚上当前值（给人一个可追溯的起点） |
| 策略是人手写的、锚点已经在了 | **一个字都不改**。对不上就是失配，由人显式 `zelto policy lock --update` 改锚 |

关键在第三条：**改锚是人的决定**，不是接管的副作用。
自动改锚会让锚点重新变成自证 —— 唯一的差别是这次写在另一个文件里。

**判与报分开：谁负责判失配**。失配由 `zelto policy lock` 判（退出码 1，可直接当门禁）；
`zelto policy validate` **只判策略文件本身是否合法**，失配在它的输出里以警告出现，
但**不改变它的退出码**。

为什么要分开：接管既有项目时，人换掉自己的策略是常态（zelto 生成的策略未必是
这个人想要的）。若 `validate` 因失配就红，人每次换策略都得先改锚 ——
「失配 = 可检出的改动」就退化成「每次改策略先走一遍仪式」，人只会绕过它。
分工是：`validate` 说「策略本身合不合法」，`lock` 说「锚点还对不对」。
两者都把失配说出来，一个都不藏 —— 只是判在哪一道。

**契约面变化**：新增 `policy/lock.json`（格式：`version` / `policy` / `lockedAt` / `source`）。
`policy.yaml` 不再写 `anchors:` 段。

### 3.3 合并守卫要认识 zelto 自己的文件

合并前有一个守卫：主仓工作区必须干净。理由是合并会把分支上的改动带进主干，
未提交的本地改动会被盖掉 —— 这是真问题。

但守卫的判据「`git status --porcelain` 非空」太粗：它把 zelto 自己生成的
**规格文件**（`specs/slices/**`）也算成「工作区不干净」。
规格文件不是代码 —— 合并不会碰它，它是追溯链的出处，该入库、要看、要提交，
但不该挡路。接管既有项目时基线规格是新建文件，人还没来得及提交 ——
把它算成「工作区不干净」，合并就永远过不去。

处置：守卫把 porcelain 输出分成两类 ——
zelto 管理的规格文件（照实提示「不影响合并」）与真正的代码改动（挡住合并）。

**口径只认仓库根下的 `specs/` 树**，不认别处恰好同名的子目录。
另一个坑：git 报告未跟踪内容时会把目录**折叠成目录本身**
（`?? specs/` 而不是 `?? specs/slices/epsilon.md`），
所以 `specs` 与 `specs/slices` 这两个祖先目录也要认，否则未跟踪的规格目录照样挡路。

### 3.4 两条初始化入口产出同一份基线

`zelto init`（建目录）与 `zelto project init`（接管）是两条入口，
它们必须产出**完全一样**的基线切片 —— 否则人先跑 init 再跑 project init，
会看到两次不同的登记记录（切片 id 相同但内容不同），追溯链就说不清了。

做法：登记动作收敛到 `registerBaselineSlices` 一个函数，两条入口都调它。

### 3.5 基线写集用目录通配

ADR-038 §8 把这条留成「待人拍板」。本次定案：**用目录通配**。

理由：基线标的是「这一片涵盖哪些既有代码」，而不是「这一片当时有哪些文件」。
用具体文件的话，往该模块新增的文件就落在基线范围之外 ——
那片新文件既不属于基线，也还没有对应的后续切片，写集归属悬空。

**代价（认下来）**：基线写集与后续切片的写集会重叠（后续切片要改同一模块）。
并行调度据此降级成串行。这是可接受的：
基线切片状态是 `completed`、不参与运行，真实冲突只发生在
「两片都在跑、且都写同一目录」的场景里 —— 而基线片不跑。

## 4. 被否决的方案

**方案一：把锚点继续写在 `policy.yaml` 里，只是加个「必须人改」的注释。**
否决理由：注释挡不住手。改策略的人不会特意想起「这里还有一行哈希要一起改」——
正是这一行让他改策略这件事变得不可检出。锚点必须独立于被它锚定的东西。

**方案二：改锚需要人显式跑命令，但接管时自动检测到失配就自动改。**
否决理由：那还是自证，只是绕了一圈。失配的价值就在于「没人承认的改动」这件事
是可见的；自动改锚等于每次接管都把失配洗掉。

**方案三：合并守卫放行所有未提交改动，只提示不拦。**
否决理由：守卫拦的「人改了代码还没提交」是真会丢东西的场景 ——
合并会把分支上的改动盖掉本地未提交内容。放行等于把这个保护拆了。
正确做法是区分「代码改动」与「zelto 的产物」，不是把守卫整体放松。

**方案四：基线写集保持具体文件，新文件的写集归属交给后续切片自己声明。**
否决理由：新文件会同时落在「不属于基线」和「还没有切片」之间 ——
写集归属悬空，而写集是运行时强制（C9）的判据。悬空等于没人判。

**方案五：把基线登记放进 `project init` 独有的一条路径，`init` 不登记。**
否决理由：两条入口产出不同的基线，人看到的登记记录取决于他先跑了哪条命令 ——
追溯链说不清。入口可以有两条，登记只能有一条。

## 5. 影响与迁移

**契约面变化**：

- **新增事件类型 1 个**：`slice.baseline_registered`（ADR-038 §5 说「事件类型没变」，
  本次变了 —— 见 §6）；
- **新增文件** `policy/lock.json`（策略哈希锚点）；
- **`policy.yaml` 的 `anchors:` 段移除**（锚点不再写在策略体内）；
- 切片状态机、门禁判定、保护域定义**未变**；
- 写集口径从具体文件改为目录通配（影响基线切片的 `writes` 字段）。

**破坏性变更**：

1. 已有基线切片的写集仍是具体文件 —— 需要重跑一次接管才会变成目录通配；
2. 新增 `zelto policy lock` 子命令（查看 / 显式改锚）；
   `zelto policy validate` 的退出码**只反映策略文件本身是否合法** ——
   锚点失配不再让 `validate` 失败（此前没有锚点概念）。
   判锚点用 `zelto policy lock`，失配时退出码 1；
3. 旧的 `policy.yaml` 里若有 `anchors:` 段，接管时会被移除（zelto 生成的策略会重建；
   人手写的策略**不动**，其中的 `anchors:` 段会被忽略）。

## 6. 与 ADR-038 的关系

ADR-038 §5 写的是「事件类型集合**没变**（沿用 `draft.created` / `draft.confirmed`）」。
本次新增了 `slice.baseline_registered` —— 这是**修正**而非推翻：
ADR-038 的判断在新写的代码里不成立，因为「登记现状」这个动作
发生在 `draft.*` 之外，且它必须独立留痕（它决定追溯链的起点，不是草稿流程的一环）。

事件类型的真源是 `contracts/schemas/event-envelope.json` 的 enum，
本次同步补齐 —— 顺带发现 ADR-036 加的 4 个事件类型
（`contract.*` 与 `version.regression_*`）从未进过该 enum，
「代码能发、契约不认」的状态一直持续到本次补齐才暴露。
已一并修正，并把「三方对账」变成编译期 + 测试期的强制约束
（见 `docs/zelto-场景功能地图.md` §5）。

## 7. 不变式核对

| 约束 | 核对 | 合规 |
|---|---|---|
| **C1** 状态只在文件里 | 锚点落 `policy/lock.json`；基线切片落 `.zelto/slices/*.json` + `specs/slices/*.md`；事件追加 `.zelto/events/**/events.jsonl`。未新增内存状态或常驻进程 | ✅ |
| **C2** `core/` 零第三方依赖 | `core/policy/lock.ts` 只用 Node 内置 `fs`/`path` + 既有 `hashPolicy`；`core/project/managed-paths.ts` 是纯字符串判定；`core/project/baseline.ts` 只用 `crypto`/`fs`。未新增任何 npm 依赖 | ✅ |
| **C3** 判定确定性 | 锚点比对是读文件 + 算哈希 + 比较；写集归类是纯路径判定；合并守卫分类是纯字符串判定。全部不调模型、不触网 | ✅ |
| **C4** append-only 事件流 | 基线登记落 `slice.baseline_registered`；锚点失配在 `policy lock`（退出码 1）与 `policy validate`（警告）报出（不落事件 —— 校验不是动作）。事件流仍只追加 | ✅ |
| **C5** 保护域与锚点外部化 | 锚点从策略体内移到 `policy/lock.json`，独立于策略本身；失配可检出；改锚只由人显式执行。保护域（`PROTECTED_PATTERNS`）未动 | ✅ |
| **C7** llm 只产草稿 | 五处收尾全程无模型参与 —— 登记、锚定、守卫分类、入口收敛、写集口径全是确定性计算 | ✅ |
| **C9** 写集预约强制 | 判定机制完全未动；本次只改了基线切片 `writes` 字段的**内容**口径（具体文件 → 目录通配），运行时逐写判定与审计兜底照常 | ✅ |

禁区检查：未新增自动批准、自动合并、自动改规格、自动改锚。
改锚是人的显式动作（与 ADR-018「签字不自动合并」同一条思路 ——
把决策权交回给人）。

## 8. 验证方式

新增单元测试 `tests/takeover-followups.test.ts`（五组）：

- **基线留痕**：登记基线切片时事件流里有 `slice.baseline_registered`，
  actor 与 payload 的 `module` / `writes` 正确；CLI `project init` 落的事件在
  `.zelto/events/<id>/events.jsonl` 里。
- **锚点外部化**：初始化写出 `policy/lock.json`，锚点值等于当前策略哈希，
  `source` 为 `generated`；人手写的策略锚上后 `source` 为 `manual`；
  改策略后失配为真、**再次接管锚点一个字不改**、失配被明确报告；
  CLI `policy lock` 报失配退出码 1，`--update` 改锚后一致；
  `policy validate` 只判策略本身（失配时仍退出 0，但输出里要报出失配，
  `--json` 的 `anchor.mismatch` 为 true）。
- **合并守卫**：未提交**代码**改动仍挡住合并；未提交的 zelto 规格文件不挡路。
- **入口一致**：`zelto init` 与 `zelto project init` 产出同一份基线切片。
- **目录写集**：基线写集是目录通配，模块内新增文件自动落在基线范围内。

事件类型的三方一致性由 `tests/event-contract-parity.test.ts` 保证
（契约 enum ↔ 代码 `EVENT_TYPES` ↔ 审计摘要表 ↔ 文档计数）。

## 9. 遗留（需人拍板）

**`policy/lock.json` 该不该进版本库。**

当前它不自动进 `.gitignore`，所以默认是被 git 看见的。本次的理由是：
锚点记的是「**这个仓库当时的**策略标准」，它跟策略文件一样是仓库级事实 ——
策略进库，锚点也应该进库，否则换一个人 clone 下来就看不到当时的锚点，
失配检查在别人机器上直接失效（没锚点 = 不判）。

但这有一个反方向的顾虑：锚点进库意味着「改策略」会同时改两个文件，
而人改策略时未必想改锚 —— 偏偏这时最需要失配被报出来。
若人认为锚点应当本地化（不进库），则应把 `policy/lock.json` 加进 `.gitignore`，
并明确「没锚点 = 不判」在 CI 环境下的语义（CI 里没有锚点，
失配检查等于不生效）。本次**未动**，留给人决定。
