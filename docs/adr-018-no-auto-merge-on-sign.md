# ADR-018: 签字不再自动合并，合并必须显式执行

**状态**: 已实现
**日期**: 2026-11-04
**作者**: 系统架构
**关联约束**: C1, C3, C4, C9
**关联文档**: `AGENTS.md`, `docs/adr-012-parallel-coordination.md`,
`docs/zelto-并行自治计划.md`（§6 待人决策第 1 项）

---

## 1. 摘要

`zelto sign <id> --approve` 通过后，zelto 会**自动**把切片的改动提交、
合入 `main`，甚至（在加 `--push` 时）推到远端。

这与 `AGENTS.md` 负向清单里明写的「自动合并」直接冲突，而且这条路径
从来没有对应的 ADR——它是一条「实现先于契约」的路径。

本 ADR 取消签字后的自动合并：**签字只改状态**，合并必须由人显式执行
`zelto merge`。`--push` 也随之从 `zelto sign` 移到 `zelto merge`。

---

## 2. 动机

### 2.1 现状

| 事实 | 位置 | 影响 |
|---|---|---|
| `sign --approve` 后无条件调用 `autoMergeSlice` | `src/cli/commands/gate-sign.ts` 的 `sign` 注册 | 签字这个「批准」动作顺带改了主分支 |
| 交互式 `inbox` 批准同样调用 `autoMergeSlice` | 同上 | 交互路径也无法阻止 |
| `autoMergeSlice` 里还留着非 worktree 分支的旧逻辑（`git checkout main && git merge --ff-only`） | 同上 | 第二个并行分支必然 ff 失败 |
| `sign --approve --push` 会 `git push origin <当前分支>` | 同上 | 推的不是「已合并的结果」，而是签字那一刻的分支状态 |
| 负向清单写着「自动合并」不做 | `AGENTS.md#禁区` | 现状与清单直接冲突 |
| `docs/zelto-并行自治计划.md` §6 把这条列为待人决策 | 该文件 §6 问项 1 | 一直没人拍板 |

### 2.2 为什么「签字即授权合并」这个隐含假设站不住

签字回答的是「**这份改动可以不可以合入主线**」，不是「**现在就替我合**」。
两件事在语义上不同，在操作上更不同：

1. **签字可以批量、可以脚本化。** `zelto sign --approve` 可以在流水线里跑。
   一旦签字附带合并，脚本就获得了写主分支的权限——而负向清单恰恰要拦这个。
2. **合并的时机需要人判断。** 并行切片的合并有顺序与冲突问题
   （ADR-012 的 `MergePlanner` 就是为这件事建的）。签字时把「这一个」
   切片合进去，会绕开依赖图和写集冲突检测——`mergePendingSlices` 里的
   计划生成失败时只是打印一句警告就放弃，静默地把切片留在半路。
3. **合并失败不该被签字掩盖。** 现在的流程里，签字成功但合并失败，
   退出码仍然是 0。从人眼里看「签字过了 = 事情办完了」，
   而实际上产物还躺在 worktree 里。
4. **推送更不该挂在签字上。** `--push` 推的是当前分支，不是合并结果。
   要推就推合并后的 `main`。

### 2.3 为什么不能简单删掉合并功能

合并本身是必须的（否则切片永远进不了主线）。要删的是「**自动**」，
不是「合并」。ADR-012 已经建好了显式的 `zelto merge` 命令、依赖图解析、
工件冲突检测和合并计划编排——这条路本来就该是唯一的路。

## 3. 设计

### 3.1 职责切分

```
zelto sign <id> --approve   →  只改状态（已批准），写事件，打印下一步提示
zelto merge <id> [id ...]   →  显式合并：提交 worktree 产物 → 生成合并计划
                               → 执行 → 清理 worktree 与分支 → （--push）推送
```

`zelto merge` 不带切片 id 时，合并**所有已批准但尚未合入**的切片——
这正是原先 `autoMergeSlice` 内部做的事，现在它归 `zelto merge` 所有。

### 3.2 合并前必须先提交 worktree 里的产物

这是从旧实现里搬过来的一条硬要求：**分支必须先带上产物**。
切片在 worktree 里跑完，改动可能还没提交；直接合并分支会得到一个空分支，
产物静默丢失。所以 `zelto merge` 在生成计划之前，先把待合并切片的
worktree 提交掉。

### 3.3 `--push` 迁移

| 命令 | `--push` 行为 |
|---|---|
| `zelto sign <id> --approve --push`（旧） | 推当前分支——不是合并结果，语义错误 |
| `zelto merge <id> [--push]`（新） | 合并成功后推 `main`——推的确实是合并结果 |

`zelto sign` 不再接受 `--push`，传入时给出提示指向 `zelto merge --push`。

### 3.4 失败时的退出码

| 情形 | 退出码 | 说明 |
|---|---|---|
| 签字成功 | 0 | 与是否合并无关——签字这一环本来就只管状态 |
| 合并成功 | 0 | |
| 合并有冲突，中止 | 1 | 主分支回滚到合并前状态，列出冲突文件 |
| 合并计划生成失败 | 1 | 给出手动合并的命令 |

## 4. 契约变更

| 变更 | 位置 | 说明 |
|---|---|---|
| `zelto sign --approve` 不再自动合并 | `src/cli/commands/gate-sign.ts` | 纯删除调用路径，不改事件类型 |
| `zelto sign` 不再接受 `--push` | 同上 | 参数变更，见 §3.3 |
| `zelto merge` 承担 worktree 提交与清理 | `src/cli/commands/merge-runner.ts`（新） | 从 `gate-sign.ts` 搬移 |
| `zelto merge` 支持不带 id（合并全部待合切片） | `src/cli/commands/merge.ts` | 新用法 |

事件类型不变：`merge.planned` / `merge.phase_complete` / `merge.completed` /
`merge.stale_base` / `merge.conflict` 都已经在 ADR-012 里定义并实现。

## 6. 替代方案

### 方案 A：保留自动合并，用 ADR 追认现状

**放弃理由**：追认只是把冲突写进文档，冲突本身还在。
`AGENTS.md` 负向清单是硬约束，「实现与清单冲突」不能靠一份 ADR 合法化——
ADR 是「记录并解释决策」，不是「推翻约束的许可证」。真想推翻清单，
得先改清单。

### 方案 B：保留自动合并，但加 `--no-merge` 开关

**放弃理由**：默认仍是自动合并，等于冲突照旧，且多一个要记住的开关。
用户要的是「合并是显式动作」。

### 方案 C：签字后自动合并，但只合当前这一个切片（不走依赖图）

**放弃理由**：绕过依赖图与写集冲突检测。并行切片里先合哪一个会变成
「谁先签字谁先合」，冲突在事后才暴露。ADR-012 的合并计划就是为避免这件事。

---

## 7. 决定

1. 取消签字后的自动合并。`zelto sign --approve` 只改状态，不碰主分支
2. 合并统一走 `zelto merge`；不带 id 时合并全部「已批准且未合入」的切片
3. `zelto merge` 在生成计划前先提交待合并切片的 worktree 产物
4. `--push` 从 `zelto sign` 移到 `zelto merge`，推的是合并后的分支
5. 合并有冲突时退出码 1，主分支回滚到合并前状态
6. 这条决策回应 `docs/zelto-并行自治计划.md` §6 待人决策第 1 项；
   该文件其余三项已分别由 ADR-011（worktree 共享方式）、
   ADR-013（问题严重度与是否允许自行决定）回答
