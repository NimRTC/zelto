# ADR-040: 接管既有项目时的策略迁移（老版本生成物识别 · `anchors:` 兼容 · 根级构建清单随迁）

**状态**: 已实施
**日期**: 2026-11-10
**作者**: 系统架构
**关联约束**: C1, C2, C3, C4, C5, C9
**关联文档**: `docs/adr-038-takeover-gates.md`, `docs/adr-039-takeover-followups.md`,
`src/core/project/initializer.ts`, `src/core/project/legacy-migration.ts`,
`src/core/policy/validator.ts`, `src/core/policy/lock.ts`

---

## 1. 摘要

把 zelto 接在一个真实的大型 C++ 项目（nimrtc）上验证时，接管路径上暴露出三处
「看起来接管成功了、其实什么都没接管」的问题：

| # | 缺口 | 症状 | 本次处置 |
|---|---|---|---|
| 1 | **老版本生成物识别不出来** | ADR-038 用 `# zelto:generated:<hash>` 标记 + 哈希比对判断「这份文件还是不是 zelto 留下的原样」。但标记行是 ADR-038 **之后**才有的 —— 更早的 zelto 生成的文件没有这一行，判定一律落到「人手写的」 | 引入第三态 `legacy`（靠内容特征识别），并给老版本生成物一条**迁移**路径 |
| 2 | **`anchors:` 段让校验直接判红** | 老策略把锚点写在策略自己体内（自证）。ADR-039 把锚点外部化到 `policy/lock.json`，但没处置老项目里已经存在的 `anchors:` 段 —— 校验器把它当「未知顶层键」判红，`policy validate` 退出码 1 | 校验器认它、忽略它、报出来（警告而非错误）；接管时把老锚点搬进 `policy/lock.json` |
| 3 | **老策略里没有根级构建清单规则** | 老生成器只给「顶层目录」发规则，根级的 `CMakeLists.txt` / `package.json` 不在任何规则里 → 落到 `default: deny`。规格里明写「在顶层 CMakeLists.txt 注册新模块」，agent 一改就被 PreToolUse 钩子当场拒掉 | 根级构建清单规则（`ab0e9ff`）随迁移一起生效 |

三处是同一件事的三个面：**「接管」这条路径只对 ADR-038 之后接管的项目有效**。

---

## 2. 为什么现在做

这不是理论问题，是在真实项目上量出来的。nimrtc-zelto 上实测：

```
$ zelto policy validate
Validation: FAILED
  line:116: Unknown top-level key "anchors". Only "rules", "protected" and "arch" are allowed
```

而更早的一批项目（ADR-038 之前接管的）连这一步都走不到：它们的
`.zelto/config.yaml` / `policy/policy.yaml` 没有标记行，接管时被判成「人手写的」，
于是：

- 门禁命令还是通用的 `pnpm test`（在 CMake 项目上是错的命令）；
- 写集规则没按实际模块生成；
- 根级构建清单没有规则 → agent 改根级 `CMakeLists.txt` 被当场拒掉。

后果是接管路径**整体走不通**：看起来「接管成功了」，实际上一行代码都动不了。

需要说清楚的是：**这不是 ADR-038/039 做错了**，那两份 ADR 的判据在它们自己的
前提下都是对的。问题在于判据本身有一个**生效边界**（ADR-038 之后生成的文件），
而这个边界当时没有被写出来，于是「接管既有项目」这条对外主场景在老项目上
静默失效。

## 3. 决策

### 3.1 托管文件有三态，不只有两态

| 态 | 判据 | 处置 |
|---|---|---|
| `generated` | 有标记行，且去掉标记行后的正文哈希与记录一致 | 按真实探测结果重建 |
| `legacy` | **无标记行**，但有**老生成器的内容特征**（文件头 + `# Auto-generated for` 行） | 见 §3.2 —— 分两种情况 |
| `manual` | 其余（人手写的） | 一个字都不动 |

**「无标记行」是 legacy 的必要条件，不是可选项**。这一条在实现时被漏掉过一次，
后来在真实项目复验时补上（见 §3.6）—— 漏掉的后果是：人被改过的**当前版本**
策略会被当成 legacy 重建，从而覆盖掉人的规则。

**为什么 `legacy` 不能直接归到 `manual`**：那正是现在发生的事 ——
「没证据证明它是 zelto 生成的」不等于「它是人写的」。把两者混为一谈，
结果是 zelto 对自己写过的文件也不认。

**为什么 `legacy` 不能直接归到 `generated`**：老文件没有哈希，
**无法证明人此后没动过它**。直接重建会覆盖掉人的规则。

所以 `legacy` 必须**再分一次**（§3.2），靠可判定的条件分，不靠「看起来像」。

**内容特征是什么**：老生成器固定写两行 —— 文件头（`# zelto policy rules` /
`# zelto project configuration`）与 `# Auto-generated for "<项目名>"`。
两条都满足才算。只满足一条的话，人手写的文件只要抄了标题就会被误判成
可重建的生成物 —— 那会覆盖掉人的规则。

### 3.2 `legacy` 的处置：能不能安全重建，靠规则集合判定

**策略文件**：判据是「老策略里的每一条规则，在新生成物里都能找到同样的
（路径, 操作, 动作）」。

- 成立 → 可以安全重建。新生成物比老的多了根级构建清单规则（§3.4），
  其余一致 → 重建即升级；
- 不成立 → 说明**人加过规则**（自定义 deny / ask / 放行某目录）。
  这份文件当人写的处理，**一个字都不动**，并明确告诉人「这份是老版本生成的，
  含人工规则，请人工核对」。

为什么比「路径 / 操作 / 动作」而不是整份比对：规则 `id` 与 `basis` 在新旧
生成器之间会变（id 带序号，basis 指向 id），拿它们比会把「同一份策略的新旧
两版」判成不同。

**配置文件**：判据是「门禁命令仍然是通用默认值」（`pnpm test` / `pnpm lint` / 空）。

- 成立 → 重建为真实探测结果（C++ 项目上探测出来的是 cmake + ctest，
  通用默认值在那边是错的）；
- 不成立 → 不动。老生成器对 C++ 项目发的默认命令是**按机器探测出来的**
  （`cmake .. -GNinja && ninja && ctest` 之类），分不清它是「人写的」还是
  「老生成器探测的」—— 宁可不动，让人自己核对，也不替人改门禁命令。

### 3.3 `anchors:` 段：认它、忽略它、报出来

ADR-039 把策略哈希锚点从策略体内外部化到 `policy/lock.json`（C5），
但**没有处置已经存在的 `anchors:` 段**。校验器把它当未知顶层键 → 判红 →
`policy validate` 退出码 1 → 接管路径整体走不通。

而 ADR-039 §5 自己写的口径是「人手写的策略**不动**，其中的 `anchors:` 段会被
**忽略**」—— 也就是说，ADR 的意图本来就是「忽略它」，代码却把它判成了非法。
本次把这个偏差补上：

- **校验器**：`anchors:` 段不再判红，改为**警告**（`W_DEPRECATED_ANCHORS`）。
  警告不是放过 —— `policy validate` 的输出里会明确报出「这一段已被忽略，
  锚点真源在 `policy/lock.json`」，退出码仍是 0（策略本身确实合法）。
- **接管时**：老锚点搬进 `policy/lock.json`，`source` 记 `manual`。
  搬完之后**这一轮不再自动覆盖它** —— 哪怕这次是我们迁移动了策略，
  策略也「变过了」，失配应当被判出来（由人确认后 `zelto policy lock --update` 改锚），
  而不是被迁移顺手洗掉。

### 3.4 根级构建清单随迁移一起生效

`ab0e9ff` 已经把根级构建清单（`CMakeLists.txt` / `package.json` / `Cargo.toml` …）
纳入生成的策略（精确路径粒度）。本次把它接到迁移路径上：

- `legacy` 策略被重建 → 自动带上根级构建清单规则；
- `legacy` 策略含人工规则 → 不重建，**明确告诉人「这份策略里没有根级构建清单
  的规则，agent 改根级 `CMakeLists.txt` 会被拒」**。

这一层是外层粗边界：真正的精确边界是每个切片的写集预约（人批准的），
以及运行后的 git 审计。

### 3.5 迁移要留痕

迁移是一个动作：它改了策略 —— 「当时按什么标准拦的」换过了。
按 C4，它必须留痕。事件类型 `project.policy_migrated`，payload 带
每个被迁移文件的 `from` / `to` / 人话说明。

事件类型集合因此 +1，契约 enum（`contracts/schemas/event-envelope.json`）
同步补齐 —— 事件类型的真源是契约，不是代码里的数组。

### 3.6 补上实施时漏掉的一档：无标记行是 legacy 的必要条件

这一条是**实施过程中漏掉、复验时补上**的，记在这里是因为漏掉的原因本身
值得写下来。

第一版实现里，`legacy` 的判据只有两条内容特征：文件头 + `# Auto-generated for`。
问题在于：**当前版本的生成器写的也是这两行**（`buildPolicyYaml` / `buildConfigYaml`
的第一、二行至今不变）。也就是说，内容特征**区分不了新旧**——
被判成 legacy 的还包括「当前版本生成、但人后来改过」的文件。

后果：一份被人加过规则的新格式策略，若那份人工规则恰好都包含在新生成物里，
`legacyPolicyIsRebuildable` 判为成立 → 策略被重建 → **人的规则被覆盖**。
这与 §3.1「`legacy` 不能直接归到 `generated`」是同一条底线：
老文件没哈希所以要靠规则集合比较，而**新格式文件有哈希**，
它的「人改过」是可以精确判定的，不该被降级成 legacy 再走一遍模糊比较。

补法：`looksLegacyGenerated` 先看有没有标记行 —— 有标记行就是当前版本生成的
（无论被改过与否），一律按「人手写的」处置，一个字都不动；
只有**无标记行**的文件才有资格谈 legacy。

用例由 `tests/policy-legacy-migration.test.ts` 的
「被人改过的当前版本策略 → 不能被当成 legacy 覆盖」守住。

## 4. 被否决的方案

**方案一：把没有标记行的一律当人写的（现状）。**
否决理由：这正是问题本身。老版本 zelto 生成的文件被人当成人写的，
接管路径对它们**完全失效** —— 而人看不出区别（接管命令返回成功）。

**方案二：把没有标记行的一律当 zelto 生成的，直接重建。**
否决理由：老文件没有哈希，无法证明人此后没动过它。人加了条自定义 deny，
接管的瞬间就被覆盖掉 —— 那是**毁掉人的规则**，比不改严重得多。

**方案三：用「内容看起来像不像老生成器」来判定，不做规则集合比较。**
否决理由：那还是「看起来像」。规则集合比较是可判定的：老策略的每条规则在新
生成物里都能找到同样的（路径, 操作, 动作）—— 成立就能重建，不成立就不动。
人能复核的判据，不需要模型参与（C3）。

**方案四：接管时直接把 `anchors:` 段从策略文件里删掉。**
否决理由：那会改掉人的策略哈希 —— 而老锚点正是用来发现「策略被改过」的。
正确做法是**把锚点搬到它该在的地方**（`policy/lock.json`），策略文件本身
在「含人工规则」时一个字都不动。

**方案五：让 `policy validate` 继续判红，人自己改策略。**
否决理由：那等于让 zelto 把「用新版本的 zelto 接管老项目」这条主路径堵死。
ADR-039 自己写的口径就是「忽略 `anchors:` 段」—— 代码与 ADR 不一致时，
改代码去对齐 ADR，而不是改 ADR 去迁就代码。

**方案六：把「老版本生成物」这件事写进文档，让人手工改。**
否决理由：判据是可判定的（§3.2），机器能确定地做这件事，就不该让人手工做。
人工只保留真正需要判断的部分（含人工规则 → 人自己核对）。

## 5. 影响与迁移

**契约面变化**：

- **新增事件类型 1 个**：`project.policy_migrated`；
- `ValidationResult` 多了一个可选的 `warnings` 字段（不改变既有字段语义）；
- `policy validate` 的输出多了一段警告（JSON 输出多 `warnings` 数组）。

**行为变化**：

1. 接管一个**老版本 zelto 接管过**的项目（无标记行的生成物）时，
   `config.yaml` / `policy.yaml` 可能被重建 —— 条件见 §3.2；
2. 含人工规则的老策略 / 自定义门禁的老配置**不动**，并明确报出；
3. 含 `anchors:` 段的策略不再让 `policy validate` 判红（改为警告）；
4. 老锚点被搬进 `policy/lock.json`；策略若因此被改动，会报锚点失配 ——
   这是**故意的**：失配要被判出来，由人确认后改锚。

**破坏性变更**：

- `initializeProject` 变成 **async**（要落事件）。调用方（`zelto init` /
  `zelto project init`）已改为 `await`；库内调用方需同步调整。

## 6. 不变式核对

| 约束 | 核对 | 合规 |
|---|---|---|
| **C1** 状态只在文件里 | 迁移只改文件（`policy/policy.yaml` / `.zelto/config.yaml` / `policy/lock.json`）；事件追加到 `.zelto/events/project/events.jsonl`。未新增内存状态或常驻进程 | ✅ |
| **C2** `core/` 零第三方依赖 | 新增 `core/project/legacy-migration.ts` 只用 `core/policy/yaml.ts` 与本地类型；未新增任何 npm 依赖 | ✅ |
| **C3** 判定确定性 | 「是不是老版本生成物」「能不能安全重建」全是内容特征比较与集合包含判定：读文件 + 字符串比较 + 集合运算，不调模型、不触网 | ✅ |
| **C4** append-only 事件流 | 迁移落 `project.policy_migrated`；事件流仍只追加 | ✅ |
| **C5** 保护域与锚点外部化 | 人手写的策略、含人工规则的老策略、自定义门禁的老配置**逐字不动**；锚点只从策略体内搬到 `policy/lock.json`，失配可检出，改锚仍是人的显式动作 | ✅ |
| **C7** llm 只产草稿 | 迁移全程无模型参与 —— 识别与重建都是确定性计算 | ✅ |
| **C9** 写集预约强制 | 判定机制完全未动；本次只改了**生成的策略内容**（多了一组根级构建清单规则），运行时逐写判定与审计兜底照常 | ✅ |

禁区检查：未新增自动批准、自动合并、自动改规格、自动改锚。
迁移改的是 **zelto 自己生成的**文件，且只在可判定为「可安全重建」时才改。

## 7. 验证方式

新增单元测试 `tests/policy-legacy-migration.test.ts`（7 个用例）：

- 老版本生成的策略 → 被重建，补上根级构建清单规则，重建后带标记行；
- 老版本生成但含人工规则的策略 → 逐字不变，并报出「含人工规则」；
- 老版本生成、门禁命令是通用默认值的配置 → 按真实探测结果重建；
- 老版本生成、门禁命令是自定义的配置 → 逐字不变；
- 老策略内嵌的 `anchors:` 锚点 → 搬进 `policy/lock.json`，哈希值不变
  （不被洗掉）；
- 含 `anchors:` 段的策略 `validatePolicyYaml` 仍然 valid，且报出
  `W_DEPRECATED_ANCHORS` 警告；
- 被人改过的当前版本策略 → 不被当成 legacy，逐字保留（§3.6）。

真实项目复验（nimrtc-zelto）：把该项目的 `policy/policy.yaml` 还原成
「ADR-038 之前的老版本生成物」形态（去掉标记行 + 去掉根级构建清单规则），
重跑 `zelto project init`，实测：

```
🔄 policy/policy.yaml：老版本 zelto 生成的策略，无人工规则 → 按真实模块重建（补上根级构建清单）
```

随后核对：

| 核对项 | 结果 |
|---|---|
| 重建后的策略是否带标记行 | 是（此后接管走哈希比对那条路） |
| 根级构建清单规则是否补上 | 是（`allow-write-root-0` / `-1`） |
| `policy validate` | PASSED，退出码 0，15 条规则 |
| 根级 `CMakeLists.txt` 写集判定 | `allow`（规则 `allow-write-root-0`） |
| 根级 `README.md` 写集判定 | `deny`（规则 `default`）—— 没有顺手开更大的洞 |
| 迁移事件 | `project.policy_migrated` 已落 `.zelto/events/project/` |
| 人手写的 `.zelto/config.yaml` | 逐字未动，报告为「人手写的，未改动」 |

## 8. 遗留（需人拍板）

**`policy/lock.json` 该不该进版本库**（ADR-039 §9 的遗留，本次仍未动）。
锚点记的是「这个仓库当时的策略标准」，进库才有跨机器的可检出性；
不进库则「没锚点 = 不判」在 CI 里等于失配检查失效。

**老项目要不要批量迁移**。本次只提供「接管时自动迁移」这一条路径 ——
人重跑一次 `zelto project init` 就完成迁移。没有提供「一次性批量扫盘迁移」
的命令：那是一次批量改写别人仓库治理文件的动作，风险与收益不对称，
需要人显式决定。
