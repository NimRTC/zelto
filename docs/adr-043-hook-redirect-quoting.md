# ADR-043: hook 的重定向识别必须认引号

**状态**: 已实施
**日期**: 2026-11-11
**作者**: 系统架构
**关联约束**: C3, C5, C9
**关联文档**: `docs/adr-014-runtime-policy-enforcement.md`,
`docs/adr-042-write-set-judgment-layers.md`,
`src/hook/pretool.ts`, `tests/hook/pretool.test.ts`

---

## 1. 摘要

运行时写集守卫（hook）把 agent 的一条**完全无害**的命令判成了越界写入：

```console
policy.decision {
  "decision": "deny",
  "ruleId": "writes:v1-exception-handling",
  "reason": "写入目标 \"100\" 不在切片 \"v1-exception-handling\" 的写集内 …",
  "path": "100",
  "tool": "Bash"
}
```

真实案例：nimrtc-zelto 的 `v1-exception-handling` 切片里，
agent 执行 `awk 'NR>100 { … }'`，hook 把引号里的 `>100`
读成了「重定向到文件 `100`」，于是拿 `100` 去判写集 → 越界 → 拒绝。

根因：重定向识别用**正则直接扫原串**，分不清「引号里的 `>`」与
「引号外的 `>`」。

本次定案：重定向识别改为**逐字符扫描 + 引号状态跟踪**。

---

## 2. 问题

### 2.1 现象

`src/hook/pretool.ts` 的 `extractBashWriteTargets` 原来这样找重定向：

```typescript
const redirect = /(?:^|[^0-9&]|\d)>{1,2}\s*(?:"([^"]*)"|'([^']*)'|([^\s"';&|<>]+))/g;
```

这个正则作用在**未经处理的原始命令串**上。shell 里引号内的 `>`
是普通字符，不是重定向 —— 但正则分不出来。

于是：

| 命令 | 真实语义 | hook 的读法 |
|---|---|---|
| `awk 'NR>100 {print}' data.txt` | 比较表达式 | 重定向到文件 `100` |
| `grep 'a>b' file` | 搜索字面量 | 重定向到文件 `b` |
| `echo "x > y"` | 打印字符串 | 重定向到文件 `y` |

### 2.2 为什么后果严重

这不是「少拦了一次」，而是「**错拦了一次**」。

hook 是 fail closed 的（ADR-014）：抽不出目标就放行，抽出目标就严格判。
所以一旦抽出**假目标**，判定必然是「不在写集内」→ deny。

一条无害的 `awk` 被拒之后，agent 会：
1. 收到 deny 理由「写入目标 "100" 不在写集内」；
2. 困惑于「我只是想读文件」；
3. 尝试换一条写法绕过 —— 比如把表达式改写；
4. 或者放弃这个检查。

**守卫的误报会训练 agent 绕过守卫。** 这是比漏拦更坏的失败模式：
漏拦是「没守住」，误报是「守不住，而且让人学会不守」。

### 2.3 为什么会漏

`tokenize()` 那个函数**是**认引号的 —— 但它只用于第 2 步
（按命令名找写文件目标）。第 1 步（重定向）绕过了它，直接用正则。

两处语义不一致，而**不一致的那一处**恰好是覆盖面最广的
（任何命令里的 `>` 都会被扫到）。

---

## 3. 决策

### 3.1 重定向识别改为逐字符扫描

新增 `extractRedirectTargets(command)`，按字符扫，跟踪引号状态：

| 遇到的字符 | 处理 |
|---|---|
| 引号外的 `>` | 真重定向（`>>` 是追加，同样算写） |
| 引号内的 `>` | 普通字符，忽略 |
| `>&` / `2>&1` | 文件描述符复制，**不是写文件**，忽略 |
| `&>` | 真重定向（重定向 + 追加 stderr） |

重定向目标的读取规则：
- 引号包裹的（`> "out file.txt"`）→ 取引号内内容；
- 否则 → 取到空白 / 分隔符为止。

### 3.2 为什么不用「先剥引号再扫正则」

试过这个更简单的方案，但有两个问题：

1. **会丢掉引号包裹的重定向目标**。`> "out file.txt"` 剥完引号后
   变成 `>  out file.txt `，正则只能取到 `out`，而真实目标是
   `out file.txt`。
2. 引号里的内容被整体丢弃后，可能与引号外的字符粘连，
   产生新的误判。

逐字符扫描一次到位，且两处语义统一在同一个函数里。

### 3.3 保守性不变

本次只修**误报**，不放宽任何拦截：

- 真重定向照样抽出、照样判写集；
- 抽不出目标时照样 fail closed（放行）；
- 保护域、路径逃逸、写集预约的判定逻辑一个字没改。

---

## 4. 被否决的方案

**方案一：把 hook 从 fail closed 改成 fail open。**

否决理由：那等于取消运行时守卫（C9）。ADR-014 的整个设计就是
「判定不了就拒绝写」。误报是**判定逻辑的错**，不是判定策略的错 ——
修策略等于用「以后真越界也不拦」换「现在少错拦一次」。

**方案二：只对已知的「只读命令白名单」（awk / grep / sed 之类）跳过重定向识别。**

否决理由：白名单永远不完整，而且要靠人维护。新命令随时会踩同一个坑。
正确做法是**把识别本身做对**，而不是枚举不该触发的命令。

**方案三：在 deny 理由里加一句「如果这是误报，请改写命令」。**

否决理由：把工具的错转嫁给使用者。误报就是 bug，要修 bug。

## 5. 影响与迁移

**契约变更**：无。事件类型、字段结构、hook 的输入输出协议都没变。

**行为变更**：

- 引号内的 `>` 不再被当成重定向 —— 这是本次修复的核心；
- 引号包裹的重定向目标现在能正确取出（原来会截断）——
  这是修复带来的**附带收紧**，方向是对的（更准，不是更松）；
- `>&` / `2>&1` 明确不视为写（原来可能被 `redirectErr` 误读）。

**新增文件**：无。

**改动文件**：

| 文件 | 改动 |
|---|---|
| `src/hook/pretool.ts` | 新增 `extractRedirectTargets`，重定向识别改用它 |
| `tests/hook/pretool.test.ts` | 新增 8 个用例（引号内 `>`、引号包裹目标、`>>`、`>&`、`&>`、混合） |

---

## 6. 验证方式

- 单元测试 `tests/hook/pretool.test.ts`：
  - `awk 'NR>100 {print}' data.txt` → 无写目标（回归点）；
  - `echo "a > b"` → 无写目标；
  - `echo hi > out.txt` → `out.txt`；
  - `echo hi > "out file.txt"` → `out file.txt`；
  - `echo hi >> log.txt` → `log.txt`；
  - `cmd 2>&1` / `cmd >&2` → 无写目标；
  - `cmd &> all.log` → `all.log`；
  - `echo 'x > y' > out.txt` → 只有 `out.txt`。
- 全量测试全绿（见提交记录）。
- 真实项目验证：nimrtc-zelto 的 `v1-exception-handling` 切片，
  agent 的 `awk` 命令不再被误判为越界写入。

## 7. 附带发现（本次不改，记录在此）

`extractBashWriteTargets` 的第 2 步用 `splitSegments` 按
`|`、`;`、`&&` 切段，而 `splitSegments` **不认引号**：
`echo "a|b" | grep x` 会被切成 `echo "a` 与 `b" | grep x` 两段。

后果：这类命令的写目标识别可能不完整（漏抽，或把引号内的片段当路径）。
它不会产生**假目标**（只是漏抽），所以不会造成误拦，
但会削弱拦截能力。

修它要动 `splitSegments` 与 `tokenize` 的关系，属于独立的一次整理，
留待后续。
