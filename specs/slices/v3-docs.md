# Slice: v3-docs

## 目的
将 0.7.0 可验证性版本的关键设计决策固化到文档与 ADR 中，包括哈希链设计（只读 `src/core/events/stream.ts` 扩展）、`audit verify` 只读路径、现有写保护机制的 e2e 验证策略、帮助分层与 Windows CI，并补充 `zelto why` 与分层帮助的用户文档，使相关实现有据可依、决策可追溯。

## 范围
要改的（这些是 agent 会去改的文件）：
- `docs/**`

只读参考（不得修改，agent 只许读）：
- 只读 `src/core/events/stream.ts` —— 哈希链 ADR 需要记录对该文件的扩展，读它才能准确描述当前接口与扩展点。

## 需求
无。

## 验收标准
1. `docs/**` 下存在或更新 0.7.0 规划文档，其中包含五个主题小节：哈希链设计、`audit verify` 只读路径、写保护 e2e 验证策略、帮助分层、Windows CI；验证方式：用 `grep -rl "0.7.0" docs/**` 定位该文档，逐一核对五个小节标题存在且正文非空。
2. 新增/更新的 ADR 文档中记录哈希链设计，写明基于只读 `src/core/events/stream.ts` 扩展实现；验证方式：在 `docs/**` 下定位 ADR 文件，用 `grep -n "src/core/events/stream"` 命中，且附近文本包含“哈希链”或“hash chain”及追加/校验语义。
3. 新增/更新的 ADR 文档中记录 `audit verify` 为只读路径；验证方式：在 `docs/**` 下定位 ADR 文件，`grep -ni "read-only\|只读"` 命中，并写出该命令不修改审计日志或状态。
4. 新增/更新的 ADR 文档中记录现有写保护机制的 e2e 验证策略；验证方式：在 `docs/**` 下定位 ADR 文件，内容中包含“e2e”或“端到端”关键词，并列出写保护开启时写操作被拒绝的验证场景或步骤。
5. 新增/更新的 ADR 文档中记录帮助分层设计；验证方式：在 `docs/**` 下定位 ADR 文件，内容中包含帮助层级划分（如顶层帮助、命令帮助、子命令/参数帮助）及各自入口。
6. 新增/更新的 ADR 文档中记录 Windows CI 双平台决策；验证方式：在 `docs/**` 下定位 ADR 文件，内容中同时出现“Windows”与至少一个其他平台名（如 Linux），并说明两者都纳入 CI。
7. `docs/**` 下存在 `zelto why` 的用户文档；验证方式：用 `grep -rn "zelto why" docs/**` 找到对应文档，其中包含命令用途、输出说明和至少一个示例。
8. `docs/**` 下存在分层帮助的用户文档；验证方式：用 `grep -rn "帮助\|help" docs/**` 找到该文档，内容说明用户如何获取各层帮助（如 `zelto --help`、`zelto <command> --help`）。
9. 本片全部改动落在 `docs/**` 内；验证方式：运行 `git status`，确认修改文件均在 `docs/` 下，无 `docs/` 之外的文件被改动。

## 风险
- 设计上下文只给出一个源码参考（只读 `src/core/events/stream.ts`），其余决策（如 audit verify 只读路径、写保护验证的具体命令）可能缺少实现细节；应对：ADR 只记录已批准的决策层内容，不写未经确认的实现细节。
- 现有 docs 目录结构不明时，新增/更新位置可能与既定组织方式不一致；应对：先只读扫描 `docs/**` 现有结构与 ADR 编号，新内容沿用现有组织方式。
- 没有关联需求条目，验收口径仅依据设计上下文，可能与后续补齐的需求不一致；应对：在评审时由人对本文档中的验收标准做确认，不一致时按补齐后的需求修订。
- agent 可能因需要核对实现而误改 `src/` 或其他目录；应对：范围中明确只读 `src/core/events/stream.ts`，并靠验收标准第 9 条用 `git status` 拦截。
